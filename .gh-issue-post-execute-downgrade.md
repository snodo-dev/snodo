A post-execute quality blocker is downgraded to a warn on any recovery attempt, and a red suite reaches the base branch

## Severity

This defeats the guarantee snodo exists to make. A task whose test suite exits
non-zero can reach the base branch through the recovery path.

## Observed

Same validator, same failure class, one task, two attempts:

```
attempt 1  ->  quality: blocker  ->  recovery spawned
attempt 2  ->  quality: warn     ->  action: log  ->  merged
```

The decision's justification was `Pre-execute recovery finding(s) (2) passed to
coder as evidence` — a pre-execute rationale attached to a post-execute
decision. The acceptance validator additionally printed
`[CONTRADICTION DETECTED: execution validator 'quality' failed ... Acceptance
claim superseded]` and the run still proceeded.

## Root cause

`PolicyEvaluator.evaluate()` declares:

```python
phase: str = "pre_execute"      # policy.py:115
```

`_validate_node` passes it explicitly:

```python
decision = self.policy_evaluator.evaluate(
    ..., is_recovery=is_recovery, phase="pre_execute",   # validation.py:84-90
)
```

`_post_validate_node` does not pass it at all:

```python
decision = self.policy_evaluator.evaluate(
    results,
    self.protocol.disagreement_policy,
    decision_records=getattr(self, '_decision_records', []),
    task_ref=loop_state.task.id,                          # validation.py:407-412
)
```

so post-execute evaluates as `phase == "pre_execute"`. Meanwhile:

```python
in_recovery = is_recovery or ("_fix_" in task_ref)        # policy.py:163
if in_recovery and phase == "pre_execute" and (blocker_count > 0 or warn_count > 0):
    return PolicyDecision(action=PolicyAction.PROCEED_WITH_LOG, blocker_count=0, ...)
```

A recovery subtask's id contains `_fix_`, so `in_recovery` is true without
`is_recovery` being passed either. Every post-execute blocker on a recovery
attempt therefore takes the escape branch.

That branch sits immediately above:

```python
# Any blocker always halts (hard invariant — INV3)
# DecisionRecords are consulted AFTER this check, so they can
# NEVER override a genuine blocker.
if blocker_count > 0:
```

The comment is not true as written. There is a path above it that lets blockers
through, and it is reachable whenever `task_ref` contains `_fix_`.

Introduced by #90 (`1acef52`), which correctly scoped the escape to
`phase == "pre_execute"` in the evaluator but did not audit the call sites for
the defaulted argument.

## Fix

1. Pass `phase="post_execute"` and `is_recovery` explicitly at
   `validation.py:407`.
2. Make `phase` a **required** parameter of `evaluate()`, or default it to
   `"post_execute"`. A permissive default on a safety-critical branch means any
   forgotten argument fails open — which is exactly what happened.
3. Reconsider `"_fix_" in task_ref` as a recovery test. A substring match on a
   task id is a fragile way to reach a branch that suppresses blockers; prefer
   `depth > 0` / an explicit flag.
4. Make the acceptance validator's `CONTRADICTION DETECTED` state terminal. An
   execution validator that failed while a read-only judge claims success is not
   a warn under any phase or depth.

## Canary — required, must fail before the fix

A recovery-depth task (`depth > 0`, id containing `_fix_`) whose post-execute
`quality` validator returns `blocker`. Assert the run halts. Against current
main it returns `PROCEED_WITH_LOG` with the justification
`Pre-execute recovery finding(s) ...`.

Add a second test asserting `evaluate()` cannot be called without a phase, so
the defaulted-argument class of this bug cannot recur.

## Related
