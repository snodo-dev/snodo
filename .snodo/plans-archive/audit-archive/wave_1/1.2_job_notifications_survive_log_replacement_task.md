# Job notifications keep working when the audit log file is replaced

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
The job notification monitor follows the project audit log while a job runs, so it can notify on halts and authorisation requests. It remembers a byte position in `audit.log` and reads from there on each poll. A later change will archive the log, moving the current file aside and starting a fresh one. A position into the old file means nothing in the new file, so the monitor would miss or repeat events. The monitor should notice that the file it was following was replaced (a different file, or shorter than its position) and carry on from the start of the new file. It must not repeat a notification it has already sent.

## THE CHAIN
- `packages/snodo-mcp/src/snodo/jobs/notifications.py`: the monitor loop keeps the byte position into `.snodo/audit.log` and de-duplicates notifications by event hash.
- Tests for job notifications live under `tests/jobs/` or `tests/mcp/`.

## CONSTRAINTS
- When the file is not replaced, behaviour is unchanged.
- No new audit event, status, severity or halt type.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run --extra dev ruff check` on touched files, and run the notification tests.

## ACCEPTANCE
- Tests show:
  - after the followed file is moved aside and a new one is started, events in the new file are notified;
  - nothing from before the swap is notified twice;
  - a file that only grows behaves as today.
