# 1.1 — a coder history query must not leave a git helper process running

GitHub issue #961 already exists for this work. Do not open another; put "Fixes #961" in the commit message. Add one CHANGELOG entry under [Unreleased] (soft wording, "(Fixes #961)").

## INTENT

The read-only history tools added for the coder (`packages/snodo-engine/src/snodo/coders/history_tools.py`) open the repository for every query and never release it. GitPython's default object database starts a long-lived `git cat-file --batch-check` / `git cat-file --batch` pair on first object read and only ends it from a finalizer that runs at an unpredictable later garbage-collection pass. In the suite that shows up as a leaked child process; in the product it leaves helper processes behind for each query a coder makes.

## Evidence

```text
ERROR tests/coders/test_history_tools.py::test_history_tools_refuse_protected_state_and_unresolvable_ref
  Failed: TEST LEAKED running work into later tests ...: live child process(es):
  'git' git cat-file --batch-check; 'git' git cat-file --batch.
  End whatever the test started before it returns — close git repos through
  snodo.tools.git.open_repo (which spawns no persistent child), join or daemonise threads,
  and kill+reap subprocesses (Fixes #258).
```

It appeared on an unrelated plan's gate run (5803 passed, 1 error), so it blocks any task whose gate happens to collect that module at the wrong moment. The same family of problem was fixed before for other code (see the project's repository opener in `snodo.tools.git`).

## Where the leak is (found by the previous attempt and a read of the test module)

The previous attempt established that the history tool's own repository handle already goes through the project's sanctioned opener, so the production code needs no change. The leaked `git cat-file` pairs come from the **test module** `tests/coders/test_history_tools.py`: its workspace-building helper creates and commits with a plain GitPython repository handle (`Repo.init(...)` then `index.commit(...)`), and one test reopens the repository with a plain `Repo(...)` to commit again. Reading objects through a plain handle starts the persistent helper pair, which outlives the test and trips the leak guard on three of that module's tests (the gate failed with exactly those three errors; everything else, 5801 tests, passed).

Fix it in the tests: create the repository, then do all reading and committing through the sanctioned opener (the way other test modules in this repository build throwaway repositories, for example the coverage-accountability tests), and close what you open. Do not change production code unless you find a real leak there.

## Outcome

- After a history query returns (success or refusal), no persistent git child process belonging to it is left running, in the product code path as well as in the tests.
- The tool results and refusals the coder sees are unchanged.
- Prefer fixing where the repository handle for these queries is created, so every caller benefits; if that handle is shared with other code, make sure their behaviour is unchanged.

## Acceptance

- A test that runs a history query and a refused history query and asserts no git child process remains afterwards.
- The existing history-tool tests in `tests/coders/test_history_tools.py` stay green, including under the suite's leak guard.
- Run `tests/coders` and `tests/tools` together in one pytest invocation, then the whole gate with a long timeout, and the linter.
