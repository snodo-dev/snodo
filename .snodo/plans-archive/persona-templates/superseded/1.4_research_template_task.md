# A `research` protocol template for research analyst work

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
A team that runs `snodo init` and picks the `research` template gets a protocol for research analyst work. The coder produces research or market reports and decision memos as Markdown files under a `research` folder inside the project's docs tree. Role-specific validators judge each diff, and verified work is delivered as a change request, so a person signs off before it merges.

## THE CHAIN
- Every `*.yml` in `packages/snodo-foundation/src/snodo/protocols/templates/` is auto-discovered as a template. `snodo init` lists them, so a new file needs no engine change.
- Today's templates are all code-centric. The maintainer wants roles beyond engineering, and decided on four separate templates (product, design, docs, research), with Markdown deliverables in the repo and `change_request` delivery by default.
- The coder is the only actor that writes repository files, so documents arrive as a git diff, exactly like code.
- These work on a Markdown diff unchanged: LLM-type validators with free-text criteria (llm, conventions, planning and so on), `acceptance` (judges the diff against the spec's ACCEPTANCE) and `protocol`.
- `quality` runs `tooling.test_command`. For documents it should be a docs check rather than a test suite.
- The default delivery is read from the template: `_configure_delivery` in `snodo/cli/commands/init_cmd.py` looks at the producer mode's `delivery`, the top-level `delivery`, or `execution.delivery`.

## CONSTRAINTS
- Add one new template file named `research.yml`. Model its structure on the existing templates; `team.yml` and `feature-warden.yml` are good references. Keep the header comment explaining why the template is shaped this way, as the others do.
- Validators: LLM-type with criteria for this role: every claim is sourced; facts are kept separate from inference; counter-evidence is considered; the recommendation follows from the evidence presented. Include `acceptance` and `protocol`. Leave out code-only checks such as the 2+n `tests_exist` constraint.
- `quality`: the shipped `test_command` must not fail in a repo that lacks optional tools. Follow `team.yml`'s pattern of a harmless default with commented suggestions, here a link checker.
- Delivery defaults to `change_request` through the existing `delivery` key. No new protocol field, mode type, status, severity, halt type or audit event.
- Touch only the new template, a new test file of your own (for example `tests/golden/test_research_template.py`) and CHANGELOG.md. Sibling tasks are adding the other role templates in parallel, so do not edit shared docs, the templates README, `packages/snodo-foundation/src/snodo/protocols/__init__.py` or shared test files. A later task updates the docs tables.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo. Tests use temporary directories.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the targeted tests: your new test file and `tests/golden/test_template_wellformedness.py`.
