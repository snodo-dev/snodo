# Bind each validator's completion to its own model (Fixes #990)

Open nothing new: GitHub issue #990 already tracks this. Put "Fixes #990" in the commit message.

## INTENT
A validator pinned to a model on a different provider than the role default must be answered by that provider. Today the validator runner receives one completion function, bound once to the role's default validator model together with that provider's base URL and key, and hands the same function to every validator. A validator whose effective model differs from the default (a per-validator override or the validator's own model setting) therefore keeps the default provider's base URL and key. Reported symptom: a validator on an OpenAI-compatible provider was sent to api.openai.com carrying another provider's key.

## THE CHAIN
1. The runner decides each validator's effective model (override, then the validator's own model, then the default).
2. When that effective model is the one the shared completion function was bound for, the shared function is used exactly as today.
3. When it differs, the validator gets a completion function bound to its own effective model: litellm routing name, base URL and key resolved together from the configured name, then wrapped with the same task-scoped header injection the shared function gets. The validator context carries that function for the duration of that validator only; other validators and the shared function are unaffected.
4. The single home of the completion-binding rule in the validator runner is reused for this. Do not add a second implementation of the rule.

## CONSTRAINTS
- Indications only: the runner's shared function is a partial around the litellm completion call, wrapped for headers; the agent may find the cleanest way to obtain the base callable to rebind. Follow the codebase's own path.
- A validator with no model difference must see identical behaviour and identical call arguments to main.
- Do not add a status, severity, halt type or audit event.
- No new third-party dependency.
- Add one entry under [Unreleased] in CHANGELOG.md in the repo's existing style, referencing "Fixes #990". Soft wording. This is the only task in this plan that edits CHANGELOG.md.
- Only touch the validator runner and its tests; the validator classes themselves are changed by a sibling task.
- Targeted validator tests only.

## ACCEPTANCE
- With two validators in one run, one on the default model and one on a model from a provider with a different base URL and key, each validator's completion call reaches its own provider's base URL with its own key (observed with a stub in place of the litellm call).
- The validator on the default model gets the same function and arguments as before.
- Task-scoped provider headers are still injected for both validators, resolved from each validator's own configured model.
- Targeted validator runner tests pass and lint is clean for the whole tree.
