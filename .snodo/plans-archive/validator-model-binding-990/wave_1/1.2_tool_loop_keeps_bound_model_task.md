# Validator tool-loop must not override the bound model (Fixes #990)

Open nothing new: GitHub issue #990 already tracks this. Put "Fixes #990" in the commit message.

## INTENT
The validator completion function carries its model, base URL and key as one bound unit; the plain and structured judge calls rely on that and pass no model. The tool-reading judge loop is the odd one out: it passes its own resolved model name on every turn, which replaces only the model while the base URL and key stay whatever the function was bound with. The three call paths should agree, so the model, base URL and key always come from the same binding, and a model name can never be paired with another provider's credentials by the validator itself.

## THE CHAIN
1. The tool-reading judge loop builds its request without a model argument, exactly like the plain and structured paths, and keeps passing the configured model name only for the task-scoped header lookup.
2. The loop also reads the request's model argument to fill the "model" field of its per-turn telemetry record. With the argument gone that field would silently become empty. The record must keep naming the model the turn was requested for, now taken from the configured model name the loop already holds, on every turn including the forced-verdict final turn. The served-model provenance beside it is unchanged.
3. The existing per-turn telemetry provenance tests read the requested model from the recorded request's model argument. They must now compare against the configured model name instead; keep every other assertion in them (served model present, absent when the provider reports nothing) exactly as is.
4. Everything else about the loop's request (messages, tools, token limit, metadata, temperature rule, forced verdict choice on the final turn, provider-rejection fallbacks) stays as it is.
5. The comment that explains why the other paths pass no model also holds for this path; keep one explanation, not two diverging ones.
