# Two-provider validator run, end to end (Fixes #990)

Open nothing new: GitHub issue #990 already tracks this. Put "Fixes #990" in the commit message.

## INTENT
Wave 1 changed how validators get their provider binding. Pin the behaviour from the outside: a run whose validators sit on two different providers must reach each provider's own base URL with its own key, on every call path a validator can take. This is the regression test for the reported symptom (a validator on an OpenAI-compatible provider sent to api.openai.com with another provider's key).

## THE CHAIN
1. Configure, in the test, a role-default validator model on one provider and a second validator pinned to a model on an OpenAI-compatible provider with its own base URL and key (test config only, no real keys).
2. Run the validators through the normal runner entry with a recording stub in place of the litellm call.
3. Exercise the tool-reading loop, the plain judge call and the structured judge call for the pinned validator.
4. Assert, per call, the model routing name, base URL and key the stub received.

## ACCEPTANCE
- All three call paths for the pinned validator reach the second provider's base URL with its key and its routing name; none reaches the default provider's base URL or key.
- The default-model validator still reaches the default provider's.
- The new test fails against the code as it stood before wave 1 and passes now.
