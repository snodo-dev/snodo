Before starting, open a GitHub issue on snodo-dev/snodo titled "Discover third-party validators through package entry points". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
Validators are the core of snodo's value: teams describe their process as a protocol of validators. But `docs/extending.md` says third-party validators are not discovered. Installing a package does not load it, so a process must import the module itself before protocol dispatch. That blocks a shared ecosystem, such as one security validator reused across teams.

Code-host providers already solve this. They use the `snodo.providers` setuptools entry-point group, discovered at startup by the provider registry in snodo-tools, which reports which plugins loaded and which failed.

When this is done, a package that declares an entry point in a `snodo.validators` group has its validator registered automatically, before protocols are dispatched. A protocol can then reference the validator by name with no extra import code. A plugin that fails to load is recorded with its error and does not crash snodo.

THE CHAIN
1. The validator registry discovers the `snodo.validators` entry-point group, following the provider registry's discovery and error handling.
2. Load failures are kept in a form a later readiness report can read, mirroring how provider load failures are kept.
3. Tests:
   - a fake entry point registers a validator that a protocol can reference;
   - a broken entry point is reported and does not crash snodo;
   - built-in validators are unaffected.

CONSTRAINTS
- Snodo's state machine is closed: add no status, severity, halt type or audit event. Third-party validators use the existing severity vocabulary.
- Core stays vendor-neutral.
- Do not touch the predicate or coder registries, `snodo ready`, or `docs/extending.md`. Other tasks own those.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
