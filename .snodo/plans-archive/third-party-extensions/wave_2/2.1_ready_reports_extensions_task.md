Before starting, open a GitHub issue on snodo-dev/snodo titled "snodo ready reports installed validator/predicate/coder extensions; document the install path". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
Validators, predicates and coder adapters are now discovered through the `snodo.validators`, `snodo.predicates` and `snodo.coders` entry-point groups, in the same way code-host providers use `snodo.providers`. Each registry keeps the extensions it loaded and those that failed, with the error.

An adopter needs to see what loaded, and needs documentation for the publish-install-reference path.

When this is done:
- `snodo ready`, and its `--json` output, reports the installed and failed extensions for all four groups, in the same style it already uses for providers.
- `docs/extending.md` replaces the "not discovered / no plugin loader" statements with the entry-point path. It includes a minimal example of a validator package's `pyproject.toml` entry, plus an example for predicates and coders.

THE CHAIN
1. The readiness checks report the loaded and failed extensions for each group.
2. Machine-readable readiness output includes them, following the versioned `--json` contract in `docs/machine-interface.md`. If the payload shape changes, follow that document's versioning rule.
3. `docs/extending.md` documents the entry-point path for validators, predicates and coders.
4. Tests:
   - readiness lists a loaded fake extension;
   - readiness lists a failed one with its error.

CONSTRAINTS
- Snodo's state machine is closed: add no status, severity, halt type or audit event.
- Keep the guide markers in docs intact.

ACCEPTANCE
- The tests in link 4 exist and pass.
- The docs are updated.
- The CHANGELOG entry is present.
- `make gate` and the docs build pass.
