Fixes #952

INTENT
A user with a Cloudflare AI Gateway gets from nothing to a passing model check by following one new guide, "docs/providers/cloudflare-ai-gateway.md", without hitting the endpoint, header, model-id and vendor traps we hit while setting it up.

THE CHAIN
- Cloudflare's gateway "compat" endpoint (gateway.ai.cloudflare.com/v1/<account>/<gateway>/compat) supports chat completions only and Cloudflare marks it deprecated for single-model calls. The setup that works uses Cloudflare's REST API base URL https://api.cloudflare.com/client/v4/accounts/<account>/ai/v1 with the gateway chosen by the "cf-aig-gateway-id" request header.
- Snodo provider blocks accept "extra_headers", which are sent with every call for models in that block. Read the provider config model and the header resolution in the core config module to confirm before documenting.
- Model ids resolve to a provider block by the name before the first slash, after snodo's built-in prefix rules (read that order in the core config module). A block name that starts with "cloudflare/" would be captured by the Workers AI rule, so the guide uses a block named "cf-gateway".
- With "litellm_provider: openai", snodo strips the block name and prepends "openai/" unless the rest of the id already starts with "openai/". Trace the litellm model resolution in the core config module and describe what the gateway receives for each id form in the guide. Consequence the guide must explain: "cf-gateway/google/<model>" reaches the gateway as "google/<model>", but "cf-gateway/openai/<model>" loses its vendor prefix because the remainder already starts with "openai/".
- For OpenAI-vendor models the confirmed working id is "cf-gateway/responses/openai/<model>" (for example "cf-gateway/responses/openai/gpt-6-sol"): the "responses/" prefix sends the call to the gateway's responses endpoint and keeps the vendor prefix. The "responses/" prefix does not work for other vendors; the gateway answers "Model not found: responses/google/…".
- Since the provider-adaptation work, when a provider asks for reasoning_effort "none" (OpenAI gpt-6 / gpt-5.6 reject function tools on chat completions otherwise), snodo applies that value and remembers it per model. Read the shared parameter-adaptation module in snodo-foundation's infrastructure package to describe this accurately; mention it only as a troubleshooting row.
- Gemini models through the gateway failed in multi-turn use with Cloudflare error 7003 "Model execution failed (User Input Error)". Recommend the native Google provider guide for Gemini instead, without claiming a cause.
- The token must belong to the account in the base URL; a mismatch gives Cloudflare error 10000, as in the Workers AI guide.

Working config confirmed live (replace the account id with a placeholder in the guide):
  cf-gateway:
    account_id_env: CLOUDFLARE_ACCOUNT_ID
    base_url: https://api.cloudflare.com/client/v4/accounts/YOUR_ACCOUNT_ID/ai/v1
    litellm_provider: openai
    api_key_env: CLOUDFLARE_AI_GATEWAY_TOKEN
    extra_headers:
      cf-aig-gateway-id: YOUR_GATEWAY_ID
