# 1.1 — pre-execute judges must see the operator's spec, not the engine's failure report

## Why this task exists

A retry is not the same input as the attempt it follows. The retry prompt is built in
`snodo/cli/commands/run_cmd.py`, where the original spec, the previous attempt's validator
verdicts, the list of files it changed and a closing instruction to fix the issues are
concatenated into one string, and that string becomes the task's spec. The pre-execute
quorum then judges the concatenation.

The verdict text quotes code: file names, line counts, gate output. So a spec that passed
the prescriptiveness rule when dispatched fresh can be blocked when retried, for the
content of its own failure report — text the operator never wrote and cannot edit. The
only way forward is to weaken the spec below the specificity of the evidence, which is the
opposite of what a retry is for. Worse, the attempt counter still advances on these
instant refusals, so a task can spend its whole retry budget without the coder ever
running.

The observed shape, from issue #931: the same spec passed pre-execute on a fresh dispatch
and ran eight minutes; on the retry it died in nine seconds with a meta-spec blocker and
zero artifacts.

## Outcome

- Pre-execute validators judge the task's specification — the authoritative text the
  operator wrote, which the retry path already carries separately from the composed prompt.
  The previous attempt's failure evidence reaches them as clearly separated evidence they
  may read, not as part of the description the prescriptiveness rule is applied to.
- A retry still tells the coder what went wrong before. What changes is only what the
  judges hold accountable: the spec, plus the failure report as context.
- A pre-execute refusal that never reached the coder does not consume a coder attempt. The
  operator's retry budget is a count of judged coding attempts, and an instant refusal is
  not one. The task record and the message the operator reads say which happened, so a
  blocked-on-input halt is distinguishable from a failed attempt at a glance.
- The retry prompt keeps its existing opening line, because the task branch name is derived
  from the leading words of the spec and a changed header would move the work to a new
  branch.

## Acceptance

- A test that composes a retry prompt whose failure evidence quotes code paths and line
  counts, and asserts the pre-execute quorum judges the authoritative spec rather than the
  composed text — the same spec passes on retry that passed fresh.
- A test that a pre-execute refusal leaves the coder-attempt count unchanged, and that a
  post-execute failure still advances it as today.
- The failure evidence remains visible to the coder in the retry prompt, asserted by test.
- The existing retry tests in `tests/cli/test_retry_spec_safety.py` stay green, as do the
  loop validation tests in `tests/engine/test_loop_validation.py`.
- The CLI and engine test suites pass, and the linter is clean.

## Constraints

- Do not lower or special-case the prescriptiveness rule itself; the fix is what it is
  applied to.
- Do not remove the failure context from the coder's prompt, and do not change what
  post-execute validators judge.
- No new halt type unless an existing one genuinely names this outcome.

## Correction for this retry

The previous attempt made the right behavioural change in the wrong place, and it also rewrote
large parts of `packages/snodo-engine/src/snodo/engine/nodes/writeback.py` that this task does
not concern. Both need correcting.

### 1. Leave the recorded attempt number alone

The attempt changed the arithmetic that writes the recorded failure entry so that a pre-execute
halt does not increment it. That collides with two existing tests in
`tests/engine/test_writeback_coverage.py` — the ones asserting the first recorded entry carries
attempt 1 and that a retry carries the next number. Their fixture records validators declared
for the pre-execute phase, so a rule keyed on the phase alone mislabels a run that did dispatch
a coder and had it judged.

Restore that arithmetic to what it is on main. The statement "a refusal before dispatch was not
a coding attempt" belongs in the narrative builder `_build_attempt_summary`, which the previous
attempt already handles correctly, and in whatever the operator-facing retry text renders. If a
distinction really is needed inside the recorded entry, key it on whether this run dispatched a
coder at all — the run facts already say that — never on the phase string by itself.

Do not edit `tests/engine/test_writeback_coverage.py`. It is the pin, not the defect.

### 2. Do not rewrite code this task does not change

The previous diff deleted dozens of comment and docstring lines throughout `writeback.py` whose
only content is the rationale for behaviour this task leaves untouched, including lines naming
the issues that produced them. That is not cleanup, it is loss: those notes are how the next
operator knows why a branch exists, and several were added by review of a specific incident.

Restore every such line. The task's diff should be confined to the code paths it changes — the
judge's input, the summary it builds from that input, and the tests for both. If a comment the
previous attempt deleted still describes the code as it now stands, it stays exactly where it
was.

### 3. Run the gate that decides

Before submitting, run the whole gate command from the contributing guide, not only the test
half, and leave it clean: the suite with the marker filter cleared, the coverage floor, the
patch-coverage script and the linter. The previous attempt's own new tests passed while two
existing ones did not, which means the gate was never run to completion.
