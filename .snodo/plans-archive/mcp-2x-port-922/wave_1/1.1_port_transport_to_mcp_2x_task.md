# 1.1 — the producer MCP transport runs on mcp 2.x

GitHub issue #922 already exists for this work. Do not open another; put "Fixes #922" in the commit message. Do not edit the CHANGELOG; the last task in this plan owns the entry.

## INTENT

`snodo serve` is the producer interface the orchestrator uses. When the `mcp` package resolves to 2.x the server dies at import time with `ModuleNotFoundError: No module named 'mcp.server.fastmcp'`: 2.x renamed FastMCP to `MCPServer` under `mcp.server.mcpserver`, and every producer tool becomes unavailable, leaving only the CLI. The project has held that resolution back with a `<2` bound in the MCP package's own manifest and by telling Dependabot to stop proposing the bump. Neither is a fix. Make the server build and run on 2.x with the behaviour it has today, then lift the bound.

The task branch already carries most of the work, committed: the transport imports and constructs `MCPServer`, the lockfile resolves mcp 2.3.0, the package bound is raised, `transport.py` is under its length limit, and the tests under `tests/mcp/` are migrated to the 2.x names, result shapes and in-process client pairing. Inspect the branch and its commits and continue; do not reproduce that work. A previous attempt may also have left uncommitted edits in the workspace: look at them with a diff, keep what is sound, discard what is not.

## What is left

One test fails, and it is the only thing between this branch and green: `tests/mcp/test_progress_notifications.py::TestProgressRoundTrip::test_call_with_token_streams_narration` fails with `expected progress notifications while the call ran`. A tool call made with a progress token should stream narration to the client while it runs; on 2.x the client's callback never fires. Two earlier attempts concluded "progress does not work on 2.x" without establishing why, and one ran the whole `tests/mcp/` directory repeatedly until it timed out.

Work diagnostically, in this order, and write down (in your final message only, not in the tree) what you found at each step:

1. Run only that one test and nothing else while you iterate; it is quick. Do not run the whole `tests/mcp/` directory until the very end, and only once.
2. Establish which side drops the notification. On the server side, does the tool handler's call to report progress reach the session's notification sender at all, and is a request-scoped progress token present on the context at that point? On the client side, how does the 2.x client session register the `progress_callback` it is given, and what signature does it call it with (the callback in the test takes `progress, total, message`; check whether 2.x passes something different)? A failure on either side has a different fix, and the fix may be in the transport's bridge, in how the handler obtains its context, or in the test's callback; make the smallest correct change at the place the evidence points to.
3. If the 2.x context API changed how a handler reaches progress reporting (for example the helper moved, was renamed, or needs the related request id), update the transport's progress path to the 2.x way, not a shim.

Scope this to progress reporting only; resources, the traffic-logging hook and the bearer-token auth path remain the next task's work.
