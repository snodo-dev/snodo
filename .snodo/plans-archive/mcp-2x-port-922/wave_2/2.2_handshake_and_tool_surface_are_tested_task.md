# 2.2 — a test guards the server's handshake and tool surface on mcp 2.x

GitHub issue #922 already exists for this work. Do not open another; put "Fixes #922" in the commit message. Do not edit the CHANGELOG; the last task in this plan owns the entry.

## INTENT

The producer MCP server crashed at import when the `mcp` dependency moved to 2.x, and nothing in the gate noticed until a live session lost every tool. Task 1.1 ported the transport. This task adds the guard that was asked for on the issue: a bump that breaks the server, or silently drops a tool, must trip the gate rather than a running session.

## Outcome

Two new tests, in a new test module under `tests/mcp/` (do not edit existing test files):

- A test builds the server for a representative protocol configuration, completes the `initialize` handshake through the real in-process client/server pairing the `mcp` package offers, and lists the tools. The listed names equal the tool surface the protocol layer says that configuration should expose, so a tool dropped by the port or by a future bump fails here.
- A test builds the server for a second, restricted mode and shows the mode filtering still applies: tools hidden in that mode are absent from the listing, tools it allows are present.

Where the in-process pairing is awkward, a stdio round trip against the built server is acceptable; either way the handshake and tool listing must be genuine round trips, not assertions on attributes of the server object.

## Acceptance

- Both tests pass on mcp 2.x and finish quickly (no sleeps, no fixed waits).
- Removing a tool from the registered set makes the first test fail; you can show this by briefly doing it locally, but leave no trace of the experiment.
- The linter is clean; only a new test module is added.

## Constraints

- Do not change production code. If you find the surface cannot be tested without changing it, stop and say so in your final message instead.
- No new dependency; do not raise any length baseline; no new halt types, severities or statuses.

## Running tests

Run only the new module, the existing `tests/mcp/test_server.py` and the linter, and do not run the whole suite yourself: the engine runs it right after you finish, and a multi-minute silent command has been dropping the coder connection. Make sure you finish by committing with the issue reference above.

## Diff discipline

Confine the change to the new module. Do not touch other files.
