Before starting, open a GitHub issue on snodo-dev/snodo titled "Guide: a blocked plan is unfinished work — fix it forward before starting new work". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
Owner's rule: merge every healthy piece, but make sure all pieces of a plan complete, and don't move attention elsewhere while a plan is unfinished.

Orchestrating agents learn how to work from the MCP connect-time instructions and the `guide` topics, especially `planning`, `outcomes` and `automation`. Today those don't tell an orchestrator what to do when a plan blocks partway. In practice orchestrators move on, or dispatch one-off tasks against main for work that lives on the plan's integration branch. That one-off then sees the wrong code.

When this is done, the guidance says:
- A blocked plan is unfinished work.
- The orchestrator reads the halt, then fixes it forward inside the same plan by replacing the blocked task's spec and running that wave again, until every wave lands.
- The orchestrator does not start new plans meanwhile, and does not dispatch one-off tasks for that plan's remaining work.
- Completed healthy waves are already on main, so fixing forward builds on them.

THE CHAIN
1. The connect-time instructions (`_build_instructions` in the snodo-mcp transport) add one short sentence on finishing blocked plans first. The canonical plans-as-default rule text stays exactly as it is, because a guard test pins it.
2. The guide topic docs that cover the plan loop and outcomes (find them by their `snodo-guide` markers) describe the fix-forward-inside-the-plan loop.
3. Tests that assert on the touched wording are updated or added. `tests/mcp/test_structure_guidance.py` must still pass unchanged.

CONSTRAINTS
- Wording only.
- Snodo's state machine is closed. Add no status, halt type, severity, audit event or field.
- Keep the `snodo-guide` markers intact.
- Do not touch the plan runner or the get_plan response. Other tasks own those.

ACCEPTANCE
- The updated tests pass.
- The CHANGELOG entry is present.
- `make gate` and the docs build pass.
