# A TypeSafe plugin package that gives LLM validators a `decide` tool backed by Jev

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
A separate, installable workspace package (like `packages/snodo-provider-github`) registers one validator tool, `decide`, through the `snodo.validator_tools` entry-point group added in #836. An LLM validator that opts into it (#837, #838) can ask TypeSafe's Jev decision model several typed questions in one call, over a chosen context: the task diff, the spec, or a few named repository files. It gets back per-question probabilities and confidence as compact text it can cite. Core stays vendor-free.

## THE CHAIN
- Jev is a decision model: text in, typed answers with calibrated probabilities out. It writes no text, so it supplements the LLM judge, which still writes the verdict.
- Public API details:
  - Calls go to `POST https://api.typesafe.ai/v1/systemone` with `Authorization: Bearer <key>` and a JSON body: `model` (for example `jev-latest`), `state` (text, a JSON object or an array of text), and `questions`.
  - `questions` is an object of named questions, each with `type` (`noul` for yes/no, `choice`, or `score`) and `instructions`. A `choice` question also has `criteria`, a map of option to description or null. A `score` question has `criteria`, an ordered list of level labels.
  - The response has `model`, `answers` keyed by question name, and `usage` (input and output tokens).
  - `noul` answers have `noul`, a probability. `choice` answers have `choice`, `probabilities` and `confidence`. `score` answers have `score`, `legend`, `probabilities` and `confidence`.
  - Pricing is $0.042 per million input tokens. The context length is not published.
- Read the registry module from #836 for the tool contract (definition, handler, context) and the validator-tools section in `docs/extending.md` with its example under `examples/` (#839).

## CONSTRAINTS
- Package layout, naming and pyproject should follow the existing provider packages. Register the tool under `snodo.validator_tools`.
- The tool's function schema lets the model pass a list of questions (name, type, instructions, optional criteria) and a context choice. The context is the diff, the spec, or up to a few repository file paths, read through the context the registry provides and only inside the workspace.
- Configuration comes through the per-tool options in protocol config:
  - `model` (default `jev-latest`);
  - `api_key_env` (default `TYPESAFE_API_KEY`);
  - `base_url` (default `https://api.typesafe.ai`);
  - `timeout_seconds`;
  - `max_input_chars`: a cap on what is sent. Because the context length is unknown, report truncation in the tool result.
- The API key is read only from the environment, and is never logged or echoed in tool results.
- Errors come back as plain tool-result text the model can act on: missing key, HTTP errors, timeouts, malformed responses. They are never raised into the validator loop.
- Use an HTTP client the workspace already depends on. Add no new heavy dependency.
- The tool result is compact text: one line per question, giving its type, the chosen answer and probability (or score with its distribution), plus the confidence, followed by a usage line.
- No network in tests: mock the HTTP layer.
- No new status, severity, halt type or audit event, and no change to core modules beyond what registration needs.
- If the release tooling (`uv build --all-packages`, `scripts/enforce_release_package_docs.py`) needs the new package listed somewhere, do that.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the new package's tests plus the registry and release-package-docs tests.

## ACCEPTANCE
- With a mocked API, tests show:
  - the tool is discovered through the registry;
  - the request body has the documented shape for noul, choice and score questions;
  - the response is rendered as the compact text described;
  - a missing key, an HTTP error and a timeout each produce a readable tool-result message;
  - input longer than `max_input_chars` is truncated and the result says so;
  - the key never appears in results or logs.
