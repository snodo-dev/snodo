INTENT
GitLab support ships as a second code-host plugin, `snodo-provider-gitlab`, built exactly the way a third party would build one. A project whose git remote is on gitlab.com (or a self-hosted GitLab named in protocol metadata) gets merge requests, merge-request comments and approvals through snodo's vendor-neutral change-request contract, with no change to snodo core. It is the proof that "another vendor is just another plugin".

What is already true: the provider contract is vendor neutral (`packages/snodo-tools/src/snodo/providers/base.py`: `create_change_request`, `read_change_request_diff`, `post_change_request_comment`, `approve_change_request`, `request_change_request_changes`, `merge_change_request`, `read_change_request_discussion`, with opaque string ids). `packages/snodo-tools/src/snodo/providers/registry.py` builds in only `local` and discovers every other provider through the `snodo.providers` entry-point group, asking each plugin's `claims_remote(url)` whether it owns a git remote. `packages/snodo-provider-github` is the reference plugin: its own import package `snodo_provider_github`, its own `pyproject.toml` with the entry point `github = "snodo_provider_github:GitHubProvider"`, token from metadata or `GITHUB_TOKEN`, tests in `tests/providers/test_github.py`. docs/extending.md section 4 describes how to write a provider. Both base.py and registry.py are read-only context for this task.

A previous attempt at this task (its preserved task branch and worktree; commit "Add GitLab code-host provider (Fixes #575)", issue #575) implemented the plugin and its tests pass, but the repository gate refused it on one lint error: a `subprocess.run(["git", "remote", "get-url", "origin"], ...)` call in the plugin trips ruff's subprocess rules (S603/S607).
