INTENT
A plugin author reading docs/extending.md sees two real code-host plugins to copy, GitHub and GitLab, and understands how change-request delivery uses whichever plugin claims the project's remote.

What is already true: `packages/snodo-provider-github` (bundled with snodo) and `packages/snodo-provider-gitlab` (installed separately, e.g. `pip install snodo-provider-gitlab`, or as a workspace package in development) both register in the `snodo.providers` entry-point group and implement the neutral change-request contract in packages/snodo-tools/src/snodo/providers/base.py. The registry, packages/snodo-tools/src/snodo/providers/registry.py, builds in only `local` and picks a plugin by `metadata.provider` or by `claims_remote(url)`. With `execution.delivery: change_request`, snodo/cli/commands/run_merge.py pushes the task branch and calls the resolved provider's `create_change_request`; the delivery setting itself is documented in the delivery rows of docs/protocol.md, which this task only links to. docs/extending.md already has a provider section that cites the GitHub plugin as the reference example.

Authoritative records: the two plugin packages and the registry above. Where this spec and the code disagree, the code wins.

THE CHAIN

2. `docs/extending.md` — a short note on how `delivery: change_request` picks the provider and what the user sees when no plugin claims the remote or the token is missing, linking to the protocol reference for the delivery setting.
