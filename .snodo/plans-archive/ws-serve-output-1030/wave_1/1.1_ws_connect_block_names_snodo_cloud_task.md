# 1.1 — the ws connect block says the endpoint is reached through snodo cloud

GitHub issue #1030 already exists for this work. Do not open another; put "Fixes #1030" in the commit message. Do not edit the CHANGELOG (the last task in this plan owns the entry).

## INTENT

After `snodo serve --tunnel --tunnel-transport ws` starts, the terminal shows the same "Connect your MCP client" block as a Cloudflare tunnel, with `OAuth: https://<hostname>/mcp` and the `mcp-auth.snodo.dev` line. For a ws hostname that reads as a public address an outside client (Claude.ai, curl) can use. It is not one: a `-ws.snodo.dev` hostname has no DNS record and no inbound route; the machine dials out to snodo cloud and the cloud sends requests down that connection (ADR-0053). The block should tell the user that the endpoint is reached through snodo cloud (Dispatch) and should not invite them to paste the hostname into an outside client.

## Evidence

```text
- Smoke run on 6d6394a: hostname ws-smoke-producer-9i4oli-ws.snodo.dev; curl: (6) Could not resolve host.
- dig +short is empty for that host at 1.1.1.1 and 8.8.8.8 while mcp-auth.snodo.dev resolves. snodo cloud confirmed this is expected for ws.
- Output is built by _print_tunnel_urls and _print_first_run_info in snodo/cli/commands/serve_cmd.py; the ws branch passes them to run_ws_tunnel as print_active.
```

## Outcome

- For the ws transport, the first-run block and the repeat-run block both say the endpoint is reached through snodo cloud (Dispatch) and show the hostname as that endpoint's name. Neither contains a "Connect your MCP client" heading, an `https://<hostname>/mcp` URL or the `mcp-auth.snodo.dev` line.
- Wording is soft and plain; avoid "not X but Y" contrast phrasing.
- The Cloudflare transport prints exactly what it printed before, in both blocks.
