# 1.3 — the cloud relay says when it is connected to snodo cloud, and why it is not

GitHub issue #1030 already exists for this work. Do not open another; put "Fixes #1030" in the commit message. Do not edit the CHANGELOG.

## INTENT

A healthy ws relay prints nothing, and its failures are only logged, which the user sees only under the global `snodo --verbose`. Someone who just started `serve --tunnel --tunnel-transport ws` cannot tell whether the machine reached snodo cloud. `CloudRelay` (`packages/snodo-foundation/src/snodo/infrastructure/cloud_relay.py`) should be able to tell its owner the few things the user needs to know.

## Outcome

- `CloudRelay` accepts an optional `notify` callable that receives one plain-text message. When omitted it does nothing and existing callers behave as before.
- Once per connection, right after the first `hello` frame of that connection has been sent, `notify` says the machine is connected to snodo cloud. The extra `hello` sent when the set of endpoints changes does not repeat it.
- `notify` also says, in short plain sentences: when the cloud login is missing or expired and the user must sign in; when snodo cloud rejected the connection (the 403 and 426 cases); when this connection was replaced by a newer runner connection; and, when an established connection drops and the relay will retry, that the connection was lost. Each existing log line stays as it is.
- A `notify` that raises never breaks the relay loop.
- No new state, severity or halt type: these are informational messages only.

## Acceptance

- Tests beside the existing cloud relay tests (find them under tests/infrastructure): connected message once after the first hello and not after a later endpoint-change hello; one case per reason above; a raising `notify` does not break the loop.
- The linter is clean.

## Constraints

- Do not change the framing, reconnect timing or what the hello frame contains. Do not change relay_participant.py or serve_tunnel_ws.py.
