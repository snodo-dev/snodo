# 1.2 — the relay participant says when it is waiting for the machine-wide relay lock

GitHub issue #1030 already exists for this work. Do not open another; put "Fixes #1030" in the commit message. Do not edit the CHANGELOG.

## INTENT

Only one serve process per machine holds the relay (`machine_id.relay.lock` in `packages/snodo-foundation/src/snodo/infrastructure/relay_participant.py`). A second `snodo serve --tunnel --tunnel-transport ws` retries the lock every second in silence, and the terminal already said the tunnel is active, so a user cannot tell a connected relay from one parked on the lock. The participant should be able to tell its owner, once, that it is waiting because another snodo serve on this machine holds the connection to snodo cloud and that this one takes over if that one stops.

## Outcome

- `RelayParticipant` accepts an optional `notify` callable that receives one plain-text message. When omitted it does nothing and existing callers behave as before.
- When the lock is held by someone else, `notify` is called once with a short message to that effect, not on every retry. When the lock is later obtained after waiting, `notify` is called once to say this serve now holds the cloud connection. A participant that gets the lock at once sends neither message.
- A `notify` that raises never stops or breaks the participant.
- No new state, severity or halt type: these are informational messages only.

## Acceptance

- Tests in tests/infrastructure/test_relay_participant.py (new cases beside the existing ones): waiting reported once across several retries; acquisition after waiting reported once; no messages when the lock is free; a raising `notify` does not stop the participant.
- The linter is clean.
