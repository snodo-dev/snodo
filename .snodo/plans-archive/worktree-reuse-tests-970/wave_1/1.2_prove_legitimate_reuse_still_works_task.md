# Prove a legitimate retry still reuses its own workspace

## Intent

The ownership check added for #970 must never block a genuine retry. This ticket adds the missing proof for the reuse side: a workspace the repository registered itself is still reused and keeps its work.

## Tracking

Open a GitHub issue first, or reuse https://github.com/snodo-dev/snodo/issues/970, and put "Fixes #970" in the commit message. This change adds tests only; no CHANGELOG entry is needed unless the repository's changelog gate demands one.

## Symptom and evidence

- Retrying a halted task keeps its previous work on purpose. The reuse step in the foundation worktree module now verifies the existing path is in the repository's own worktree listing and that the checked-out branch belongs to the task, and refuses otherwise. No test covers the passing path or the branch-mismatch refusal.

## Contract

- Add a new test module beside the existing foundation worktree tests, with its own name, so it does not collide with other work.
- Case one: a task workspace created by the engine in a real temporary repository, with an uncommitted or committed change left in it, is reused on a second request for the same task; the change is still there and the same path comes back.
- Case two: a workspace created under the legacy (pre-project-scoping) path identity that is registered to this repository is still reused and keeps its work.
- Case three: a path registered to this repository whose checked-out branch belongs to a different task is refused with a message naming the branch and the removal hint, and is not modified.

## Acceptance

- The new tests pass, use real repositories in temporary directories, and need no network.
- Existing foundation worktree and retry-workspace ownership tests still pass; repository lint passes on the new file; no baseline is edited.

## Constraints

- Tests only. Do not change production code; if a case cannot pass because production behaviour differs from the contract above, say so in the task result rather than editing it.
- Do not touch .snodo/. Do not weaken, skip or deselect existing tests.
- Do not leave notes about validation anywhere in the tree.
