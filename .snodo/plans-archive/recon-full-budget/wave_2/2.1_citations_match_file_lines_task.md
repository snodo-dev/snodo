INTENT
Recon answers are used to write specs, so a cited file:line must point at the code it describes. In recon rec_83a958 (2026-10-08 ~16:00Z), the query asked for file:line on every claim, using read_file_lines. ocgo/qwen3.6-plus described packages/snodo-mcp/src/snodo/recon/__init__.py correctly, but every line number was wrong:
- it cited 530-534 for the forced `tool_choice` kwargs, which are at line 558;
- it cited 569-570 for `trace["ended"] = "truncated:tool_calls"`, which is at line 610;
- it cited 682-683 for the "Model returned tool calls instead of an answer" error, which is at line 800.
The offsets are inconsistent (24 to 118 lines), so they are estimates, not a stale copy. The trace shows the agent used read_files and read_file as well as read_file_lines. Only read_file_lines output is numbered: `_execute_recon_read` prefixes each line with `N: `. Whole-file and batch reads come back without line numbers, so the model has to guess. Earlier test recons showed the same drift (qwen in rec_831df0).

When this is done, every read a recon agent can make shows real line numbers, so the model can cite exactly from whatever it read:
- read_file and read_files output carries the same `N: ` line prefixes as read_file_lines, or an equivalent that is just as unambiguous;
- the batch-read 32KB truncation and its notice (#777) still work correctly with the extra prefix bytes, and the notice's suggested read_file_lines range is still right.
Recon is the only consumer to change. The coder and validator tools that share `LiteLLMAdapter._execute_tool` must keep their current output.

THE CHAIN
1. Extend the existing numbering in `_execute_recon_read` (packages/snodo-mcp/src/snodo/recon/__init__.py) to the whole-file and batch read tools.
