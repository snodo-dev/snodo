Before starting, open a GitHub issue on snodo-dev/snodo titled "Recon: stall limit still forces answers after 7-9 of 40 turns". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
#777 ("keep reading after truncated batch") identified the cause of agents stopping at 8 turns: the recon loop forces a final answer after `_MAX_STALL_TURNS` (3) consecutive turns in which every read was a repeat. It improved the truncation notice but the early stop persists. Recon rec_83a958 (2026-10-08 ~16:00Z, server restarted on current main, 2 agents, same question as rec_dec7a0) finished in under 3 minutes, so the 300s per-agent deadline was not the cause:
- ocgo/qwen3.6-plus: `turns_used: 7`, `ended: "submitted_answer"`. Its answer covers part 1 only, and part 2 ends mid-investigation with "Let me re-read the `plan_run.py` file to find the "✓ Merged" logic:" followed by a literal `<tool_call>`. It was clearly forced to answer while still reading.
- ollama-cloud/deepseek-v4-pro:0813: `turns_used: 9`, 23 tool calls (12 of them read_file_lines), `ended: "truncated:tool_calls"`, empty result, with the error "Model returned tool calls instead of an answer after 9 turns."
Both are far below the 40-turn budget (RECON_DEFAULT_MAX_TOOL_TURNS).

Two further observations:
- When the stall limit fires, `trace["ended"]` is first set to `"stalled"` (packages/snodo-mcp/src/snodo/recon/__init__.py, around line 650). It is then overwritten by the later outcome (`submitted_answer` or `truncated:tool_calls`), so the trace never shows that the run was cut short by stalling.
- The stall counter only counts turns where every read was a repeat (`read_tracker.check_read` → `format_repeat_read_response`). The likely pattern is that models re-request content they already received, for example overlapping read_file_lines ranges or a re-read after context trimming, are refused, and then stall out.

When this is done, an agent that is still making real progress is not forced to answer early, and a run that truly stalls is visible as such:
- Find out from rec_83a958, or from a faithful reproduction with a fake provider, which reads counted as repeats and why. Fix the cause. Possible fixes include treating a read of new lines in an already-read file as progress, returning useful content or exact guidance on a repeat instead of a bare refusal, or making the stall rule tolerate re-reads that follow trimmed context. Choose what is robust and explain the choice in a comment.
- When the stall limit is what ended the reading window, the trace says so: `ended` stays `"stalled"`, or the existing value is otherwise preserved through the forced answer. Do not invent a new value.
- A model that really loops on identical reads still gets forced to answer. Keep the safeguard.
