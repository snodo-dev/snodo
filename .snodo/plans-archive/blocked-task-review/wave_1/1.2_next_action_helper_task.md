Before starting, open a GitHub issue on snodo-dev/snodo titled "One shared mapping from halt outcome to the operator's next action". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
`docs/outcomes.md` explains what each outcome means and what to do next:
- `escalate`: a human runs `snodo authorize`;
- `blocker`: fix the spec or code, then retry with `--append-spec`, or fix forward in the plan;
- `validator_error`, `environment_error` and `internal_error`: repair and retry.

But the CLI and MCP surfaces don't consistently tell the user that at the moment of the halt. Each surface phrases it differently, or not at all.

When this is done, one shared helper maps a halt record to the recommended next actions, with concrete command lines filled in for that task. Plan tasks get the fix-forward-in-plan guidance. Its wording matches `docs/outcomes.md`. Later tasks will wire it into the CLI and MCP output.

THE CHAIN
1. A pure function in the appropriate shared package takes a halt record (and plan context, if any) and returns the ordered next actions with ready command lines.
2. It covers every outcome in the closed vocabulary, and only those.
3. Tests: one case per outcome, plus plan versus non-plan task; a test asserts that every outcome in the closed vocabulary is handled.

CONSTRAINTS
- Snodo's state machine is closed: add no outcome, status or severity.
- Pure logic only. Do not change CLI or MCP output yet; another task does that.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
