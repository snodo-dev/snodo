INTENT
When a task blocks, the developer reads the structured halt payload, then finds the preserved worktree or branch and runs `git diff` by hand to see what the judges were judging. Correlating the two is the most common friction point for new users. That is evidence from adoption recon rec_d6ff28 (`docs/runbook.md`, task blocked; `docs/outcomes.md`).

When this is done, `snodo task show <task_id> --diff` resolves the task's preserved branch or worktree against its base, and prints:
- the diff, as a stat summary plus the patch, with a way to limit the patch length;
- next to it, the validator verdicts from the task's halt record, grouped by validator with each validator's justification.

`--json` returns the same data per the machine-interface conventions.

A previous attempt implemented this, but `make gate` failed its file-length check: the change pushed an existing CLI module past its line-count limit. The gate's file-length check and its frozen debt list are the rule. Put the new logic in its own focused module that the existing `task show` command calls, rather than growing an already-large file.

THE CHAIN
1. `snodo task show` gains a diff option. It resolves the task branch and base the same way the merge and worktree code does, and uses git only.
2. Verdicts come from the existing halt record and are grouped by validator.
3. Tests: a blocked task shows its diff and its grouped verdicts; a task whose branch is gone degrades with a clear message; `--json` output is valid.
