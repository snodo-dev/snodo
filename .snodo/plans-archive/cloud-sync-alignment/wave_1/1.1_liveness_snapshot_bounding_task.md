INTENT
A liveness snapshot always carries the rows that describe what is happening now, even in a project with a long run history. Today build_liveness_snapshot in packages/snodo-foundation/src/snodo/infrastructure/cloud_liveness.py collects every run directory under .snodo/tasks and .snodo/jobs of the project, not only the current session's, so the top-level tasks and jobs lists grow without bound (146 tasks and 140 jobs in this repository today). The cloud stores plans, tasks and jobs capped at 200 items each and drops the rest silently, so an in-progress task can disappear from the dashboard once history grows.

Indications: keep the wire shape exactly as it is (same keys, plans, tasks and jobs always present as arrays, no new fields). Order each list so active rows (running, in_progress, blocked, pending) come before finished ones, most recent first within each group, and cap each list on the client below the cloud limit (a named constant, e.g. 150) so truncation is decided here, deliberately, rather than by the cloud. Consider scoping the top-level tasks/jobs to the current session or a recent time window where the session information makes that reliable; the status counts must still describe the same set that is sent, or say plainly in a code comment why they cover more. Check the nested plan, wave, task and job lists for the same unbounded growth.

Acceptance: tests with temporary project directories holding more rows than the cap show active rows are always kept, the lists never exceed the cap, the order is active-first then newest, and a small project produces the same snapshot as before. CHANGELOG.md updated.
