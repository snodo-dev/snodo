Before starting, open a GitHub issue on snodo-dev/snodo titled "Plan delivery prints 'Merged … into the base branch' twice". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
After a plan's last wave delivers, the run log sometimes shows the delivery line twice in a row:

```
Wave 1 total: 6m 1.6s
✓ Merged plan/gate-guard-concurrent-worktrees/integration into the base branch
✓ Merged plan/gate-guard-concurrent-worktrees/integration into the base branch

Plan progress: 1/1 completed
```

The same happened for notification-icons and recon-reliability on 2026-10-06/07. Single-wave and multi-wave plans both show it. It looks like the per-wave healthy delivery (#730) and the final plan delivery both report the same merge. Or the second is a no-op merge that still prints success. The reader can't tell whether two merges happened.

When this is done, each real merge into the base branch is reported exactly once. A delivery step that finds nothing new to merge, because the per-wave delivery already merged it, either says nothing or says so plainly ("already delivered"). It does not repeat the success line.

THE CHAIN
1. Find the two paths that print the line: per-wave delivery and final plan delivery.
2. Decide which reports. Make the second one either skip when the integration branch is already contained in the base branch, or report that it is already delivered.
3. Tests:
   - a single-wave plan run prints the delivery line once;
   - a two-wave plan prints one line per real delivery;
   - an already-delivered integration branch does not produce a second success line.

CONSTRAINTS
- Snodo's state machine is closed: add no status, outcome, halt type or audit event. This is a wording and flow fix only.
- Do not change when or whether delivery happens.
- No file may exceed its file-length limit or baseline.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes, including lint and the file-length check.
