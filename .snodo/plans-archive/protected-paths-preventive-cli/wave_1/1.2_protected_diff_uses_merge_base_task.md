INTENT
The post-execution protected-path guard stops accusing a task of changing a protected path when the change actually arrived from the base branch. `_protected_path_result()` in `packages/snodo-engine/src/snodo/engine/nodes/validation.py` compares the captured `base_ref` with the current head through `changed_paths_between_refs()`. `base_ref` is the head sha captured before the coder ran (see the comment at the top of `_execute_node()` in the same file, which records why the anchor exists). If the coder rebases the task branch onto newer base-branch commits, that range replays the base branch's own commits inside the diff, so a protected path touched by someone else's merged work is reported as this task's change and the task is blocked for a file it never edited. What must become true: the comparison measures only what the task branch contributes relative to its common ancestor with the base, so base-branch history is never attributed to the task, while any protected path the task genuinely changed is still caught. `docs/decisions/049-protected-paths-detect-before-prevention.md` is the authoritative record of what this guard means and when it fires; where this spec and that record disagree, the record wins. The blocker's severity, validator id, justification wording, and audit events stay as they are — only the set of paths attributed to the task changes.

THE CHAIN
1. `packages/snodo-engine/src/snodo/engine/nodes/validation.py` — `_protected_path_result()` derives the task's own changes from the common ancestor of the captured base ref and the task branch head, rather than from the stale base ref itself, so commits that arrived from the base branch are excluded.
2. The same function — when no common ancestor can be resolved (unrelated or missing history), it falls back to the current base-ref-to-head comparison rather than silently reporting no changes, so the guard degrades to today's behaviour instead of opening a hole.
3. The same function — a protected path the task itself edited is still reported, including a descendant of a declared directory, exactly as ADR 049 describes.
4. The same function — an exception while resolving the ancestor is audited through the existing unchecked-path audit event and returns no blocker, matching how a failed diff is handled today; the task is not blocked on an operational error.
5. `tests/engine/test_protected_paths.py` — tests cover: a rebased branch whose incoming base commits touch a declared protected path and whose own commits do not, which must produce no blocker; a branch whose own commit touches a declared protected path, which must still produce the blocker; and the unresolvable-ancestor fallback.

CONSTRAINTS
- Detection remains post-execution and remains a blocker: this is a correctness fix to the change set, not a new enforcement level, and it must not soften or delay the halt for real violations.
- The blocker's `validator_id`, severity, and the `protected_path_blocked` / `protected_paths_unchecked` audit events keep their current names and shapes, since records and tests depend on them.
- `packages/snodo-engine/src/snodo/coders/` is out of scope; prompt guidance is separate work and must not be added here.
- `packages/snodo-foundation/src/snodo/protocols/templates/*.yml` and `docs/` are out of scope.
- The `.snodo/` mutation guard in `packages/snodo-engine/src/snodo/coders/base.py` is a separate mechanism and stays untouched.

ACCEPTANCE
- A test that simulates a task branch rebased onto base commits which change a declared protected path yields no blocker, while the same fixture without the rebase fix fails.
- A test in which the task's own commit changes a declared protected path, or a file beneath a declared directory, still yields the blocker with the path named in the justification.
- A test in which the common ancestor cannot be resolved falls back to the base-ref comparison and still blocks a genuine task change.
- All existing tests in `tests/engine/test_protected_paths.py` pass, and `uv run pytest tests/engine -q` is green.
