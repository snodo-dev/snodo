# The README shows the value, then install, before the explanation

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
The README's readers are engineers who already use coding agents (Claude Code, Codex, opencode, Cursor and the like) and keep checking by hand whether "done" really means done. Today they read about 80 lines of explanation, including the plans, waves, queues and MCP-host details of "The working loop", before reaching install at "Install and first run". The top of the README should, in order:
1. say in a sentence or two what snodo does for them;
2. show the evidence: a few lines from the "what the gate caught" docs page added earlier in this plan, linked;
3. give install and the first run;
4. answer briefly "why add this when I already have CI, agent instructions and code review?";
5. continue with the existing explanation.

The answer to (4) covers three things:
- What snodo enforces: the protocol's validators and the test gate, before the work merges, inside the agent's own loop.
- When it intervenes: a failure goes back to the coder as evidence, a blocker halts and can't be outvoted, and every decision lands in a hash-chained audit log.
- What it costs: a gate run per task, plus the validators' model calls.

## THE CHAIN
- `README.md`: sections are the badges and tagline, flow diagram, "Built with snodo", "The working loop", "Install and first run", "Container image", "What a mock run does", "Project status", "Where to go next", "Research", "Contributing", "License".
- "Project status" says "The `opencode` coder paths are experimental" and that `litellm` (the default), `agy` and `mock` are supported. Check `docs/coders.md` for the current support status, and make the README agree with it.
- The docs page from task 1.1 of this plan: link it by its actual path.
- Repo docs checks live in `scripts/` with tests in `tests/scripts/`, for example the docs coverage check. Check whether any of them pin README headings or anchors (such as `#built-with-snodo`, used by the badge), and keep those anchors working.

## CONSTRAINTS
- Mostly a reorder. Keep the existing content and claims; move "The working loop" detail below install. New copy is limited to the opening statement, the evidence lines and the short "why add this" answer.
- Copy reads soft and natural. Avoid "not X but Y" contrast phrasing and superlatives.
- Do not mention snodo cloud.
- No new status, severity, halt type or audit event.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run the docs-related tests in `tests/scripts/`.
