# A short page: what snodo's gate caught while building snodo

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
Since v0.19.0, snodo has been built with snodo. Its own history is the most direct evidence of the problem snodo exists for: coding agents reporting work as finished while checks fail. Engineers who already use coding agents should be able to read one short page and see that with real numbers and one concrete example. The page is a docs page linked from the README. It is evidence, not marketing.

The figures below were computed by the maintainer's orchestrator from this repository's audit log (`verification_executed` and `validator_contradiction_detected` events for tasks run in their own worktrees, excluding mock runs), as of 2026-10-14. Use them as given, with that date and method stated on the page:
- 353 tasks ran the test gate (`make gate`) in their own worktree, across 515 gate runs. 102 runs did not pass.
- In 40 tasks, 61 times in all, the acceptance judge concluded that every criterion was met while the test gate failed the same work. snodo kept the failing verdict.
- 15 tasks were caught, then fixed: the gate named the failing tests, snodo sent that evidence back to the coder, and the next attempt passed.
- An example of one of those (task `task_9e66dcc7cd4e`, 2026-09-29): the first gate run ended with two named failures in `tests/mcp/test_pr.py` (`TestFetchPrContext::test_fetch_pr_context_full` and `test_fetch_pr_context_no_comments`) and the summary "4 failed, 4834 passed". The second attempt passed the full gate.

The page should also say plainly what this does not show: these are one project's numbers, with one protocol and the coders used here. Link the paper (README Research section) for the controlled experiments.
