# 1.1 — a WebSocket tunnel hostname is a recognised tunnel hostname

GitHub issue #1015 already exists for this work. Do not open another; put "Fixes #1015" in the commit message. Do not edit the CHANGELOG (a later task in this plan owns the entry).

## INTENT

The cloud will provision WebSocket tunnels under hostnames of the form `<slug>-<mode>-<short>-ws.snodo.dev` (one DNS label under `snodo.dev`, ending `-ws`). The CLI's tunnel-hostname recognition (`snodo/cli/commands/serve_security.py` and the tests that pin it) only knows the Cloudflare shapes, `<label>.tunnel.snodo.dev` and `<label>-tunnel.snodo.dev`. Recognition matters in the conflict path: when provisioning is refused with a 409, the CLI extracts the name of the tunnel that is blocking it, falling back to scanning the response text, and offers to delete it. A ws hostname in free text is not found, so the user is told the conflict did not name the existing tunnel.

## Evidence

```text
- The hostname pattern matches only ...tunnel.snodo.dev and ...-tunnel.snodo.dev.
- The extractor takes any non-blank JSON "hostname" first, so a ws hostname in JSON works;
  only the free-text fallback misses it.
- Tests that pin the pattern: tests/cli/test_serve_tunnel_slug.py (hostname-shape cases).
```

## Outcome

- The recogniser accepts a ws hostname with the same single-label discipline as the existing shapes (a lowercase DNS label ending `-ws` directly under `snodo.dev`, no extra dots), and still rejects look-alikes such as a multi-label prefix, a label not ending `-ws`, or a different parent domain.
- Free-text conflict bodies that mention a ws hostname yield that hostname; the existing Cloudflare shapes keep working exactly as before.
