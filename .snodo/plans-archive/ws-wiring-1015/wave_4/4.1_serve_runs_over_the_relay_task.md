# 4.1 — a ws tunnel runs: the serve starts the relay instead of cloudflared

GitHub issue #1017 already exists for this work. Do not open another; put "Fixes #1017" in the commit message. Do not edit the CHANGELOG (a later task in this plan owns the entry).

## INTENT

After the earlier tasks in this plan, `snodo serve --tunnel --tunnel-transport ws` can provision and save a WebSocket tunnel but cannot run it. For a Cloudflare tunnel the serve command (`snodo/cli/commands/serve_cmd.py`) starts the MCP server as a child, waits until it is bound, starts `cloudflared`, waits for its "registered" signal, announces the URL, supervises both and tears both down on exit or failure. A ws tunnel has the same shape with a different outbound piece: the machine relay replaces `cloudflared`, taking part through the relay-owner module added earlier in this plan (one process per machine owns the connection; others take over when it leaves).

## Outcome

- For `ws`, the command starts the MCP server child as today, waits for it to be bound as today, then starts relay participation instead of `cloudflared`. The user is told the tunnel is active once the server is bound and relaying has started; no `cloudflared` is looked for or launched.
- The serve process records itself in the serve registry with its transport and tunnel hostname, so the relay announces it; a Cloudflare serve records `cloudflare` exactly as before and is not announced by the relay.
- Supervision and teardown mirror the Cloudflare path: if the MCP child exits, relaying stops and the command fails; on interrupt or failure relaying stops, the child is terminated, and a tunnel that was provisioned in this very run and then failed to start is rolled back (deprovisioned) as the Cloudflare path does; the registry entry is removed. A ws tunnel being served does not require the remote port to match a provisioned port the way Cloudflare ingress does; the relay forwards to the live port from the registry.
- Authentication for a ws serve is oauth only; the same local verification the Cloudflare oauth path uses applies to relayed requests, and nothing in the service-token path is reachable for ws.
- The Cloudflare path (tests in `tests/mcp/test_serve_lifecycle.py` and the rest) behaves exactly as before.

## Acceptance

- Tests (with fakes for the relay participant, no network and no real child processes beyond what the existing lifecycle tests already fake): a ws run starts the server child, then relay participation, never `cloudflared`; the registry entry carries `ws` and the hostname; an interrupt stops relaying and the child and removes the entry; a child exit fails the command and stops relaying; a ws tunnel provisioned in this run and failing to start is rolled back; the Cloudflare path tests are untouched and green.
- The linter is clean; run the targeted tests and the linter, and do not run the whole suite yourself: the engine runs it right after you finish, and a multi-minute silent command has been dropping the coder connection.
