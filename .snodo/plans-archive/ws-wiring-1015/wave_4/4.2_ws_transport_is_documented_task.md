# 4.2 — the WebSocket tunnel transport is documented and recorded in the changelog

GitHub issues #1015, #1016 and #1017 already exist for this work. Do not open another; put "Fixes #1015, Fixes #1016, Fixes #1017" in the commit message. This is the only task in its plan that edits the CHANGELOG.

## INTENT

This plan adds a second way to expose a served project: `snodo serve --tunnel --tunnel-transport ws`, where the machine holds one outbound WebSocket to the cloud instead of running `cloudflared`. The user-facing documents describe only the Cloudflare tunnel, and the command reference notes that `--transport` is the local MCP transport, which makes the new option easy to confuse.

## Outcome

- `docs/command-reference.md` lists the new option next to the other serve options, says what each value means in a sentence, states that `ws` currently supports oauth only and needs no `cloudflared`, and makes the difference from `--transport` clear.
- `docs/specs/serve-tunnel.md` describes the ws variant: the extra provision fields, the hostname shape, the saved state without a tunnel token, one relay owner per machine with takeover, what is announced to the cloud, and teardown. Where the spec states details the code has since moved on from, keep the spec's existing text and add the new material; do not rewrite unrelated parts.
- One CHANGELOG entry under [Unreleased] in soft wording describing that a served project can now be reached over a WebSocket tunnel without `cloudflared`, with "(Fixes #1015, #1016, #1017)".
- Any link added to the docs resolves (the repository has a docs link gate).
