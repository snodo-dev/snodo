INTENT
After #784, the wave stops at any output written through Python's streams or rich consoles. The operator then ran `snodo task list` on the Mini, in a terminal. The table came up quickly, but it is shown in a pager: snodo/cli/task_list_display.py uses `with console.pager():`, which hands the table to the system pager (less), with arrows to navigate and q to quit. Because the table goes to the pager process and never through the streams the wave watches, the wave kept animating on the pager's bottom line, where the navigation hint belongs:

  │ 1.3_land_halt_reaping │ task/1.3_land_halt_reaping │ 1 │ merged │ 6h ago │ 2026-10-08 23:25 UTC │
  [▃▅▇▇▅] loading tasks… 8.9s

When this is done, the wave is gone, its line cleared, before any pager or other process takes over the terminal, and it never comes back for that command. That includes:
- rich `Console.pager()`;
- pydoc or other pagers;
- subprocesses that inherit the terminal, such as an editor;
- any wait for keyboard input, such as prompts or confirm dialogs.
Prefer one central mechanism in snodo/cli/spinner.py, for example treating entry into rich's pager context as output, plus a small helper commands can call before handing off the terminal. Avoid patching each command. Check other commands that use a pager or interactive input and make sure they are covered.

THE CHAIN
1. Reproduce with `snodo task list` under a pty, with PAGER set to a test pager such as `cat` or a script that records what it received.
2. Stop and clear the wave on pager entry, terminal handoff and input waits; keep it one-shot.
3. Tests:
   - entering `console.pager()` stops and clears the wave before the pager starts;
   - the pager's output contains no wave frames;
   - a prompt or confirm call stops the wave first.
