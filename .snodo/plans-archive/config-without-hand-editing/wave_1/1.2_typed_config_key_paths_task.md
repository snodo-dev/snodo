Before starting, open a GitHub issue on snodo-dev/snodo titled "Typed dotted-key access to provider, cloud and notification config". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
`snodo config set` and `config get` accept only `model`, `engine.*` and `llm.*`. Everything else answers "Unknown config key" and has to be edited by hand. That includes `providers.<name>.base_url`, `litellm_provider`, `api_key_env`, and the `cloud.*` and `notifications.*` sections (`docs/runbook.md`). Self-hosted and local-model users (Ollama, vLLM, LM Studio) feel this most. That is evidence from adoption recon rec_d6ff28.

When this is done, the config layer provides one typed way to read and write a dotted key path across the provider, cloud and notification sections:
- Values are validated with the same strict models used at run time.
- Unknown keys and wrong types are rejected with a clear message.
- Secret-bearing fields are marked so the CLI can redact them.

This task builds the layer only. A later task wires it into `snodo config set` and `config get`.

THE CHAIN
1. In the config package, a key-path resolver for provider (any provider name), cloud and notification fields. It validates through the existing models.
2. Secret fields are identifiable, so callers can redact them.
3. Tests: set and get round-trip for each section; an unknown key is rejected; a wrong type is rejected; a new provider entry can be created by setting its `base_url`.

CONSTRAINTS
- Do not change the CLI command module; the next wave does that.
- Snodo's state machine is closed.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
