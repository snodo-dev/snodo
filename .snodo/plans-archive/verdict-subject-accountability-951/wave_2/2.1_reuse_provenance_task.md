Fixes #951

INTENT
When a validator verdict is served from the project's verdict cache instead of being freshly judged, anyone reading the run can see what that verdict was reused from, and a cached verdict is only ever served for the same subject it was originally gathered against. A reuse that cannot be justified by the question being asked today must be a miss, not a shortcut.

THE CHAIN
- Caching verdicts saves most of the LLM calls a task makes, and it is deliberately only an optimisation: a cold, corrupt or unwritable cache degrades to a fresh judgement and never changes governance.
- Today a reused verdict appears in the run payload as a bare `reused: true` flag. The cache itself keeps only the verdict text under an opaque digest, with no record of the question that produced it — not the subject, the criteria, the model, the phase or the mode. So when a run's verdicts looked wrong, the investigation could not tell whether a reuse was responsible, and the incident behind this ticket was first misdiagnosed as cross-task reuse when it was in fact a fresh verdict about the wrong subject.
- A reader needs to be able to answer, for any reused verdict: which task or repository state it was gathered against, when, and why the same question is being asked again now.

CONSTRAINTS
- Each stored verdict records the identity of the question it answers — the subject it was judged against and the run context that key covers — in a form an operator can read back from the cache and from the run payload.
- A reused verdict carries that provenance with it wherever the verdict is reported, so the audit trail shows a reuse as a reuse *of something specific*.
- Serving a verdict for a question whose recorded identity does not match the question being asked today must be impossible by construction: a mismatch is a miss and a fresh judgement.
- Keep every property the cache already guarantees: an optimisation only, never a halt and never a governance change; never stores an error, a skipped pass or a non-cacheable verdict; project-local, bounded, thread-safe; a cache file written by an older shape is discarded rather than guessed at.
- Never record secrets, credentials or full task specifications in the cache or the audit trail — an identifier or digest of the subject is enough.
- Do not change what a verdict means, the quorum policy, or the criteria of any validator. Do not touch the load-sensitive process-group assertion in the quality-validator tests.

- A previous attempt at this task deleted roughly 400 lines from `tests/validators/test_verdict_cache.py` and stripped contract comments from `packages/snodo-core/src/snodo/core/interfaces.py` and the validator runner. That is not a solution to anything. Existing test cases are the record of the cache's guarantees: keep them, and add the new ones. Where a stored record's shape changes, the old cases must still pass against the new shape.
- The two sentences that were removed said what the cache promises - that an error and a skipped pass are never stored or reused, and that the runner never raises because a cache fault becomes an unusable verdict. Put that wording back where it belongs before changing the code it describes.
- The cache must remain an optimisation only. Two tests pass at the revision you start from and failed at the previous attempt's delivery, and they are the proof: `tests/coders/test_truncation_handling.py::TestTruncationExecutionFailure::test_truncated_response_produces_execution_error` and `tests/engine/test_turn_budget_exhaustion.py::test_turn_budget_exhaustion_is_an_operational_halt_not_internal_error`. A coder fault must still be reported as a coder fault, and running out of turns must still be an operational halt rather than an internal error - so nothing in this task may turn a cache problem into a verdict, a halt or a changed taxonomy.

ACCEPTANCE
- Reading a run, an operator can tell for each reused verdict which subject it came from, and can compare that with the task being judged.
- Inspecting the cache file shows, for a stored verdict, the subject identity it was gathered against.
- A question that differs from a stored verdict's recorded subject does not receive that verdict.
- The cache's existing degradation guarantees still hold: removing, corrupting or making the cache unwritable changes nothing about outcomes.
- Tests cover the recorded provenance, the match requirement, and the unchanged degrade-to-fresh behaviour.
