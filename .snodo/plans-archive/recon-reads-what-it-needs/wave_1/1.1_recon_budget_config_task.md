Before starting, open a GitHub issue on snodo-dev/snodo titled "Recon reading budget is hard-coded at 10 turns; make it configurable like the validator's". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
Recon agents lose their read tools after 10 tool-use turns. That limit is a hard-coded default, `max_turns: int = 10`, in `packages/snodo-mcp/src/snodo/recon/__init__.py`, and nothing on the MCP path overrides it.

Evidence: in recon rec_00a4f8, gemini was cut off after about 11k input tokens of directory listings and answered without opening a file. In rec_480b88, gemini and qwen reported their tools "revoked".

Validators already get a configured budget from `llm.validator` (`max_tool_turns`, `max_tokens`), which is set to 40 turns in the owner's config. Recon's config (`ReconConfig` in `packages/snodo-foundation/src/snodo/infrastructure/config.py`) has only `models` and `num_agents`.

When this is done, `llm.recon` accepts `max_tool_turns` and `max_tokens`, following the validator's pattern. The values flow from the MCP recon handler, through the recon manager, to each agent run. When unset, the defaults give recon a working budget: match the validator's default turn budget, not 10.

THE CHAIN
1. The recon config schema accepts the two budget fields, with validation consistent with the validator's.
2. The MCP recon handler reads them and passes them through the manager's submit path to each agent's run. The CLI recon path, if there is one, honours them too.
3. `docs/configuration.md` documents the two keys.
4. Tests: a configured budget reaches the agent run, and the default is no longer 10.

CONSTRAINTS
- Config keys only. Snodo's state machine is closed: add no status, halt type, severity, audit event or result field.
- Do not change the recon tool surface or the final-answer logic. Later tasks own those.

ACCEPTANCE
- The tests in link 4 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
