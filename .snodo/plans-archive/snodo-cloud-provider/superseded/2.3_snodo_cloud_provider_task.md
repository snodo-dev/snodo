# snodo cloud's model gateway is not a provider snodo knows

This work is tracked by GitHub issue #869, which is already open; reference it as "Fixes #869" and keep exactly one CHANGELOG entry for #869 under ## [Unreleased].

## INTENT
"snodo-cloud" is a built-in model provider. A model named "snodo-cloud/<id>" routes to the snodo cloud gateway's OpenAI-compatible API, at https://models.snodo.dev/v1 by default, configurable as `cloud.models_url`. It authenticates with the user's snodo cloud login: the OAuth access token, refreshed when needed, or else the configured `cloud.api_key`. With no cloud login, it behaves like any other unconfigured provider. The full gate passes: tests, import-layer contracts and config validation.

## THE CHAIN
- The previous attempt (task 2.2_snodo_cloud_provider in this plan, on its task branch) is nearly complete. It has routing, the gateway URL, catalog tests that name providers, and a foundation-registered credential capability that respects the import-linter contracts. Its focused tests, ruff and lint-imports all passed. The coder may build on it.
- The full suite then failed 9 tests on config validation, e.g. "Invalid config value for cloud.typo ... cloud.models_url Extra inputs are not permitted". There are two strict schemas for the user config: `packages/snodo-core/src/snodo/config_validation.py` and the CLI's `snodo/config_validation.py` (`_CloudConfig`, with `extra="forbid"`). The new `cloud.models_url` key, along with anything else the change writes to or reads from the user config, has to be accepted by both, and existing config tests should keep their meaning.
