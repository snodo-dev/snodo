INTENT
An idle relay connection stays open and keeps receiving frames, and when a connection ends nothing it started is left running. The behavior is proven against a real WebSocket on the loopback interface, not only against fakes. Read the relay as it stands on the branch before editing; do not change how requests are forwarded, how leases are fetched, or the reconnect backoff.

GitHub issue #1004 already exists for this work. Do not open another; put "Fixes #1004" in the commit message. No CHANGELOG entry (the plan's entry already covers it).

EVIDENCE
- The relay waits for the next frame with a short timeout so it can re-check the serve registry while idle. It does this by timing out the socket library's message iterator. Cancelling that iterator ends it for good: on the first idle timeout the next read reports the end of the stream, the relay leaves its connection block and closes the socket. Reproduced with the installed websockets library: a client waiting 0.25 seconds for a frame that arrives a second later gets a timeout and then a stream end, and the server sees a normal close. The relay's fakes iterate a plain list, so no existing test notices; a real idle connection would drop and reconnect about four times a second.
- When a connection ends while requests are in flight, their tasks keep running; their later sends on the closed socket raise inside their error handling and surface as never-retrieved task exceptions, and their entries stay in the relay's tables.

CONTRACT
- Waiting for frames and re-checking the registry must not end or cancel the connection's read side. Reading with a cancel-safe receive call (one that documents cancellation as safe) with a timeout, or reading in its own task and checking the registry on a timer beside it, both satisfy this; choose what fits the code. A frame that arrives while the registry is being checked is never lost.
- A normal close by the cloud ends the connection quietly and goes through the usual reconnect path; a close with code 4001 still stops the relay as before.
- When a connection ends for any reason, every in-flight request task of that connection is cancelled and awaited, and the relay's request state is empty afterwards. A failed send on a closed socket during teardown is not an error worth reporting.
- The relay's existing public behavior and its injectable seams stay as they are.

CONSTRAINTS
- The loopback test uses the websockets library already declared for this package, a server on 127.0.0.1 with an ephemeral port, and short real waits well under a second; no external network.
- Never log or store leases, headers or bodies.
- Do not touch the lease module, the registry module, serve, the CLI or the MCP transport. No new third-party dependency. No new status, severity, halt type or audit event. Respect the layer rules and run the import-layer check.
- Targeted tests only, plus the relay test files and the whole tests/infrastructure directory once. Do not run the snodo CLI, make gate or make release. Do not touch .snodo/.

ACCEPTANCE
- A test in its own new file, using a real loopback WebSocket server: the relay connects, the server stays silent for longer than several registry-check intervals, then sends a req and its body; the connection was never closed in between and the request is dispatched. A second case: the server closes normally and the relay reconnects once per its backoff rather than in a tight loop; a third: code 4001 stops the relay.
- A test that ends a connection with requests in flight and shows they are cancelled and the relay's tables are empty, with no unretrieved task exceptions.
- Existing tests pass and lint is clean. Run the targeted tests and report their output.
