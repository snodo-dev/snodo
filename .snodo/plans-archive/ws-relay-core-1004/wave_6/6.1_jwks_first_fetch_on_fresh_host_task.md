INTENT
The signing-key client used to verify JWTs always fetches the published keys on first use and throttles repeat fetches by elapsed time since the last real fetch, whatever the host's uptime. Today a host whose monotonic clock reads less than the cache lifetime (fresh containers and CI runners) refuses every valid token.

GitHub issue #1012 already exists for this. Do not open another; put "Fixes #1012" in the commit message. Add one CHANGELOG entry under [Unreleased] for the fix (soft wording, "(Fixes #1012)"); this is the only ticket in this wave.

EVIDENCE
The client records "last fetched" and "last unknown-key refresh" as zero before anything has happened and later compares the current monotonic clock minus that value against the cache lifetime (300 seconds). When the monotonic clock itself is below 300 (about five minutes after boot) both checks conclude that nothing needs fetching: the key set stays empty, the key is unknown, and the throttled refresh is skipped too, so verification returns nothing for valid tokens. The existing test that verifies an Access assertion against a faked key set fails with 401 instead of 200 on a sandbox with 50 seconds of uptime, and passes elsewhere; the same suite on Python 3.13 failed in CI on a freshly started runner.

CONTRACT
- A client that has never fetched fetches on its first verification, and one that has fetched keeps the cache for the configured lifetime.
- An unknown key id triggers at most one refresh per cache lifetime, measured from the last refresh that actually happened; the first unknown key id on a fresh client may refresh immediately.
- Behavior on hosts with long uptime is unchanged, and no token is accepted that was not accepted before.

CONSTRAINTS
- Other users of this client (OAuth verification and the Access assertion verifier) keep their call shape.
- No new status, severity, halt type or audit event. No new third-party dependency.
- Targeted tests only: the jwks tests, the Access assertion tests, the tunnel ASGI tests and the OAuth verification tests that use this client. Do not run the snodo CLI, make gate or make release. Do not touch .snodo/.

ACCEPTANCE
- A test with the monotonic clock patched to a small value (for example 5) shows a valid token verifies on a brand new client, and that a second unknown key id within the cache lifetime does not refetch again; a test with the clock patched to a large value shows the same behavior.
- The existing tunnel ASGI test with a faked key set passes regardless of host uptime.
- Existing tests pass and lint is clean. Run the targeted tests and report their output.
