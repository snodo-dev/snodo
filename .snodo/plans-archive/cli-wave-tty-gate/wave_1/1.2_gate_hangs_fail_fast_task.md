Before starting, open a GitHub issue on snodo-dev/snodo titled "Gate: a hanging test burns the whole 600s budget with no traceback". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased]. If CHANGELOG.md conflicts with a sibling task's entry, keep both entries.

INTENT
The project quality gate (`make gate`) runs scripts/gate_remote.sh over ssh. Its `gate` mode runs `pytest tests/ -q -n $GATE_JOBS` with no per-test timeout, while `gate-ci` uses `--timeout=60`. Twice today, a change that made some test hang only under the gate's pseudo-terminal used up the whole 600s quality budget. The result was "Test command timed out after 600.0s: 'make gate'", with no indication of which test hung. Coders and the operator then had to guess.

When this is done, a hanging test in `make gate` fails within a bounded time, well under the 600s budget, with pytest's timeout traceback naming the test. The suite still passes normally: no legitimate test is near the limit. Measure the slowest tests with `--durations` and pick a per-test timeout with comfortable headroom; the 60s that gate-ci uses may already be right. Keep `gate` and `gate-ci` otherwise as they are, since the script documents why they differ.

THE CHAIN
1. Check the slowest tests' durations, using the gate-ci invocation or `--durations=30` on a chunked local run.
2. Add a per-test timeout to the `gate` pytest invocation in scripts/gate_remote.sh, using pytest-timeout, which is already a pinned dev dependency.
3. Add or extend a test or script check that the gate invocation includes a timeout, if the repo has tests for the gate scripts. Otherwise explain in the commit message why none is added.
