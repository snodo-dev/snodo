## Intent
An operator signs in to a provider that uses OAuth with `snodo models --provider <name> --authenticate`. It works on a headless machine: it prints the sign-in address and the short code so the operator can finish the sign-in on any other device, and then it waits and saves the token itself. It never touches a provider that uses an API key.

## Evidence
- LiteLLM's ChatGPT authenticator performs the device-code sign-in when its get_access_token method finds no usable token: it prints the address and the user code, polls until the operator finishes and stores the token file. It can only do this on the main thread outside an event loop, which is how the command line runs. It also keeps a short cooldown between device-code requests.
- The models command dispatches by flag in the models command module (register builds a namespace and models_command checks each flag in turn); the benchmark, check and baseline commands are each in their own module beside it, and the benchmark command shows how a refusal is printed and how it is reported under `--json` with the existing error helper.
- The snodo cloud login command is the closest precedent for headless sign-in wording and error handling but uses a different protocol (authorization code with a pasted code); this command does not need a pasted code because the device-code flow finishes by itself.
- The `auth` provider setting and its helper `provider_uses_oauth` on the config manager already exist in the core config module.
- The token module already exists in this checkout as the Python module `snodo.infrastructure.chatgpt_oauth` in the foundation package. It offers the context manager `chatgpt_token_lock()` (a lock across threads and processes for the token file), the function `chatgpt_sign_in_state()` (reads the token file only, no network, returns a small mapping with the expiry when signed in or None), and `token_path()`. Use this module for the lock and the state; do not create another token module (no module named chatgpt_oauth_tokens exists or is wanted), and do not use the snodo-cloud OAuth store or cloud credential modules.

## Outcome
- `snodo models --provider <name> --authenticate` runs the device-code sign-in for a provider whose `auth` setting is `chatgpt-oauth`: the address and code are printed before waiting, and on success the command says the provider is signed in and until when. The sign-in runs under the token module's lock so it cannot collide with a refresh in another process.
- If the provider already holds a valid sign-in, the command says so and does nothing, unless the operator passes a flag to sign in again; keep the flag name consistent with the existing models flags.
- A provider without the `auth` setting, an unknown provider, a missing `--provider`, and `--authenticate` combined with another models mode (listing filters aside) each print a clear message and exit non-zero; under `--json` they use the existing machine-readable error shape. The message for an API-key provider says that provider uses an API key and nothing was changed.
- Denied, expired and interrupted sign-ins end with a short message and a non-zero exit, and leave any existing valid token untouched.
- The help text for the option says what it does and that it is only for OAuth providers.
- Tests cover: success with a fake authenticator printing address and code; already signed in; API-key provider refused; unknown provider; missing provider; denied or expired sign-in; the `--json` error; the help text. No network and no real token file.
- `make gate` passes, including ruff (no unused imports), the import-linter contract, and the file-length and docs-coverage checks.
