Title: Tunnels are OAuth-only; retire service-token tunnel auth in the CLI

Reuse GitHub issue #901 in snodo-dev/snodo, which already describes this change. The commit message must include "Fixes #901". Add an entry to CHANGELOG.md under [Unreleased].

INTENT
The cloud decided that tunnel provisioning creates no Cloudflare Access service tokens and returns only the tunnel token and hostname: a replayable credential to a developer's machine is the most dangerous thing it could hold. The CLI still offers service-token auth for tunnels, and that now misleads people and can leave a tunnel unprotected. A tunnel should always be served behind OAuth, and the CLI should say plainly that OAuth is how clients connect.

THE CHAIN
Observed on a real tunnel:
- Starting a tunnel with service-token auth requested printed "CF-Access-Client-Id: (not returned)" and "CF-Access-Client-Secret: (not returned)" under a success banner, because the cloud returns no such credentials.
- Restarting an existing OAuth tunnel with only service-token auth requested reported "Authentication: service-token" and started the local MCP server without its OAuth bearer check, since that check is only wired when oauth is among the requested methods. Nothing at the Cloudflare edge stands in for it, so the endpoint answered without any credential.
- The rotate flow reports that the tunnel has no rotatable credentials, which is now always true.
A previous attempt at this task completed the behaviour and its tests passed, but the lint gate failed: two local variables left assigned and unused in the serve command module after the auth handling was removed, and an unused import in the tunnel config module. Finish that work and leave the changed files lint-clean.

CONSTRAINTS
- A served tunnel always runs with the OAuth bearer check. There is no way to start a tunnel without it.
- Asking for service-token auth is refused before anything is provisioned, with one short, soft message saying tunnels connect through OAuth and naming the OAuth auth server. An older tunnel record that lists service-token keeps working and is treated as OAuth.
- The rotate and credential options go away; say so in the issue and the CHANGELOG. No new commands or flags.
- Remove dead service-token code rather than leaving it unreachable. The serve command module is over the file-length ratchet, so this change must not make it longer.
- Help text and docs describe OAuth as the tunnel's authentication. Update the --delete help to say it works with --tunnel.
- Run `uv run --extra dev ruff check` on the changed files before finishing, plus the serve and tunnel tests and any you add. Tests must not touch the real home folder. Do not run the snodo CLI, make gate or make release, and do not touch .snodo/.

ACCEPTANCE
- Starting a tunnel with service-token auth requested fails fast with the OAuth message and provisions nothing.
- A tunnel record listing service-token starts with the OAuth check active, and the banner shows only the URL and the OAuth auth server.
- No output path prints CF-Access-Client-Id or CF-Access-Client-Secret.
- A test proves the tunnel's MCP server rejects a request carrying no bearer token.
- ruff reports no errors on the changed files.
