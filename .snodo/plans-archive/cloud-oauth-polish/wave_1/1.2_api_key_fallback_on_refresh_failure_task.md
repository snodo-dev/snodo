INTENT
A machine that has both an OAuth login and a cloud API key keeps syncing when the OAuth login dies. Today, when the refresh token is expired or revoked, resolve_cloud_credential in packages/snodo-foundation/src/snodo/infrastructure/cloud_credentials.py returns no credential, safe_cloud_sync_credential logs "run `snodo cloud login` again", and sync sends nothing on every run until someone logs in again, even though a working API key is configured. Headless servers and long-running hosts are the ones that hit this.

Indications: OAuth still takes precedence while it works. When the OAuth credential cannot be produced (no refresh token left, refresh refused, refresh response unusable) or a refresh after a 401 fails, and cloud.api_key is configured, warn once per run (without secrets) that the OAuth login needs `snodo cloud login` and that the API key is being used, and sync with the API key. When no API key is configured, keep today's behaviour. Never open a browser or start a login from sync. Check the lease path in cloud_lease.py and cloud_sync.py so the fallback also covers the 401-then-refresh-fails case. Update the "which credential wins" wording in the cloud section of docs/configuration.md to match.

Acceptance: tests with a stubbed transport cover: expired refresh with API key falls back to the key; revoked refresh (refresh endpoint refuses) with API key falls back; 401 then failed refresh with API key retries with the key; no API key keeps the existing refusal and message; a working OAuth login still wins over the key. CHANGELOG.md updated.

First open a GitHub issue in snodo-dev/snodo for this ticket and put "Fixes #<n>" in your commit message; mention the issue number in the CHANGELOG.md entry. Secrets (access tokens, refresh tokens, authorization codes, PKCE verifiers, API keys) are never printed, logged, put in audit events, or sent anywhere except the cloud endpoints already in use. The state machine is closed: add no new status, halt type, severity, audit event type or audit field. Do not touch snodo-cloud. Tests use temporary directories and a stubbed HTTP transport (no real network, no real browser) and never write the repository's own .snodo/ directory. `make gate` must pass.
