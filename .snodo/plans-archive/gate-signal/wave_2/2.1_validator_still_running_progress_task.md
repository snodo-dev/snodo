# A long-running validator says it is still running

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
While a task's validators run, the job log shows "<validator>: started" and then nothing until "<validator>: finished". In this repo the quality validator runs the full gate, which can take up to its 600s timeout. During that window:
- the job log does not change;
- the progress summary sent to the cloud keeps the old line and the log's old modification time;
- the run looks frozen even though it is working.

A validator that is still running should add a short "still running" line about once a minute. The log then moves, and the progress summary reads as running the gate with a fresh time.

## THE CHAIN
- `packages/snodo-engine/src/snodo/validators/runner.py` (around lines 600–640):
  - `_dispatch_with_progress` emits "    <id>: started" through `progress_sink`;
  - futures are collected from a `ThreadPoolExecutor`;
  - "finished" is emitted elsewhere in the same function.
- `packages/snodo-foundation/src/snodo/infrastructure/job_progress.py`, `_summarize`, maps log lines to a fixed vocabulary. "running the gate" needs "gate" plus running/started/checking, so "quality: started" and a new still-running line are not recognised today. A still-running line from the quality validator should map to the existing "running the gate" phrase. Other validators map to nothing new.
- `packages/snodo-engine/src/snodo/engine/progress.py` filters and renders engine lines for the terminal (patterns around line 237). The new line must render cleanly there or be folded into the existing validator line. It must never be shown as an error.

## CONSTRAINTS
- Emit at most one still-running line per validator per minute, only while it is outstanding, and stop the moment it finishes. No line for validators that finish within the first minute.
- The line carries elapsed time, for example "    quality: still running (3m)".
- Use a timer or wait loop that cannot delay or reorder the verdicts, and that cannot leave a thread behind after the run.
- No new status, severity, halt type or audit event. Progress lines are not audit events.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run --extra dev ruff check` on touched files, and the runner, job_progress and engine progress tests.

## ACCEPTANCE
- Tests show:
  - with a short interval injected, a slow validator stub produces still-running lines and a fast one produces none;
  - lines stop after the validator finishes, and verdicts are unchanged;
  - `job_progress` turns a quality still-running line into "running the gate";
  - the terminal renderer shows the line without breaking its layout.
