Before starting, open a GitHub issue on snodo-dev/snodo titled "Mock coder fixtures for Go and Rust (and confirm Node/TS)". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
The `--mock` first run is how people try snodo without spending API credits. The mock coder (MockAdapter) writes a fixed fixture that follows the project's declared language. Python and JavaScript fixtures exist, per CHANGELOG 0.7.2 and the runbook. A Go or Rust developer's mock run doesn't exercise their toolchain, so the first impression is weak exactly for the communities most likely to adopt agent-driven SDLC.

When this is done, the mock coder writes a minimal source file plus a test that passes under that language's standard test command:
- Go (`go test ./...`);
- Rust (`cargo test`);
- Node/TypeScript, confirming the existing JS fixture passes `npm test` or an equivalent.

The language is chosen the same way as today.

THE CHAIN
1. The mock coder's language dispatch gains Go and Rust fixtures.
2. Each fixture is self-contained and passes its stack's test command on a clean repository.
3. Tests check the fixture selected and the files written for each language. Where the toolchain is available, an optional smoke test runs it.

CONSTRAINTS
- Python behaviour unchanged.
- Snodo's state machine is closed.
- Do not touch `snodo init` detection or docs; other tasks own those.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
