Before starting, open a GitHub issue on snodo-dev/snodo titled "snodo init: detect language and test command for Go, Rust and Node, not just Python". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
The quickstart is Python-only (`docs/runbook.md`, quickstart: `--test-command "PYTHONPATH=. pytest"`). Every shipped template's default test command is a no-op echo, so a Go, Rust or TypeScript developer who omits `--test-command` gets a `no_tests` outcome on their first run. That is evidence from adoption recon rec_d6ff28. The runbook mentions test-command detection from marker files (`pyproject.toml`, `package.json`, `Cargo.toml`, `go.mod`). Check what that detection actually does today and extend it.

When this is done, `snodo init` on a repo with no `--test-command` detects the stack from its marker files and writes a working test command into the protocol:
- Python: pytest;
- Node/TypeScript: the package's test script through the detected package manager;
- Go: `go test ./...`;
- Rust: `cargo test`.

It says what it detected. An explicit `--test-command` still wins. With no recognised stack, the current behaviour stays, with a clear message.

THE CHAIN
1. Stack detection covers the four stacks from marker files, extending the existing detection rather than adding a parallel one.
2. `snodo init` writes the detected test command and reports it.
3. Tests: each stack's marker detected; explicit flag overrides; unknown stack falls back.

CONSTRAINTS
- No new top-level CLI command.
- Snodo's state machine is closed.
- Do not touch the mock coder or docs; other tasks own those.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
