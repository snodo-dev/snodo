Before starting, open a GitHub issue on snodo-dev/snodo titled "Interactive snodo init on an existing repo: survey, intake, ready, next steps". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
`snodo init` now detects the language and test command for Python, Node/TypeScript, Go and Rust, and the mock coder writes a passing fixture for each.

Adopting snodo on an existing repo still means separate steps the developer must discover on their own:
- pick a template;
- run `snodo survey`;
- run `snodo intake` to turn decision records into validator criteria;
- run `snodo ready`.

That is evidence from adoption recon rec_d6ff28.

When this is done, an interactive `snodo init` in a repo that already has code offers, in one flow:
- show the detected stack and test command for confirmation;
- choose the template;
- optionally ingest existing decision records through the existing intake path;
- run the readiness check;
- print the next steps: a mock run and a first real run.

The flow composes the existing survey, intake and ready code; it does not duplicate them. Non-interactive (`--yes`) behaviour is unchanged.

THE CHAIN
1. The interactive init flow on a non-empty repo calls the existing survey, intake and ready implementations.
2. Each step can be skipped. `--yes` keeps today's behaviour.
3. Tests: the interactive flow calls each step (stubbed I/O); `--yes` doesn't prompt; a skipped step doesn't run.

CONSTRAINTS
- No new top-level CLI command. The owner avoids adding them, so this lives in `snodo init`.
- Snodo's state machine is closed.
- Do not change the mock coder.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
