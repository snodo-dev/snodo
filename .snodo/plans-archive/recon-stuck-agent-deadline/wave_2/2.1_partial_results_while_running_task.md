Before starting, open a GitHub issue on snodo-dev/snodo titled "Recon: read finished agents' answers while others are still running". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
While rec_831df0 was still `running`, two of its three agents had already written full answers to `.snodo/recons/rec_831df0/results.json`. `get_recon_results` refused with "Recon rec_831df0 is not complete (status: running)", and `get_recon_status` returned `"results": []`. The orchestrator could only read the finished answers by opening the file directly.

When this is done, the orchestrator can read the agents that have finished while the recon is still running, without any change to recon statuses. The MCP status call, the CLI equivalent, or both, show the per-agent results already written. They make clear which agents are still running. `get_recon_results` keeps its meaning for a complete recon, or includes finished agents with an explicit note that the recon is still running. Choose whichever fits the existing machine-interface conventions, and document it.

THE CHAIN
1. Surface already-written per-agent results through the existing status path (MCP `get_recon_status`, and the CLI if it has one).
2. Mark which agents are still pending, using fields or wording that already exist where possible.
3. Tests:
   - with one agent done and one still pending, the status shows the finished answer and the pending agent;
   - a complete recon's results are unchanged.
4. Update the recon docs and guide text to describe reading partial results.

CONSTRAINTS
- Snodo's state machine is closed: add no recon status, severity, halt type or audit event.
- No file may exceed its file-length limit or baseline.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The docs are updated.
- The CHANGELOG entry is present.
- `make gate` passes, including lint and the file-length check.
