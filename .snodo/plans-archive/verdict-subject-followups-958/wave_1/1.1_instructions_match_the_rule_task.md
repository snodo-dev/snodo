# 1.1 — the instructions and test scaffolds must match the verdict subject rule

GitHub issue #958 already exists for this work. Do not open another; put "Fixes #958" in the commit message. Add one CHANGELOG entry under [Unreleased] (soft wording, "(Fixes #958)") if the change is user-visible; otherwise none.

## Why this task exists

A verdict is only admissible when the judge names the task it was asked about: the
submit-verdict tool requires a task identifier and the engine rejects a submission whose
identifier does not exactly match the task being judged. That rule is implemented and
working. Three things still describe or exercise the older shape, and each one costs the
operator time when a run halts.

The acceptance judge's own prompt still tells the model to answer with a two-argument call:

```
"`submit_verdict(severity, justification)` tool — this is the\n"
```

The instruction the engine gives every other judge names three arguments, so the acceptance
prompt is teaching the model to produce a submission the engine will reject. The general
tool-loop instruction is at `packages/snodo-engine/src/snodo/validators/llm_validator.py`
and is already correct; the acceptance prompt in
`packages/snodo-engine/src/snodo/validators/acceptance.py` was left behind.

The extraction helper that performs the check accepts its expected identifier as an optional
keyword defaulting to an empty string. Every caller that passes it gets the rule; a caller
that forgets it silently gets a judge that rejects any real identifier, because nothing
matched the empty string. A required argument would fail at once instead of producing a
mysterious rejection at run time.

Finally, the test scaffold that keeps the older telemetry transcripts honest injects a fixed
identifier into any submission that lacks one, rather than binding the submission to the
identifier the transcript under test was built around. It hides exactly the class of defect
this rule exists to catch: a judge answering about a task it was not shown.

## Outcome

- The acceptance judge is instructed to submit the same shape the engine accepts, so a
  correctly-behaving model is not rejected by its own prompt.
- The expected identifier is not optional where it is knowable: a call site that has a task
  must say which task, and a call site that genuinely has none must say so explicitly rather
  than relying on a default that inverts the rule.
- The telemetry scaffold binds a submission to the subject of the transcript being replayed
  instead of inventing an identifier, so it can no longer pass a verdict that names the wrong
  task.
- The published description of the verdict tool matches the tool the engine actually exposes.
  Where a document is a record of a change that was delivered at the time, add a short
  correction note pointing at the current shape rather than rewriting the record; where it is
  living reference documentation, bring it in line.

## Acceptance

- A test that the acceptance prompt assembles a submission instruction naming the task
  identifier, and that a model following it is not rejected by the subject check.
- A test that a call site cannot omit the expected identifier without an explicit statement
  that there is no subject, and that the explicit no-subject path still behaves as the
  current default does.
- A test that the telemetry scaffold binds the recorded subject rather than a constant, and
  that a transcript naming a different task is rejected rather than patched.
- The existing subject tests in `tests/validators/test_verdict_subject.py` stay green, as do
  the telemetry tests the scaffold exists for.
- The validators and engine suites pass and the linter is clean.

## Constraints

- Do not change the matching rule itself: exact equality, a rejection that is terminal, and
  no inference from telemetry.
- Keep the severity and justification fields as they are; this is about the subject, not the
  verdict vocabulary.
- No new halt types or severities, and no new dependency.

## Diff discipline

Confine the change to what this task asks for. Do not reformat, reword, rename or delete code,
comments, docstrings or tests that this task does not change — the rationale notes in this
repository name the issue or incident that produced each branch and are part of the behaviour.
Messages an existing test quotes are a contract with the operator: add new text where this task
needs it, never replace pinned text. New coverage goes in new cases or new files rather than by
rewriting existing ones. Before submitting, look at the diff and remove any hunk that this task's
outcome does not require, then run the whole gate command from the contributing guide and leave
it clean.
