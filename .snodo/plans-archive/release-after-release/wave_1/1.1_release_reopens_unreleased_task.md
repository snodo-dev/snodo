# Release leaves no [Unreleased] heading behind

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
Right after `make release`, CHANGELOG.md has an empty `## [Unreleased]` heading above the version section it just wrote. That way the next ticket has somewhere to add its entry, and nobody has to restore the heading by hand.

## THE CHAIN
- `scripts/prepare_release_documents.py` (#799) turns `## [Unreleased]` into `## [X.Y.Z] — <date>` during `make release`. It does not add a new `[Unreleased]` heading.
- After v0.22.0 the heading was gone, and it had to be put back by hand (commit "chore: reopen [Unreleased] after v0.22.0").
- If nobody puts it back, the next ticket's changelog entry has no section to go under. `scripts/enforce_changelog.py` then flags any issue-closing commit that is not under [Unreleased].

## CONSTRAINTS
- Promoted entries stay byte-identical. The only change is one new empty `## [Unreleased]` heading directly above the new version section, with the same blank-line spacing as the existing headings.
- The released tree must still pass `scripts/check_release_version.py` and `scripts/enforce_changelog.py` in both modes.
- Edit only `scripts/prepare_release_documents.py`, its tests and CHANGELOG.md. Leave the Makefile and `scripts/enforce_changelog.py` alone, because a sibling task is changing them.
- Don't edit SECURITY.md. Tests use temporary copies of the CHANGELOG and SECURITY files.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/`.
- Run only the targeted tests.

## ACCEPTANCE
- Tests cover:
  - after preparation, the CHANGELOG has an empty [Unreleased] heading directly above the new dated section;
  - the promoted entries are unchanged;
  - the result passes `check_release_version.py` for the new tag.
- There is a CHANGELOG entry under ## [Unreleased].
