# 1.2 — `snodo serve --tunnel --tunnel-transport ws` asks the worker for a ws tunnel even without `--auth`

GitHub issue #1029 already exists for this work. Do not open another; put "Fixes #1029" in the commit message. Do not edit the CHANGELOG; the entry is already there.

## SYMPTOM AND EVIDENCE

With `--tunnel-transport ws` and no `--auth`, serve used to call `_provision_tunnel` without the transport or the machine id, so the worker returned a plain Cloudflare tunnel (hostname ending `-tunnel.snodo.dev`, not `-ws.snodo.dev`) and serve printed "tunnel active". The fix is already on main (the provisioning call in `snodo/cli/commands/serve_cmd.py` now takes the full call shape whenever the transport is ws). Nothing pins it.

## INTENT

In a new test module under `tests/cli` (do not edit existing modules), drive the serve tunnel provisioning path the way the existing lifecycle tests do (`tests/mcp/test_serve_lifecycle.py` patches `_provision_tunnel` and the surrounding process machinery; follow that pattern) and show: with the ws transport and no `--auth`, `_provision_tunnel` is called with `tunnel_transport="ws"` and a machine identifier; with the cloudflare transport and no `--auth` the call keeps its legacy shape and carries neither. A second test shows the request body sent to the worker for a ws provision contains `transport: "ws"` and the machine id (the existing `_provision_tunnel` tests in `tests/mcp/test_server.py` show how to capture the request).
