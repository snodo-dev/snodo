# 2.1 — a test pins that the tunnel path wrapper keeps host protection on mcp 2.x

GitHub issue #1027 already exists for this work. Do not open another; put "Fixes #1027" in the commit message. Do not edit the CHANGELOG; the entry is already there.

## INTENT

For a service-token tunnel the MCP server's `streamable_http_app` and `sse_app` factories are wrapped so the tunnel path router (`TunnelMCPPaths`) sits in front of the real app. On mcp 2.x those factories take `host` and `transport_security`. If the wrapper dropped or mis-forwarded either, the router would serve an app that refuses the tunnel hostname (or has no protection) and nothing would say so. The previous task of this plan moved the wiring into one named function, `install_tunnel_mcp_paths` in `snodo/cli/commands/serve_tunnel_asgi.py`, which `_run_server` calls.

Pin this with a test that exercises the real code: the real server builder, the real installer, the real `build_transport_security_settings` for a tunnel hostname, and both wrapped factories, driven in process with no sockets. The Access verifier may be stubbed; nothing else may be.

## Acceptance

- The tunnel hostname is not refused with 421 on either factory's app, and a foreign hostname is refused with 421 on both. The SDK default protection would refuse the tunnel hostname, so a wrapper that dropped `transport_security` or `host` fails the test.
- Each factory is exercised on its own routes, discovered from the app rather than assumed (`sse_app` does not serve `/mcp`).
- The test finishes by itself in a few seconds. A test that can hang is a failure: it stalls the engine's whole-suite gate, which has already failed this task twice at its ten-minute limit.
- The test lives in `tests/mcp/test_tunnel_factory_host_protection.py`. The module `tests/mcp/test_tunnel_factory_security.py` is a leftover of an earlier attempt on this task's own branch (it is not on main) and is the one that hangs; remove it.
- Existing tests stay green and the linter is clean.

## Findings from the earlier attempts

These are observations, not instructions; solve them as you see fit.

- A server cannot be built from a protocol that exposes no tools: the builder refuses when its generated instructions name tools the server does not expose. `tests/mcp/test_serve_http_real_process.py` writes a minimal protocol that does build.
- What a wrapped factory returns is not the object that owns the routes: the builder wraps the factories as well, so the routes sit some `.app` hops below the `TunnelMCPPaths` instance. Requests must still go through the wrapper, since the wrapper is what is under test.
- An SSE response for an allowed host never ends by itself, and `TestClient` waits for it forever.
- For a refused SSE request the SDK's SSE transport sends the 421 and then raises `ValueError("Request validation failed")`.
- `tests/mcp/test_auth.py` shows how this repo's tests give the streamable-http app's session manager its task group.
