# 2.1 — `snodo task show` prints the runs of the task

GitHub issue #1018 already exists for this work. Do not open another; put "Fixes #1018" in the commit message. Do not edit the CHANGELOG (the last task in this plan owns the entry).

## INTENT

An operator who runs `snodo task show <task>` gets the halt, findings and spec, and nothing about which job produced them. The previous wave added a reusable function and table renderer that answer "which jobs ran this task" (look for the new task-runs module in `snodo/cli`), and made the task record carry its `job_id`. Use them here so the trail from a task to its logs is visible in the one command people already run.

## Outcome

- The human output of `snodo task show` gains a "Runs" section with the table from the new module, placed after the existing halt and failure sections and before the spec, with a follow-up line telling the reader that `snodo meta <job id>` or `snodo job logs <job id>` shows a run in detail (use the command names that exist; check the job command module).
- With `--json`, the payload gains a `runs` list in the plain data form from the new module. Existing keys are unchanged.
- A task with no runs prints no Runs section.
- The existing fallback that scans job states to recover missing diagnostics keeps working as it does today.

## Acceptance

- Tests: the Runs section appears with a seeded task and job fixtures; `--json` carries `runs`; no section for a task without runs; existing output of the command for a task without runs is byte-for-byte what it was. New cases or a new test module.
- The existing task-show tests stay green; the linter is clean; run the targeted tests and the linter, and do not run the whole suite yourself: the engine runs it right after you finish, and a multi-minute silent command has been dropping the coder connection.

## Constraints
