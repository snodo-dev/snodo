Before starting, open a GitHub issue on snodo-dev/snodo titled "Example third-party validator plugin". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased]. If CHANGELOG.md conflicts with a sibling task's entry, keep both entries. Don't run the full `make gate` inside your session; run only the targeted tests. Run any snodo commands only inside temporary directories, never in the repo or worktree, so `.snodo/` is never touched.

INTENT
Adoption item 2 (third-party extensions) shipped the snodo.validators, snodo.predicates, snodo.coders and snodo.providers entry-point groups. `snodo ready` reports installed extensions under `extensions`, and docs/extending.md documents the interfaces. What's missing is a real, installable example. An adopter, or the operator verifying the feature, has to write a package from scratch just to see the mechanism work.

When this is done, the repo contains a minimal, well-commented example plugin package at examples/snodo-hello-validator/. It has its own pyproject.toml that registers one validator under the `snodo.validators` entry point, and a validator that makes a trivial, deterministic judgement, for example "warn if the task spec has no ACCEPTANCE section".
- Installing it into snodo's environment with one command (for example `uv pip install -e examples/snodo-hello-validator`) makes it show up in `snodo ready --json` under `extensions` → `snodo.validators`.
- A protocol can reference it as a validator, and `snodo validate` runs it.
- A short README in that folder gives the copy-paste steps: install, check with ready, add it to a protocol, run, uninstall.
Follow the interface in docs/extending.md exactly (ValidatorBase from snodo.validators.context). If the docs and the code disagree, trust the code and note the mismatch in the commit message.

THE CHAIN
1. Create the example package.
2. Add a test under tests/ that, in a temporary environment or by registering the distribution's entry point in-process, proves:
   - entry-point discovery finds the example;
   - `ready` reports it;
   - the validator returns the expected verdicts for a spec with and without an ACCEPTANCE section.
   Keep it fast and offline.
3. Make sure the example isn't picked up by the main package build or the test collection by accident.

CONSTRAINTS
- Do not modify docs/extending.md; a sibling task links to the example.
- Add no status, severity, halt type, audit event or result field.
- No file may exceed its file-length limit or baseline.

ACCEPTANCE
- The example installs and is listed by `ready`.
- The test exists and passes.
- `make gate` passes.
