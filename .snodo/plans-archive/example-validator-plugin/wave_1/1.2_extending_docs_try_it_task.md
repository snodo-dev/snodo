Before starting, open a GitHub issue on snodo-dev/snodo titled "Docs: point extending.md at the example plugin". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased]. If CHANGELOG.md conflicts with a sibling task's entry, keep both entries. Don't run the full `make gate` inside your session.

INTENT
A sibling task adds a runnable example validator plugin at examples/snodo-hello-validator/. It registers under the `snodo.validators` entry point, installs with one command, shows up in `snodo ready --json` under `extensions`, and can be referenced from a protocol. docs/extending.md documents the interfaces, but has no "try it" path.

When this is done, docs/extending.md opens with a short "Try it in a minute" section that points to examples/snodo-hello-validator/. It gives the copy-paste sequence: install the example, confirm it in `snodo ready --json`, add it to a protocol's validators, run `snodo validate`, and uninstall. The "Verify your plugin" section near the end refers back to the same check. Keep it brief; the example's own README has the detail.

THE CHAIN
1. Read docs/extending.md and the validator interface it documents.
2. Add the section and the cross-reference, using the exact example path and package name above. The package name is `snodo-hello-validator`, and the entry-point group is `snodo.validators`.

CONSTRAINTS
- Docs only. Do not touch examples/ or the tests; the sibling task owns them.
- No file may exceed its file-length limit or baseline.

ACCEPTANCE
- docs/extending.md has the "Try it" section and the cross-reference.
- The CHANGELOG entry is present.
- `make gate` passes, including the docs checks.
