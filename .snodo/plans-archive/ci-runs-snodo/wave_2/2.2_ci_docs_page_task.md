Before starting, open a GitHub issue on snodo-dev/snodo titled "Docs: running snodo in CI (GitHub Actions and GitLab CI)". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
Two pieces now exist:
- a container image definition for snodo;
- a CLI path that judges a branch or pull request's changes with the project's own protocol validators, resolving PR and MR numbers through the code-host provider plugins.

There is no docs page telling a team how to run snodo in CI. The existing CI material covers only the advisory PR-review workflow (`docs/configuration.md`, "Automated pull request reviews").

When this is done, the docs have a "Running snodo in CI" page covering:
- GitHub Actions, pointing to the repository's action and example workflow;
- GitLab CI, as a `.gitlab-ci.yml` example using the container image and the GitLab provider plugin for merge requests;
- how provider keys are passed as CI secrets;
- what the exit codes mean for a pipeline.

The page links from the docs index and from the advisory PR-review section.

THE CHAIN
1. A new docs page. Link it in the docs navigation and index.
2. Cross-links from `docs/configuration.md` and `docs/machine-interface.md` where they are relevant.
3. The docs build passes with the new page.

CONSTRAINTS
- Documentation only.
- Describe the action and image by the names and paths that exist in the repo. Read them; don't invent options.
- Keep guide markers intact.
- Snodo's state machine is closed.

ACCEPTANCE
- The page exists and is linked.
- The docs build passes.
- The CHANGELOG entry is present.
- `make gate` passes.
