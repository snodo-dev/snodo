INTENT
Two pieces now exist:
- the repository ships a container image definition for snodo itself;
- the CLI can judge a branch or pull request's changes with the project's own protocol validators. It uses the documented machine-interface exit codes and structured halt payload, and resolves PR numbers through the code-host provider plugin.

A team adopting snodo on GitHub should be able to add one step to a workflow to gate pull requests on their protocol.

When this is done, the repository provides a reusable GitHub Action (composite or container-based) that:
- installs or uses snodo;
- runs `snodo ready`;
- runs the protocol validation against the pull request;
- writes the verdicts to the job summary and fails the job on a blocking verdict.

Provider keys come from repository secrets that the user configures. The action never stores them.
