Before starting, open a GitHub issue on snodo-dev/snodo titled "Ship a container image for snodo itself". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
Teams adopt process controls where their process already runs: CI. Today `docker/` holds only `Dockerfile.opencode`, an image for the opencode coder, and there is no image that runs the snodo engine itself. That is evidence from adoption recon rec_d6ff28.

When this is done:
- The repository has a container image definition for snodo: a slim Python 3.12 base, snodo installed the way users install it (uv), `git` available, and `snodo` as the entrypoint.
- `docker run <image> --version` and `docker run <image> ready` work against a mounted repository.
- A CI workflow in this repo builds the image on changes to its definition, so it can't silently rot.

THE CHAIN
1. A Dockerfile for the snodo engine sits next to the existing `docker/Dockerfile.opencode`, following its conventions.
2. A GitHub Actions workflow builds the image (no push needed yet) and runs `snodo --version` inside it.
3. A short README note or docs mention points to the image and says how to build it.

CONSTRAINTS
- Core stays vendor-neutral: the image is plain snodo, with no code-host credentials baked in.
- Bake in no secrets or provider keys.
- Snodo's state machine is closed: add no status, severity, halt type or audit event.

ACCEPTANCE
- The Dockerfile and workflow exist.
- Any test the repo uses to lint workflows or Dockerfiles passes.
- The CHANGELOG entry is present.
- `make gate` passes.
