# Document validator-tool plugins, with a runnable example

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
A plugin author can learn from `docs/extending.md` how to add a tool to the LLM validator: the interface, the entry-point registration and the protocol wiring. They can copy a small working example from `examples/`, the same way the hello-validator example teaches custom validators.

## THE CHAIN
- Wave 1 added the registry (entry-point group `snodo.validator_tools`, contract in its module) and the per-validator `tools` protocol field. A sibling task in this wave wires them into the LLM validator.
- `docs/extending.md` has numbered sections (custom validators, predicates, coder adapters, code-host providers), each with Interface, Registration and Wiring subsections. `examples/snodo-hello-validator/` is the existing runnable example (pyproject with the entry point, a module and a README).

## CONSTRAINTS
- Add a new section to `docs/extending.md` in the same shape as the others. Mention the motivating case in one neutral sentence: an external decision model that answers yes/no questions over a large input, while the LLM keeps writing the verdict. Name no vendors.
- Add a tiny example package under `examples/`, for example a tool that counts lines of the diff touching a given path glob. It must not call any network service. It has its own pyproject entry point and README, and a test that loads it through the registry.
- Copy reads plain and soft. Avoid "not X but Y" contrast phrasing.
- Do not edit `llm_validator.py` or the registry module; those belong to other tasks.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run the strict docs build (`uv run mkdocs build --strict`) and the example's own test. Run nothing broader.

## ACCEPTANCE
- The strict docs build passes, with the new section in place.
- The example's test shows the tool is discovered through the registry, and its handler returns the expected text for a small diff.
- There is a CHANGELOG entry under ## [Unreleased].
