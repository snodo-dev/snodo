# The LLM validator offers and dispatches the plugin tools a validator opted into

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
When a protocol lists plugin tools on an LLM validator, that validator's model sees those tools alongside its built-in ones, calls them, and gets each handler's text back as a normal tool result. Its verdict and justification still come from `submit_verdict`. Validators that list no tools are unchanged.

## THE CHAIN
- Wave 1 added a registry of plugin-provided validator tools (entry-point group `snodo.validator_tools`; read its module for the contract: definition, handler, context) and an optional per-validator `tools` field in protocol config, each entry a name or a name with options.
- The LLM validator builds its tool list and dispatches calls in `packages/snodo-engine/src/snodo/validators/llm_validator.py`. Definitions are around lines 836–947, `_execute_tool` around line 1040, and some tools are post-execute only (`_POST_EXECUTE_ONLY_TOOLS`).

## CONSTRAINTS
- Offer only the tools the validator listed, resolved through the registry. A listed tool that isn't installed is reported clearly in the verdict path; follow how the validator already reports tool/config problems. A missing plugin never crashes a run.
- Build the handler context from what the validator already has: workspace root, spec text, diff refs, validator id, and the tool's options from config. Give the handler no write access.
- A handler exception or timeout becomes a tool-result error message to the model, the way built-in tool errors are handled. It is not an operational crash.
- `llm_validator.py` is under the file-length ratchet. Do not grow it; put the wiring in a small helper module and call it from the validator.
- No new status, severity, halt type or audit event.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the targeted validator tests.

## ACCEPTANCE
- Tests use a fake registered tool and a scripted model:
  - a validator that lists the tool offers it, dispatches the call with the right context and returns the handler's text;
  - a validator that doesn't list it never sees it;
  - a listed but uninstalled tool is reported without crashing;
  - a raising handler yields a tool-result error and the loop continues to a verdict.
