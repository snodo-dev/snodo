Before starting, open a GitHub issue on snodo-dev/snodo titled "Test-suite repo guard fails concurrent gates in sibling worktrees". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
Four plan queues ran in parallel, each task in its own worktree under ../.snodo-worktrees. Every task's `make gate` ended with about 24 pytest ERRORs in unrelated tests. Examples are tests/test_version_build.py, tests/test_verification_gate.py, tests/mcp/test_plan_verification.py and tests/properties/test_invariants.py. Typical output: "5189 passed, 24 errors". Six tasks were blocked by the gate for this reason alone. Tasks that ran with no other gate in flight passed the same gate.

Recon rec_6d6228 traced it to the session-scoped autouse guard `_guard_suite_repo_unchanged` in tests/conftest.py (around lines 72–116). It snapshots HEAD, the set of local branches (`git for-each-ref refs/heads`), and fingerprints of `.snodo/` and `.snodo/plans/`, then asserts at session end that none of them changed. Local branch refs are shared by every worktree of a repository. So when a concurrent snodo job creates its task branch, merges into a plan integration branch, or removes a worktree and its branch, the branch set changes and an unrelated gate fails. Verify this reading before changing anything. Also check whether the `.snodo/` fingerprints can be changed by a sibling job, for example through a shared path.

When this is done, the guard only reports mutations made by the pytest session it is guarding. A test that moves this worktree's HEAD, or creates or deletes a branch, is still caught. Ref activity from other worktrees that happens during the session is not.

THE CHAIN
1. Decide how the guard can tell its own session's mutations from sibling-worktree activity, and implement it. This worktree's HEAD is per-worktree. For branches, one approach is to snapshot only what this suite's tests can touch. Another is to ignore refs owned by other worktrees or snodo's task and plan namespaces. Choose what holds up, and explain the choice in the docstring.
2. Keep the failure message pointing at the mutating test, as it does today.
3. Tests:
   - a branch created from a sibling worktree during the session does not trip the guard;
   - a branch created or HEAD moved in the suite's own worktree still trips it;
   - an existing behaviour test for the guard, if there is one, still passes.

CONSTRAINTS
- Do not disable or skip the guard, and do not narrow it to nothing. It exists because tests once mutated the real repository.
- Snodo's state machine is closed: add no status, severity, halt type or audit event.
- No file may exceed its file-length limit or baseline.

ACCEPTANCE
