# 3.1 — a real HTTP server is started by a test, and the fix is announced

GitHub issue #1027 already exists for this work. Do not open another; put "Fixes #1027" in the commit message.

## INTENT

The crash in #1027 reached main because every serve test replaces the MCP server with a mock; nothing ever built a real server and ran it over HTTP on mcp 2.x. Add that test.

In a new test module under `tests/mcp`, start `snodo serve --transport streamable-http` against a minimal protocol in a temporary git repository, on a free loopback port, as a real subprocess (follow the pattern `tests/mcp/test_serve_lifecycle.py` uses for real processes and for reaping the process group, so a failed test leaves nothing listening). Wait for the port to accept connections with a bounded timeout, then show:

- the server started and answers a request to `/mcp` with a good `Host` header (`127.0.0.1:<port>`) as a live server would: any HTTP response that is not a Host refusal counts. A plain loopback serve has no tunnel and no OAuth configured, so it does not issue a 401 challenge; do not assert one and do not change serve code to produce one;
- a request whose `Host` is a foreign name is refused by the DNS-rebinding protection (421 or the status the SDK's transport security uses), not served; the refusal must differ from the good-Host response, so a server that had lost its protection would fail this test;
- the process exits cleanly when terminated.

The tests must skip, with a stated reason, only where the sandbox cannot bind a loopback socket; they must not be marked or configured so the gate silently never runs them.

Add the plan's single CHANGELOG entry under Unreleased in the repository's usual form: serve over HTTP and managed tunnels start on mcp 2.x again, "(Fixes #1027)".
