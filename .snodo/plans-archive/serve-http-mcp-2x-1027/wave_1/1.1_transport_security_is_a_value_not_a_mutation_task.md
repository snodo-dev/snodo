# 1.1 — the HTTP host protection is built as a value

GitHub issue #1027 already exists for this work. Do not open another; put "Fixes #1027" in the commit message. Do not edit the CHANGELOG; a later task in this plan owns the single entry.

## INTENT

`snodo serve` over HTTP, and therefore every managed tunnel, crashes at startup on mcp 2.x. The server object no longer has `host`, `port` or `transport_security` settings; mcp 2.x takes them as arguments when the app is built or run. `snodo/cli/commands/serve_security.py` still configures DNS-rebinding protection by mutating `mcp.settings.transport_security`, which does not exist any more.

This task is the first, self-contained step: make the protection computable without a server object. Add a pure function beside `configure_http_transport` that takes the port and the optional tunnel hostname and returns the mcp 2.x `TransportSecuritySettings` carrying exactly the allowed hosts, allowed origins and enabled DNS-rebinding protection that `configure_http_transport` computes today (loopback names with the port, the tunnel hostname with and without port, and its https origin when a tunnel is present). Check the real class and its field names in the installed mcp package rather than assuming them.

Leave `configure_http_transport` and its callers alone in this task; the next wave switches the caller over and removes it. Keep the `FORWARDED_ALLOW_IPS` handling where it is.

## Acceptance

- The new function returns the same hosts and origins the mutation computes, for a loopback-only server and for a server with a tunnel hostname, and protection is on in both cases.
- Tests for it in a new test module, with no mock of the mcp package: they build the real settings object. Do not rewrite existing tests.
- Existing serve tests stay green; the linter is clean.

## Constraints
