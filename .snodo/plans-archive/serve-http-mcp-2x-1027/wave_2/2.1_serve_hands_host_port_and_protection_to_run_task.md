## SYMPTOM AND EVIDENCE

On main with mcp 2.3.0, `snodo serve --tunnel --tunnel-transport ws` provisions a tunnel and then dies:

```
snodo/cli/commands/serve_cmd.py:335 in _run_server
    mcp.settings.port = port
ValueError: "Settings" object has no field "port"
```

The same happens for any non-stdio serve (`--transport streamable-http` or `sse`, with or without a tunnel). Stdio serve starts, which is why MCP clients never noticed.

## INTENT

On mcp 2.x `host`, `port` and `transport_security` are arguments, not server settings: the installed `MCPServer.run` forwards keyword arguments to `run_streamable_http_async` / `run_sse_async`, which take all three, and the transport-security value is built by the helper `serve_security.py` gained in the previous wave. `_run_server` must hand the chosen loopback host, the chosen port and that transport security to `mcp.run`, for a tunnel server and a non-tunnel server, and touch no removed settings field. Keep every other behaviour: port choice and bind-failure messages, `FORWARDED_ALLOW_IPS`, printed URLs, the tunnel ASGI wrapper, and the recorded-port behaviour for the stdio branch with an explicit `--port`.

The tests that read the removed attributes now assert the arguments passed to `run`, plus one in-process test with the real MCP server object for a tunnel and a non-tunnel server. Keep them as they are.
