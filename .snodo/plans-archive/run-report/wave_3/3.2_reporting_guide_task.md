# No guide explains how to read an overnight run

Before any change, open a GitHub issue in snodo-dev/snodo describing the gap. Write the issue body to a file under /tmp and pass it with `--body-file`; never pass text containing backticks or `$(` in an inline shell string. Put "Fixes #<issue number>" in the commit message, and add a CHANGELOG entry under ## [Unreleased].

## INTENT
An operator coming back to an overnight run has one docs page that says where to look and what the numbers mean:
- the plan run summary;
- the window report;
- how each metric is defined (block rate, first-pass rate, unknown versus estimated cost);
- what to do when a validator's block rate looks wrong.

## THE CHAIN
- The window report is `snodo task report`, and the single-run summary is an opt-in flag on `snodo plan status`. Both are already documented per command, in docs/command-reference.md and docs/following-a-plan-run.md.
- Metric definitions live in the docstrings of the run-outcome and validator-stats modules in this repo. Use their exact definitions.
- docs/running-unattended.md covers overnight runs but not reading the results.

## CONSTRAINTS
- Docs only: a new guide page, plus links from docs/running-unattended.md and the mkdocs nav. Don't edit docs/command-reference.md or docs/following-a-plan-run.md beyond a one-line link.
- Use the real flag names and output as implemented; read the code. Don't describe anything that doesn't exist.
- Copy reads soft and plain.
- Do not run the `snodo` CLI or `python -m snodo` in the worktree, and do not create, change or delete anything under `.snodo/`.
- Run only the strict docs build, not `make gate`.

## ACCEPTANCE
- The strict docs build passes, with the page reachable from the nav and from running-unattended.md.
- There is a CHANGELOG entry under ## [Unreleased].
