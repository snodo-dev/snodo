# No per-validator block rate exists anywhere

Before any change, open a GitHub issue in snodo-dev/snodo describing the gap. Write the issue body to a file under /tmp and pass it with `--body-file`; never pass text containing backticks or `$(` in an inline shell string. Put "Fixes #<issue number>" in the commit message, and add a CHANGELOG entry under ## [Unreleased].

## INTENT
A pure, tested function answers, for a time window: for each validator, how many verdicts it gave by severity, and its block rate. This lets an operator see which validators block most and which never fire. Later tasks surface it in the CLI.

## THE CHAIN
Facts from recon rec_d596f8, with two agents in agreement:
- The audit log (`.snodo/audit.log`, hash-chained JSONL; packages/snodo-foundation/src/snodo/infrastructure/audit.py:89-98, 143-150) records `validate` events with `phase`, `task_ref`, `validators_invoked`, `results` (per validator: `validator_id`, `severity`, `justification`, possibly `reused`), `outcome` and `policy_decision`. They're emitted in packages/snodo-engine/src/snodo/engine/nodes/validation.py:154-163 (pre) and 839-847 (post). The pinned data keys are in packages/snodo-foundation/src/snodo/infrastructure/cloud_sync.py:120-212.
- There is no per-validator block rate in product code. `snodo task report` (snodo/cli/commands/task_cmd.py:922-1029) already aggregates audit events over a `--days` window, for human review only.

## CONSTRAINTS
- Read-only over existing records. No new audit event types, data fields, statuses or severities; use the existing severity vocabulary as-is.
- Split counts by phase (pre/post), and count reused (cached) verdicts separately, so cache hits don't inflate rates.
- Tolerate older events with missing fields: skip and count them, don't crash.
- Put this in a new module of its own, with no CLI or MCP wiring yet. Another task, in the same wave, builds a separate run-outcome module; don't touch it.
- Do not run the `snodo` CLI or `python -m snodo` in the worktree, and do not create, change or delete anything under `.snodo/`. Tests build audit logs in tmp_path.
- Run only the new tests, not `make gate`.

## ACCEPTANCE
- Unit tests over a synthetic audit log cover: severity counts and block rate per validator per phase, window filtering, separate counts for reused verdicts, and tolerance of malformed or old events.
