## INTENT
Pure, tested functions answer two questions:
1. For one plan run: each task's final outcome, halt type, attempts, duration, tokens and cost, whether it was delivered, and the run's totals.
2. Over a time window: how many tasks ran, the first-pass rate (resolved on the first coder attempt), the outcome mix by halt type, and total and median cost, tokens and duration.

Later tasks surface these in the CLI and over MCP.

## THE CHAIN
Facts from recon rec_d596f8, with two agents in agreement:
- Job `state.json` (.snodo/jobs/<id>/) holds:
  - `status`, timestamps and `exit_code`;
  - `halt`: `final_decision`, `halt_type`, `validator_results`, and `attempts` {`total`, `coder_dispatches`, `history`[{`attempt`, `outcome`}]} (packages/snodo-engine/src/snodo/engine/nodes/writeback.py:784-970);
  - `usage`, one record per LLM call with tokens and `cost` in USD, plus `cost_source` (packages/snodo-foundation/src/snodo/infrastructure/usage_tracker.py:136-244);
  - a `cost` summary {`tokens`, `turns`, `attempts`, `duration_seconds`, `change_size`, `provenance`} (snodo/cli/commands/task_record.py:73-143);
  - `delivered_branch`.
- Task `state.json` (.snodo/tasks/<id>/) carries the same `cost`, `halt` and `usage`.
- Plan `status.json` maps task id to status, and plan-run child jobs carry `parent_job` (snodo/cli/commands/plan_run.py:887-910).
- In-place coders record usage with `source: "inplace_coder"` and a `measured` list. Cost may be absent, which is not the same as zero (usage_tracker.py:261-364).
- Existing partial aggregations, to reuse where it fits: `snodo meta` (snodo/cli/commands/meta_cmd.py:310-587), `snodo models --stats` (snodo/cli/commands/models_cmd.py:515-656), and the dashboard `cost_rollup` (snodo/dashboard/liveness.py:201-253).
