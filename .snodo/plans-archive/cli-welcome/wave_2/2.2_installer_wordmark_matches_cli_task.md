# The installer's wordmark can drift from the CLI's

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
The installer script and the CLI both draw the snodo.dev wordmark, but the shell script can't import Python. A small test keeps the two identical, so changing one without the other fails fast.

## THE CHAIN
- Wave 1 added two copies of the wordmark:
  - the docs folder's `install.sh` embeds it as plain rows;
  - a wordmark module under `snodo/cli/` renders it in Python.
- Find the actual module and function names in the code.
- The CLI version adds the version number after row three. The installer prints its own version line instead.

## CONSTRAINTS
- Test only, unless a real mismatch exists. In that case, fix the docs folder's `install.sh` to match the Python module, which is the source of truth.
- Compare the three rows glyph for glyph, ignoring the trailing version on the CLI's third row and any colour codes.
- Keep the test independent of the network and of the user's environment.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo. Never execute the installer against the real environment.
- Run `uv run ruff check` on touched files. Run only the new test and the existing installer test.

## ACCEPTANCE
- A test fails if a single glyph differs between the docs folder's `install.sh` and the Python wordmark, and passes on the current code.
- There is a CHANGELOG entry under ## [Unreleased].
