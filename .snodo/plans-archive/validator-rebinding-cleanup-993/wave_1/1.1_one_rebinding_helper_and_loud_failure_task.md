# One rebinding helper, and a loud failure when a model override cannot be rebound (Fixes #993)

GitHub issue #993 already tracks this work. Put "Fixes #993" in the commit message.

## INTENT
#991 made each validator call the provider of its own model by rebinding the shared completion function to the validator's model. That rule is written out twice in the validator runner, once for the parallel validators and once for the deferred acceptance pass, and in both places it is skipped without a word when the shared completion function cannot be rebound. A skipped rebinding restores the original defect (the default provider's base URL and key) with no signal. One helper should own the rule, and a model override that cannot be honoured should say so.

## EVIDENCE FROM THE PREVIOUS ATTEMPT
The previous attempt got the helper, the loud failure and the CHANGELOG edits in place, and it failed the gate on exactly one existing test: the provider-headers test that checks the completion function reaching a validator injects the task-scoped headers (tests/validators/test_provider_headers.py, the "run_validators wraps completion_fn" case; the call arrived without extra_headers). The cause is in the helper's default-model branch: it returns the raw shared completion function the runner was handed. But the validator context the runner builds already carries a completion function that is wrapped for task-scoped header injection, and each validator's context is a copy of it. By returning the raw function the helper replaced the wrapped one on every default-model validator, so those validators lost their task-scoped headers. Keep everything else the attempt did; fix that.

## THE CHAIN
1. Both validator passes obtain the validator's completion function from one helper that takes what the validator's context already carries, the underlying shared function it can be rebound from, the validator's effective model, the default model and the task id, and returns the function to use for that validator.
2. A validator on the default model keeps exactly the function its context already carries, which includes the task-scoped header injection. Nothing about its behaviour changes: the provider-headers test passes unchanged.
3. A validator on another model gets the rebound function with task-scoped headers, exactly as today.
4. When a validator needs a rebinding and the shared function cannot provide one, that validator ends with the runner's existing validator-error result, naming the validator and the model, instead of running against the default provider. Other validators in the run are unaffected.
5. No behaviour change anywhere else.
