INTENT
A served tunnel with service-token in its auth list answers MCP requests on its access path (/mcp-st) once the Cloudflare Access assertion is verified, beside /mcp which keeps the mcp-auth OAuth verifier. With both schemes both paths are served. With service-token only, the mcp-auth verifier is skipped and only /mcp-st is served (the cloud shows such a tunnel offline and never dispatches to it). oauth-only serve behaves exactly as today. Docs and the serve-tunnel spec say how the service-token path is used.

GitHub issue #1000 already exists for this. Do not open another; put "Fixes #1000" in the commit message. Add a CHANGELOG entry under [Unreleased].

EVIDENCE
The server framework takes one token verifier for its whole app, and that verifier receives only the token string, so the Access assertion header cannot be checked inside it. The project already serves a second route beside the MCP route through its own ASGI wrapper (the browser watch link), which is the pattern to follow: a wrapper on the same port that routes by path and applies its own check. The Access verifier from the previous wave (issue #998) and the saved tunnel config fields from the same wave (issue #999: auth list, access path, team domain, audience) are the inputs; read what they actually look like on the branch before wiring.

THE CHAIN
Serve starts with the saved auth list and the Access team domain and audience -> oauth in the list keeps the existing /mcp route and verifier untouched -> service-token in the list adds the /mcp-st route, which runs the same MCP handler behind a check of Cf-Access-Jwt-Assertion using the Access verifier; refusals answer 401 with no detail -> service-token without oauth means no mcp-auth verifier and only /mcp-st is reachable (a request to /mcp gets a plain refusal) -> the protected-resource discovery document and the printed URLs show the path each scheme uses, and the resource audience for the OAuth path stays https://<hostname>/mcp.

CONSTRAINTS
- Do not change how /mcp verifies mcp-auth tokens, its audience, or the existing browser watch route.
- Without a verifiable Cf-Access-Jwt-Assertion, /mcp-st never reaches the MCP handler. Fail closed, including when the Access key host is unreachable.
- The two paths share one port and one MCP handler; do not start a second server process.
- The client secret and Access tokens never appear in logs.
- No new status, severity, halt type or audit event.
- Keep the change local to serve wiring, the tunnel startup, docs and tests. Do not alter the verifier module or the provision code from the previous wave except to fix a real defect you find, and report such a fix plainly.
- Targeted tests only. Do not run the snodo CLI, make gate or make release. Do not touch .snodo/.

ACCEPTANCE
- Tests cover, through the real ASGI app with a fake key set: a valid Access assertion reaches the MCP handler on /mcp-st; missing, wrong-audience, expired and bad-signature assertions get 401 and never reach it; an oauth-only config serves /mcp exactly as before and has no /mcp-st; a both-schemes config serves both paths each with its own check (an OAuth token does not open /mcp-st and an Access assertion does not open /mcp); a service-token-only config refuses /mcp and serves /mcp-st.
- The serve-tunnel spec and the user docs describe the service-token path, the two Access headers a client sends, and that such a tunnel is offline to cloud dispatch.
- Existing tests still pass and lint is clean.
- Run the targeted tests and report their output.
