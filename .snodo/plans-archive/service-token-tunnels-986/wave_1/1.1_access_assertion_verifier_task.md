INTENT
A request that came through a Cloudflare Access app can be verified: the Cf-Access-Jwt-Assertion token is checked against the team's published keys, the audience, the issuer and the expiry. This ticket adds only that verifier and its tests. Nothing in serve uses it yet; a later ticket mounts it.

GitHub issue #998 already exists for this. Do not open another; put "Fixes #998" in the commit message. This ticket adds no CHANGELOG entry (nothing user-visible yet); another ticket in this plan owns the wave's CHANGELOG edit.

THE CHAIN
Provision returns access_team_domain (the full host of the team, no scheme or path, for example <team>.cloudflareaccess.com) and access_aud. A request on the service-token path carries the Access-signed token in the Cf-Access-Jwt-Assertion header. The verifier fetches the team's keys from https://<access_team_domain>/cdn-cgi/access/certs, finds the key the token names, checks the signature, requires aud to equal access_aud, requires the issuer to be https://<access_team_domain>, and requires a valid expiry. It answers accepted or refused.

The existing mcp-auth verifier (the JWKS client and the token verifier in the foundation and mcp packages) is the pattern to follow: reuse the key-fetching and caching approach it already has, extend it rather than writing a second one, and keep the same failure behaviour (fail closed, no secrets or tokens in log lines).

EVIDENCE FROM THE PREVIOUS ATTEMPT
A first attempt produced a verifier and a test module, and was stopped by one failing test of its own: the unknown-key-id case asserted two key fetches in total and observed three. Either the verifier fetches more often than the rule below allows, or the test counts the wrong thing. Settle it from the rule, not from the number: with a cold cache, the first verification fetches once to fill the cache; an unknown key id then allows exactly one more fetch for that verification; a second bad token with the same unknown key id shortly after must not force yet another fetch. Make the verifier and the assertions agree with that rule, and make the test name the counts it expects and why.

CONSTRAINTS
- Fail closed: a missing header, unknown key id, bad signature, wrong audience, wrong issuer, expired token, unreachable key host, or malformed input is a refusal, never an accept.
- Keys are cached with a short lifetime and refetched once on an unknown key id (Access rotates keys), without letting a bad token force a fetch on every request.
- Tokens and keys never appear in log lines.
- No new status, severity, halt type or audit event.
- Do not touch serve wiring, the CLI, the tunnel config or the provision code: other tickets in this wave and the next own those files.
- Targeted tests only. Do not run the snodo CLI, make gate or make release. Do not touch .snodo/.

ACCEPTANCE
- Tests generate their own signing key and serve the key set through a fake fetcher (no network), and cover: a valid token is accepted; wrong audience; wrong issuer; expired; bad signature; unknown key id (one refetch, then refusal, and no further fetch for the same unknown id inside the cache lifetime); a rotated key picked up after the refetch; fetch failure; missing or malformed header.
- The whole targeted test module passes when run on its own and together with the existing mcp-auth tests; lint is clean.
- Existing tests still pass.
- Run the targeted tests and report their output.
