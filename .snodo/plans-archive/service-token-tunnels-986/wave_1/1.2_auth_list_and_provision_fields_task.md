INTENT
`snodo serve --tunnel` accepts repeatable --auth oauth and --auth service-token (default oauth). The provision request carries the auth list. For service-token the provision response adds client_id, client_secret (shown once), access_path, access_team_domain and access_aud. The client prints the secret once at first provision only and never stores it, and keeps the non-secret fields in the tunnel config. Serving the new path is a later ticket; this one covers the CLI, the provision exchange, the stored config and the printed output.

GitHub issue #999 already exists for this. Do not open another; put "Fixes #999" in the commit message. Add a CHANGELOG entry under [Unreleased] (this is the only ticket in the wave that edits CHANGELOG).

EVIDENCE
Today the auth option is already repeatable on the command line, but validation accepts only oauth (service-token is refused with a message about OAuth), the provision body carries no auth list (a test pins exactly that), and the tunnel config keeps only hostname, tunnel token, created_at and port. Before the earlier change that made tunnels OAuth-only, the client printed the client id and secret and saved the non-secret parts; git history on the serve and tunnel-config code shows how, but the contract below is what to build to.

A first attempt implemented the feature and its new tests passed, and was stopped by existing tests elsewhere in the suite that it did not run:
- Several existing tests replace the provision call with a small stand-in that has the old call shape, and now fail because the client passes a new keyword to it on every run. The oauth-only path is meant to stay exactly as today, which includes calling provision exactly as before when the user passed no --auth; the new field should reach provision only when it is needed. Where a stand-in genuinely has to learn the new field (the service-token cases), update it.
- One existing test about the tunnel config saving no client secret also asserts that no client id is saved. Under this contract the client id is a non-secret field that is saved for service-token tunnels, so that assertion expresses the old rule. Keep the test's secret-related assertions, and move the client id expectation to match the new rule (saved for service-token, still absent for oauth-only). Say in the task result which existing tests you changed and why.
Find every existing test affected by these two rules by running the broader suites around serve, tunnel and MCP provisioning (tests/cli, tests/mcp and the tunnel-related tests), not only the new tests.

CONTRACT (from snodo-cloud, ADR-0052, merged on their side)
- Provision request body gains "auth": a list of "oauth" and/or "service-token". Absent means oauth only; the client sends the list only when the user passed --auth, as the pre-change client did.
- Provision response, for service-token only: client_id, client_secret (returned once), access_path (the string "mcp-st"), access_team_domain (full host), access_aud, and the auth list echoed back.
- Rotation (a separate ticket later) will return a new client_id and client_secret.
- A tunnel with service-token but not oauth is shown offline by the cloud and is never dispatched to. Say so in the printed output.

THE CHAIN
User passes --auth values -> validation accepts oauth and service-token and rejects anything else with a clear message -> provision request carries the list -> response fields are read; the secret is printed once with the client id, ready to paste as the two Access headers (CF-Access-Client-Id and CF-Access-Client-Secret) -> the non-secret fields and the auth list are saved in the tunnel config next to what is already there -> on later starts the saved fields are read back, the secret is never asked for or printed again.

CONSTRAINTS
- Gate on the new fields: if service-token was requested and the response lacks any of them (the cloud side reaches prod only after its worker deploy), say so plainly and roll back the tunnel provisioned in this run, as other provision failures already do. Do not crash with a trace.
- The client secret never goes into the tunnel config, logs, process arguments or error messages. Extend the existing secret redaction to cover it.
- oauth-only behaviour and output stay exactly as today. Existing saved tunnel configs without the new fields still load.
- Do not touch the serve routes, the Access verifier module or any MCP transport code: other tickets own those.
- Update the existing test that pinned "no auth in the provision body" so it expresses the new rule: absent unless --auth is passed.
- No new status, severity, halt type or audit event.
- Targeted tests only, but "targeted" here includes the existing serve, tunnel and MCP provisioning test directories named above. Do not run the snodo CLI, make gate or make release. Do not touch .snodo/.

ACCEPTANCE
- Tests cover: --auth oauth, --auth service-token, both together, an unknown value refused; the provision body with and without --auth; the response fields read and saved (non-secret only); the secret printed once and absent from the saved config, from logs and from redaction-sensitive output; a response missing the fields handled plainly with rollback; an old saved config still loading.
- The existing serve, tunnel and MCP provisioning tests pass (changed only as described above); lint is clean.
- Run the targeted tests and report their output.
