# Cloud sync cursor updates race and can move backwards

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
Concurrent cloud syncs never move a session or project cursor backwards and never leave the refusal flag, the session cursor and the project cursor inconsistent with each other.

## THE CHAIN
- Recon rec_30f4e0, confirmed against the code: in `packages/snodo-foundation/src/snodo/infrastructure/cloud_sync.py`, every `CloudSyncState` mutation (`advance_cursor` around line 634, plus the project cursor, refusal, pending and error setters around lines 634–728) is load → mutate → `_save`. `_save` uses `atomic_write_json` (temp file plus rename) but takes no lock.
- A background per-task sync and a CLI `snodo cloud sync` can interleave. A later write with a lower `last_synced_sequence` can then clobber a higher one.
- A delivered batch also does three separate load/save cycles (around lines 894–897): clear refusal, advance cursor, advance project cursor.

## CONSTRAINTS
- Serialise read-modify-write of the sync state file with the same file-locking approach used elsewhere (the locked atomic update helper in the infrastructure package).
- Make cursor advances monotonic: never lower a stored sequence.
- Do the three post-delivery updates in one locked update.
- No new status, severity, halt type or audit event, and no change to what is sent to the cloud.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo. Tests use temporary state directories.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the targeted cloud-sync tests.

## ACCEPTANCE
- A test with two concurrent updaters (threads or processes) never ends with a cursor lower than the highest advanced value.
- Advancing to a lower sequence leaves the stored one unchanged.
- The post-delivery update happens as one locked write.
