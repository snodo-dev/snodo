# `snodo task complete` rewrites task state non-atomically and without a lock

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
Every writer of a task's `state.json` goes through the same locked, atomic update. A crash or a concurrent writer can then never leave it truncated or lose a field.

## THE CHAIN
- Recon rec_30f4e0, confirmed against the code: in `snodo/cli/commands/task_complete.py` (around lines 210–222) the code reads `state.json`, mutates it and writes it back with `write_text`. That is a truncate-and-write, with no lock.
- The engine's own completion path (`snodo/cli/commands/task_record.py`, around line 135) uses the locked `atomic_update_json`.
- The failure is also swallowed at debug level.
