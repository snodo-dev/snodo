# A task is recorded `completed` before its merge runs

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
A task's recorded terminal status always matches its delivery. A crash between recording and merging can never leave a task marked `completed` with no merge and no `task_merged` event.

## THE CHAIN
- Recon rec_30f4e0, confirmed against the code: in `snodo/cli/commands/run_cmd.py` (around lines 1018–1036), `_record_task_completion(..., "completed" if resolved else "failed", ...)` runs before `_deliver_on_success` performs the merge. That merge may later flip the status to `unmerged`.
- `_record_task_completion` (`snodo/cli/commands/task_record.py`, around lines 135–143) also writes the task state and the job state in two separate atomic updates.

## CONSTRAINTS
- Use only the existing statuses and transitions; this changes ordering, not vocabulary. When delivery applies, record the terminal status once its outcome (merged or unmerged) is known. When it doesn't, record it as today.
- Keep the task and job records consistent. If they must stay two writes, order them so a crash leaves the job non-terminal (and so recoverable) rather than contradicting the task.
- Existing reconciliation and recovery paths that read these records must keep working. Check them.
- No new status, severity, halt type or audit event.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files (`run_cmd.py` is under the ratchet). Run only the targeted run, merge and task-record tests.

## ACCEPTANCE
- Tests show:
  - with auto-merge, the task is recorded `completed` only after a successful merge and `unmerged` after a refused one;
  - a simulated crash before delivery leaves no `completed` record;
  - without delivery, behaviour is unchanged.
