## STATE
- The earlier attempt refused every write resolving inside `.snodo/`. That was wrong, and it broke 4 tests in `tests/mcp/test_write_capability.py`, for example "Write path '.snodo/spec.md' resolves inside protected .snodo/ state".
- MCP `write` mode exists to write under `.snodo/`: its default `write_allowed_prefixes` is `.snodo/`, and orchestrators write specs there.
- Its read-side work (refusing `.snodo/tunnel.json`) can be reused; take what is right from that branch.

## INTENT
- **Reads:** credential files under `.snodo/` can never be read through the workspace tools. The protocol, plans and other context there stay readable (ADR 026).
- **Writes:** writes reach `.snodo/` only through a write prefix that itself lies inside `.snodo/`, so a broad prefix such as `.` or `""` can't. Credential files can never be written, and symlinks can't be used to escape a prefix.

## THE CHAIN
- `packages/snodo-tools/src/snodo/tools/workspace.py` makes all of `.snodo` readable (`_READABLE_IGNORED_DIRS = {".snodo"}`, around line 26; exemption around lines 214–220).
- `_save_tunnel_config` (`snodo/cli/commands/serve_tunnel_config.py`) writes `.snodo/tunnel.json` with the live `tunnel_token`, `client_id` and any `credentials`. cloudflared needs these to run the tunnel, so the file stays, but tools must not read it.
- `write_file_with_prefixes` (around lines 435–483) checks prefix membership after `resolve()`.
