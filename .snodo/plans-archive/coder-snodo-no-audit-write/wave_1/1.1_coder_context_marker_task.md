# Coder subprocesses should say they are coder subprocesses

Issue #796 already exists for this. Don't open a new issue, and don't edit the issue body. Put "Fixes #796" in the commit message, and add a CHANGELOG entry under ## [Unreleased].

## INTENT
A snodo process started by a coder inside its task worktree has no way to tell it is running under a coder job, so it writes governance state into the worktree's `.snodo/`, and the task gets blocked. Give the coder's subprocess environment an explicit marker, so snodo code running inside it can recognise the situation.

## THE CHAIN
- `SubprocessCoderAdapter._run_subprocess` starts the coder with `env=subprocess_env_without_job_context()` (packages/snodo-engine/src/snodo/coders/subprocess_adapter.py:402-412). That helper removes SNODO_PROJECT_ROOT, SNODO_JOB_ID and the other job vars (packages/snodo-core/src/snodo/paths.py:17-35).
- The previous attempt of this task implemented everything correctly: the constant, `is_coder_subprocess()`, a marked child-env helper applied to the coder launch, and tests. 23 targeted tests passed.
- It was then blocked for writing `.snodo/audit.log`. The cause: the coder opened the GitHub issue with an inline, double-quoted shell `--body` string. Backticked text in the body, such as `snodo ready`, ran as command substitution. That executed `snodo ready` in the worktree, which wrote the audit log.
- `git status --porcelain .snodo` can't detect this, because `.snodo/audit.log` is gitignored.

## CONSTRAINTS
- Same design as before. The env var is `SNODO_CODER_SUBPROCESS=1`, and sibling task 1.2 reads exactly that name. Define it once next to the job-context vars in paths.py, with a helper. Set it only in the coder child's environment, never in the engine's own. Keep removing the job-context vars, and don't touch the snapshot guard.
- No new status, severity, halt type or audit event.
- **Never pass text containing backticks or `$(` through an inline shell string**, whether in issue bodies, commit messages or anything else. If you need `gh` at all, write the text to a file under /tmp and use `--body-file` or `-F`.
- Do not run the `snodo` CLI or `python -m snodo` in the worktree. Use tmp_path projects in tests.
- **Do not create, modify or delete anything under `.snodo/`**, not even to clean up. Any change there, including removing a file, blocks the task. This worktree is reused from a previous attempt, and its earlier uncommitted work may already be present: build on it.
- Run only targeted tests, not `make gate`.

## ACCEPTANCE
- A test proves a coder child process sees `SNODO_CODER_SUBPROCESS=1` and still doesn't see SNODO_JOB_ID or SNODO_PROJECT_ROOT.
- A test proves the parent process environment is unchanged.
- The helper has unit tests.
- `.snodo/` is untouched, and there is a CHANGELOG entry under ## [Unreleased].
