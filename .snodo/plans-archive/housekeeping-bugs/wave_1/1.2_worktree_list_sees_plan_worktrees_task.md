# Worktree list is slow and prune never removes plan worktrees

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
`snodo worktree list`, `prune` and `remove` cover all of this project's retained worktrees. That includes the plan worktrees nested as `<plan>/<task>` and `<plan>/integration`. Listing returns in seconds even when the worktree root is shared with other projects.

## THE CHAIN
- Evidence: on the maintainer's Mac, `snodo worktree list` ran for more than 170s. The worktree root is shared by five projects and held 326 entries.
- `snodo worktree prune --days 0 --force` then removed only 24 `task_*` worktrees. It left 40 snodo-public plan worktrees (for example the docs-template task of plan persona-templates, and the integration worktree of plan ci-runs-snodo), which had to be removed with `git worktree remove`.
- `list_worktrees` in `packages/snodo-foundation/src/snodo/infrastructure/worktree.py` walks the whole root with `rglob("*")`. That means every file of every worktree of every project, which explains the time.
- It returns only `p.name`, so a nested worktree comes back as `integration` or `1.1_x`. Prune then resolves that name with `worktree_path(project_root, name)` to a path that doesn't exist, its `stat()` fails, and the worktree is silently skipped (in `snodo/cli/commands/worktree_cmd.py`).
- The project's own worktree list (what `_project_worktree_paths` already uses) is the authoritative set.

## CONSTRAINTS
- Derive the set from the project's own worktree registry rather than walking the shared directory. Report plan worktrees with an identifier that `remove` and `prune` accept, for example the path relative to the worktree root.
- `snodo worktree remove <task_id>` keeps working for existing `task_*` names.
- Another project's worktrees are never listed or removed.
- No new top-level CLI command, and no new status, severity, halt type or audit event.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo. Tests use temporary git repositories.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the targeted worktree tests.

## ACCEPTANCE
- Tests use a temporary repo with a `task_*` worktree, a `<plan>/<task>` worktree and a `<plan>/integration` worktree, plus another repo's worktree under the same root:
  - list shows the first three and not the foreign one;
  - prune with `--days 0 --force` removes all three;
  - the foreign worktree survives.
- Listing doesn't recurse into worktree contents. A test or assertion guards this, for example by not calling rglob on the root.
