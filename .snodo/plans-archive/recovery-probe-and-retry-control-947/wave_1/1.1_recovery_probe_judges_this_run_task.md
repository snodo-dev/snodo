# 1.1 — the work-recovery probe must judge this run, not the plan's history

## Why this task exists

When a coder returns no files, the engine asks a recovery probe whether the task branch
already carries the work — the case where an earlier attempt committed its work and then
the run failed afterwards. The probe is handed the plan's base branch. From the second
wave of a multi-wave plan onward, the task branch is created from the plan's integration
branch, which already contains the earlier waves. The probe therefore always finds a
non-empty difference, and an empty run is promoted to a pass.

The call site that supplies the wrong base is in
`packages/snodo-engine/src/snodo/engine/nodes/executor.py`, on the no-file-operations
path, where the probe is called with the task's plan base:

```python
existing = self._existing_task_branch_work(
    git_mcp, getattr(task, "base", None)
)
```

What was observed in the field (issue #947): a wave whose coder relocated to a different
checkout and wrote nothing was reported completed, the plan advanced to delivery, and the
workspace-escape check below the probe was never consulted, because that check only runs
when the probe returns nothing.

## Outcome

- The recovery probe judges the commit this run started from. The executor already
  snapshots local refs before dispatching the coder; use that snapshot's entry for the
  active task branch as the recovery base when it is available. Work committed by this
  task's own previous attempt is still recovered — that is the behaviour the probe was
  built to provide — while commits inherited from earlier waves are no longer mistaken
  for this attempt's output.
- When the snapshot has no entry for the active branch, resolve the branch the task
  branch actually diverged from (the plan's integration branch, when the plan has one)
  and use its merge-base with HEAD.
- Only when neither is resolvable may the probe fall back to the plan base, and then it
  must not claim recovered work: the record it writes says the verdict is ambiguous, and
  the progress line the operator reads does not assert that an earlier attempt committed
  the files.
- The escape check is reached whenever this run produced nothing, including when the
  branch carries commits this run did not make. An empty run in a multi-wave plan is a
  halt, not a pass.
- The subprocess coder adapter states only what it observed. It knows the diff was empty;
  it does not know the task is complete.

## Constraints

- Keep the probe's purpose. Recovering a previous attempt's committed work is what lets a
  retry finish the job; do not remove the probe and do not narrow the fix to one call
  site if the bounded-run recovery path shares the same probe.
- Do not change what post-execute validators judge: they judge the branch, as today.
- No new configuration knobs, and no new dependency.

## Correction for this retry

The previous attempt implemented the probe in roughly the right shape, but its own tests
never executed the path they claim to cover, and one existing test module was broken. Both
must be fixed before this task can pass.

1. Every case in the new test module halts as `wf3` before the coder is dispatched, so
   none of them exercise recovery. That halt is the compiler's workflow-condition-3
   rejection of a mode with no pre-execute validator, and this module's protocol fixture
   declares a mode whose only validator is a post-execute one. Build the fixture the way
   the existing harness in `tests/engine/test_bounded_run_work_is_judged.py` does — a
   pre-execute validator plus the post-execute one, and the disagreement policy — or reuse
   that fixture directly. Then confirm each test actually reaches the probe: a test that
   would still pass when the recovery base is the plan base is not testing this change.
2. The probe body was moved into a new module whose logger name and message wording
   differ from the executor's. `tests/engine/test_failure_reason_survival.py` pins the
   logger name and the wording of the inspection-failure warning, and it is part of the
   suite that must stay green. If the probe is extracted to keep the executor module
   within its size gate, the extraction must preserve the logger name and the messages
   those tests assert, or the executor must emit them itself. Do not edit that existing
   test module to match.
3. The previous attempt submitted without running anything. Before submitting, run the
   engine suite and the linter, and state the result:

```
uv run pytest tests/engine -q -p no:randomly
uv run ruff check .
```

Both must be clean. A halt is better than a submission whose tests do not run.

## Second correction (this round)

The probe fix and the fixture are in place: the engine suite is down to one failure, in
`tests/engine/test_recovery_probe_run_start.py`, and the previously broken modules are green.

The remaining case asserts a halt type the engine does not produce, and it is the assertion
that is wrong, not the code. The escape path raises the engine's execution error, and the
node that catches it records that fault as `internal_error` — the behaviour
`tests/engine/test_default_executor.py` pins when it calls the executor directly, and the
behaviour on the branch before this task. Do not change that mapping: it is pre-existing
engine classification, an ADR-governed halt vocabulary, and outside this task.

Restate the case as the property the spec asks for — an inherited-history run that escapes
is reported rather than passed:

- assert the attempt is blocked, and that it is not the no-file-operations halt and not a
  completion;
- assert the escape message reaches the record, so the operator is told which ref moved in
  which external checkout;
- leave the halt type at what the engine actually assigns rather than naming a type it does
  not use here.

Then run the engine suite and the linter as above and confirm both are clean before
submitting.

## Third correction (this round)

The suite is green: the full gate run reached 5695 passed with the recovery tests included, so
the fixture and the pinned-wording problems are settled. What stopped the task is the linter
half of the same gate command.

Two `B904` findings, both in `packages/snodo-engine/src/snodo/engine/nodes/executor.py`, at the
lines that raise the workspace-escape error from inside an existing `except` clause — the one
that handles a depleted turn budget, and the one that handles a coder timeout. Ruff requires an
explicit exception chain there: either `raise ... from err` when the handled exception is part
of the story, or `raise ... from None` when the new error supersedes it.

Choose deliberately rather than reflexively. The escape is a different failure from the budget
or timeout that was being handled, and the handled exception is already recorded by the fact
recording that runs before the raise — so chaining it into the escape error would suggest a
causal link that is not there. Whichever you pick, the failure reason the engine records must
still survive: the existing tests that pin it stay green unchanged.

Then run the whole gate command, not only its test half, and leave it clean.
