# An environment halt must not consume a coder attempt (Fixes #992)

GitHub issue #992 already tracks this work. Put "Fixes #992" in the commit message.

## INTENT
A coder gets a fixed number of attempts per task. A dispatch fault (the environment halt type that already exists for operational faults) is not the coder's failure, so it should not use one up. Issue #975 lost two attempts on one task to a coder that was looking at the wrong tree. Make sure that holds for environment halts, so the sibling ticket in the next wave can halt without penalising the coder.

## THE CHAIN
1. Find where a run's attempt count is advanced after a halt, and how halts are classified into the existing halt types.
2. An environment-type halt leaves the attempt count where it was, so the next retry is not charged for it.
3. If that is already true, pin it with a test and change nothing in behaviour. If it is not, make it true for environment halts only.
4. Genuine coder failures (blocked, verdict failures) keep their current budget semantics, including the three attempts and the reset a spec replacement gives.

## CONSTRAINTS
- Do not change the retry budget for any non-environment halt.
- Do not add a status, severity, halt type or audit event. The environment halt type already exists.
- No new third-party dependency.
- Do not touch CHANGELOG.md; a sibling ticket owns the entry.
- Targeted tests only.

## ACCEPTANCE
- A test where a run halts with the environment halt type shows the task's attempt count unchanged afterwards.
- A test where a run halts as a normal coder failure still advances the attempt count as before.
- Targeted tests pass and lint is clean for the whole tree.
