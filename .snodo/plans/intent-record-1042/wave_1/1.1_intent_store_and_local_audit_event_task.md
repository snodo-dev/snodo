## Intent
An operator's intent should exist as a durable record before any plan is cut from it, so that plans can later point back to it. This task creates the local store for those records and the one audit event that announces a new record. It does not connect plans to intents yet.

## Evidence
- The closest existing pattern is the recon store: ReconManager in packages/snodo-mcp/src/snodo/recon/__init__.py keeps one directory per record under `.snodo/recons/<id>/`, allocates ids as `rec_<6-hex>` with a collision retry, writes via temp file plus `os.replace`, and lists newest first. Shared atomic helpers live in packages/snodo-foundation/src/snodo/infrastructure/ (atomic_json.py, state.py, queue_store.py). The foundation package is the right home for the store because the plan verifier (also foundation) will need to look intents up in a later task.
- Local-only audit events are declared in `_LOCAL_EVENT_DATA_KEYS` in packages/snodo-foundation/src/snodo/infrastructure/audit.py (recon_started, recon_completed, retry_worktree_continued are the examples); scripts/enforce_audit_event_contract.py fails the gate for any emitted event type that is not declared. tests/recon/test_recon.py (around the recon_started / recon_completed assertions) shows how a test pins a local event's data keys.
- Writes under `.snodo/` must go through an official interface (ADR 026, ADR 027, ADR 038); the store is that interface for intents.

## Outcome
- A new module named `intent_store` in the foundation infrastructure package (the directory packages/snodo-foundation/src/snodo/infrastructure/, next to queue_store.py) provides: record an intent (required non-empty text, bounded in length with a clear error beyond the bound; optional `issue` reference such as `#1042` or a GitHub issue URL; optional `supersedes` naming an existing intent id), get one by id, and list newest first. Ids look like `int_<6-hex>`. Each record is stored under `.snodo/intents/<id>/` as a small JSON file with id, text, created_at (UTC), issue and supersedes.
- A record is written once and there is no edit or delete operation: a correction is a new intent whose `supersedes` names the old one (fix forward). Superseding an id that does not exist is refused with a clear error. Reading an unknown or malformed id is a clear error, not a crash.
- Recording an intent appends one new local-only audit event, `intent_recorded`, carrying the intent id, the issue reference and the superseded id (not the full text). It is declared in `_LOCAL_EVENT_DATA_KEYS` and nowhere in the cloud contract.
- Tests in a new test module named test_intent_store in the tests/infrastructure directory cover record, read, list order, the supersedes check, empty and oversized text, malformed ids, atomic write behaviour you can observe, and a test pinning the `intent_recorded` data keys against `_LOCAL_EVENT_DATA_KEYS` in the style of tests/recon/test_recon.py.
- `make gate` passes, including the audit event contract and vocabulary checks.
