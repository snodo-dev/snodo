## Intent
When an orchestrator proposes a plan, it should be able to say which recorded intent the plan implements, so the link is written into plan.yml from the start.

## Evidence
- `propose_plan` is declared in `TOOL_REGISTRY` in packages/snodo-mcp/src/snodo/mcp/tools.py (inputSchema: intent, plan_name, waves), handled by `PlanToolHandler.handle_propose_plan` in packages/snodo-mcp/src/snodo/mcp/plan_handlers.py, which calls `PlannerMCP.decompose(intent, plan_name, waves)` in packages/snodo-mcp/src/snodo/mcp/planner.py; `decompose` writes the scaffold `{name, intent, waves}` to plan.yml with `_atomic_write_yaml`.
- `Plan.intent_ref` (optional, round-trips through plan.yml) comes from task 2.1; the verifier (task 3.1) rejects a ref to an intent that does not exist, and the intent store (task 1.1) is packages/snodo-foundation/src/snodo/infrastructure/intent_store.py.
- The CLI `snodo plan create` path (snodo/cli/commands/plan_cmd.py `_plan_create`) also calls `decompose`; it does not need a new option in this task.
- Tests: tests/mcp/test_plan_tools.py (`TestProposePlan`), tests/mcp/test_planner.py (`TestDecompose`).

## Outcome
- `propose_plan` accepts an optional `intent_ref`. When given, the id is checked against the store before anything is written: an unknown or malformed id is refused with a clear error and no plan directory is created. When valid, plan.yml carries `intent_ref` and the proposal result shows it. When omitted, behaviour is exactly as before.
- The plan_proposed audit event payload is unchanged.
- Tests cover: omitted ref unchanged, valid ref written and returned, unknown ref refused with no plan directory left behind, and a test asserting the plan_proposed event data has the same keys as before.
- `make gate` passes.
