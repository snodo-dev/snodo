## Intent
Operators and orchestrators should be able to learn how a plan points to the intent it implements. The behaviour is already merged by earlier waves of this plan, so the page can state it as fact.

## Evidence
- Behaviour: plan.yml accepts an optional `intent_ref` naming a recorded intent (an id of the form `int_` followed by six hex characters); propose_plan accepts it and validates it against the intent store; `get_plan` and `list_plans` show it when set; the MCP tools `record_intent` and `get_intent` record an intent and read it back together with the plans that name it, so whether an intent has been acted on is read from those plans. Intents are written once, a correction is a new intent with `supersedes`, there is an optional `issue` link and no status field, and the audit event `intent_recorded` is local only. Plan history events and the cloud wire are unchanged.
