## Intent
Operators and orchestrators should be able to learn how to record an intent, how a plan points to it, and how to read the trace in both directions. The behaviour is already merged by earlier waves of this plan, so the pages can state it as fact.

## Evidence
- Behaviour: `snodo intent record|show|list` (text and `--json`), MCP tools `record_intent`, `get_intent`, `list_intents`, optional `intent_ref` on `propose_plan` (validated against the store), shown by `get_plan`, `list_plans`, `snodo plan status` and `snodo plan list`; intents live under `.snodo/intents/<id>/`, are written once, a correction is a new intent with `supersedes`, an optional `issue` link, no status field, and a local-only audit event `intent_recorded`. Plan history events and the cloud wire are unchanged. The decision record is docs/decisions/060-intent-record.md.
- Pages to update: docs/authoring-a-plan.md (the plan.yml schema section lists name, intent and waves; add the optional `intent_ref` and how to set it), docs/command-reference.md (the `snodo intent` group; earlier tasks may have added a minimal entry to replace with a full one), docs/machine-interface.md if it lists `--json` shapes for the commands touched, and docs/decompose-and-recon.md only if it describes proposing plans.
