## Intent
An orchestrator reading a plan through MCP should see which intent it implements, so the trace from work back to intent is visible without opening files.

## Evidence
- `handle_get_plan` in packages/snodo-mcp/src/snodo/mcp/plan_handlers.py returns `{name, intent, waves, tasks, task_modules, task_runs, run_summary, validation}`; `PlannerMCP.get_plan` and `PlannerMCP.list_plans` in packages/snodo-mcp/src/snodo/mcp/planner.py read plan.yml (`list_plans` returns `{name, intent, wave_count, task_count, status_counts}`). The tool descriptions for `get_plan` / `list_plans` in packages/snodo-mcp/src/snodo/mcp/tools.py list the returned fields.
- `intent_ref` is an optional plan.yml key (tasks 2.1 and 3.2). Tests: tests/mcp/test_plan_tools.py (`TestGetPlan`), tests/mcp/test_planner.py (`TestPlanManagement`).

## Outcome
- `get_plan` includes `intent_ref` in its result only when the plan has one, and `list_plans` includes it per plan only when set. Plans without one return exactly what they return today. The tool descriptions mention the new optional field.
- Tests cover plans with and without the key for both tools, and a test asserting the plan_proposed / plan_run event data keys are unchanged.
- `make gate` passes.
