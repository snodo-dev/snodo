## Intent
The trace should work in both directions: reading an intent should show the plans that implement it. Whether an intent has been acted on is read from those plans; there is no status field on the intent.

## Evidence
- The intent store (the `intent_store` module in packages/snodo-foundation/src/snodo/infrastructure/, task 1.1) knows nothing about plans, and should stay that way: a review of an earlier version of this spec objected to putting plan discovery and task-status summarising inside the store, because that couples it to the plan.yml / status.json layout and duplicates plan-listing behaviour. Put the plan lookup in its own small module beside the intent store (for example intent_trace), which uses the store only to validate the id.
- Reuse what exists for reading plans instead of writing a parallel parser: plans live under `.snodo/plans/<name>/plan.yml` (optional `intent_ref` key, tasks 2.1 and 3.2) with per-task status in each plan's status.json; the `Plan` model in the compiler package loads plan.yml, and the plan listing code (`list_plans` in the planner module of the mcp package) shows how unreadable plans are skipped and how task status counts are derived. Do not edit the planner module in this task; call or mirror its status counting through an existing helper if one is importable, otherwise count the existing status values in the same way.
- The MCP tools `get_intent` / `list_intents` are in the `intent_handlers` module beside plan_handlers.py (task 2.2); `snodo intent show` / `list` are in the `intent_cmd` module beside plan_cmd.py (task 2.3).
- Tests: the intent store, intent tool and intent CLI test modules created by tasks 1.1, 2.2 and 2.3, plus a new test module for the lookup.
- New MCP tools or CLI commands are not added here, so no new docs mention is required; if a docs check does fail, fix it in docs/. Run `ruff check` on the files you touch before finishing: unused imports fail the gate.

## Outcome
- A helper in the new lookup module finds the plans whose `intent_ref` names a given intent and returns, per plan, its name and a derived summary of task status counts using the existing status values (no new values). Unreadable or malformed plans are skipped, not fatal. The intent store module itself is unchanged.
- `get_intent` and `snodo intent show` (text and `--json`) include that plans list; `list_intents` and `snodo intent list` do not, to stay cheap. Where the show payload is documented (docs/machine-interface.md), add the plans key.
- Tests cover an intent with no plans, with one plan, with several, and with a malformed plan directory alongside.
- `make gate` passes, including ruff and the docs checks.
