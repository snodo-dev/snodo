## Intent
The operator at a terminal should be able to record an intent and look at recorded intents with `snodo intent`. This task adds that command group on top of the intent store (the `intent_store` module in packages/snodo-foundation/src/snodo/infrastructure/, from task 1.1). It does not connect plans to intents.

## Evidence
- CLI command groups live in the snodo/cli/commands/ directory (see plan_cmd.py for a Typer group with list / status / create subcommands, `emit_json` and `schema_name` from snodo/cli/json_output.py for `--json` output, and how plan_cmd is registered in the CLI app in snodo/cli/main.py). Mirror that structure, output style and error handling rather than inventing a new one.
- A previous attempt already wrote intent_cmd, its tests and a docs section, and is present in this workspace. Build on it and correct it; do not start over. A review of that attempt found four things to put right:
  1. The command bodies catch a bare `Exception` and show it as a tidy user error. Catch only the store's `IntentError` (print a clear message, exit non-zero) so programming errors surface as real failures.
  2. tests/cli/test_intent_cli.py has no test for `--supersedes`. Add one with a valid id (the new record points at the older one) and one with an unknown id (clean error, non-zero exit).
  3. The `--json` payloads use a single schema name for record, show, list and the error shape. ADR 022 names schemas `snodo.<command>.v<N>`. Give record, show and list each their own schema name in that convention (for example `snodo.intent.record.v1`, `snodo.intent.show.v1`, `snodo.intent.list.v1`, following how plan_cmd names its schemas) and keep the error shape consistent with how other commands emit errors under `--json`.
  4. docs/command-reference.md has the prose section but the list of "Work records" commands near the top of the page was not updated to include `intent`; docs/machine-interface.md has no entry for the intent payloads. Update both, with the smallest entry in machine-interface.md for each of the three shapes.
- The "Work records" panel in `HELP_PANELS` in snodo/cli/main.py must list `intent` exactly once (tests/cli/test_top_level_help.py::test_top_level_commands_are_assigned_to_exactly_one_help_panel must pass unchanged); check whether other places enumerate top-level commands (a completion list, a help snapshot) and keep them consistent.
- The docs-coverage check (scripts/enforce_docs_coverage.py) requires every new command to be mentioned in the docs; docs/command-reference.md is the natural page.
- tests/cli/test_plan_cli.py shows how CLI commands are tested. The store provides record, get and list; recording appends the local `intent_recorded` audit event itself.
