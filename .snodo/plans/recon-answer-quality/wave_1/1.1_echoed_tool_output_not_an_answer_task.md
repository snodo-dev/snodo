INTENT
#775 ("Keep recon answers free of tool output") changed the refused-answer fallback in `_retry_forced_answer` to use `earlier_prose`, the assistant text from tool-calling turns, instead of raw tool results. Recon rec_dec7a0 (2026-10-08 15:29Z) ran on that code. The deepseek agent (ollama-cloud/deepseek-v4-pro:0813) still returned a 138,834-character `result` that is visibly tool output: a directory listing of snodo/cli/commands, the top of packages/snodo-mcp/src/snodo/recon/__init__.py verbatim, and source from snodo/cli/commands/plan_delivery.py. The error was "Output was truncated (finish_reason=tool_calls)" and the trace showed `turns_used: 8`, `ended: "truncated:tool_calls"`.

The server was on current code; its version string tracks the repo. The most likely explanation is that this provider/model puts the tool results it received, or file text it read, into the assistant `content` of its tool-calling turns. That makes `earlier_prose` mostly echoed tool output. Verify this from the recon's saved state before changing anything. If the cause is different, fix that cause instead.

When this is done, a recon agent's `result` contains only text that is substantively the model's own:
- Assistant text that is mostly a copy of tool output the agent received is not counted as prose for the fallback answer.
- If nothing real remains, the agent ends with an empty `result` and the existing clear error ("Model returned tool calls instead of an answer after N turns.").
- Real prose written alongside tool calls is still kept, as #775 intended.

1. Confirm, from rec_dec7a0's stored data or by reproducing with a fake provider, where the dumped text enters `earlier_prose`.
2. Exclude echoed tool output from the fallback answer. For example, drop prose segments that mostly reproduce text returned by the agent's own tool calls, or keep tool output out of the assistant content the loop records. Choose what is robust, and explain it in a comment.
