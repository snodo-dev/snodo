# Bare `snodo` doesn't say where the user stands

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
Running `snodo` with no arguments should answer "where am I, and what do I do next?" in a few lines:
- a header line with the project folder name and the active mode;
- a few check lines (protocol, coder, cloud sync when it's on), each marked ✓ or !;
- one "Next step:" command.

This task builds that view as a renderer. A later task puts the wordmark above it and wires it into bare `snodo`.

## THE CHAIN
- Today bare `snodo` prints a fixed "Start here" list whatever state the project is in (`snodo/cli/main.py`, `_app_callback`).
- `snodo ready` (`snodo/cli/commands/ready_cmd.py`, `ready_command`) already does the real assessment:
  - `assess_readiness` from `snodo.readiness.checker`;
  - `sync_issue_notice` from `snodo/cli/commands/cloud_status.py` for stuck cloud sync.
- `ready` also logs an audit event and runs a subprocess check of installed MCP clients. Both are too heavy for a greeting.
- `resolve_project_root` (`snodo.infrastructure.paths`) returns None outside a snodo project.
- The approved mockup, rendered without colour:
```
0.24.0 · my-app · producer

✓ protocol   .snodo/protocol.yml (team)
✓ coder      opencode-cli
! cloud      1 session has 1,456 unsent events
             they're catching up in the background · snodo cloud status

Next step:
  snodo run "describe the change you want"

All commands: snodo --help
```

## CONSTRAINTS
- New module, for example `home_view.py` in the `snodo.cli` package, exposing a function that returns the view as text. It optionally adds colour when told the stream is a TTY and `NO_COLOR` is unset.
- Reuse `assess_readiness` and `sync_issue_notice`. Don't copy their logic. Skip the MCP subprocess check and any network call. Write no audit event and change no state; it is read-only.
- Pick the next step by state:
  - not in a git repository: suggest `cd` into one;
  - in a repository without snodo: `snodo init`;
  - a blocking readiness finding: `snodo ready` to see the details;
  - otherwise: `snodo run "describe the change you want"`.
- Keep it fast and at most about a dozen lines. Show at most the three most important findings, using the existing severity order.
- Copy reads plain and soft. Avoid "not X but Y" contrast phrasing.
- Don't wire it into `main.py` yet.
- No new status, severity, halt type or audit event.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo. Tests build their own temporary repositories.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the new home-view tests.

## ACCEPTANCE
- Tests in temporary directories show the right next step for each of these:
  - outside git;
  - git without snodo;
  - a ready project;
  - a project with a blocking finding.
- A test shows that a stuck cloud sync appears as a "!" line.
- A test shows that no audit event is written.
- Output without colour contains no escape codes.
- There is a CHANGELOG entry under ## [Unreleased].
