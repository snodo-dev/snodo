# Dispatched opencode-cli runs must launch against the CLI that is installed

## Intent

Restore dispatch. A task dispatched with the `opencode-cli` coder must start and do work on a
machine running opencode 2.x, while keeping the workspace containment that #941 and #945
established. Today the launch is rejected by the CLI before the coder runs, so no new task can
be dispatched at all; issue #976 carries the repro, the error, and the installed CLI's list of
accepted flags.

## Constraints

- Containment is not negotiable. The dispatched run stays confined to its own task workspace,
  cannot move sessions or create worktrees, does not attach to a server started for another
  tree, and the executor's escape detection is left as it is. This task restores launchability;
  it does not relax the boundary.
- The engine must not send the host CLI any argument that CLI version does not accept. 1.x and
  2.x have different argument sets and both are supported; the 1.x path keeps its current
  behaviour.
- Whatever replaces the rejected argument must be something the installed 2.x CLI actually
  documents. If 2.x offers no supported way to name the project directory, record that in the
  adapter and rely on the boundary mechanisms that do exist rather than inventing one.
- A dispatched coder must still be able to edit files inside its own workspace, and must be
  refused outside it. Determine what the current confinement configuration really does and make
  the behaviour explicit rather than assumed.
- A disagreement of this class must surface in the gate, not in a production dispatch: the gate
  needs to be able to fail when the arguments the adapter builds and the arguments the targeted
  CLI version accepts stop matching. Keep it hermetic — recorded output only, no live CLI, no
  network, no model calls.
- The suite that already covers this adapter encodes the previous launch arguments and the
  previous permission shape. The change must leave the whole suite green by bringing those
  expectations in line with the contract being established here — superseding an expectation is
  not removing coverage, and the suite must still fail if the adapter drifts back.
- CHANGELOG.md stays present with its complete release history, carrying one added bullet under
  `## [Unreleased]` naming #976 and no other change: several in-flight branches edit the same
  block, so reflowing or reordering it invites a conflict.
- Keep every file under the project's file-length gate; split rather than grow.

## Acceptance criteria

- A test shows the launch arguments the adapter builds for a 2.x host contain only arguments the
  recorded 2.x CLI help accepts, and that the workspace boundary is still expressed.
- Re-adding an argument the recorded help does not list makes the gate fail. Name the assertion
  that trips in the pull request description.
- The 1.x launch path is still covered, with its own arguments.
- The in-workspace edit behaviour is settled by a test, and the pull request description states
  whether the previous configuration blocked edits everywhere or only outside the workspace.
- `make gate` and `lint-imports` green.
