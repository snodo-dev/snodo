New files this task will create: none.

INTENT
When an end-to-end test that drives the snodo CLI runs long or times out, the failure says which CLI invocation was slow and how long each one took, so the cause can be read from a single gate log.

Symptom and evidence: the same e2e queue journey has failed the release gate three times with a bare pytest-timeout whose traceback ends inside subprocess.communicate in tests/e2e/conftest.py (the _run helper of the snodo_cli fixture). Nothing in the output says which of the roughly fifteen CLI calls in the test was running or how long the earlier ones took, and every attempt to find out costs a full fifteen minute release gate.

What it should do: make the snodo_cli helper in tests/e2e/conftest.py record the arguments and elapsed time of each invocation, and make that record appear in the test output when the test fails, including when it fails by timeout while a call is still running. The record should name the call that was in flight and how long it had been running. Keep the helper's return value and behaviour for passing tests unchanged, and keep the output short, one line per call. Use whichever mechanism fits the suite best.

CONSTRAINTS
Files that may change: tests/e2e/conftest.py and CHANGELOG.md (one entry under [Unreleased] ending with the issue reference Fixes #<n>). Do not change product code or the individual e2e tests. No new state, status, severity or halt type.

ACCEPTANCE
A failing or timed-out e2e test that uses snodo_cli shows a per-call timing summary naming the invocation in flight, and passing e2e tests are unaffected. make gate-task is green.

PROCESS
Open a GitHub issue first and put Fixes #<n> in the commit message. This is a non-interactive run: open the issue directly with gh issue create, without asking for confirmation of title or body, then continue.
