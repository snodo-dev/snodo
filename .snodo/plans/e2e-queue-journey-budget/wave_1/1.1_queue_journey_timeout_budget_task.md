New files this task will create: tests/scripts/test_e2e_timeout_budget.py.

INTENT
The end-to-end queue journey tests get a time budget that matches what they do, so they stop failing the release gate on a 60 second limit meant for ordinary unit tests, and a regular test keeps that budget from quietly disappearing.

Symptom and evidence: the release gate (make release PART=minor, gate-ci, which runs with -m "" and --timeout=60 --timeout-method=signal so the e2e tests are included) failed three times in a row on tests/e2e/test_queue_run.py::test_blocked_queue_can_be_corrected_while_another_queue_finishes. One failure is a plain pytest-timeout at the line that runs the second queue run (resumed = snodo_cli(["queue", "run", "default", "--mock"])), inside subprocess communicate; another is in the teardown of the same test, meaning its body had used almost the whole 60 seconds. Run alone on a quiet machine the same test takes about 19 seconds, passes, and everything else in the suite passes (6932 tests). The test drives about fifteen separate snodo CLI processes, each a cold Python start, on a gate host running about twenty test workers at once, so it takes roughly three times as long there. A change earlier in this wave made the per-test .snodo guard cheaper and the total gate time did not move, so that was not the dominant cost. Separately, a ticket that changes only e2e files cannot pass the per-task gate, because e2e tests are deselected by default and only the release gate runs them (see ADR 031); that is why this ticket also adds a regular test.

What it should do: give the tests in tests/e2e/test_queue_run.py a timeout that fits a multi-process journey, using the timeout marker the suite already registers so it overrides the gate's command-line limit for these tests only; pick a value with clear headroom over the roughly 60 seconds seen under load and say in a short comment why. Add a regular test, not marked e2e, in the new file that reads the e2e journey tests (by parsing the file or collecting it) and fails if the queue journey tests lose a timeout above the gate's 60 seconds, so gate-task actually runs something that pins this change. Do not weaken any assertion and do not change the limit for the rest of the suite.

CONSTRAINTS
Files that may change: tests/e2e/test_queue_run.py, the new tests/scripts/test_e2e_timeout_budget.py, and CHANGELOG.md (one entry under [Unreleased] ending with the issue reference Fixes #<n>). Do not change scripts/gate_remote.sh, the selector, pyproject.toml, validators or product code. No new state, status, severity or halt type.

ACCEPTANCE
The journey tests run under their own limit while other tests still run under the gate's 60 seconds, the new regular test fails if that limit is removed or lowered to 60 or less, and make gate-task is green with the new test actually executed.
