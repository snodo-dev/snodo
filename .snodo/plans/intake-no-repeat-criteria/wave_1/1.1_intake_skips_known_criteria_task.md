INTENT
Running snodo intake again on a project whose protocol already holds a criterion does not offer it, add it a second time, or claim to have written it.

Evidence: an operator reported that intake with accept-all re-adds criteria it already wrote. In the code, snodo/cli/commands/intake_cmd.py calls propose_criteria (packages/snodo-engine/src/snodo/survey/criteria.py) which reads only the decision records and never the protocol, so every run lists every criterion as a new proposal. The function append_criteria in the same module skips a criterion only when the exact text is already in the single validator being written to, so a criterion already held by a different validator (for example after an earlier run with the validator option, or after the default validator changed) is added again. The confirmation line in intake_cmd.py reports the number of accepted proposals as the number written, even when the append added none.

What it should do: proposals whose text is already a criterion of any validator in the protocol are not offered, and the output says how many were skipped as already in the protocol, so a repeat run reads as nothing new rather than as a fresh batch. The write step reports how many criteria were actually added, and when that is zero it says nothing was added and leaves the protocol file untouched. Matching stays exact on the criterion text; do not add fuzzy matching. The JSON output keeps every key it has; if the skipped criteria are worth reporting there, add one new key and extend the published schema for the intake output consistently with how the other keys are described, and keep the existing tests for the shape passing. The generate-adr path is separate and is not part of this ticket.

CONSTRAINTS
Files that may change: snodo/cli/commands/intake_cmd.py, packages/snodo-engine/src/snodo/survey/criteria.py, tests/cli/test_intake_cmd.py, tests/survey/test_criteria.py, the intake output schema or its docs only if the new JSON key needs it, docs/command-reference.md only if it describes the written count, and CHANGELOG.md (one entry under [Unreleased] ending with the issue reference Fixes #<n>). No new state, status, severity or halt type.

ACCEPTANCE
Tests show: a second intake run over the same records offers nothing new and writes nothing; a criterion held by a different validator than the one selected is not added again; the written count equals the criteria actually added; the protocol file is not rewritten when nothing is added. `make gate-task` is green.
