Before starting, open a GitHub issue on snodo-dev/snodo titled "Show the next action wherever a halt is reported (CLI and MCP)". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
Two pieces now exist:
- a shared helper that maps a halt record to the recommended next actions, with concrete command lines, covering every outcome in the closed vocabulary;
- `snodo task show --diff`, which shows a blocked task's changes next to its grouped validator verdicts.

Users still have to know to go looking for both.

When this is done, the recommended next actions from the shared helper appear in three places:
- the CLI output printed when a task halts, after the structured halt payload;
- `snodo task show` for a halted task, which also suggests `--diff`;
- the MCP job and task status responses for a halted task, in their existing instruction or summary text with no new fields.

`docs/outcomes.md` and the runbook's "task blocked" section describe the review loop: look at the diff and verdicts, then take the next action.

THE CHAIN
1. The CLI halt report and `task show` include the helper's next actions.
2. MCP status responses for halted tasks include them in existing text fields.
3. The docs describe the loop, and guide markers stay intact.
4. Tests: the CLI halt output includes the next action for a blocker and an escalate case; the MCP status for a halted task includes it; non-halted output is unchanged.

CONSTRAINTS
- Snodo's state machine is closed: add no outcome, status, severity or field.
- Use the helper; don't duplicate its wording.

ACCEPTANCE
- The tests in link 4 exist and pass.
- The docs are updated.
- The CHANGELOG entry is present.
- `make gate` passes.
