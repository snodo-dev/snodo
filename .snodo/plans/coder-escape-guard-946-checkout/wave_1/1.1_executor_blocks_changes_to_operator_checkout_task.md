## Intent
A host CLI coder that edits the operator's checkout through its shell should be stopped at acceptance, whether or not any branch tip moved. The executor takes a content baseline of the operator's checkout before dispatch and compares it when the run ends, reporting any change through the same existing escape error. If the baseline cannot be established, the run does not proceed on a guess. An implementation of the guard already exists on this task's branch and reads correctly; what is still wrong is one failing test, caused by how the test builds its scenario, and a few missing tests. Fix the test setup, add the missing tests, and touch the executor or the snapshot helper only if a test shows a real defect.

## Evidence
- A checkout content helper already exists in packages/snodo-engine/src/snodo/engine/ (the checkout snapshot module). It returns the changed paths between a baseline and now, or an explicit "could not establish or compare" result. Its `.snodo/` handling keeps only operator-authored files (protocol.yml, plan.yml, wave spec files) and ignores engine runtime state.
- The executor's escape comparison in packages/snodo-engine/src/snodo/engine/nodes/executor.py runs on every way a coder run can end after the coder started, guarded by an `escape_checked` flag; the checkout comparison sits next to it at the same exits. On `SnodoMutationError` and `AdapterError` the original exception, halt classification and audit events are kept (ADR 027, ADR 015) and a found change is only logged; on every other exit a found change is reported through the same `ExecutionError` as the branch-tip escape.
- The guard applies by the declared kind of coder: host CLI coders (the subprocess adapter family), when the dispatched workspace is a different directory from the primary checkout, and the coder is not configured `sandboxed`. In-place work and in-process coders are untouched.
- Git access goes through GitPython (ADR 010); no subprocess.
- Diagnosis of the failing test, `test_host_coder_checkout_content_escape[untracked-plan-delete]` in tests/engine/test_default_executor.py: it commits `.snodo/plans/demo/plan.yml` and then runs `git rm --cached` on it. That leaves git reporting the same path twice (a staged deletion AND an untracked file), which is not the real-world situation and is not what the helper is built for, so the deletion goes unnoticed and the test never raises. The real situation is a plan record that was never committed: git reports it once, as untracked. Two earlier attempts changed only the order of operations and kept the `git rm --cached` trick; do not keep it.

## Outcome
- The `untracked-plan-delete` scenario builds a genuinely untracked plan record: commit the repository first WITHOUT the plan record, then create `.snodo/plans/demo/plan.yml` as an ordinary untracked file (no `git rm --cached`, nothing staged), then let the baseline be taken, and have the fake coder delete the file during its run. It must then stop the run with the changed-paths error naming that file.
- Add one more case to the same parametrized test or the helper's own tests: a path that git reports twice (staged deletion plus an untracked file with the same name) is fingerprinted from what is actually on disk, so a later deletion of that file is still detected. If this shows a defect in the helper, fix the helper.
- These exist as real-Git tests (real temporary repositories; the fake coder performs the edit during `implement`, after the baseline): shell-style edit of a clean file stops the run; edit of an already-dirty file stops the run; deletion of a genuinely untracked plan record stops the run; an unchanged checkout passes; engine runtime state written during the run is not reported; in-place work (workspace is the primary checkout) is not blocked; an in-process coder is not checked; an unavailable baseline halts before dispatch with a message saying the checkout could not be examined; an unavailable comparison after the run reports a message saying it could not be compared (distinct from the changed-paths message); a changed checkout on the `SnodoMutationError` exit and on the `AdapterError` exit leaves the original exception and halt classification untouched and logs the finding (use a real changed checkout, not a stub of the escape helper). Some of these may already exist; add only what is missing.
- Existing executor tests keep passing. `make gate` passes. If an unrelated test in the gate times out or leaks a process, say so in the commit message rather than editing unrelated tests.
- No new states, statuses, severities or halt types. No new configuration setting.
