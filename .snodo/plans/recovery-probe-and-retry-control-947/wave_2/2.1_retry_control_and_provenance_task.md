# 2.1 — retries inherit silently; the operator has no first-class way to choose

## Why this task exists

Continuing a retry from the previous attempt's worktree is deliberate and valuable, and it
must stay the default. What is missing is control and honesty. The person driving the CLI
cannot ask for a clean start, even though the MCP retry tool already offers that choice,
and neither the operator nor the coder is told which revision an attempt began from or that
the revision carries commits from an attempt that was halted.

The MCP side names the choice: `packages/snodo-mcp/src/snodo/mcp/server.py` reads a
fresh-start argument and records either a fresh branch or a continuation, and
`packages/snodo-mcp/src/snodo/mcp/tools.py` documents it to callers. The CLI side, in
`snodo/cli/commands/run_cmd.py`, has no equivalent option: a retry always continues.

## Outcome

- `snodo run --retry` and the plan retry path offer the same choice the MCP retry offers:
  continue from the previous attempt's work (default, unchanged behaviour), or start fresh
  from the task's base revision. The option carries the same name and the same meaning on
  both surfaces. Choosing fresh does not destroy the earlier attempt's branch or its
  records, and the run output says what was left alone.
- The status an attempt records names the revision it started from and whether that
  revision already carried work from an earlier attempt, so a halt can be read as
  "this attempt continued from the previous one's commits" without opening a worktree by
  hand to find out. The task detail the operator reads after a halt shows it.
- A coder whose attempt starts on a branch that already carries work is told, in the task
  text it receives, that it is continuing and from what. Today only the explicit retry
  command composes that notice, so a re-run wave that silently reuses the worktree leaves
  the coder to infer the situation by reading files.
- Retention is stated in the documentation a user would read: where preserved worktrees
  live, that a machine accumulates them across runs, and the one command that discards
  them.

## Acceptance

- Retrying from the CLI with the clean-start option produces a worktree whose task branch
  starts at the base revision, with the previous attempt's commits absent, and the previous
  attempt's records still readable.
- Without the option, behaviour is unchanged: the worktree and branch are reused.
- An attempt's recorded status shows its starting revision and whether inherited work was
  present, and that shows up in the task detail read after a halt.
- Tests cover the continue path and the fresh path, and assert that the fresh path does not
  delete the earlier attempt's branch. Extend the retry tests in
  `tests/cli/test_retry_spec_safety.py` and the surface-parity tests in
  `tests/cli/test_surface_parity.py` so the CLI and MCP options are checked to agree.
- The CLI test suite and the engine test suite pass, and the linter is clean.

## Constraints

- Do not make discarding preserved work the default and do not remove the reuse behaviour:
  a halted attempt's work is what makes the next attempt able to finish the job.
- Commits made before post-execute validation are part of the current design — validation
  judges what is actually on the branch. Do not change that here.
- Any new option must reach both surfaces with the same name and meaning; no surface gains
  a capability the other lacks.
- Reuse the existing worktree lifecycle commands rather than inventing a parallel one.

## What the last attempt got wrong — read this before editing

Its implementation is on this branch already and is close to what is wanted: the shared
choice handling, the recorded origin, the coder notice, the retention documentation, and new
tests for the continue and fresh paths. This attempt finishes and cleans that work; it does
not begin again. Three things must change.

One. No validation notes. The previous attempt wrote a file at the repository root
describing why it believed it could not run the suite. That file is wrong — the suite ran and
5700 tests passed — and a root-level note like it has now twice been merged into the product
by accident. Do not create any file whose purpose is to record validation status, blockers,
or what still needs doing. Either the gate passes and you submit, or it does not and you fix
it. Nothing else.

Two. Nothing unrelated may move. In `snodo/cli/commands/plan_cmd.py` the previous attempt also
rewrote two lines of the output that prints a plan's wave and task counts after creation. That
has nothing to do with this task; put those two lines back exactly as they were. Check your full
diff against the base for anything of that kind and remove it.

Three. The option travels the same route as its siblings. The fresh-start flag reaches the run
through the same arguments object that carries the retain-worktree and no-isolation flags, and
that is the whole of the wiring this task needs. Those two existing options are not forwarded to
child jobs either, so do not invent a new forwarding mechanism here to satisfy a concern about
parallel dispatch — being consistent with the existing options is the correct outcome, not a gap.

## One failure you will meet again

`tests/cli/test_spinner.py::test_wave_output_completes_under_a_real_pty` fails when several
full-suite runs share the machine: it drives the CLI under a pseudo-terminal and asserts the
child makes progress, and under load it does not make it inside the window. It passes on the
base commit and passes when run on its own. If it fails, run it alone, confirm it passes, and
leave the test and the spinner untouched — do not lengthen a timeout or loosen an assertion to
buy a pass.
