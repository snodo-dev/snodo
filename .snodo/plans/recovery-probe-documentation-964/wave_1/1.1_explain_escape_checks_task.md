# 1.1 — explain the escape checks the recovery probe now shares its path with

## Why this task exists

The automated review of the delivery that moved the work-recovery probe into its own module
recorded that the change was under-explained. Three findings, all about visibility rather than
behaviour:

- The probe moved out of `packages/snodo-engine/src/snodo/engine/nodes/executor.py` into
  `packages/snodo-engine/src/snodo/engine/nodes/work_recovery.py`, and the architecture
  description still presents the probe as something the executor does itself.
- The workspace-escape check is now consulted in places it was not before: alongside the probe in
  the path that handles a coder that wrote nothing, and in both bounded-run handlers, where a
  halted coder's work is recovered. One of those three places says why the check belongs there;
  the other two are bare.
- A file called `WORK_RECOVERY_VALIDATION.md` sits at the repository root. An attempt that could
  not run the test suite wrote it, and it asserts that the work it describes is unverified and
  must not be merged. That work was since verified by the engine's merge gate and delivered, so
  the file is now a false warning that a reader will take at face value.

## Outcome

- Each place where the escape check is consulted on a recovery path carries one or two lines
  naming why it belongs there: work recovered from the task branch must not stand as a pass if
  this run's coder committed outside the dispatched workspace. Match the voice and length of the
  one that already explains this. Do not restate what the surrounding code does.
- The architecture description of the probe says where it lives and why the module keeps the
  executor's logger name, and mentions that recovery is refused when the run's work landed
  outside the dispatched workspace. Edit the existing passage in place, in the document's
  existing shape; do not add a new document and do not describe behaviour that does not exist.
- `WORK_RECOVERY_VALIDATION.md` is gone. Confirm nothing references it before deleting it.

## Acceptance

- The change is comments, one document passage and one deletion: no Python behaviour differs, so
  the existing tests that pin the probe's logger name and its message wording pass unchanged.
- The published documentation builds strictly, with no new unrecognised link.
- The lint gate is clean.

## Constraints

- The order of the escape check and the recovery result in each handler stays exactly as it is —
  this task explains that order, it does not change it.
- The exception chaining that the linter requires on those raises stays as it is.
- Do not reword the messages the failure-reason tests quote.
