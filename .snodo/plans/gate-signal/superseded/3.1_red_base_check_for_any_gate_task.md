# A gate failure that already fails on the base commit is recognised as predating the task

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
When the quality validator's test command fails, it checks whether the same failure already happens on the task's base commit. If it does, the verdict says the failure predates the task, and it does not go to task recovery. Today that check only runs when the command contains "pytest" and the output lists FAILED node ids. Projects whose gate is a make target or a script never get it, and that includes this repo (`make gate`). When main was red, for example over a version-cutoff check or a file-length violation, every task in the wave was blamed for it and sent through recovery to fix something it did not break.

The check should also cover other commands. When the cheap pytest-id rerun does not apply:
1. run the same command once on the base commit;
2. remember the result for that base commit and command, so a wave of tasks sharing a base pays for at most one extra run;
3. if every failure line of the task's run also appears in the base run's failure lines, treat the failure as predating the task, through the existing route;
4. if the base passes, or the task run has failure lines of its own, the task owns the failure as today. When the base was red too, the justification says so and names the base's failure lines.

## THE CHAIN

  - the caller (around line 383) applies the existing "predates the task" route (`res.error = True` plus the justification wording) when the base fails.
- Failure-line extraction for the output tail was added to this file by the earlier task in this plan ("A failed gate's output keeps the lines that say what failed"). Reuse it to compare the two runs; do not write a second extractor. This task may build on task 1.1's branch.
- `packages/snodo-engine/src/snodo/validators/verdict_cache.py` may fit for remembering the base result. Use it if it does; otherwise use a small cache in the same file, keyed by base commit SHA and command.
- Existing tests in `tests/validators/test_quality.py`, `test_base_failure_is_named_and_cannot_route_to_recovery`, `test_baseline_pass_does_not_clear_possible_flake` and `test_baseline_rerun_uses_only_failed_pytest_nodes`, cover the pytest path. They must keep passing unchanged.

## CONSTRAINTS
- The pytest-id fast path stays first and unchanged. The full-command base run is the fallback only.
- The base run uses the same timeout as the primary run. A base run that times out or cannot start leaves today's behaviour (the task owns the failure).
- A base pass never clears a failure.
- Reuse the existing route and wording family. No new status, severity, halt type or audit event.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run --extra dev ruff check` on touched files, and run `tests/validators/test_quality.py`.

## ACCEPTANCE
- Tests show, with a non-pytest command:
  - base fails with the same failure lines: the failure predates the task and does not go to recovery;
  - base fails with different lines: the task owns it, and the justification mentions the base was red;
  - base passes: the task owns it;
  - a second task on the same base commit reuses the remembered base result without running it again;
  - the existing pytest-path tests are unchanged and pass.
