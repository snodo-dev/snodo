# A gate failure that already fails on the base commit is recognised as predating the task

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
When a task's test gate fails, the quality validator can check whether the same failure already happens on the task's base commit. If it does, the verdict says the failure predates the task, and the task is not sent to recovery to fix something it did not break. Today this check only works when the test command is pytest and its output lists failing node ids. Projects whose gate is a make target or a script never get it, and that includes this repository (`make gate`). When main was red, for example over a version-cutoff check or a file-length violation, every task that ran was blamed and sent through recovery.

The check should cover any test command. A wave of tasks sharing a base commit should pay for at most one extra base run per command. A failure counts as predating the task only when the base run shows the same failures. When the base is red with different failures, the task still owns its failure, and the verdict mentions that the base was also red. A base pass never clears a failure.

## THE CHAIN
- The quality validator lives in `packages/snodo-engine/src/snodo/validators/quality.py`. It already has the pytest-only base comparison and the existing "predates the task" outcome, so reuse that outcome and its wording.
- Earlier work in this plan taught the same file to pick out the failure lines from a gate's output. That is a natural basis for comparing two runs.
- `packages/snodo-engine/src/snodo/validators/verdict_cache.py` may help with remembering a base result.
- The existing base-comparison tests in `tests/validators/test_quality.py` describe the current pytest behaviour, which must stay.

## CONSTRAINTS
- The pytest behaviour stays as it is.
- A base run that times out or cannot start changes nothing: the task owns the failure, as today.
- No new status, severity, halt type or audit event.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run --extra dev ruff check` on touched files, and run `tests/validators/test_quality.py`.

## ACCEPTANCE
- Tests show, for a non-pytest test command:
  - when the base fails the same way, the failure is reported as predating the task and is not routed to recovery;
  - when the base fails differently, the task owns it and the verdict notes the red base;
  - when the base passes, the task owns it;
  - a second task on the same base commit and command does not run the base again.
- The existing pytest-path tests pass unchanged.
