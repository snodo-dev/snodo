# Installed validator plugins are silently missing from snodo ready

Issue #794 already exists for this. Don't open a new issue. Put "Fixes #794" in the commit message, and add a CHANGELOG entry under ## [Unreleased].

## INTENT
A user who installs a third-party validator plugin should see it listed by `snodo ready`, either as installed or as failed with a reason, whatever order snodo's own modules get imported in. The fix must not break anything that already imports from the validators package.

## THE CHAIN
- Real install: `entry_points(group='snodo.validators')` returns `hello_acceptance`, but `snodo ready --json` reports `'snodo.validators': {}`.
- Root cause: importing `snodo.validators.registry` runs the `snodo.validators` package initializer first. That eagerly imports the built-in validators, which re-enter the partly initialised registry before `_default_registry` exists. `ready_cmd` imports the registry module directly (`from snodo.validators.registry import _default_registry`), so the registry-first path is the one that matters in production.
- Earlier attempts:
  - **Attempt 1:** the package initializer was made side-effect free. The gate then failed with 39 failures and 7 ImportErrors, because callers rely on `snodo.validators`' import surface.
  - **Attempt 2:** `snodo.validators.__init__` was reordered to initialise the registry first, then load built-ins. 130 targeted tests passed locally. The full gate: **1 failed, 5300 passed**. The only failure is `tests/validators/test_validator_entry_points.py::test_plugin_is_discovered_when_registry_is_imported_first`, which is exactly the production path.
  - So either the fix doesn't hold when the registry module is imported first, or the test passes alone but fails depending on order or process state when the whole suite runs in parallel. Find out which from evidence. The gate runs pytest with xdist across many workers and `--timeout=60`; see scripts/gate_remote.sh for the exact arguments.

## CONSTRAINTS
- Keep the public import surface of `snodo.validators` working.
- Plugins must be discovered when either `snodo.validators` or `snodo.validators.registry` is imported first, in a fresh interpreter.
- The regression tests must be order-independent: do the fresh-import check in a subprocess or an isolated `sys.modules`, and don't rely on earlier tests' import state.
- No new status values. Plugin status stays `installed` / `failed` (closed state machine).
- **Do not run the `snodo` CLI or `python -m snodo` in the worktree, in any form.** Any snodo run there writes `.snodo/audit.log`, which blocks the task. Use `tmp_path` projects in tests. Confirm `git status --porcelain .snodo` is empty at the end.
- Don't run `make gate`. Do run tests/validators, plus the ready-command tests, using pytest with xdist (`-n 8`) and also with `-p no:randomly` if that plugin is installed, so that order effects show up before you hand back.

## ACCEPTANCE
- `test_plugin_is_discovered_when_registry_is_imported_first` and the other entry-point tests pass both alone and in a parallel run of tests/validators plus the ready tests.
- Both import orders are covered: registry-first and package-first.
- A broken entry point is reported as `failed`, with an error.
- `git status --porcelain .snodo` is empty, and there is a CHANGELOG entry under ## [Unreleased].
