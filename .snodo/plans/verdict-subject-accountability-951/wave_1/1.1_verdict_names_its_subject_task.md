Fixes #951

INTENT
A validator verdict that is about something other than the task under judgement can no longer be counted as a favourable judgement by the quorum. Every verdict a judge delivers must say which task it judged, and a verdict that does not name the task it was given is treated as an unusable verdict rather than a pass.

THE CHAIN
- The pre-execute quorum of judges is the only gate between a task specification and a coder dispatch, so a favourable verdict that has nothing to do with the task lets junk through.
- Each judge is given the task specification in its prompt and answers by calling a single submit-your-verdict step. In the incident behind this ticket, an `adr` judge answered "All 40 ... criteria evaluated successfully against the architecture proposal framework principles and decision records. No blockers or violations found." while its justification and its cited criterion were about a decision record for a different project's cloud interface version. It had the task in front of it and still returned a pass about something else; the quorum passed and the dispatch went ahead.
- Nothing a verdict carries identifies the subject it was about, so neither the run nor a later investigation could see that the answer did not apply. The protocol already fails closed when a judge cannot produce a usable verdict (a validator error is not a pass and halts the run), and a judge that lacked tool access can already report that it was limited. What is missing is the same protection for a judge that answered confidently about the wrong subject.

CONSTRAINTS
- The judge must be told the identifier of the task it is judging and must return that identifier with its verdict; the engine accepts a verdict only when the identifier it names is the task actually under judgement. Keep the check exact and deterministic — do not try to score the quality or relevance of prose.
- A verdict that omits the identifier, or names any other one, must land exactly where an unusable verdict lands today: recorded as such in the run payload and the audit trail, with the judge that produced it and the reason visible to the operator, and never silently downgraded to a warn that still counts toward consensus.
- A judge must not be penalised twice for the same shortfall, and a rejected verdict must not consume the retry budget of an unrelated stage.
- Applies to every judge that answers through the submit-your-verdict step, in both evaluation phases. Do not change what any criterion means, which validators exist, their phases, their tool grants, or the quorum policy itself.
- Behaviour-preserving for an honest verdict: a judge that names the task it was given must produce exactly the outcome it produces today.
- Follow the repo's existing conventions for validator behaviour, and record the change to what a verdict must contain where such changes are recorded.
- Do not change how a cached verdict's key is computed or what the cache stores; a later task covers the cache's own provenance. Do not touch the load-sensitive process-group assertion in the quality-validator tests — it is flaky under parallel load and unrelated here.

- Several existing test doubles hand back a verdict without naming anything. They must be updated to declare the task they judge, the way a real judge does; the engine's check must never be relaxed to accommodate a double.
- A decision record added by this task must appear in the decisions index, or the golden index test stays red.
- Meeting a file-length limit must not cost the reader their orientation: keep the explanatory comments and docstrings this change has no reason to alter. If a file is genuinely too long, give cohesive parts of it their own home, the way this codebase already splits large packages. A delivery whose tests are green but whose reviewed file is now harder to read has not met the intent of this plan.

- Verify with the narrowest test target that actually covers this change - a single file or module, not a whole directory of tests. Test output is handed back to the coder without any size bound today, and a directory-wide run of a failing suite has been seen to carry tens of megabytes into the next model call and abort the task as an operational fault.

- Two test files still hand back verdicts that name nothing: `tests/validators/test_verdict_cache.py` and `tests/validators/test_validator_progress_callbacks.py`. Their doubles must declare the task they judge like the others do; four of the five remaining gate failures are reuse assertions in the cache tests and they fail because the verdict they reuse is now rejected, not because reuse is broken.
- The file-length ratchet counts lines of code only - blank lines, comments and docstrings are excluded from the count on purpose, because this codebase explains itself in prose. Restoring explanation cannot breach it. Put back the commentary and docstrings this task removed from the validator module and the mock coder; a shorter file that no longer tells the reader why it behaves this way is a regression, not a fix.

ACCEPTANCE
- A verdict that does not name the task under judgement cannot contribute a pass: the run records an unusable verdict and halts fail-closed instead of dispatching.
- A verdict naming a different task's identifier — for example one gathered for another plan's proposal — is rejected the same way.
- A normal verdict against the task it was given still passes the quorum exactly as before.
- Tests show both the rejection path and the unchanged happy path.
