Title: Failed tunnel deletion must not restart a stale token or claim unsupported auth

INTENT
After a managed tunnel DELETE fails with HTTP500, the next serve must guide the operator through completing cleanup rather than silently reusing the saved token and claiming success. In snodo/cli/commands/serve_cmd.py, _handle_tunnel_delete preserves the local config on error, _run_tunnel provisions only when tunnel_token is absent, and requested auth overrides the saved auth without a cloud update. The observed Cloud error is service-token405 and missing DNS after partial deletion. Cloud is fixing retry-safe cleanup separately; it is not deployed by this task. Authoritative docs/specs/serve-tunnel.md and docs/decisions/015-mcp-validation-four-outcome-contract.md govern existing behavior. Cloud's accepted OAuth-only policy is documented in docs for the separately connected Cloud repository (ADR-006-K and ADR-0027-B); do not implement new service-token support.
Existing completed plan tunnel-oauth-only was pushed to branch plan/tunnel-oauth-only/integration for issue #901, not merged into current main. Preserve its direction and avoid claiming that delivered means merged; reuse any already-present behavior, and keep this task focused on recovery.

THE CHAIN
1. snodo/cli/commands/serve_cmd.py: a failed delete retains the recovery target and credentials but prevents a later startup from silently treating that partially deleted tunnel as healthy. The operator gets an actionable retry-by-hostname instruction using existing commands. Retrying delete is permitted; successful200 or no-record404 clears only the matching local record. An explicit different target never damages the unrelated recorded tunnel.
2. snodo/cli/commands/serve_tunnel_config.py: any persisted local recovery information survives save/load without exposing secrets or silently disappearing. Existing healthy configurations remain compatible. Keep local tunnel recovery metadata distinct from engine task/job/plan status vocabularies.
3. snodo/cli/commands/serve_cmd.py: requested authentication never masquerades as a cloud configuration change on reuse. Explicit unsupported service-token requests fail before provisioning or starting a tunnel, with a short OAuth connection explanation. Legacy records must not disable OAuth. Reuse existing OAuth-only safeguards if the starting branch already includes them; do not expand the separate issue #901 work into an unrelated refactor.
4. Create `tests/cli/test_tunnel_delete_recovery.py`. Tests exercise failed delete followed by restart, retry and successful delete; preserve unrelated target state and verify no false active/provision claim. Update narrowly necessary existing auth tests in tests/cli/test_serve_auth.py.
5. docs/specs/serve-tunnel.md: document failed-delete retry and the Cloud/CLI boundary, including no blind local-record deletion and OAuth-only connection semantics.

CONSTRAINTS
Only snodo/cli/commands/serve_cmd.py, snodo/cli/commands/serve_tunnel_config.py, tests/cli/test_tunnel_delete_recovery.py, tests/cli/test_serve_auth.py and docs/specs/serve-tunnel.md may change. Do not touch the runtime .snodo directory, governance/protocol files, unrelated pushed branches, deployments, user home or real tunnels. New tests isolate all state in temporary directories and mock network/processes. No new task/plan/job/recon statuses, severities or halt types. Do not treat any HTTP500/405 error text as proof resources are gone. No new reset/force flags, automatic live delete, or widened credentials. Preserve delete-by-hostname and port ownership guarantees. Keep changes within file-size/quality limits; no unsolicited changes to issue #901.

ACCEPTANCE
A simulated partial-delete500 then serve neither provisions nor starts cloudflared nor prints active, and points to deliberate cleanup retry. The same target can be retried, successful200/404 permits fresh provisioning, explicit other-target failure leaves the recorded healthy tunnel usable, and recovery metadata round-trips. Unsupported service-token requests produce no network/process effects, and legacy records cannot turn OAuth off. Existing auth/delete/serve tests and required protocol quality gates pass; no secrets enter captured diagnostics.
