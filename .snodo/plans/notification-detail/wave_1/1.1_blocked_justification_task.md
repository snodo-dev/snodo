# 1.1_blocked_justification

## INTENT
When a task is blocked, or waiting for a human, the Slack/notification message says why: it carries the validator justification, so the reader does not have to open the logs to learn what was wrong.

## THE CHAIN
1. Open a GitHub issue first ("Notifications: include validator justification when blocked") and put "Fixes #<n>" in the commit message.
2. Symptom (seen in Slack): messages read "Blocked — Inspect: snodo logs <job>" and "Waiting for a human — Inspect: snodo logs <job>" with no reason.
3. Evidence: in `packages/snodo-mcp/src/snodo/jobs/notifications.py`, `monitor()` builds the reason in two places, the halt-event branch and the job-finished branch, each calling `format_halt_summary({"reason": ...})` with only the halt reason. `format_halt_summary` in `packages/snodo-mcp/src/snodo/jobs/halt_summary.py` already renders `validator_id (severity): justification` lines from a `validator_results` list, but that list is never passed in, so the justification is dropped. The halt payload that carries `validator_results` is available on the task state (`halt`) and on the halt audit event.
4. Make both branches hand the full halt payload (reason plus validator results) to the existing formatter, so blocked and waiting-for-a-human messages show the most severe validator findings with their justification. Keep the existing length bounds and markup neutralising. When no payload or no results exist, the message reads exactly as it does today.
5. Add tests in the existing `tests/jobs/test_notifications.py`: a blocked task whose halt carries a blocker validator with a justification produces a message containing that validator id and justification; a halt without validator results is unchanged; a very long justification stays bounded.

## CONSTRAINTS
- Reuse the existing situation names, event types and formatter. No new state, status, severity, halt type, event name or notification field.
- Keep the change inside the notification code path; delivery behaviour (when a message is sent, deduplication) does not change.
- Add one line under `[Unreleased]` in `CHANGELOG.md`.

## ACCEPTANCE
- A blocked-task notification contains the blocking validator's id, severity and justification text, truncated to the existing bound.
- A notification with no validator results is byte-identical to today's.
- The new and existing notification tests pass under `python -m pytest tests/jobs/test_notifications.py`.
