# 1.2_notification_docs

## INTENT
The documentation for notifications describes what a blocked or waiting-for-a-human message contains, so an operator knows to expect the reason and the command to act.

## THE CHAIN
1. Open a GitHub issue first ("Docs: notification message contents for blocked and waiting-for-a-human") and put "Fixes #<n>" in the commit message.
2. `docs/running-unattended.md` and `docs/configuration.md` both mention the "Waiting for a human" situation. Read how each describes the notification text.
3. Update that description, in the voice and place the docs already use, to say: a Blocked message lists the most severe validator findings, each as the validator id, its severity and its justification, shortened to a fixed length; a Waiting for a human message shows the same findings plus the command to authorize the task (`snodo authorize <task id>`); a message with no validator findings keeps the plain form.
4. Run `make docs` yourself to confirm the docs still build in strict mode and the anchor check passes. This is a check for you to run; the reviewer does not re-run it.

## CONSTRAINTS
- Documentation files only. Do not touch code or tests.
- Soft, natural wording; no new terminology and no new states, statuses, severities, halt types or event names.
- Add one line under `[Unreleased]` in `CHANGELOG.md`.

## ACCEPTANCE
- Both docs describe the justification content and the authorize command for the waiting-for-a-human message.
- The change is verifiable from the diff of the two docs files and `CHANGELOG.md`; no git history lookups are needed.
