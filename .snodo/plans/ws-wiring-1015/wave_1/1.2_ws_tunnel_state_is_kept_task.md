# 1.2 — a WebSocket tunnel's state is saved, loaded and validated without a tunnel token

GitHub issue #1015 already exists for this work. Do not open another; put "Fixes #1015" in the commit message. Do not edit the CHANGELOG (a later task in this plan owns the entry).

## INTENT

`snodo serve --tunnel` keeps its provisioned tunnel in `.snodo/tunnel.json`, written through the helpers in `snodo/cli/commands/serve_tunnel_config.py`. Those helpers write through an allowlist of known fields and the serve command treats a saved tunnel token as the sign that "a tunnel already exists, skip provisioning". A WebSocket tunnel has no token: the cloud returns a hostname and the machine connects out over the relay. Today a ws tunnel's state would be silently dropped on save (its transport and machine fields are not on the allowlist) and the tunnel would be re-provisioned on every run.

The tunnel-option validation sits in the same module (the helper that normalises the repeatable `--auth` values to `oauth` / `service-token`, defaulting to oauth, and returns exit code 2 from the command when invalid). A new tunnel-transport option needs the same kind of validation next to it.

## Outcome

- Tunnel state can carry a transport (`cloudflare`, the default when absent, or `ws`) and a machine identifier, and these survive a save/load round trip. A state file written before this change (no transport) still loads and means `cloudflare`, with all its existing fields and behaviour.
- A saved ws tunnel counts as an existing tunnel without a token: the helper the serve command can ask ("is there a usable saved tunnel?") answers yes for a ws state that has a hostname, and still requires the token for a Cloudflare state.
- A validator for the tunnel transport value, in the style of the auth validator: accepts `cloudflare` and `ws`, defaults to `cloudflare` when not given, and rejects anything else with a message naming the allowed values. A second rule rejects the combination of `ws` with `service-token` auth with a message saying service-token is not supported over ws yet; ws with the default or explicit oauth is fine.
- A secret never lands in the state file as a side effect (keep the existing guarantees: the service-token secret is not persisted).

## Acceptance
