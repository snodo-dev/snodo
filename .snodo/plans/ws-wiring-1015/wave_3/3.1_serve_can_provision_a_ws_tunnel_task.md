# 3.1 — `snodo serve --tunnel` can ask the cloud for a WebSocket tunnel

GitHub issue #1017 already exists for this work. Do not open another; put "Fixes #1017" in the commit message. Do not edit the CHANGELOG (a later task in this plan owns the entry).

## INTENT

`snodo serve --tunnel` (`snodo/cli/commands/serve_cmd.py` and its helper modules in the same folder) provisions a managed Cloudflare tunnel: it posts a provision request to the cloud's tunnel endpoint and expects a hostname and a tunnel token back, then needs the `cloudflared` binary to run it. The cloud now also provisions WebSocket tunnels: the request carries `transport: "ws"` and the machine identifier, and the response carries a hostname of the form `<slug>-<mode>-<short>-ws.snodo.dev` and no tunnel token. This task covers the choosing and the provisioning, not the running (the next task runs it).

The existing `--transport` option is the local MCP transport (`stdio`, `sse`, `streamable-http`), so the new choice needs its own option. Follow the pattern `--auth` already uses: a Typer option declared in the command registration, carried into the argument namespace, validated early with exit code 2 on bad input (the validator from an earlier task in this plan sits next to the auth validator), documented in the option's help text. Name it `--tunnel-transport`, values `cloudflare` (default) and `ws`.

## Outcome

- `--tunnel-transport ws` with `--tunnel` provisions a ws tunnel: the provision request additionally carries `transport: "ws"` and the machine identifier. The machine identifier comes from the one place that already creates and persists it (the relay module's machine identifier function); do not add a second source. With the default transport the request is byte-for-byte what it is today (no new fields).
- For ws, the response is accepted when it names a hostname; a missing tunnel token is not an error, and neither the `cloudflared` binary nor the service-token response fields are required. The Cloudflare path still requires what it requires today.
- The ws state is saved with its transport and machine identifier through the state helpers from the earlier task; a saved ws tunnel with a hostname is reused on the next run without re-provisioning.
- `--tunnel-transport ws` together with `--auth service-token` is refused before anything is provisioned, with the validator's message. The delete flow (`--delete`, `--hostname`) works for a ws tunnel without needing `cloudflared`.
- The warning that reports an unservable hostname understands ws hostnames and no longer calls a valid `-ws` hostname unservable; the Cloudflare cases it pins keep their behaviour.
- `serve --help` names the new option and its values.

## Acceptance

- Tests: the request body for ws includes transport and machine id and the default request is unchanged; a ws response without a tunnel token is accepted and saved; a Cloudflare response without a token is still an error; ws + service-token is refused with exit code 2 before any request; delete of a ws tunnel does not require cloudflared; the hostname warning for a `-ws` hostname; help text names the option.
- Existing tunnel tests (`tests/mcp/test_server.py` tunnel cases, `tests/cli/test_serve_auth.py`, `tests/cli/test_serve_tunnel_slug.py`, `tests/cli/test_tunnel_delete_recovery.py`, `tests/mcp/test_serve_lifecycle.py`) stay green; the linter is clean; run the targeted tests and the linter, and do not run the whole suite yourself: the engine runs it right after you finish, and a multi-minute silent command has been dropping the coder connection.

## Constraints

- Starting the relay, the registry transport tag and the shutdown path are out of scope here (next task). Do not start `cloudflared` for ws and do not start the relay yet; after provisioning a ws tunnel the command may stop with a clear "not yet runnable" message that the next task replaces.
- The serve command module has a file-length baseline that may only fall. Put new logic in a new helper module in the same folder with thin call sites in the command module, and never raise a baseline.
- No new dependency.
