# 2.1 — exactly one process per machine owns the relay connection

GitHub issue #1016 already exists for this work. Do not open another; put "Fixes #1016" in the commit message. Do not edit the CHANGELOG (a later task in this plan owns the entry).

## INTENT

The machine relay (`packages/snodo-foundation/src/snodo/infrastructure/cloud_relay.py`, class `CloudRelay`) is an asynchronous task that holds one outbound WebSocket per machine to the cloud and forwards requests to the local `snodo serve` processes listed in the serve registry. Nothing starts it yet. The cloud accepts one connection per machine and closes an older one with code 4001 when a newer one arrives, after which the relay stops for good. So if every `snodo serve` simply started its own relay, starting a second serve would silently end the first one's relay, and stopping whichever serve held the connection would leave the other serves unreachable with nobody reconnecting.

The serve command that will use this is synchronous (it supervises child processes and waits), while the relay is async.

## Outcome

- A small module under the infrastructure package gives a serve process a way to take part in relaying without caring about the others: it starts, and it stops, and between those two moments exactly one process on the machine holds the relay connection.
- Ownership is decided with an exclusive lock held for as long as the owner runs, kept in the user's snodo home next to the machine identifier, so it is released by the operating system if the owner dies without cleaning up. Every participant that does not hold the lock re-tries it periodically and takes over soon after the owner goes away, so the relay is back without any user action. The takeover delay is short and configurable for tests.
- The relay runs in a background thread with its own event loop, so a synchronous caller can start and stop it; stopping cancels the running relay, closes its connection and releases the lock promptly, and a stop that is requested before the relay has started, or twice, is harmless.
- A relay that stops on its own for a terminal reason (cloud rejection, credentials refused) does not spin: the participant logs it once and does not re-acquire in a tight loop.
- The relay itself keeps its behaviour. If a small seam is needed on it so that it can be cancelled cleanly from outside, add that without changing what it does today.

## Acceptance

- Tests: two participants in one process space, one holds ownership and the other does not; stopping the owner makes the other take over within the (short, test-configured) delay; a stop before start and a double stop are safe; a participant stopped while it is a waiter never starts a relay; a relay that ends for a terminal reason is not restarted in a loop. Use fakes for the relay and a temporary snodo home; no real network. No test may leave a thread or child process behind (the suite's leak guard runs).
- The existing relay and registry tests stay green; the linter is clean; run the targeted tests and the linter, and do not run the whole suite yourself: the engine runs it right after you finish, and a multi-minute silent command has been dropping the coder connection.
