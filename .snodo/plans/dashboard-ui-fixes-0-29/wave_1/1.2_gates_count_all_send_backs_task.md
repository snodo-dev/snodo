INTENT
The Gates view counts every task a validator sent back, so its numbers agree with the first-try rate on the Delivery page, and its empty panels say why they are empty.

Evidence: snodo/web/gates.py identifies a send-back only by the existence of a recovery task record named like the task with a fix suffix and a number. In this repository 229 of 830 task records carry a blocked halt in their state or archived attempts, while a single fix record exists, so the Gates view reports almost nothing (a real dashboard shows 0 sent back, an empty What the validators caught panel and a 0 / 0 project bar) although the Delivery page first-try rate in snodo/web/flow.py (its helper that detects a blocked halt in state.json and attempts/*.json) shows work was sent back regularly. A send-back that was handled by a respec or a plain rerun leaves no fix record, so it never appears.

What it should do: a task counts as sent back in the window when its state or one of its archived attempts holds a blocked halt completed inside the window, whether or not a fix record exists; keep the stopping validator taken from the blocked validator results, the plan taken from the recorded plan name, and the outcome taken from the current plan task status (landed after retry when completed, otherwise not landed yet). Use the same detection as the Delivery page so the two views agree, preferably by sharing one helper rather than copying it. In snodo/web/static/gates.js show a short plain sentence in the What the validators caught panel and in the Per project panel when there is nothing to show, instead of an empty box, and make the summary sentence read naturally when the count is zero. Update the module description at the top of snodo/web/gates.py to match, and the Gates paragraph in docs/web-dashboard.md if it says that fix records identify a send-back.
