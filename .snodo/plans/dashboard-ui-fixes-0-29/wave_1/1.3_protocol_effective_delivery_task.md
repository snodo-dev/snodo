INTENT
The Protocol view tells the truth about how finished work is delivered, including when the setting comes from a mode or from the older auto_merge switch.

Evidence: on a real dashboard the Delivery tile of the Protocol view reads leave unmerged with the line merge by hand for a protocol whose delivery is local merge. The tile (snodo/web/static/protocol-tiles.js) and the Deliver stage of the pipeline (snodo/web/static/protocol-pipeline.js) read only the execution level delivery value that snodo/web/protocol.py sends. The engine resolves delivery differently: the protocol model method delivery_for in packages/snodo-foundation/src/snodo/compiler/models.py prefers the mode setting, then the execution delivery, then the legacy auto_merge flag (true means local merge, false means leave unmerged), and finally leave unmerged. A protocol that delivers through a mode setting or only through auto_merge therefore shows the wrong label.

What it should do: the protocol API response carries the effective delivery for the initial mode, resolved with the same method the engine uses (leave_unmerged is one of its values), and the tile and the Deliver stage show that value. The existing labels stay: auto-merge on a clean pass for local merge, push branch, change request, and for leave unmerged the text leave unmerged with merge by hand. Keep the raw execution values in the response so the editor still shows what is written in the file. Read the existing protocol API and static tests and extend them with a protocol that sets delivery only on the initial mode and one that only sets auto_merge.
