## Intent
`snodo logs rec_<id> --watch` should follow a running recon the way it follows a job: stay attached until the recon is finished, showing each agent's answer once as it arrives.

## Evidence
- Running `snodo logs` on a recon id with `--watch` prints the recon's state once and returns, while the recon is still running.
- In snodo/cli/commands/logs_cmd.py, both places that handle a recon id call `_show_recon(project_root, composite_id)` without the parsed arguments, so the watch flag never reaches it, and `_show_recon` has no loop.
- Recon state lives in `.snodo/recons/<id>/state.json` (status becomes `complete` or `failed` when done) and `results.json` (a list of per-agent results appended as each agent finishes). `ReconManager.get_status` in packages/snodo-mcp/src/snodo/recon/__init__.py reads this state.

## Outcome
- With `--watch`, a recon id is followed until its status is `complete` or `failed`: the header (id, query, status, agents) is printed once, then each agent result is printed exactly once when it first appears, then the command returns 0. Identify a result by its position in the results list, not by its agent label, because two agents can share a label.
- A recon that is already finished when the command starts prints everything once and returns, with or without `--watch`.
- Without `--watch` the output is byte-for-byte what it is today.
- Ctrl-C ends the watch quietly with a short note that the recon keeps running, and exit code 130 or the project's existing convention for interrupted watches.
- A missing or briefly unreadable state or results file during polling is tolerated and retried; it does not crash the watch.
- The `--watch` option help text describes both jobs and recons accurately.
- Tests cover: watch follows a recon that completes after a delay, each result printed once, already-finished recon, failed recon, interrupted watch, and unchanged non-watch output. Polling must be injectable or patched so the tests do not sleep for real.
- `make gate` passes.
