New files this task will create: none.

INTENT
The per-test guard over the suite repository's own .snodo directory costs about the same on every test and stops growing with the number of committed plans, while still failing any test that writes there.

Symptom and evidence: the release gate (make release PART=minor, gate-ci, which runs tests with -m "" so the e2e tests are included) failed twice with a 60 second pytest-timeout on tests/e2e/test_queue_run.py::test_blocked_queue_can_be_corrected_while_another_queue_finishes. The second run reported it as an ERROR at teardown, and the traceback ends inside tests/conftest.py, in _guard_suite_snodo_per_test calling _snodo_dir_state, in the middle of its rglob loop. That autouse fixture fingerprints the whole suite .snodo directory before and after every test by reading every file and taking a sha256 of its bytes. The directory holds about 1300 tracked files (roughly 610 under plans and 686 under plans-archive) and gains more with every plan, so the work is paid about 14000 times per full run, and the heaviest e2e test, which spawns about fifteen CLI processes, ran out of its 60 seconds partly inside it. A full run on this machine is about 0.2 seconds per fingerprint over the tracked files alone, and the gate run takes about 15 minutes.

What it should do: make the fingerprint cheap by not reading file contents. A file's size and modification time are enough to notice that a test created, changed or deleted something, and the guard already treats any write under the suite .snodo as a violation whatever the content. The same cost applies to _plans_dir_state, the second fingerprint in the same file, which hashes plan contents at session level; give it the same treatment if that is the clean way to do it, or leave it if it runs rarely enough not to matter, and say which in the commit. Keep the failure messages and what they report (which paths changed) as they are. Existing tests of these helpers, for example tests/scripts/test_suite_repo_plans_guard.py, must keep passing; update them only if they pin the content hash itself rather than the behaviour of noticing a change.

CONSTRAINTS
Files that may change: tests/conftest.py, the existing tests of these helpers if they need it, and CHANGELOG.md (one entry under [Unreleased] ending with the issue reference Fixes #<n>). Do not change product code. No new state, status, severity or halt type.

ACCEPTANCE
Creating, modifying or deleting a file under the suite .snodo is still reported against the test that did it, and the fingerprint no longer reads file contents. make gate-task is green.

PROCESS
Open a GitHub issue first and put Fixes #<n> in the commit message. This is a non-interactive run: open the issue directly with gh issue create, without asking for confirmation of title or body, then continue.
