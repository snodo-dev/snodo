## Intent
Parallel jobs that share the home-level agent checkpoint database should wait for each other instead of failing with "database is locked".

## Evidence
- The checkpoint store opens a new SQLite connection per call in `get_checkpointer` in packages/snodo-foundation/src/snodo/infrastructure/memory.py, with `check_same_thread=False` and no busy timeout or WAL setting, and hands setup to the LangGraph saver. Separate job processes share one database file (normally under the home directory), and tasks in the same project and mode share one checkpoint thread.
- The token store in the same package (tokens.py) already sets a busy timeout and WAL after an earlier fix; follow its approach.
- A lock error during a graph run becomes an internal error; during setup it only logs a warning and runs without memory.
- Check the installed version of the LangGraph SQLite saver first to see whether it already sets any of this, and do not duplicate what it does.

## Outcome
- A busy timeout is set before the first write on the connection the checkpointer uses, and WAL is set once for the database, not on every connection.
- A test opens the checkpointer and asserts both settings on the resulting database, and a test shows two connections writing concurrently without a lock error.
- Existing memory tests pass unchanged.
- `make gate` passes.
