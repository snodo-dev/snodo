## Intent
The workspace text search tool should not be able to produce a huge result from one huge line. `search_string` in packages/snodo-tools/src/snodo/tools/workspace.py caps the number of matches at 50 but copies each matching line whole, so a single hit in a multi-megabyte single-line file (the repository holds some, for example under .snodo/ and experiments/results/) returns tens of megabytes.

The change is confined to the tools package (workspace.py and its test). It imports nothing from the coders, validators or recon packages and does not touch the model-boundary bound that another task in this plan adds there.

## Evidence
- Recon rec_04abc0 on 2026-10-28: an agent using only list_files, read_file(s), read_file_lines, search_string and search_symbol had a tool result of 93,549,595 characters refused by the provider (limit 10,485,760).

## Outcome
- A matching line longer than a modest limit is shortened in the result with a visible marker saying it was cut, while the result still names the file and line number so the caller can read the area with the line-range tool.
- Short matching lines, the match-count cap and the result format are unchanged.
- A test under tests/tools proves a file with a multi-megabyte single line yields a small result that still carries the path and line number, and that ordinary matches are returned as before.
- No file crosses the file-length ratchet (scripts/enforce_file_length.py passes). The coder runs the new test and the ratchet check and reports their results in its summary.

No new states, statuses, severities or halt types.
