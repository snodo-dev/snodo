# Refuse a whole-file write of a file the coder only read part of

## Goal

`https://github.com/snodo-dev/snodo/issues/944` records an in-process coder that
submitted a complete replacement for files it had only read a slice of, deleting real
content: one observed commit was +355/−7,705, which turned `CHANGELOG.md` into 21
lines and `validation.py` into 45. Nothing in the loop recognised that as wrong; the
suite caught it only incidentally, and `enforce_vocabularies.py` caught part of the
rest.

Two changes, in priority order: make the impossible write fail at the tool boundary,
and add a diff backstop for the mass deletion it lets through.

## 1. The write boundary (primary)

`packages/snodo-tools/src/snodo/tools/workspace.py:422` (`write_file`) and `:446`
(`write_file_with_prefixes`) accept a whole-file replacement without knowing whether
the caller ever saw the file's existing content. Track what the session read and
refuse the blind overwrite:

- Record, per workspace session, which paths were read and whether the read covered
  the file completely (a full read, or a range read that spans the file's whole line
  count) versus only a portion.
- A `write_file` that replaces an **existing** file whose complete content was never
  read is refused, with a message that names the file, says how much of it was seen,
  and offers the two valid moves: read it in full, or apply a targeted edit/patch
  operation instead of a whole-file replacement.
- Creating a new file, or overwriting a file the coder did read completely, must keep
  working exactly as before. This is a guard against blind replacement, not a general
  write restriction, and it must not require a read for files that do not exist yet.
- The read-tracking state must not leak between tasks or attempts — a coder in a fresh
  worktree starts with no recorded reads. Follow how the workspace MCP already scopes
  per-session state.

Keep the refusal a tool-level error the coder observes and can act on, not a halt: the
coder gets a chance to read the file and resubmit within the same attempt.

## 2. The diff backstop

A coder can still legitimately submit a short replacement for a file it read fully.
Add a blocker check to the post-execution validation: for any changed file, when the
diff removes a large fraction of the file's lines and the additions do not account for
them (e.g. the file ends up a small fraction of its previous size), raise a blocker
naming the file, the removed line count, and the resulting size, so the run halts
instead of delivering the truncation.

Choose thresholds that cannot fire on ordinary refactors and say what they are in the
code. The existing file-length ratchet (`--update-baseline`, baselines may only fall)
is a different check with different semantics — do not reuse its numbers or its
baseline file for this, and do not weaken it.

## Constraints

- The in-process coder and the host-CLI coders must not diverge in a way that leaves
  one unprotected: state which path each guard covers. The CLI coders edit in place
  through their own tools, so the tool-boundary guard may only reach the in-process
  coder — if so, the diff backstop is what protects the CLI path, and the spec's
  acceptance criteria should say that plainly rather than implying blanket coverage.
- Do not add arbitrary shell or new capabilities to any coder to implement this.
- The workspace MCP is used by validators and other tools too; the read-tracking must
  not change behaviour for callers that never call `write_file`.

## Acceptance criteria

- A test that a whole-file write of an existing file fails when the coder only read a
  range of it, and that the error text names the file and the two valid next steps.
- A test that the same write succeeds after a complete read, and that creating a new
  file never requires a read.
- A test that the backstop blocker fires on a mass-deletion diff and does not fire on
  an ordinary rewrite that replaces content rather than removing it.
- A test that read-tracking state does not carry over between attempts.
- CHANGELOG entry under **Unreleased** naming #944.
- `make gate` green.
