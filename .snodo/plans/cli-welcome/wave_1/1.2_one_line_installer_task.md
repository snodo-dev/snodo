# Installing or updating snodo takes several steps

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
One command installs snodo on a fresh machine and updates it on a machine that already has it:
```
curl -fsSL https://snodo.dev/install | bash
```
There is no separate update command; running the same line again is how you update. The script is published with the docs site, and the maintainer points snodo.dev/install at it.

## THE CHAIN
- Today the docs ask people to `uv tool install snodo`, or to use pip (`README.md` around line 91, `docs/runbook.md` around lines 16–22 and 289–302). People need uv first, and nothing says how to update.
- The docs site (`mkdocs.yml`, site_url https://docs.snodo.dev) copies static files from `docs/`. A script named `install.sh` in the docs folder is therefore served on the docs site as install.sh. Check that `exclude_docs` in `mkdocs.yml` doesn't drop it.
- snodo requires Python >= 3.12. `uv tool install` provides a suitable Python itself.

## CONSTRAINTS
- POSIX `sh`-compatible script named `install.sh` in the docs folder, readable top to bottom, with `set -eu`. It should:
  - say what is installed now (snodo version or "none") and which uv it found;
  - if uv is missing, install it with astral's official installer, then make it usable for the rest of the script;
  - install with `uv tool install snodo`, or upgrade with `uv tool upgrade snodo` when snodo is already present;
  - finish with the snodo.dev wordmark, the "Updated A → B" or installed version line, and three short next steps (`cd` into a git repository, `snodo init`, `snodo`);
  - mention the docs at https://docs.snodo.dev.
- Embed the wordmark as plain rows, exactly:
```
╭──  ┌─╮  ╭─╮  ╭─┤  ╭─╮   ╭─┤  ╭─╮  ╷   ╷
╰─╮  │ │  │ │  │ │  │ │   │ │  ├─╯  ╰╮ ╭╯
──╯  ╵ ╵  ╰─╯  ╰─╯  ╰─╯ ▪ ╰─╯  ╰──   ╰─╯
```
  Colour it (grey #dce3e6 for "snodo", teal #2ccfbc for "▪" and "dev") only when stdout is a TTY and `NO_COLOR` is unset.
- After an update, add one soft line: a running `snodo serve` picks up the new version the next time your agent reconnects.
- Update `README.md` and `docs/runbook.md` so the one-liner is the first install option. Keep `uv tool install snodo` and pip as alternatives.
- Copy reads plain and soft. Avoid "not X but Y" contrast phrasing.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo. Never run the installer against the real environment.
- Run `uv run python scripts/enforce_file_length.py` on touched files, and `shellcheck` on the script if it is available.

## ACCEPTANCE
- A pytest runs the script with a fake `uv` and fake `snodo` on PATH (stubs that record their arguments) and shows:
  - with no snodo present, the script calls `uv tool install snodo`;
  - with snodo present, it calls `uv tool upgrade snodo` and prints the old → new versions;
  - piped output (not a TTY) contains no escape codes and still includes the wordmark rows.
- `README.md` and `docs/runbook.md` show the one-liner first.
- There is a CHANGELOG entry under ## [Unreleased].
