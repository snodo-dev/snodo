## Intent
Every model call that goes through a provider with the `auth` setting set to `chatgpt-oauth` must find a fresh token waiting, without each call site knowing anything about OAuth. All the call sites obtain their credential through the same config manager call, so the refresh belongs there.

## Evidence
- The core package's config module resolves credentials in get_key_for_model, which the validator binding, the coder loop, recon, `models --check`, `models --benchmark` and `config test` all use; it already special-cases the snodo-cloud provider by delegating to a credential resolver registered from the foundation package, and a single global resolver exists for that one provider.
- The `auth` provider setting and its helper `provider_uses_oauth` on the config manager already exist in the core config module.
- The token module already exists in this checkout as the Python module `snodo.infrastructure.chatgpt_oauth` in the foundation package, and it is read-only for this task: do not modify or recreate it. It offers `ensure_chatgpt_access_token(provider_name, ...)`, which refreshes the stored ChatGPT token under a cross-process lock and returns it, and the exception `ChatGPTReauthenticationRequired`, whose message asks the operator to run `snodo models --provider <name> --authenticate` again. Use this module; do not create another token module, and do not use the snodo-cloud OAuth store or cloud credential modules for ChatGPT.
- For the chatgpt route LiteLLM reads the token file itself and takes no api key, so the credential returned for these providers is no key at all.
- Validators bind their credential once per pass before their threads start, the coder resolves it every turn, and recon resolves it once per agent call.

## Outcome
- Resolving the credential for a model of a provider that signs in with OAuth first makes the stored token fresh through the token module and then returns no API key, so the call proceeds and LiteLLM finds a valid token.
- When the token module raises its named error, the error reaches the operator unchanged with its message asking to run `snodo models --provider <name> --authenticate` again, instead of being swallowed or replaced by a raw authentication failure. Check each of the call sites that resolve a credential and make sure the message is what the operator sees in validator, coder, recon, check and benchmark output; adjust call sites minimally where one hides it.
- Providers without the `auth` setting resolve exactly as before, including snodo-cloud.
- The registration of the token refresh follows the existing pattern for the cloud credential resolver rather than importing the foundation package from the core package against the import rules; keep the import-linter contract passing.
- Tests cover: an OAuth provider refreshes then returns no key; the named error propagates with its message from the resolution call; a non-OAuth provider is unchanged; snodo-cloud is unchanged; the refresh is called once per resolution. Use a fake token module and no network.
- `make gate` passes, including ruff (no unused imports), the import-linter contract, and the file-length and docs-coverage checks.
