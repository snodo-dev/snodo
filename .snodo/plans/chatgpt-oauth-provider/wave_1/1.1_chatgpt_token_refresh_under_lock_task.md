## Intent
Snodo will let a provider sign in with a ChatGPT subscription through LiteLLM's chatgpt route instead of an API key. Several threads and processes make model calls at the same time, and the refresh token is single-use, so snodo needs one place that keeps the access token fresh under a lock, so that LiteLLM always finds a valid token and never refreshes on its own.

## Evidence
- LiteLLM's ChatGPT authenticator (its authenticator module under the chatgpt llms package) keeps the token in a file whose directory comes from the CHATGPT_TOKEN_DIR environment variable (default in the user's config directory under litellm/chatgpt) and whose name comes from CHATGPT_AUTH_FILE (default auth.json). It refreshes an expired access token itself, with no lock: the file is rewritten in place with default permissions, and two callers refreshing at once spend the same single-use refresh token, so the second fails. Its get_access_token method refreshes without any prompt when the refresh token still works, and only falls to the interactive device-code sign-in when it does not; it refuses that sign-in from a worker thread or a running event loop and raises an error saying a login is needed.
- Validators run up to four threads at once, recon up to four per recon, and background jobs are separate processes, all sharing the same token file.
- Snodo already solves the same problem for its cloud login: the cloud OAuth store module in the foundation package's infrastructure modules combines an in-process lock with a file lock, and the cloud credentials module rereads state after taking the lock, checks whether another caller already refreshed, refreshes only if still needed, and saves atomically. Follow that pattern and its conventions.

## Outcome
- A new module in the foundation package's infrastructure modules, beside the cloud OAuth store, offers: a lock context for the ChatGPT token file that is safe across threads and processes; a function that returns when the stored access token is valid for at least a safety margin larger than LiteLLM's own expiry margin, refreshing it under that lock only when needed and rereading the file after taking the lock; and a function that reports the sign-in state (signed in with expiry time, or not signed in) by reading the file only, with no network call.
- The refresh function never starts an interactive sign-in. When there is no token file, the refresh token is rejected, or the file is unreadable, it raises one clearly named error whose message tells the operator to run `snodo models --provider <name> --authenticate` again; the provider name is passed in by the caller.
- The token directory and file are kept owner-only (directory 0700, file 0600) after every write that snodo performs or triggers, and the module honors the same two environment variables LiteLLM does.
- Tests cover: a fresh token needs no refresh and no lock contention; an expired token is refreshed exactly once when many threads ask at the same time; the same with several separate processes, using a fake authenticator and no network; a rejected refresh token raises the named error with the re-authenticate message; a missing file raises it; the permissions end up owner-only; the state function reports signed in and not signed in. Tests must never reach the network or a real token file.
- `make gate` passes, including ruff (no unused imports) and the file-length and docs-coverage checks.
