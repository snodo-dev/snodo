## Intent
An operator needs a way to say, in a provider's settings, that this provider signs in with OAuth instead of using an API key. Today nothing in the provider settings can say that, and API-key providers must stay exactly as they are.

## Evidence
- The provider settings class and the default provider catalog are in the core package's config module (ProviderConfig); the provider settings are also validated and set through `snodo config set` by two validation modules, one under snodo and one in the core package, that each hold their own provider schema and must stay consistent.
- A provider block named chatgpt already routes model names starting with chatgpt through the chatgpt route with no code change, and may be written with all api key fields empty.
- A user's provider entry replaces the catalog entry of the same name rather than merging with it.

## Outcome
- Provider settings gain one optional setting named `auth`. Absent means an API key, exactly as today. The one accepted value is `chatgpt-oauth`; any other value is refused with a message that lists the accepted value.
- A provider that sets `auth` and also sets an api key field (the key itself, an environment variable name or a key reference) is refused with a clear message saying an OAuth provider takes no API key.
- Both validation modules and `snodo config set` accept, validate, show and store the setting consistently, including `snodo config set providers.<name>.auth chatgpt-oauth` creating a new provider entry without an api key.
- A small helper on the config manager answers whether a named provider signs in with OAuth, for later tasks to use. It returns false for every provider that has no `auth` setting.
- No existing provider in the default catalog changes, and a config file written before this change loads and behaves identically.
- Tests cover: the setting accepted and stored through `snodo config set`; refusal of an unknown value; refusal when combined with an api key field; a provider without the setting unchanged; the helper in both cases; both schemas agreeing. Existing config tests keep passing.
- `make gate` passes, including ruff (no unused imports) and the file-length and docs-coverage checks.
