## Intent
`snodo models --check` sends one short prompt through each configured model. For a model whose provider signs in with OAuth, a failed check should say plainly when the cause is the sign-in, and tell the operator which command fixes it, instead of showing a raw authentication failure. Separately, snodo relies on one private method of LiteLLM's ChatGPT authenticator for its refresh, so a LiteLLM upgrade that removes it must fail loudly in the tests rather than silently in front of an operator.

## Evidence
- `models --check` lives in the models check module under snodo/cli/commands; it does not need model discovery, reads the configured models for each role, and reports OK or FAILED per role, sequentially, with the call's own message.
- Earlier tasks in this plan made credential resolution refresh the token for OAuth providers and raise one clearly named error (`ChatGPTReauthenticationRequired` in `snodo.infrastructure.chatgpt_oauth`), with a message asking the operator to run `snodo models --provider <name> --authenticate` again, when the sign-in is gone; the same module has `chatgpt_sign_in_state()`, which reports signed in or not signed in without network.
- The token module's refresh calls the private method `_refresh_tokens(refresh_token)` of `Authenticator` in LiteLLM's ChatGPT authenticator module, because the public `get_access_token` can fall through to an interactive device-code sign-in. In the installed LiteLLM that method returns the refreshed token mapping and writes the token file itself. Nothing in the tests currently checks that the installed LiteLLM still has this method.

## Outcome
- A role whose model belongs to an OAuth provider that is not signed in is reported as FAILED with the message asking for `snodo models --provider <name> --authenticate`, without making the model call.
- A role whose call fails with the named sign-in error shows that same message.
- A role on an OAuth provider that is signed in is checked like any other and reported OK or FAILED on its own result.
- The output for providers with API keys, local providers and opencode-cli coders is unchanged.
- A small separate test, in its own new test file under the infrastructure tests, asserts that the installed LiteLLM `Authenticator` class has a callable `_refresh_tokens` taking the refresh token, and its failure message says that the token module's refresh depends on this private method and must be revisited when it is gone. The test is skipped cleanly when LiteLLM is not installed.
- Tests for the check behaviour cover: not signed in (no model call made); the named error during a call; signed in and OK; signed in and a call failure; an API-key provider unchanged. Use fakes and no network.
- `make gate` passes, including ruff (no unused imports), the import-linter contract, and the file-length and docs-coverage checks.
