## Intent
An operator should find, in the documentation, how to use a ChatGPT subscription instead of an API key: how to configure the provider, how to sign in headless, what happens when the sign-in expires, and how it differs from an API key and from the snodo cloud login.

## Evidence
- Earlier tasks in this plan added the provider setting `auth` with the value `chatgpt-oauth`, the command `snodo models --provider <name> --authenticate` (headless: prints the address and code, then waits and saves the token), refresh of the token under a lock when models are called, a message asking the operator to authenticate again when the sign-in is gone, sign-in state in provider listing and `models --check`, and benchmarking a named model of a provider that cannot list its models.
- Provider documentation lives in the providers pages under docs (an index page with a credential-precedence paragraph, and one page per provider such as the OpenAI page); settings are documented in the configuration page; commands in the command reference; model choice in the choosing-models page; decisions in the decisions directory (the latest ADR number is 060 and the cloud login ADR is 057).
- The one account limit: the first version supports one ChatGPT account per machine, with the token kept in LiteLLM's token location, and the token file is kept owner-only.
- The refresh relies on one private method of LiteLLM's ChatGPT authenticator (`_refresh_tokens`), because its public token method can fall through to an interactive sign-in; a test added in this plan fails when an upgrade removes that method.

## Outcome
- A new provider page for the ChatGPT subscription, modelled on the OpenAI page: configuration with the `auth` setting and no API key, signing in headless and on a machine with a browser, the sign-in lasting about ten days and refreshing by itself, what to do when snodo asks to authenticate again, the one-account limit, and that spend is shown as unpriced.
- The providers index credential-precedence paragraph, the configuration page's provider settings table, the command reference models row and the choosing-models page each mention the new setting and the `--authenticate` flag in one or two sentences with a link to the new page.
- A short ADR numbered 061 recording the decisions: an explicit `auth` setting rather than a fake key, snodo refreshing the token under its own lock because LiteLLM takes none, sign-in only through `--authenticate`, one account for now, the reasoning that validators go through LiteLLM only, and the consequence that the refresh depends on a private LiteLLM method which a test now guards.
- The existing documentation coverage check passes with the new page and ADR linked from the right indexes.
- `make gate` passes, including the documentation checks.
