Before starting, open a GitHub issue on snodo-dev/snodo titled "get_plan / plan run results don't make an unfinished plan obvious". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
When a plan stops partway, the orchestrator should see at once that the plan is unfinished, which task blocked it, and what to do next.

Evidence: in plan `orchestrators-default-to-plans-2`, `get_plan` showed waves 1–4 "completed" and wave 5 "blocked". The orchestrator misread the earlier waves as being on main, and moved on to a one-off task.

When this is done, the MCP `get_plan` response and the plan-run job outcome tell the orchestrator three things in their existing human-readable text and instruction fields:
- the plan is unfinished, and which task or tasks blocked it;
- which completed waves are already delivered to the base branch and which are not;
- the next action: fix the blocked task forward inside this plan (replace its spec, then run that wave).

THE CHAIN
1. The MCP handlers for `get_plan`, and the completion text of a plan-run job, include that information when any task is blocked. Use existing response fields such as the instruction or summary text. Do not add new structured fields.
2. Whether a wave is delivered is read from the git state of the base and integration branches, not stored as a new status.
3. Tests cover the blocked-plan response text, and a fully completed plan whose response is unchanged.

CONSTRAINTS
- Snodo's state machine is closed. Add no status, halt type, severity, audit event or field. Task statuses stay exactly as they are.
- Do not touch the plan runner's delivery logic, or the MCP connect-time instructions and guide docs. Other tasks own those.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
