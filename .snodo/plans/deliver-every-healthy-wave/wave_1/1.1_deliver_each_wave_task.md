Before starting, open a GitHub issue on snodo-dev/snodo titled "Deliver each healthy plan wave to main; don't strand completed waves behind a blocked one". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
Owner's rule: every piece of work should leave the software healthy, and a passing gate guarantees that. So every healthy piece merges.

Today a plan delivers its integration branch to the base branch only when the whole plan completes. Evidence: in plan `orchestrators-default-to-plans-2`, waves 1–4 (#722–#725) passed and showed "completed" in `get_plan`. Wave 5 then blocked, and none of the four reached main. The owner had to merge them by hand.

When this is done, every wave whose tasks all passed is delivered from the plan's integration branch to the base branch as soon as that wave finishes. Delivery uses the same mechanism and the same delivery mode (merge, push_branch, change_request) as end-of-plan delivery today. A later blocked wave no longer strands earlier healthy ones. The plan itself still finishes only when all its waves land.

THE CHAIN
1. Plan run: after a wave whose tasks all passed, the integration branch is delivered to the base branch, reusing the existing end-of-plan delivery path. If a wave has any blocked task, nothing from that wave is delivered.
2. End-of-plan delivery still happens and is a no-op when nothing new is left.
3. Queue runs (which deliver a queue as one unit for push_branch and change_request) keep their existing semantics, unless a per-wave delivery is clearly consistent with them. Say which in the commit message.
4. Tests:
   - A 3-wave plan where wave 3 blocks leaves waves 1–2 on the base branch.
   - A fully passing plan still ends with everything delivered.
   - A wave with one blocked task delivers nothing from that wave.

CONSTRAINTS
- Snodo's state machine is closed. Add no status, halt type, severity, audit event or field. A blocked plan stays blocked.
- Fail-closed merge verification is unchanged.
- Do not touch the MCP instructions, guide docs or the get_plan response text. Other tasks own those.

ACCEPTANCE
- The tests in link 4 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
