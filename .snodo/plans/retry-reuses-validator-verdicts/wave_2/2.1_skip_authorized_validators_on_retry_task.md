# 2.1_skip_authorized_validators_on_retry

NOTE ON THE NAME: this task id is kept only because the plan already tracks it. Its original idea (skip authorized validators through a DecisionRecord lookup) was dropped. What this task does now is described below and nothing else.

## INTENT
After `snodo authorize` followed by `snodo run --retry`, the validator whose warn was just authorized is judged again for 15 to 50 minutes, although the spec and the tree are exactly what they were. The same happens to every other validator on each recovery attempt. Wave 1 took the retry evidence text out of the verdict-cache key, so a retry now finds the earlier verdict in `.snodo/verdict_cache.json`. One restriction added in wave 1 still defeats the goal: in `dispatch_validator` in `packages/snodo-engine/src/snodo/validators/runner.py` (around lines 376 to 386, the variable `spec_only_pre_execute`) a pre-execute validator that judges the spec only reuses a cached verdict only when it was a pass. So a prior warn or blocker on an identical spec is judged again, and security/architecture (which read the tree, subject kind "spec+tree") are not covered by that restriction at all, so the two kinds behave differently for no reason.

What should become true: for every pre-execute validator that is judged and cached, a cached verdict (pass, warn or blocker) whose key matches (identical spec, plus identical tree for the validators that read the tree, plus unchanged criteria, model and protocol version) is returned as a reused result on a retry or recovery, exactly like it already is on a first run. A changed spec or a changed tree gives a different key and is judged again. The signed decision of an authorized warn is applied afterwards by the policy (`packages/snodo-engine/src/snodo/engine/policy.py`, the DecisionRecord check around lines 193 to 211), so no change is needed there. Errors and skipped results are never cached (`_is_cacheable_verdict`) and stay that way.

Why this is safe: the retry evidence block is explanatory text that adds no criterion (see `packages/snodo-engine/src/snodo/validators/retry_evidence.py`); the recovery-stall detection in `packages/snodo-engine/src/snodo/engine/loop.py` compares post-execute results only; an operator who wants a different verdict on a warn edits the spec, which changes the key.
