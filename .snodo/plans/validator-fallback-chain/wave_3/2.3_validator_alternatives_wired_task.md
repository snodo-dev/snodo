New files this task will create: none.

INTENT
The engine hands every validator the configured fallback models, and each switch to another model leaves one line in the job log, so a rate-limited provider no longer halts a task as validator_error when a fallback is configured.

Evidence: llm.validator.fallback is accepted by the configuration and LLMValidator can now walk an ordered list of (model name, completion function) alternatives, but nothing builds that list. The engine builds the validator completion function in packages/snodo-engine/src/snodo/engine/loop.py through build_completion_fn in packages/snodo-engine/src/snodo/validators/runner.py, which binds a model and its api_base together (issue #237); validators can also run on a per-validator model override, and each task's completions are wrapped with task-scoped headers (wrap_completion_fn_with_headers), where the configured model name is used for the header lookup.

What it should do: for every validator model call (the pre-execute judges, the post-execute judges, the acceptance judge and the wave validators), build the alternatives from llm.validator.fallback, each with its own bound completion function made the same way the primary one is, so the order is the model in effect for that validator followed by the fallback entries. Header lookup must name the model actually being called. When a switch happens write one line to the job log naming the validator, the model that failed, the model tried next and the short reason. With fallback empty nothing changes in behaviour or logs. The work-type classifier is out of scope here.

CONSTRAINTS
Files that may change: packages/snodo-engine/src/snodo/validators/runner.py, packages/snodo-engine/src/snodo/engine/loop.py, the module that runs the wave validators if it builds its own completion function, and tests under tests/validators/ and tests/engine/. Also edit CHANGELOG.md: add one entry under [Unreleased] ending "(Fixes #<n>)". Do not change LLMValidator's fallback behaviour, the classifier, verdict handling, severities, quorum or tool access. Do not add any state, status, severity or halt type.

ACCEPTANCE
Tests show: with a fallback list a validator built by the runner receives the list in the right order, including when the validator has its own model override; a rate-limit failure on the first model that survives the retries leads to the second model answering and exactly one job-log line naming validator, failed model, next model and reason; the wave validators receive the list too; a verdict from the first model never calls the second; with no fallback the call path and log output are unchanged. `make gate-task` is green.
