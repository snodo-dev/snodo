New files this task will create: none.

INTENT
Every validator LLM call should walk the configured fallback list when the validator model fails operationally, so a rate-limited or unreachable provider no longer stops a task before the coder runs.

Evidence: a validator call that hits a rate limit or a provider fault retries within its budget and then raises, and the task halts as validator_error. The configuration now accepts llm.validator.fallback (an ordered list of model names) and a helper that tries models in order and switches only on operational failures exists in the foundation infrastructure package. Nothing connects them yet.

What it should do: where the validators (the pre-execute judges, the post-execute judges, the acceptance judge and the wave validators) make their model call, use the helper with the list made of the configured validator model followed by the fallback entries. The existing transient retries for a model stay and run first for that model; the helper moves on only after they are spent. When a switch happens, write one line to the job log naming the validator, the model that failed, the model tried next and the short reason. A verdict from any model is final: pass, warn, blocker and an unusable verdict (ADR 059) are never a reason to try another model. When the list is exhausted, the existing validator_error halt happens exactly as today, with the usual reason text; the last error is the one reported. With fallback empty, behaviour and logs are unchanged. Token usage of every attempt, including failed ones, must still be recorded by the existing usage tracking.

CONSTRAINTS
Files that may change: the validator modules under packages/snodo-engine/src/snodo/validators/, the engine module that builds the validator completion function, and their tests under tests/validators/ and tests/engine/. Also edit CHANGELOG.md: add one entry under [Unreleased] ending "(Fixes #<n>)". Do not change the work-type classifier here (a later ticket does). Do not change verdict handling, severities, quorum or tool access. Do not add any state, status, severity or halt type.

ACCEPTANCE
Tests show: with a fallback list, a rate-limit failure on the first model that survives the retries leads to the second model answering and one job-log line for the switch; a verdict of any severity from the first model is final and the second model is never called; an unusable verdict does not switch models; with every model failing operationally the task halts as validator_error with the last error in the reason; with no fallback the call path and log output are unchanged; failed attempts still count in token usage. `make gate-task` is green.
