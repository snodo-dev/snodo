New files this task will create: none.

INTENT
A validator judge can be handed an ordered list of alternative models, and its model call walks that list when the model in use fails operationally, so a rate-limited or unreachable provider does not stop the judge. A switch must never carry one provider's credentials to another.

Evidence: LLMValidator (packages/snodo-engine/src/snodo/validators/llm_validator.py) makes every model call through _call_completion_with_retry, which retries transient faults inside its budget and then raises, and the task halts as validator_error. The completion function a judge uses is a partial that binds a model and its api_base together (issue #237, see the comment in _call_llm), so using another model means using that model's own completion function, not passing a different model name. Request kwargs also carry _configured_model, which the header wrapper (wrap_completion_fn_with_headers, packages/snodo-foundation/src/snodo/infrastructure/completion_headers.py) pops to look up that provider's task-scoped extra_headers, which can hold credentials (see tests/validators/test_provider_headers.py). A switch that leaves _configured_model naming the failed model would send provider A's headers to provider B. A helper that tries names in order and advances only on operational faults exists at packages/snodo-foundation/src/snodo/infrastructure/model_fallback.py; it hands the raw error text to its on_switch callback. Nothing connects the helper to the judges yet, and the engine does not build alternatives yet (a later ticket does).

What it should do: LLMValidator accepts an optional ordered list of alternatives, each a model name with its own completion function; the default is empty and then behaviour is exactly as today. When the model in use fails with an operational error after its own transient retries are spent, the call is made on the next alternative with everything that depends on the model switched with it: the completion function, self.model, the _configured_model kwarg, and the remembered parameters and message shape that are applied per model. The result of the model that answered is used, and the model reported for that call (telemetry, usage) is the real one. A verdict from any model is final: pass, warn, blocker and an unusable verdict (ADR 059) never cause another model to be tried. When every model fails operationally, the last error is raised exactly as the single-model path raises it today, so the existing validator_error halt and its reason text are unchanged. The switch should be observable by callers through a callback or return value so a later ticket can write the job-log line; what is handed out is the two model names and the exception type only, never the provider's error text. Do not write the log line here.

ACCEPTANCE
Tests show: with one alternative, a rate-limit failure that survives the transient retries on the first model leads to the alternative answering; the request that reaches the alternative carries the alternative's own _configured_model (and so its own headers, never the failed model's); a verdict of any severity (and an unusable one) from the first model is final and the alternative is never called; with every model failing operationally the last error is raised; with no alternatives the call path is unchanged; the model reported for a call is the one that answered; the switch notification contains model names and exception type but not the error message. `make gate-task` is green.
