# Gemini rejects tool results that contain a JSON `$ref`, halting tasks as validator_error

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
An LLM tool loop running on a Gemini model can read any file in the repository and keep going. That covers both the validator loop and the coder adapter. A file whose text happens to be JSON with `$ref` keys must not make the provider reject the next request.

## THE CHAIN
Evidence: plan persona-templates, jobs j_8e35e89dc7d7 and j_a3ace1365f87.
- The `security` pre-execute validator runs with the Gemini judging model gemini-3.5-flash-lite. Twice, it used the read_file tool on the repo's published protocol JSON Schema (the v1 protocol schema file in the top-level schemas folder, which uses `$defs` and `$ref`). On the very next turn the request failed with: litellm.BadRequestError: GeminiException 400 INVALID_ARGUMENT "The referenced name `#/$defs/Severity` in function_response.response does not match to a display_name in the function_response.parts." The task then halted as `validator_error`.
- Tasks whose validators never read that file passed.
- Tool results are appended as `{"role": "tool", "tool_call_id": ..., "content": str(result)}`, in `packages/snodo-engine/src/snodo/validators/llm_validator.py` (around line 683) and `packages/snodo-engine/src/snodo/coders/litellm.py` (around line 548).
- `packages/snodo-engine/src/snodo/coders/gemini_adapter.py` documents that LiteLLM turns these into Gemini `function_response` parts. Apparently, when the content parses as JSON, it ends up as structured data, so Gemini treats `$ref` keys as references.
- Confirm the actual mechanism in the installed LiteLLM before choosing a fix.

## CONSTRAINTS
- Fix it at the shared point where tool results are handed to the provider, so the validator loop and the coder adapter both benefit. Prefer one small helper over two copies.
- Every model must still see the tool result's full text, unchanged in meaning. The fix may be limited to Gemini models or apply to all providers, whichever is simpler and safe. Say which in the commit message.
- Add no new status, severity, halt type or audit event. Leave the operational-error handling alone; the goal is to stop this error from happening.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Neither llm_validator.py nor litellm.py may grow past its ratchet baseline; put a helper in a new or smaller module if needed.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not call real provider APIs in tests. Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run only the targeted tests: your new tests plus the existing validator and coder-adapter test files you touch.
