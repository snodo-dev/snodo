# A scheduled check installs snodo from a clean machine

## Intent

Dependency drift like this one only shows up on a clean machine, and the existing install smoke check runs only at release time or by hand, so the drift sat unnoticed until a fresh install broke. The outcome: a clean-machine install of the newest published snodo is exercised on a regular schedule, so the next drift is seen within days instead of by a user.

## Tracking

Open a GitHub issue first, or reuse https://github.com/snodo-dev/snodo/issues/1006, and put "Fixes #1006" in the commit message. This is a workflow-only change; no CHANGELOG entry is needed unless the repository's changelog gate demands one.

## Symptom and evidence

- Issue #1006: a fresh `pip install snodo` failed at import because the newest litellm needs a newer mcp than snodo allows. Every other gate runs against the working tree and its lockfile, so none saw it.
- The install smoke workflow already installs the published package from an empty machine, creates a project and runs a task with the mock coder. It triggers only on a published release or a manual dispatch.

## Contract

- The existing install smoke workflow also runs on a weekly schedule, installing the latest published version, with no other change to what it does. A failing scheduled run is visible the way any failing workflow is; no new notification mechanism is added.
- It additionally proves the two imports that broke: after installing, the check imports litellm and snodo and fails clearly if either import fails.
- Keep the existing safety habits of that workflow: nothing from inputs is interpolated into shell code, actions stay pinned the way they are now, permissions stay read-only.

## Acceptance

- The workflow file parses and passes the repository's workflow lint or validation if one exists, and the schedule, the import check and the existing triggers are all present in it.
- Lint and existing tests pass; no baseline is edited.

## Constraints

- Only the install smoke workflow changes. Do not touch .snodo/ or the other workflows.
- Do not leave notes about validation anywhere in the tree.
