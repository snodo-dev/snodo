# A registry for validator tools provided by plugins

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
Installed packages can contribute tools for the LLM validator through a Python entry-point group, discovered the same way snodo already discovers plugin validators, coders, providers and predicates. Each contributed tool declares a name, a JSON-schema function definition the model sees, and a handler that receives the call's arguments plus a read-only context. This task builds the registry and the contract. A later task wires it into the validator loop.

## THE CHAIN
- The LLM validator's tools (read_diff_between_refs, git_show, git_log, read_file, read_file_lines, list_files, summarize_directory, submit_verdict) are hardcoded in `packages/snodo-engine/src/snodo/validators/llm_validator.py`. The definitions are around lines 836–947, and dispatch is in `_execute_tool`, around line 1040. No hook lets outside code add one.
- Existing plugin discovery to follow:
  - `packages/snodo-engine/src/snodo/validators/registry.py` (around line 79, group `snodo.validators`);
  - `packages/snodo-engine/src/snodo/coders/__init__.py` (around line 72, `snodo.coders`);
  - `packages/snodo-tools/src/snodo/providers/registry.py` (around line 121, `snodo.providers`);
  - `packages/snodo-core/src/snodo/predicates/registry.py` (around line 65, `snodo.predicates`).
- The motivating use is a vendor plugin that lets a validator ask an external decision model yes/no or score questions over the diff, the spec or named files, and get probabilities back.

## CONSTRAINTS
- New entry-point group, for example `snodo.validator_tools`. Follow the closest existing registry for discovery, caching, error handling (a broken plugin is reported and skipped, never fatal) and test seams.
- The contract is small and documented in the module:
  - **Tool definition:** the function schema the model sees.
  - **Handler:** called with the parsed arguments and a context object. The context holds the workspace root (read-only use), the spec text, the diff refs or diff accessor the validator already has, the validator id, and that validator's tool options from protocol config.
  - **Return value:** text for the model.
- A tool must not shadow a built-in validator tool name; registration is refused with a clear message. Handlers get no write access to the workspace or `.snodo/`.
- Core stays vendor-neutral: no vendor names or SDKs in core.
- No new status, severity, halt type or audit event.
- Do not edit `llm_validator.py` in this task; a later wave wires the registry in. A sibling task in this wave edits protocol config models, so leave those alone too.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the targeted tests.

## ACCEPTANCE
- Tests register a fake tool through a stub entry point and see it discovered with its definition and handler.
- A plugin that raises on load is skipped with a reported error.
- A tool named like a built-in (for example read_file) is refused.
- There is a CHANGELOG entry under ## [Unreleased].
