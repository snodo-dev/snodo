# 2.1 — catch documentation links whose in-page anchor does not exist

## Why this task exists

The published documentation was repaired so that every local link and every in-page anchor
currently resolves, and the documentation build now fails on unresolved links, absolute local
links, and links the build cannot make sense of. That last class is what caught links pointing at
repository files the site does not serve.

One class is still unchecked. A link like `protocol.md#execution-configuration` points at a real
file, so the build accepts it without looking at the part after the hash. If the heading it names
is renamed or removed, the link keeps passing the build and the reader lands on a page with no
anchor. There are a dozen such links across the documentation tree and nothing tests them.

The documentation build is the natural place for this check, and the repository already has the
house pattern for this kind of gate: a script under `scripts/` named for what it enforces, with a
matching test module under `tests/scripts/`, run from the Makefile and from the CI job that runs
the documentation build. Read `scripts/enforce_docs_coverage.py` and its test before starting, and
follow that shape.

## Outcome

A check that fails when a local documentation link names an in-page anchor that the target file
does not have. It covers links between files in the documentation tree, resolves anchor names the
same way the documentation site does when it turns a heading into an anchor, and reports the file,
the line and the offending link. Links to external URLs are not its business, and it does not
re-check anything the documentation build already checks.

It runs wherever the repository currently runs the documentation build check, so a broken anchor
fails a run rather than only appearing on the site.

## Acceptance

- A link to a heading that does not exist in the target file makes the check fail, naming the file,
  the line and the link; the same link pointing at a heading that does exist passes.
- The documentation tree as it stands passes the check.
- The check's own tests cover both cases above and pass, along with the test module for the
  documentation build.

## Constraints

- The documentation build itself is not changed, and the validation levels already configured in
  its configuration stay as they are.
- Do not weaken a check, exclude a file, or skip a link form to make the tree pass. If the tree
  contains a genuinely broken anchor, fix the link.
- Where the repository lists the checks that must always pass, the new check belongs alongside the
  documentation build, described in one line in the list's own style.

## Correction for this retry

The check is built, the documentation tree passes it, and its tests pass — one thing is left
broken. The repository has a guard that fails any test which mutates the process environment
without putting it back. Running the whole suite trips it:

```text
ERROR tests/scripts/test_enforce_docs_anchors.py::test_repository_passes - Failed: TEST LEAKED
environment variables: mutated os.environ without undoing it — added=['NO_MKDOCS_2_WARNING']
```

The variable is not set by the new code directly. Importing the documentation toolchain sets it
as a side effect, so the first test that reaches the check through an import leaves the variable
behind for every later test in the same worker. Fix it in the check itself rather than in the
test: either read what the check needs from the documentation configuration without importing the
library that mutates the environment, or make the check restore the environment to exactly what it
found if it must import it. Whichever route you take, no test may be left leaking, and the guard
stays as it is.

Run the whole suite, not the new test module alone, before submitting: the leak only shows when
the suite runs in one process.

## Diff discipline

- Confine the change to what this task asks. Do not reword, rename, reformat, or delete code,
  comments, docstrings, or tests that the task does not need to touch. An existing test whose
  assertions you removed or rephrased is a contract you broke, not housekeeping you improved.
- Text an operator reads — error messages, hints, help output — is a contract when a test quotes
  it. Keep the wording a passing test already asserts.
- New coverage goes in new files or new test cases; do not restructure the files that already
  cover the area.
- Before submitting, read your own diff against the base and drop every hunk the task did not ask
  for.
- Run the whole gate command from the contributing guide before submitting, and leave it clean.
