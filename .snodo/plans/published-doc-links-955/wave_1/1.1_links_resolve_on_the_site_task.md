# 1.1 — published documentation must not link readers to paths the site does not serve

## Why this task exists

The page that first-time plugin authors are sent to points at the runnable examples with
links of the form:

```
[example README](../examples/snodo-hello-validator/)
```

The examples live in `examples/snodo-hello-validator/` and `examples/snodo-diff-line-tool/`,
which are outside mkdocs' documentation directory, so nothing is ever published at those
targets. On the docs site the link resolves one level above the site root and 404s.

The build cannot notice. mkdocs leaves link validation at its default level, which is below
warning, and the documentation target in `Makefile` builds with the strict flag — a flag that
fails on warnings only. So a link that can never resolve is silently accepted, and CI stays
green while the published page is broken.

## Outcome

- A reader following "see the example plugin" on the published page either reaches the
  example or is told precisely where to find it. Choose one of: publish the examples inside
  the documentation tree, or replace the site links with references that make no claim to be
  a site link (a repository path shown as code, with the repository URL). Whichever is
  chosen, no link in the documentation may point outside the site root.
- The class of mistake is closed, not just this instance: link validation is raised to a
  level the strict build fails on, so a future link that cannot resolve breaks the docs
  build instead of shipping.
- Whatever mechanism carries the examples must stay honest about what is served: if the
  examples are copied or included into the documentation tree, they must not drift from the
  sources they claim to show, and the build must not start failing on files it now
  considers part of the site.

## Acceptance

- No remaining link in `docs/` whose target lies outside the site, and the published page
  that discussed the examples now reaches them or names their location.
- The documentation build is run and is clean, and it now fails when a link cannot resolve:
  introduce a deliberately unresolvable link, confirm the build reports it, and remove it.
- The three places that carried the broken links are all addressed, not only the first.
- Any test that builds the documentation stays green.

## Constraints

- Documentation and site configuration only. Do not change the example plugins themselves,
  their manifests, or their tests.
- Do not lower any other validation level to make the build pass, and do not add exclusions
  that silence the new failure rather than fixing the links.
- Keep the repository's existing documentation style; the site is built from the same
  config the deployment job uses.

## Diff discipline

Confine the change to what this task asks for. Do not reformat, reword, rename or delete code,
comments, docstrings or tests that this task does not change — the rationale notes in this
repository name the issue or incident that produced each branch and are part of the behaviour.
Messages an existing test quotes are a contract with the operator: add new text where this task
needs it, never replace pinned text. New coverage goes in new cases or new files rather than by
rewriting existing ones. Before submitting, look at the diff and remove any hunk that this task's
outcome does not require, then run the whole gate command from the contributing guide and leave
it clean.
