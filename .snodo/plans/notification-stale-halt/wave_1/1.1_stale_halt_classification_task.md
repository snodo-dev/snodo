# 1.1_stale_halt_classification

## INTENT
A job that finished with status completed and exit code 0 is classified as Success, even when its job state still carries a halt left by an earlier attempt that was later resolved. A plan that delivered all of its tasks is never announced as Blocked.

## THE CHAIN
1. Open a GitHub issue first ("Notifications: stale halt makes a completed job read Blocked") and put "Fixes #<n>" in the commit message.
2. Symptom (seen in Slack): "job j_41682e24fde2 — plan p305-dispatch-composer-controls — Blocked". The job log shows task 2.1 halting once (the workspace could not run the tests, `retryable` true), then a fresh retry of that task completing and merging, and the plan ending "Plan progress: 3/3 completed".
3. Evidence: `_auto_write_halt_payload` in `packages/snodo-engine/src/snodo/engine/nodes/writeback.py` (around line 925) merges `{"halt": payload}` into the job state whenever a task halts, and nothing clears it when the task later succeeds. `classify_outcome` in `packages/snodo-mcp/src/snodo/jobs/outcome.py` tests `isinstance(halt_value, Mapping)` and returns `blocked` before it reaches the branches that recognise `status` completed with `exit_code` 0, so the stale halt wins. `docs/outcomes.md` says exit code 0 is produced only when the final decision is completed.
4. Change the classification so that a finished job (status completed or finished, exit code 0) with no pending human escalation is a success, or a warn-recovered success when a recovery task exists, regardless of a halt left in the job state. Behaviour for failed, halted and unmerged jobs, for a halt with a non-zero exit, and for a pending escalation (human decision) stays as it is.
5. Add tests in a new test file named test_outcome_stale_halt.py under `tests/jobs/`: a stale halt with completed and exit 0 gives success; a halt with failed and exit 1 gives blocked; a pending escalation still gives human decision; a recovery subtask with completed and exit 0 gives warn recovered; engine faults (validator, internal and environment errors) with a non-zero exit are unchanged.
6. Add one more test in that file that drives the finished-job notification path with the seam the existing tests in `tests/jobs/test_notifications.py` use (stubbed sender, temporary project folder, job state file): a completed exit-0 job with a stale halt produces a message that says Success and not Blocked; the same halt on a failed exit-1 job says Blocked.

## CONSTRAINTS
- Reuse the existing situation names. No new state, status, severity, halt type, event name or notification field.
- Presentation only: do not change what is written to job or task state.
- No real sender and no network in tests.
- Add one line under `[Unreleased]` in `CHANGELOG.md`.

## ACCEPTANCE
- Every test above passes, and the existing tests in `tests/jobs/` still pass.
- A completed exit-0 job with a stale halt is Success; the same halt with a failed job is still Blocked.
