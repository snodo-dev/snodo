# 1.1 — the changelog coverage check must survive a rewritten branch history

## Why this task exists

The lint job of `​.github/workflows/ci.yml` computes changelog issue coverage from a base
commit supplied through the environment:

```yaml
CHANGELOG_BASE: ${{ github.event.pull_request.base.sha || github.event.before }}
```

For a pull-request event that is the base commit, which is always reachable. For a push
event it is the previous tip of the branch, and after any history rewrite that commit is no
longer reachable from any ref: the action's checkout never fetches it, and the script dies
on the revision range with a fatal "Invalid revision range" from git.

Observed on the run that pushed a rebuilt plan integration branch: the step failed while
every other step in the same job passed, and the same commit passed the same step under the
pull-request event. Because the failed check-run is attached to the abandoned head SHA, it
keeps showing on the pull request until the branch is pushed again — so recovering meant
pushing an unrelated empty commit purely to obtain a head SHA whose push event has a
resolvable base.

The check is a gate. A gate that cannot run must not be reported as a pass, but it also must
not be an unfixable red X that blocks an otherwise clean delivery.

## Outcome

- When the supplied base commit cannot be resolved in the checkout, the script resolves a
  base it can use — the merge base against the repository's default branch, or the branch's
  own upstream — and evaluates coverage over that range instead of dying.
- Falling back is visible, not silent: the run says which base it was given, why that base
  could not be used, and which base it used instead, so a reader of the log can tell a
  rewritten history apart from a genuine gap in coverage.
- If no base can be established at all, the check fails in a way the operator can act on:
  the message names what was tried and what to do, rather than surfacing a raw git revision
  error.
- A range that is genuinely empty, or commits that really do lack issue coverage, still fail
  exactly as they do today. Robustness must not turn the gate into a no-op.

## Acceptance

- A test that an unreachable base commit falls back to a resolvable base and that coverage is
  still enforced over the fallback range — a commit without issue coverage still fails there.
- A test that the fallback is reported in the output, naming the base that was unusable.
- A test that a reachable base behaves exactly as before, and that a range with nothing to
  check still passes.
- A test that when no base can be established the script fails with its own message rather
  than propagating a git revision error.
- The existing coverage tests in `tests/scripts` stay green.
- The infrastructure and scripts suites pass and the linter is clean.

## Constraints

- The script decides the fallback; do not paper over the problem by deleting the push-event
  trigger or by making the workflow step continue on error, which would let an uncovered
  change through.
- No new dependency, and no network calls beyond what git itself already does in this script.
- Keep the existing output format the workflow log is read through.

## Diff discipline

Confine the change to what this task asks for. Do not reformat, reword, rename or delete code,
comments, docstrings or tests that this task does not change — the rationale notes in this
repository name the issue or incident that produced each branch and are part of the behaviour.
Messages an existing test quotes are a contract with the operator: add new text where this task
needs it, never replace pinned text. New coverage goes in new cases or new files rather than by
rewriting existing ones. Before submitting, look at the diff and remove any hunk that this task's
outcome does not require, then run the whole gate command from the contributing guide and leave
it clean.
