Before starting, open a GitHub issue on snodo-dev/snodo titled "Validator read-tool argument errors halt the task instead of returning to the model". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
In plan third-party-extensions, task 1.2_predicate_entry_points halted with `validator_error` before the coder ran. On turn 11 the security validator called `list_files("snodo/protocol_validation.py")`. The tool raised `ValueError: Path is not a directory`, and the validator reported "Validator declared tool 'list_files' failed on turn 11 (ValueError)…" with error=true. The policy then failed closed: "1 validator(s) produced operational errors". The other three validators passed.

A model passing a file where a directory is expected is an ordinary mistake. Recon's agentic loop already handles it: the error goes back to the model as the tool result and the model tries again. The validator loop should do the same, so one bad argument doesn't cost a whole task.

When this is done, a validator's read-tool call that fails because of its arguments returns an error message to the model as that turn's tool result. The validator carries on and still has to submit a verdict within its turn budget. Failures that are not about the model's arguments still fail closed exactly as today: a provider or transport error, an unexpected exception inside the tool implementation, or running out of budget without a verdict.

THE CHAIN
1. The validator tool loop separates argument errors (path not a directory, path missing, path outside the worktree, malformed arguments) from operational failures. Argument errors become a tool-result message. Operational failures keep today's error=true and fail-closed behaviour.
2. The validator's `examined` trace still records the failed call, so the evidence trail shows what the model tried.
3. Tests:
   - a scripted validator calls list_files on a file, gets the error back, then submits a verdict, and the result is not error=true;
   - an exception raised from inside the tool implementation (not an argument error) still produces error=true and fail-closed;
   - a validator that exhausts its budget without a verdict still fails closed.

CONSTRAINTS
- Snodo's state machine is closed: add no status, severity, halt type, audit event or result field.
- Do not weaken fail-closed for operational errors. The quorum's handling of error=true does not change.
- Path containment (no reads outside the worktree) is unchanged. A path that escapes the worktree gets an error result, never data.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
