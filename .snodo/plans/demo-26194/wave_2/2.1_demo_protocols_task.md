# 2.1_demo_protocols

## INTENT
The demo can run the same task twice under the same model: once under the shipped bugfix-surgeon protocol, and once as a bare baseline where the coder works with no validator judging its output and no recovery. A user gets both protocol files from one small helper, and each one is checked to be valid before use.

## THE CHAIN
1. Open a GitHub issue first ("Demo: governed and bare protocol builders") and put "Fixes #<n>" in the commit message.
2. Evidence on what the schema allows: `Protocol.validators` needs at least one entry (`packages/snodo-foundation/src/snodo/compiler/models.py`, around line 466), while a mode's own validator list may be empty. A mode that holds the dispatch tool needs at least one pre-execute validator. The shipped template `packages/snodo-foundation/src/snodo/protocols/templates/bugfix-surgeon.yml` already declares a no-op always-pass validator named `triage` plus a `minimal-diff` post-execute reviewer, with `max_recovery_depth` 3 and `local_merge` delivery.
3. Create a new module file named protocols.py in the `demo/` folder (the folder already exists and holds the scikit-learn-26194 fixture; look at how existing tests import code that lives outside `packages/`, for example under `experiments/`, and follow that pattern so the new tests can import the module). It exposes two functions: one that returns the governed protocol text (the shipped bugfix-surgeon template, read from the installed snodo package so the demo always matches the pinned version) and one that returns the bare protocol text, derived from that same template: the active mode keeps only the `triage` validator (so the minimal-diff reviewer does not judge), `execution.max_recovery_depth` is 0, and everything else is unchanged. A third function writes a protocol text to a given path.
4. Add a function that checks a written protocol file by calling `snodo protocol validate <path> --json` and returns whether it is valid together with the findings. It must not raise when the snodo command is missing; it returns a clear unavailable result instead.
5. Add tests in a new test file named test_demo_protocols.py under the tests folder. Use exactly these test function names and keep them unchanged for the whole task, including in any follow-up fix pass (a coverage check fails the task when a test name disappears or is renamed): `test_bare_differs_from_governed_only_in_validators_and_recovery_depth`, `test_both_protocols_parse_as_yaml`, `test_governed_equals_shipped_template`, `test_protocols_validate_when_snodo_available` (skips when the command is not available). More tests may be added.
6. The project supports Python 3.12; do not use 3.13-only APIs. Before finishing, run `python -m pytest tests/test_demo_protocols.py` and do not finish until every test passes (the gate reruns the file and one failing assertion blocks the task); write each expected value from what the code really returns. Also run `ruff check` and `ruff format --check` on every file you touched and fix what they report (remove unused imports and variables). These are checks for you to run; the reviewer does not re-run them.

## CONSTRAINTS
- Derive the bare protocol from the shipped template by editing the parsed structure, so a future template change flows through. Do not paste a full copy of the template into the new module.
- Do not change the shipped template or any file under `packages/`.
- Add one line under `[Unreleased]` in `CHANGELOG.md`.
- No new states, statuses, severities, halt types or event names, and no change to the protocol schema.

## ACCEPTANCE
- In the diff, the bare protocol keeps only the `triage` validator in its active mode and sets recovery depth 0, built by editing the parsed template structure.
- In the diff, the governed protocol is the shipped bugfix-surgeon template content.
- The new test file contains the four named tests above.
- Verifiable from the diff of the new module, the new test file and CHANGELOG.md.
