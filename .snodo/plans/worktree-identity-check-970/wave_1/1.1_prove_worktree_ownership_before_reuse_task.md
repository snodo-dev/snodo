# A task workspace is reused only when this repository can vouch for it

## Intent

Retrying a halted task keeps its previous work, and that reuse is deliberate and stays. What is missing is proof: when a directory already exists at a task's workspace path, the engine reuses it without checking that it is a workspace of the repository doing the retry. A leftover from another project, a checkout whose project directory was moved or deleted, or a plain empty or non-git directory is accepted and the task runs inside it. The outcome to reach: a task only ever runs in a workspace that the repository itself records as its own, and when it cannot, the operator gets an honest, actionable refusal instead of a silent wrong run.

## Tracking

Open a GitHub issue first, or reuse https://github.com/snodo-dev/snodo/issues/970, and put "Fixes #970" in the commit message. Add one entry under [Unreleased] in the CHANGELOG, tagged (Fixes #970).

## Symptom and evidence

- Issue #970: two projects that share a parent directory and a task id resolve to the same workspace path, and the second project runs its task in the first project's leftover directory on the first project's branch, with no branch created for it. In the reported run the reused path was not even a git repository (the other project had been deleted), yet the retry reported inherited work and a later branch lookup failed with an IndexError.
- The workspace-reuse step in the foundation worktree module checks only that the path exists, then returns it.
- Already on main from the retry-control work (do not redo it): workspace paths are now scoped by project, so two projects no longer map to the same path by default; the repository's own worktree listing is read by an ownership helper that answers whether a task's workspace is registered to this repository; and one branch lookup stopped searching parent directories. The reuse step does not consult that helper yet, which is the remaining gap.
- A previous attempt at this task reached a working implementation and a fully passing test suite, and was stopped by one lint finding only: a swallowed exception (try, except, pass) in the code that reads the branch and repository for the refusal message. The repository lint rejects silent exception swallowing.

## Contract

- Reuse is allowed when the repository's own worktree listing records the existing path as its worktree. Proof comes from the repository (what it registered), not from inspecting the directory's contents.
- An existing path that the repository does not record as its own is never reused, deleted or overwritten. Depending on what is safe, the engine either creates the task's workspace at a path that cannot collide, or refuses with the existing isolation error. It never runs the task there silently.
- A refusal message names the path, what was found there (the branch and the repository it belongs to when those can be read, or that it is not a git repository at all), the project that asked, and how to clear it (the existing worktree removal command for the task). The ordinary reuse log line stays for the legitimate case.
- Reading what was found is best effort and must never mask the refusal. It handles the specific failures it expects (not a repository, detached or unborn head) by naming them, and logs anything else at debug level; no silently swallowed exceptions.
- A directory that is registered to this repository but whose checked-out branch is not the task's branch is treated as not matching and handled the same way, so a retry never lands on a different task's branch.
- Legacy workspace paths from before project scoping keep working when they are demonstrably this repository's own; a retry of an in-flight legacy workspace finds its own work rather than starting over.
- The listing, removal and ownership entry points that resolve the same workspace identity stay consistent with whatever the reuse step decides; list and remove still round-trip.
- No new status, halt type, severity or validator kind; the refusal uses the existing isolation error and the normal task-failure path. The merge lock and branch-creation flow below the reuse step are untouched.

## Acceptance

- A test with two real repositories created by the test under one parent directory: project A leaves a workspace for a task id, project B dispatches the same task id, and B is not run inside A's directory. The outcome is asserted on content (the message or the new path), not only on exception type.
- A test where the existing path is a directory that is not a git repository (the shape in the issue): the task is not run there, and the message says so.
- A test that a legitimate retry still reuses its own registered workspace and keeps its work, including a legacy-path workspace.
- Targeted tests for the foundation worktree module and the retry-workspace ownership tests pass; the repository lint passes on the changed files; keep every file under the file-length gate, and do not edit any baseline.
