# A task worktree path must be proved to belong to the project that asked for it

## Goal

`https://github.com/snodo-dev/snodo/issues/970`: `create_worktree` reuses any existing
directory at the task identity path without checking that it is a worktree of the
repository being retried in. The worktree root is a **sibling** of the project root
(`worktree_dir(project_root)/…`, i.e. `<parent>/.snodo-worktrees`), and the identity is
`<plan_name>/<task_id>` — or just `<task_id>` when there is no plan. Two projects that
share a parent directory therefore collide whenever a task id repeats, and the second
project silently runs its task inside the first project's leftover directory, on the
first project's branch, with no branch created for it.

This is not hypothetical on this machine. `/Users/ylliprifti/Dev/.snodo-worktrees/`
holds bare task-id directories such as `1.1_a-session-is-minted-hashed-and-revoked` and
`1.2_cards-index-paginated-list` whose `git rev-parse --git-common-dir` points at a
second repository on the same machine (an NFC card project) — leftovers sitting in the
same pool that `snodo-public` dispatches into. A plan-less `snodo run` in any other sibling project with
a colliding task id would be handed one of those.

## What to build

Refuse the reuse when the directory is not this project's workspace, and make the
identity not collide in the first place.

1. **Verify before reuse.** In `create_worktree`
   (`packages/snodo-foundation/src/snodo/infrastructure/worktree.py:535-563`), the
   `if wt_path.exists()` branch must confirm the directory is a worktree whose
   repository is `project_root` — the same check the issue describes: compare the
   worktree's git common directory against the project's, and confirm the checked-out
   branch is the task branch the caller expects. `_task_identity` (`:144-172`) already
   reads `repo.active_branch.name` and `task_worktree_branch` (`:111-116`) exists; use
   them rather than inventing a new probe. On mismatch, raise the existing
   `WorktreeIsolationError` (already used for the unborn-HEAD case at `:577`) with a
   message naming the path, the branch found, the repository it belongs to, and the
   project that wanted it. Never silently run in a foreign tree.
2. **Namespace the identity by project.** Add a project component to the path so
   different projects do not map to the same directory:
   `worktree_path(project_root, task_id, plan_name)` at `:94-99` currently returns
   `worktree_dir(project_root) / _name_component(plan_name) / task_id` or
   `worktree_dir(project_root) / task_id`. Include a `_name_component`-derived project
   name in both shapes. Existing worktrees must keep working — resolve the new path,
   and fall back to the current/legacy shape only when that legacy identity is
   demonstrably this project's own (the same verification as step 1). A migration test
   should show a retry of an in-flight legacy worktree still finds its own work instead
   of starting over.
3. **The reuse message must be honest.** When reuse is legitimate, keep the existing
   INFO line. When it is refused, the log/error is the operator's only clue, so it has
   to say what to do: `snodo worktree remove <task_id>` discards the stale directory.

## Constraints

- Reuse itself is deliberate and must survive: "Retrying must not erase work from a
  halted attempt" (`:558-559`), and operators rely on it after a blocked wave. The fix
  is a provenance check, not the removal of reuse.
- Proof should come from the repository's own worktree list (`git worktree list`)
  rather than by inspecting the directory's contents — the repository knows what it
  registered, and content inspection is guesswork.
- A directory belonging to another repository is never deleted or overwritten. Refusing
  is acceptable; destroying is not. Nothing outside this project's own identity paths is
  touched.
- Don't move the container: `.snodo-worktrees` stays where it is relative to the project
  root. Only the identity shape inside it gains a component, and legacy paths keep
  resolving (see step 2).
- Don't touch the `merge_lock` / branch-creation flow below the reuse branch.
- Keep the existing error vocabulary: `WorktreeIsolationError` and the normal task-failure
  path. No new halt types, severities, validator kinds or statuses.
- Keep the file's existing error taxonomy — `WorktreeIsolationError` is how the engine
  already signals "isolation cannot be guaranteed" and callers already handle it.
- `worktree_dir` layout changes must not break `snodo worktree list` /
  `snodo worktree remove`, which resolve the same identity; update them together and
  test the round trip.

## Acceptance criteria

- A test with two real repositories created under one parent directory by the test
  itself: project A runs a plan-less task, leaving a worktree; project B dispatches the
  same task id and is **refused** with an error naming A's repository and branch — it does not run in A's
  directory. Assert on the message content, not just the exception type.
- A test showing the new identity path for A and B differ, so the two tasks each get
  their own directory and both succeed.
- A test that a legitimate retry in the same project still reuses its own worktree and
  keeps the committed work (branch and file contents preserved).
- A test that a pre-existing worktree in the legacy shape belonging to the same project
  is still reused (no stranding of in-flight task branches), and one belonging to a
  different project is refused.
- CHANGELOG entry under **Unreleased** naming #970.
- `make gate` and `lint-imports` green.
