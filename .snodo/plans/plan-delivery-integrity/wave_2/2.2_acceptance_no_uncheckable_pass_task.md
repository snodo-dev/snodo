INTENT
The post-execute acceptance validator is meant to judge whether the task's acceptance criteria are met. Instead, it passes anything it cannot verify with its read-only tools. It says so in its own justifications:
- "make gate passes (uncheckable by static inspection, marked pass)"
- "required by instructions to return pass when criteria are met or uncheckable"
- "Following standard protocol for uncheckable criteria, we mark this pass"

In these cases the quality validator had actually failed the tests, so acceptance's pass was contradicted. Earlier, job `j_06ccc64c0103` passed with half the work done and no gate run. A validator that passes what it cannot see adds no signal.

When this is done:
- Acceptance judges only what it can check: files, content and the presence of tests.
- For criteria that need execution (tests pass, `make gate` passes, a build succeeds), it defers to the execution evidence the loop already has, such as the quality validator's test result or the recorded verification. It does not treat them as passed.
- If no evidence covers a criterion, its verdict says plainly that the criterion was not verified, and it does not count as a pass.

THE CHAIN
1. The acceptance validator's instructions no longer tell it to pass uncheckable criteria.
2. Acceptance verdicts that cite execution criteria reference the execution evidence they relied on.
3. Tests cover two cases: an acceptance run where a criterion needs execution and there is no evidence does not pass; and one where the quality evidence is a pass does.

CONSTRAINTS
- Snodo's state machine is closed. Use only the existing severities and verdict fields. Add no new severity, status or field.
- Validators judge independently. Acceptance must not treat the coder's own "verified" claims as evidence.
- Don't change the quality validator.
