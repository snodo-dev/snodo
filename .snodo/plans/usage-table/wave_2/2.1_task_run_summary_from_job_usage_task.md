New files this task will create: none.

INTENT
The usage table printed at the end of a task run is filled from the job's usage records, so it appears for plan and queue tasks as well and shows the coder and every validator.

Evidence: snodo/task_usage_summary.py prints the table only from the `usage` list in the task's own state.json (.snodo/tasks/<id>/state.json), and called from snodo/cli/commands/run_cmd.py after the task's closure is reported. For tasks run by plans that list is empty (it was empty for every task of a recent plan), while the job's state.json (.snodo/jobs/<job_id>/state.json) holds the per-call records written by the usage tracker, each carrying job_id, task_id and role; the coder's records carry the task id once the plan's earlier ticket has landed. So the documented end-of-run summary never prints for these tasks.

What it should do: when the task's own state has no usage records, take the job's records that belong to this task (matching task_id, including the recovery rounds named after the task) and print the same table with the same helpers; when the task state has records, behaviour is as today. Nothing is printed when neither has any. The elapsed time shown stays the task's elapsed run time.

CONSTRAINTS
Files that may change: snodo/task_usage_summary.py, snodo/cli/commands/run_cmd.py (only the call that passes what the summary needs) and tests/cli/test_task_usage_summary.py. Also edit CHANGELOG.md: add one entry under [Unreleased] ending "(Fixes #<n>)". Do not change snodo/usage_summary.py, the logs command, the plan runner or the JSON schema. Do not add any state, status, severity or halt type.

ACCEPTANCE
Tests show: with an empty task usage list and job records for this task and another task, only this task's rows and total are printed; with task-state records the output is as before; with no records anywhere nothing is printed; recovery-round records (task ids of the form <task>_fix_N) are included in the parent task's table. `make gate-task` is green.
