# 1.3_demo_verify

## INTENT
After a demo arm finishes, the patch it left behind should be checked against the instance's fail-to-pass tests when the machinery for that exists on the user's machine (Docker plus the swebench harness), and the demo should say plainly that it skipped the check when it does not. One small helper returns that result as a dictionary. The research harness already scores patches: `experiments/scoring.py` has `score_prediction(instance, model_patch, ...)` driving the swebench harness, and it looks up full instance rows from a frozen local dataset; reuse it, do not reimplement scoring. The demo fixture `demo/scikit-learn-26194/instance.json` carries only the ids and test lists, so the full row must be looked up by `instance_id` the way `scoring.py` does it.

## THE CHAIN
1. Open a GitHub issue first ("Demo: fail-to-pass verification helper") and put "Fixes #<n>" in the commit message.
2. Evidence: read `experiments/scoring.py` (its row lookup, what `score_prediction` returns, how it reports failure) and how `tests/test_experiments_scoring_image.py` imports and exercises it. Look at `tests/test_demo_protocols.py` for how modules in `demo/` are imported by tests and follow that pattern.
3. Create `demo/verify.py` with one function taking the instance dictionary and the patch text, plus an optional injectable scorer callable for tests, returning a dictionary with `status` (`resolved`, `unresolved` or `skipped`) and `reason` (short text). `skipped` when the Docker command is not found, when the full row cannot be found, or when the scorer raises; an empty patch is `unresolved` with reason `no patch`; otherwise `resolved` or `unresolved` from the scorer's own result. Importing the module must not require Docker or swebench.
4. Create `tests/test_demo_verify.py`. Use exactly these test function names and keep them unchanged for the whole task, including in any follow-up fix pass (a coverage check fails the task when a test name disappears or is renamed): `test_skipped_when_docker_missing`, `test_skipped_when_scorer_raises`, `test_empty_patch_is_unresolved`, `test_resolved_comes_from_scorer_result`, `test_unresolved_comes_from_scorer_result`. More tests may be added.
5. The project supports Python 3.12; do not use 3.13-only APIs. Before finishing, run `python -m pytest tests/test_demo_verify.py` and do not finish until every test passes (the gate reruns the file and one failing assertion blocks the task); write each expected value from what the code really returns. Also run `ruff check` and `ruff format --check` on every file you touched and fix what they report (remove unused imports and variables). These are checks for you to run; the reviewer does not re-run them.

## CONSTRAINTS
- Do not change `experiments/scoring.py`, `demo/scikit-learn-26194/`, `demo/protocols.py`, `demo/record.py` or anything under `packages/`.
- Add one line under `[Unreleased]` in `CHANGELOG.md`.
- No new states, statuses, severities, halt types or event names in snodo; the `status` values above live only in this demo helper.

## ACCEPTANCE
- The new module returns `resolved`, `unresolved` or `skipped` with a reason, delegating scoring to `experiments/scoring.py` through an injectable callable, visible in the diff.
- The new test file contains the five named tests above.
- Verifiable from the diff of the new module, the new test file and CHANGELOG.md.
