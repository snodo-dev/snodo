# 1.4_demo_report

## INTENT
At the end of a demo arm, the user should see in one place what happened: the outcome, time and tokens, what each validator said, whether the fail-to-pass tests passed, and the patch the model produced. One small helper module collects the patch from the retained worktree and formats that text. The run record it formats is the dictionary produced by `build_record` in `demo/record.py` (keys arm, model, task_id, outcome, halt_type, wall_seconds, input_tokens, output_tokens, cost_usd, cost_source, worktree_path, validator_findings, where each finding has validator_id, severity and justification); that module is correct, do not change it. The verification result is a dictionary with `status` and `reason`.

## THE CHAIN
1. Open a GitHub issue first ("Demo: run report") and put "Fixes #<n>" in the commit message.
2. Evidence: read `demo/record.py` for the exact record keys and which values can be null. Look at `tests/test_demo_record.py` for how modules in `demo/` are imported by tests and follow that pattern.
3. Create `demo/report.py` with: a function that returns the diff between a base commit and the current commit of a given worktree folder using `git diff`, and returns an empty string when the folder is missing or git fails; a function that formats the record, the patch text and the verification dictionary into one plain-text report. Null tokens, cost or time print as `n/a`, never as zero. Each validator finding prints on its own line with id, severity and a bounded part of the justification. A blocked or halted outcome states the halt type. The patch follows the summary.
4. Create `tests/test_demo_report.py`. Use exactly these test function names and keep them unchanged for the whole task, including in any follow-up fix pass (a coverage check fails the task when a test name disappears or is renamed): `test_report_lists_validator_findings`, `test_report_shows_not_available_for_null_values`, `test_report_includes_patch_text`, `test_report_states_verification_status`, `test_collect_patch_returns_diff_from_base` (a small git repository with two commits in a temporary folder), `test_collect_patch_missing_folder_is_empty`. More tests may be added.
5. The project supports Python 3.12; do not use 3.13-only APIs. Before finishing, run `python -m pytest tests/test_demo_report.py` and do not finish until every test passes (the gate reruns the file and one failing assertion blocks the task); write each expected value from what the code really returns. Also run `ruff check` and `ruff format --check` on every file you touched and fix what they report (remove unused imports and variables). These are checks for you to run; the reviewer does not re-run them.

## CONSTRAINTS
- Do not change `demo/record.py`, `demo/protocols.py`, `demo/scikit-learn-26194/` or anything under `packages/`.
- Add one line under `[Unreleased]` in `CHANGELOG.md`.
- No new states, statuses, severities, halt types or event names.

## ACCEPTANCE
- The new module collects a diff from a worktree and formats a report showing outcome, usage with `n/a` for null values, validator findings, verification status and patch, visible in the diff.
- The new test file contains the six named tests above.
- Verifiable from the diff of the new module, the new test file and CHANGELOG.md.
