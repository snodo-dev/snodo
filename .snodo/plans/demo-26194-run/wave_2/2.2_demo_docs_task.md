# 2.2_demo_docs

## INTENT
A visitor who reads the docs can run the scikit-learn-26194 demo with their own model and understand what they are looking at. One guide page, `docs/demo.md`, explains it. The command it documents already exists or is being added in the same release: `python demo/run_demo.py --model <provider/model> [--arm governed|bare|both] [--workdir DIR] [--snodo-version VERSION] [--coder NAME]`. It clones scikit-learn at the task's base commit once per arm, runs the task under the shipped `bugfix-surgeon` protocol (governed) and under a bare variant of it with no validator judging the output and no recovery, and writes a JSON record and a plain-text report per arm. Fail-to-pass verification runs only when Docker and the swebench harness are available, otherwise the report says it was skipped.

## THE CHAIN
1. Open a GitHub issue first ("Demo guide page") and put "Fixes #<n>" in the commit message.
2. Evidence to read before writing: `docs/choosing-models.md` and `docs/coders.md` (how a model string and the LiteLLM coder are chosen, including local and free models), `docs/command-reference.md`, the shipped template `packages/snodo-foundation/src/snodo/protocols/templates/bugfix-surgeon.yml` (what validators it declares and whether it runs the test suite), `demo/protocols.py` (how the bare variant differs) and `demo/record.py` (the record fields). State only what those files show.
3. Create `docs/demo.md` covering, in plain natural prose: what the demo is and which task it uses; the exact command to run it with a hosted model, a free model and a local model, taking model-string forms from the docs above; the snodo version the demo was verified with, taken from the repository's own version metadata, and how to pin it with `--snodo-version`; what the two arms are and how the bare baseline is built; what the report and the record contain; what the shipped protocol does and does not check (state whether it runs the test suite, as the template shows, and that its minimal-diff reviewer is the check that judges the patch); that the task comes from public SWE-bench data whose fix is public, so a model may have seen it and results are a demonstration, not a benchmark; and what to do if Docker is missing (verification skipped). It must not include any results or performance claims.
4. If other user guides appear in the `nav` of `mkdocs.yml`, add the new page there in the matching place. Every relative link in the page must point at a file that exists in the repository.
5. Add one line under `[Unreleased]` in `CHANGELOG.md`.

## CONSTRAINTS
- Do not change the shipped template, `demo/`, `experiments/` or anything under `packages/`.
- Keep the copy soft and natural; avoid "not this but that" contrast phrasing.
- No new states, statuses, severities, halt types or event names.

## ACCEPTANCE
- In the diff, `docs/demo.md` contains the run command with its options, the pinned snodo version, the two-arm explanation, the public-data caveat and the Docker-missing note, and contains no results.
- In the diff, `mkdocs.yml` lists the page when the other guides are listed there.
- In the diff, every relative link in the new page points at an existing file.
- Verifiable from the diff of `docs/demo.md`, `mkdocs.yml` and CHANGELOG.md.
