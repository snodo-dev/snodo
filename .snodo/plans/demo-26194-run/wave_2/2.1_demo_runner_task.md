# 2.1_demo_runner

## INTENT
One command runs the scikit-learn-26194 demo with any model: `python demo/run_demo.py --model <provider/model>`. It runs two arms on the same task from identical fresh clones: `governed` (the shipped bugfix-surgeon protocol) and `bare` (same protocol with no validator judging the output and no recovery), then prints a report per arm and writes a JSON record and the report text per arm to a results folder. The pieces already exist in `demo/` and are correct; this task only wires them, do not change them:
- `demo/protocols.py`: `governed_protocol_text()`, `bare_protocol_text()`, `write_protocol(text, path)`, `validate_protocol(path)`.
- `demo/record.py`: `build_record(...)` (project root, task id, model, arm), `find_new_task_id(before, after)` (listings of `.snodo/tasks/`), `write_record(record, path)`.
- `demo/workspace.py`: loads `demo/scikit-learn-26194/instance.json`, clones the repo at `base_commit`, runs `snodo init --template bugfix-surgeon --yes`, all through an injectable runner.
- `demo/commands.py`: the command prefix (installed `snodo`, or `uvx snodo@<version>`), the full `snodo run` argument list with `--retain-worktree`, and the exact task text from `demo/scikit-learn-26194/task.md`.
- `demo/verify.py`: fail-to-pass result dictionary (`resolved`, `unresolved` or `skipped` with reason).
- `demo/report.py`: patch collection from the retained worktree and the report text.
Read each module for its real signatures before using it.

## THE CHAIN
1. Open a GitHub issue first ("Demo: runner") and put "Fixes #<n>" in the commit message.
2. Create `demo/run_demo.py` with a function that runs one arm: fresh clone in its own folder under the work folder, protocol written for the arm and checked with `validate_protocol` (an unavailable check is reported, not fatal), task ids listed before and after the run, the `snodo run` command executed through the injectable runner, a run record built and written even when the command fails (a failed or crashed run gives the record's `unknown` or error outcome, never `passed`), the patch collected from the retained worktree path in the record, verification run, and the report text written beside the record.
3. Add a `main` taking command-line arguments: `--model` (required), `--arm` (`governed`, `bare` or `both`, default `both`), `--workdir` (default a new temporary folder, printed), `--snodo-version` (optional, pins via `uvx`), `--coder` (optional). It prints each arm's report and the folder holding the records. It must work when started as `python demo/run_demo.py` from the repository root and also be importable by tests (look at `tests/test_demo_record.py` for the import pattern).
4. Create `tests/test_demo_runner.py` using a fake runner that, instead of calling snodo, creates a task folder with a `state.json` the way snodo leaves it (read a real example's field names via `demo/record.py`'s tests). Use exactly these test function names and keep them unchanged for the whole task, including in any follow-up fix pass (a coverage check fails the task when a test name disappears or is renamed): `test_both_arms_get_separate_clones_at_base_commit` (local git repository as the source, no network), `test_each_arm_writes_record_and_report`, `test_bare_arm_uses_bare_protocol_file`, `test_failed_run_still_writes_record_not_passed`, `test_main_requires_model`, `test_arm_option_runs_only_that_arm`. More tests may be added.
5. `CHANGELOG.md` gets one new line under `[Unreleased]` in the same commit, in the style of the neighbouring entries, ending with the issue reference, for example "(Fixes #<n>)". The commit is incomplete without it; the changelog check in the gate reports a commit that closes an issue the changelog does not mention.
6. The project supports Python 3.12; do not use 3.13-only APIs. Before finishing, run `python -m pytest tests/test_demo_runner.py` and do not finish until every test passes (the gate reruns the file and one failing assertion blocks the task); write each expected value from what the code really returns. Also run `ruff check` and `ruff format --check` on every file you touched and fix what they report (remove unused imports and variables). These are checks for you to run; the reviewer does not re-run them.

## CONSTRAINTS
- Never touch the network or the real snodo in tests.
- Do not change the existing `demo/` modules, `demo/scikit-learn-26194/`, `experiments/` or anything under `packages/`.
- No new states, statuses, severities, halt types or event names.

## ACCEPTANCE
- `demo/run_demo.py` runs each selected arm from its own fresh clone with the arm's protocol and writes a record and a report per arm, using the existing helper modules, visible in the diff.
- A failed run still produces a record whose outcome is not `passed`.
- The new test file contains the six named tests above.
- The diff adds one line under `[Unreleased]` in CHANGELOG.md that mentions the issue.
- Verifiable from the diff of the new module, the new test file and CHANGELOG.md.
