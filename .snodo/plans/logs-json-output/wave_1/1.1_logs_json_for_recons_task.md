New files this task will create: tests/cli/test_logs_json_recon.py.

INTENT
`snodo logs <recon id> --json` should print exactly one JSON object describing the recon, so throughput can be computed from it without scraping the text output. It follows the machine interface contract (ADR 022 and docs/machine-interface.md), like every other --json command.

Evidence: `snodo logs rec_079678 --json` fails today with "No such option: --json". The text view of a recon already prints a usage table per agent (role, input tokens, output tokens, model time, output tokens per second) and a total line, built from the recon's state and results files, so all the data exists.

What it should do: add a --json option to the logs command. For a recon id it writes one JSON object to standard output and nothing else (no progress lines, no colour codes). Following the contract, the object carries a schema field of the form snodo.logs.v1 and an ok field (true on success), plus the id, a kind field with the value "recon", the status, the elapsed seconds, a list of agents each with its model, the model that actually served it when known, its status and its usage records, and totals across all agents: input tokens, output tokens, total model call time in seconds and output tokens per second. Reuse the same usage summarising code the text view uses, so both views always agree, and reuse the shared helpers the other --json commands use for the schema name and the error object.

Errors follow the contract too: when --json is given and the id cannot be shown (an id that is neither a recon nor a job, a task id or plan name that this ticket does not cover, or --json together with --watch), standard output carries the uniform error object (schema, ok false, error message), the exit code is non-zero, and no raw text is printed on standard output. Without --json, an unknown id keeps its present behaviour. The text output without --json does not change.

Document the new payload in docs/machine-interface.md, in the same style as the existing commands there: the schema name, the field table and the error behaviour.
