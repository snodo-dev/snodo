# 1.1 — close the rework items left open by the automated reviews of the gate and protection changes

Three small gaps were recorded against work that has since merged. Each was checked against
the current branch before this task was written; the ones that had already been fixed are
deliberately not included here.

## Item 1 — the new gate environment variables are undocumented

`scripts/gate_remote.sh` reads `GATE_SLOT_TIMEOUT` and `GATE_SLOT_PROGRESS_INTERVAL`. Neither
appears in any documentation file: the only place a reader can meet them today is a test that
sets them. The gate script's own behaviour is described in
`docs/specs/gate-remote-process-lifetime.md`, which is where a reader looks for how the gate
bounds a run.

Add both variables to that document, stating what each controls, its default, and the effect
of changing it, in the same shape the surrounding material uses. Correctness of the wording
matters more than volume: a reader should be able to set the variable from the description
alone.

## Item 2 — a swallowed exception is invisible

In `packages/snodo-engine/src/snodo/engine/nodes/validation.py`, the helper that resolves the
repository's base branch catches every exception and returns an empty string. That behaviour
is intended and the docstring says why — the guard still has the captured base ref to work
from, it simply cannot prove a newer fork point. What is missing is any trace of the fact that
resolution failed and why.

Keep the behaviour identical: still return the empty string, still never raise. Emit the
failure at a diagnostic level through the logging facility this package already uses, with the
exception's message, so an operator investigating a diff guard that seems to be working from a
stale fork point can see the cause. Nothing that a test pins by logger name or message wording
may change.

## Item 3 — two sources of protected paths may be the same list

In `packages/snodo-engine/src/snodo/coders/base.py`, the advisory notice that names paths the
engine will refuse builds one list from the protocol's own protected paths attribute and one
from a separately passed argument, and the review judged that redundant.

Investigate before changing anything: read both call sites in `subprocess_adapter.py` and
`opencode_adapter.py` and determine whether the two sources ever differ. If they always carry
the same values at every call site, remove the redundant parameter and its handling, updating
the call sites and any test that passes it. If they can differ, leave the merging as it is and
state in the docstring which source is which, so the next reader does not have to re-derive it.

Whichever way it goes, say so explicitly in the task summary — the reviewer's concern is
answered by the conclusion, not by the size of the diff.

## Acceptance

- The two gate variables are documented where the gate's other configuration is documented,
  with defaults and effects that match what the script actually does.
- A test shows that a base-branch resolution failure is logged and that the helper still
  returns the empty string.
- Either the redundant protected-paths parameter is gone with all call sites updated, or the
  two sources are documented as distinct — and the existing tests that build this notice still
  pass unchanged.
- The engine, tools and scripts suites pass and the linter is clean.

- Do not reopen the items that were already fixed — the bounded-join process teardown, the

## Diff discipline

Confine the change to what this task asks for. Do not reformat, reword, rename or delete code,
comments, docstrings or tests that this task does not change — the rationale notes in this
repository name the issue or incident that produced each branch and are part of the behaviour.
Messages an existing test quotes are a contract with the operator: add new text where this task
needs it, never replace pinned text. New coverage goes in new cases or new files rather than by
rewriting existing ones. Before submitting, look at the diff and remove any hunk that this task's
outcome does not require, then run the whole gate command from the contributing guide and leave
it clean.
