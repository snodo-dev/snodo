# Appending an audit event reads only the end of the log

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
Each audit append takes the log's exclusive lock and then finds the last event, so the new one chains off whatever the last writer persisted. Today it finds that event by reading the whole file line by line. Project logs are now 0.6 to 2.6 GB, so every single event costs a full read of the log, and a run writes hundreds of events. Finding the last event should only need the end of the file, whatever its size. The behaviour stays the same: the same sequence, the same previous hash, under the same lock, and an empty or missing file still starts the chain.

## THE CHAIN
- The audit log lives in `packages/snodo-foundation/src/snodo/infrastructure/audit.py`. The append path re-reads the tail state under the file lock. That was deliberate (Fixes #114): the next event must never chain off in-memory state.
- Other modules already read a bounded tail of the log for "what was the last event". `cloud_liveness.py` in the same package has a fixed tail byte budget, which is a pattern to follow.
- Audit tests live under `tests/infrastructure/`. Check for tests covering concurrent appends, the empty-file start and a trailing blank line, and keep them passing.

## CONSTRAINTS
- The chain semantics are unchanged: the same sequence numbering, the same previous hash, and the read still happens under the exclusive lock.
- It must handle a last line longer than any fixed read window. Single events have reached several MB, so keep reading backwards until a full line is found. It must also handle trailing newlines or blank lines.
- No new audit event, status, severity or halt type.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run --extra dev ruff check` on touched files, and run the audit tests.

## ACCEPTANCE
- Tests show:
  - appending to a large log does not read the whole file (assert on bytes read, or use a stub that fails on a full read);
  - the next event chains correctly after a last line larger than the read window;
  - trailing blank lines and an empty file behave as before;
  - the existing concurrency tests pass.
- There is a CHANGELOG entry under ## [Unreleased].
