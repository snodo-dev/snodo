INTENT
One test in the local gate fails only when the rest of the suite runs in parallel, and the anti-flake ratchet from #912 turns that intermittent failure into a blocker on unrelated producer tasks: an unrelated change halts with quality: blocker and the run is discarded. The test must stop measuring scheduler luck.

WHAT A PREVIOUS ATTEMPT GOT WRONG (do not repeat it)
A prior attempt on this exact specification changed only a docstring in packages/snodo-engine/src/snodo/validators/quality.py (the _get_timeout helper) and left the race untouched. That is a no-op with respect to this task. A diff that does not alter the assertion logic described below does not satisfy this specification, no matter what the gate reports.

THE DEFECT, EXACTLY
File tests/validators/test_quality.py, test tests/validators/test_quality.py::TestQualityValidatorEvaluate::test_timeout_preserves_output_and_kills_process_group (around line 600). Its final two lines are:

    with pytest.raises(ProcessLookupError):
        os.kill(int(child_pid_file.read_text()), 0)

The test drives QualityValidator with tooling timeout 0.3, so the validator times out and kills the test command's process group. The script under test spawns a grandchild (python -c ... time.sleep(30)) and writes its pid to child.pid. The assertion then samples the process table **once**, immediately after the kill. A process that has been signalled but not yet reaped - or not yet scheduled out on a loaded machine - still answers os.kill(pid, 0), so the sample succeeds and the assertion fails with "Failed: DID NOT RAISE ProcessLookupError".

Observed: alone the node passes (6/6 serially on macOS under uv run pytest). Inside the full parallel suite it failed in an engine gate run with "1 failed, 5568 passed, 2 skipped in 113.76s". Confirm the current behaviour yourself before changing anything.

REQUIRED CHANGE
1. In that test only, replace the single immediate sample with a bounded wait: read the pid, then poll os.kill(pid, 0) until it raises ProcessLookupError, sleeping briefly between attempts, with a generous budget (several seconds). If the process is still alive when the budget expires, fail with a message that says the process group was not killed. Keep it readable; a small module-level helper inside tests/validators/test_quality.py is fine, a new utility module in the package is not.
2. Keep every other assertion in the test exactly as it is: result.error is True, result.severity == "blocker", "gate reached slow step" in the justification, "timed out" in the justification, the audit verification_executed outcome "error", and "Timeout after 0.3s" in the audit output_tail.
3. Do not change the validator's timeout: 0.3, do not xfail/skip/delete the test, and do not relax any assertion. The behaviour under test - the gate kills its whole process group including grandchildren, and preserves output - must still be verified.
4. If your investigation shows the grandchild really does survive indefinitely (not merely for a moment), the defect is in the implementation and belongs in packages/snodo-engine/src/snodo/validators/quality.py - fix it there, and state in your report what evidence made you conclude that. Do not paper over a real leak.
5. Add one line under the "## [Unreleased]" section of CHANGELOG.md for the gate-stability fix. Touch only that section; other in-flight branches edit the same block, so do not reflow or reorder anything else in the file.
