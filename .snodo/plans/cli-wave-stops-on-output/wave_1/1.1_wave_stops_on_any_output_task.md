Before starting, open a GitHub issue on snodo-dev/snodo titled "CLI: wave keeps spinning after a command has printed its output". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
After #783 applied the wave to every command, the operator ran `snodo task list` in a terminal. The full rich table printed, and below it the wave was still animating 19.7 seconds in:

  │ 1.1_failed_agent_trace_kept │ task/1.1_failed_agent_trace_kept │ 1 │ completed │ 18h ago │ 2026-10-08 01:04 UTC │
  [▆▄▂▂▄] loading tasks… 19.7s

The contract for `wave_while_silent` (snodo/cli/spinner.py, wired in snodo/cli/slow_commands.py) is to stop and clear at the first real output. Here the output did not stop it. The most likely cause is that the table went through a rich Console, or another handle that writes to the terminal without passing through whatever the spinner watches. For example, a Console created at import time holds the original sys.stdout, or something writes to sys.__stdout__ or straight to the file descriptor. Verify the actual path before fixing.

When this is done:
- Any output to the terminal, on stdout or stderr, stops the wave and clears its line before that output appears. That includes rich Console output (tables, panels, status lines), print(), typer.echo, logging handlers, and direct writes to sys.__stdout__/sys.__stderr__.
- Once any output has appeared, the wave never starts again for the rest of the command, even if the command then goes quiet. It is strictly the indicator for "nothing on screen yet".
- The wave never interleaves with or corrupts output lines, including when the table is printed at the same moment a frame is drawn.
Choose the most robust detection. Hooking the shared console helpers, watching both streams, or detecting at file-descriptor level are all options. Explain the choice in a comment.

THE CHAIN
1. Reproduce the bug with `snodo task list` (and another rich-table command) on a pseudo-terminal. Identify the output path that bypasses detection.
2. Fix the detection, and make the wave one-shot.
3. Tests, using a pty or a fake TTY stream:
   - rich Console output stops and clears the wave;
   - output through a Console created before the spinner started stops it;
   - after output, a later silent stretch does not restart the wave;
   - stdout content is byte-identical with and without the wave.

CONSTRAINTS
