# `snodo ready` checks the installed coder CLI accepts snodo's flags (Fixes #984)

## INTENT
A user with a newer OpenCode than snodo understands should hear about it from `snodo ready`, before a run is dispatched and fails cryptically. Readiness already looks at whether the opencode-cli coder is installed and which version it is; it should additionally notice when the installed major is one snodo has no adapter for, or when the installed CLI's own `run --help` no longer lists a flag snodo sends for that major.

## THE CHAIN
1. In the readiness checker's existing opencode-cli check, after the binary is found and its version read, decide whether snodo has an adapter for that major. Use the set the opencode adapter module already defines, so the two cannot drift; keep no second list.
2. If the major is undescribed, report it as a readiness problem using a finding shape readiness already has, with a soft message naming the installed version and the majors snodo supports.
3. If the major is described, ask the installed binary for its `run --help` once, and check that each flag snodo would send for that major appears in the output. If one is missing, report it with the same existing finding shape, naming the flag and the installed version.
4. If the help text cannot be obtained (binary slow, errors, no output), say nothing extra; readiness must not fail because of an inability to ask.

## SYMPTOM AND EVIDENCE FROM THE TWO PREVIOUS ATTEMPTS
- The first attempt put the whole check into the readiness checker, with its own bare subprocess call to the binary's `run --help`. The gate's lint step failed on that call (rule S603, untrusted-input subprocess) while 5707 tests passed.
- The second attempt then implemented the check again in the CLI command module for `ready` and used the shared probe there, but left the first attempt's bare subprocess call in the checker. The lint step failed on that same untouched call. It also added no readiness tests, and the validators noted the failure as unrelated to the diff.
- So the working tree for this task can still contain leftovers from earlier attempts. Inspect what is there first, and end with exactly one implementation of this check, living in the readiness checker's opencode-cli check, not in the command module. Remove any other copy and any bare subprocess call to the opencode binary, including ones that are not obviously yours.
- The repo's blessed way to probe a host binary is the shared version probe in the coder availability module: resolved binary path with fixed flags, no shell, a time limit, the job-context-free environment, never raises, and a justified suppression comment for the lint rule. Run the help probe through that same mechanism (extend or share it) so no new bare subprocess call is needed.

## CONSTRAINTS
- Reuse existing readiness finding types and severities. Do not add a status, severity, halt type or audit event.
- Do not edit CHANGELOG.md; the first-wave task owns it.
- Do not touch the opencode adapter test file or the fixtures created by the sibling task in this wave.
- Add readiness tests in the readiness test area. They are part of the deliverable.
- The help call must be time-limited and must never run a model or require credentials.
- The gate's lint step must pass for the whole repository state, not only for the files you edited, and no blanket ignore may be added to the project's lint configuration.
- No new dependency. Soft wording.

## ACCEPTANCE
- Faked 3.x version: readiness reports the undescribed-major finding.
- Faked 2.x version whose help text lacks the auto-approve flag: readiness reports the missing flag.
- Faked 2.x version with a complete help text: no new finding.
- Help call failing or timing out: no new finding, no exception.
- A search of the source tree finds no subprocess call to the opencode binary other than through the shared probe.
- Targeted readiness tests pass and the lint step is clean for the whole tree.
