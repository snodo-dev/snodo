# A provider block can route some of its models over a different API format

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
Users configure gateway providers as custom blocks in `~/.snodo/config.yml`, with a base URL, a credential and one `litellm_provider` (usually `openai`). Some gateways serve different model families over different API formats behind one key and one host. OpenCode Go (configured by users as `ocgo`) is an example: DeepSeek, GLM, Kimi and MiMo are on its OpenAI-compatible `/v1/chat/completions` endpoint, while Claude models (and, per its docs, MiniMax and Qwen) are on its Anthropic-compatible `/v1/messages` endpoint.

snodo turns every model of a block into "<litellm_provider>/<id>". So "ocgo/claude-haiku-5-5" goes to LiteLLM as "openai/claude-haiku-5-5", and the gateway refuses it: "Model does not support this protocol". The only workaround is a second, duplicate provider block with its own copy of the credential.

A provider block should be able to say "models whose id matches this go over that LiteLLM route", for example `claude-*` over `anthropic`. Those models then reach the gateway in the right format, with the same credential and the matching base URL. Everything else in the block keeps the block's default route.

## THE CHAIN
- The user-config provider model is in `packages/snodo-core/src/snodo/config.py`, with the strict config schema in `packages/snodo-core/src/snodo/config_validation.py`. The ConfigManager resolves the LiteLLM route, the LiteLLM model string and the base URL for a model. Validators, the litellm coder, the classifier, recon, `snodo models --check` and `snodo models --benchmark` should all already resolve through it. Confirm that, and fix any caller that bypasses it.
- An Anthropic-format client builds its own request path, so a base URL that ends in the OpenAI-style `/v1` may need adjusting for the Anthropic route. Make it work for a base URL configured as `https://opencode.ai/zen/go/v1`, with or without that suffix.
- Configuration docs: `docs/configuration.md`, the provider block table and the `snodo config set providers.*` examples. Typed `snodo config set/get` key paths should accept the new field if it fits their shape; otherwise document editing the YAML.
- There are two strict user-config schemas that must stay in step. Check `snodo/` for the other one and update both.

## CONSTRAINTS
- Existing configs behave exactly as today. The new field is optional, and when it is unset nothing is emitted for it.
- Keep matching simple and predictable: model-id prefixes or simple glob patterns, first match wins, documented.
- No network calls in tests. Use the existing LiteLLM stubbing to assert the route, model string and base URL that LiteLLM receives.
- No new top-level CLI command. No new audit event, status, severity or halt type.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run --extra dev ruff check` on touched files, `uv run lint-imports`, and the config, model-resolution and models-command tests.

## ACCEPTANCE
- Tests show:
  - a block with an OpenAI default route and a `claude-*` rule to the Anthropic route sends "ocgo/claude-haiku-5-5" as an Anthropic-format call to the right base URL with the block's credential;
  - "ocgo/glm-5.3-flash" in the same block stays on the OpenAI route;
  - a config without the field resolves exactly as before;
  - both config schemas accept the field and reject a malformed value.
- The configuration docs show an OpenCode Go example.
