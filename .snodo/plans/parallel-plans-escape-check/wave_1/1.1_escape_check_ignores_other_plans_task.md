INTENT
While a coder runs, the engine checks that no branch outside the task's own namespace moved, which catches a coder that commits into an operator checkout. That check should not count branches that belong to other plans running at the same time.

Evidence: job j_2e52c3fa0493 (plan logs-json-output), task 1.1: the coder finished, then post-validation was skipped with "Workspace escape detected: ref 'plan/validator-fallback-chain/integration' changed in external checkout(s)". The branch had been advanced by a different plan running in another queue (queues run in parallel by design, ADR 053). The coder never touched it. Every concurrent plan advances its own integration branch and creates task branches, so with two or more plans running, tasks keep getting blocked for something no coder did. A clean task is lost and has to be rerun.

What it should do: when deciding which moved branches count as an escape, leave out branches that belong to a plan other than the one this task belongs to (that plan's integration branch and its task branches). Everything else keeps being reported exactly as today: the task's own plan branches, any operator branch such as main, and any other branch. The checkout-content comparison for host runs is untouched. If the current plan cannot be determined, behave as today (nothing is excluded).

CONSTRAINTS
Files that may change: packages/snodo-engine/src/snodo/engine/nodes/executor.py and the tests that cover its escape check under tests/engine/. Also edit CHANGELOG.md: add one entry under [Unreleased] ending "(Fixes #<n>)". Do not change message wording for real escapes. Do not add any state, status, severity or halt type.

ACCEPTANCE
Tests show: a moved integration branch and a moved task branch of another plan during a run give no escape; a moved branch of the task's own plan is still an escape; a moved main (or any operator branch) is still an escape; with the plan unknown, an other-plan branch is still reported as before. `make gate-task` is green.
