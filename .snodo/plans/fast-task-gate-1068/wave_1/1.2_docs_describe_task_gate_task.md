## Intent
CONTRIBUTING describes two gates; there is about to be a third, a fast per-task check, and a reader should be able to tell which one to run and which one decides.

## Evidence
- CONTRIBUTING.md "Testing and checks" says "There are **two gates, and they are not the same**": the local fast `pytest tests/` loop and the gate CI runs.
- A new `make gate-task` target (added by a later task of the same plan, not yet present) will run the same ruff, import-contract and ratchet steps as `make gate`, with only the tests the diff touches (chosen by `scripts/select_affected_tests.py`), and the full suite stays with CI, the release dry run and `make gate`.
- docs/specs/gate-remote-process-lifetime.md and docs/specs/gate-output-line-endings.md describe `make gate` and `make gate-ci`.

## Outcome
- CONTRIBUTING says there are three checks, names each (`make gate-task` for a task's own change, `make gate` for the full fast suite, the CI gate that decides), and says plainly that only the last decides.
- It says that `gate-task` selects tests from the diff against the merge base, falls back to the whole suite when a shared file such as pyproject.toml or the protocol changes, and runs no tests when only docs change.
- The two gate spec documents mention `gate-task` where they list the gate targets, without restating what the other targets do.
- The strict docs build and local anchor checks still pass (`make docs`), and `make gate` passes.
