## Intent
Make a running recon write its progress to the event log that the earlier task of this plan added, so something can be watched while agents work.

## Evidence
- `call_agent` in packages/snodo-mcp/src/snodo/recon/__init__.py runs the read-only tool loop for one agent and `call_agent_chain` tries a lane's models in order; neither reports anything until the final result. `ReconManager._run_recon_impl` fans the lanes out on a thread pool and has no way to tell an agent which recon directory to write to. Other callers (the survey and judge code) call `call_agent_chain` and `call_agent` directly and must keep working unchanged.
- The event log module from the previous wave of this plan provides the append operation and the record kinds.

## Outcome
- `call_agent` and `call_agent_chain` accept an optional observer (a callable taking an event) that defaults to none; with none given, behaviour and results are exactly as today.
- When an observer is given: an agent-started event is emitted when a model begins, a tool-turn event for each batch of read-tool calls (tool names with short argument summaries), a failover event when a lane moves to its next model or retries after a transient error, and an agent-finished or agent-failed event at the end of each model attempt.
- `ReconManager` creates the event log for the recon directory and passes each lane an observer that stamps the lane position, so every event can be attributed to its lane even when two lanes share a model.
- An observer that raises is ignored and never changes the recon's outcome.
- Existing recon tests and the survey and judge tests pass unchanged; new tests cover a two-lane recon with a stub model that makes tool calls and asserts the events written (kinds, lane positions, order within a lane), a failover, a raising observer, and the default of no observer.
- `make gate` passes.
