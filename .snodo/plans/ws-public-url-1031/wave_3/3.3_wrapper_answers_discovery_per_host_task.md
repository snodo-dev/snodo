# 3.3 — the tunnel wrapper answers discovery and tells the verifier the host

GitHub issue #1031 already exists for this work. Do not open another; put "Fixes #1031" in the commit message. Do not edit the CHANGELOG (the last task in this plan owns the entry).

## Context (same for every task in this plan)

`snodo serve --tunnel --tunnel-transport ws --public-url` opts in to a second, public address for a ws serve: an alias of the form `<random label>-pub.snodo.dev`, issued by snodo cloud, that outside MCP clients can use. Without the flag nothing changes. The machine reaches the cloud over one outbound relay connection that runs in the serve parent process; the MCP server is a child process on loopback; the relay forwards each cloud request to the child as `http://127.0.0.1:<port>` and relayed requests carry no Host header. Each relayed request frame has a `hostname` field: the host the caller used, the private host for Dispatch and the alias for a public request. Contract with the cloud side (settled in the exchange file, 2026-10-25):

- Provision: the request carries `public_url: true` when the flag is given. A ws response always carries `org_id` and has `public_hostname` when an alias exists. A repeat call with `public_url: true` returns the full body with the same active alias (or a new one if the old was released after 7 idle days); a repeat call without it never drops or changes an alias.
- Hello: `endpoints` lists both hostnames, each with `auth: ["oauth"]`.
- The serve allows exactly the private host and the alias, nothing else, for the Host check, the token audience and the discovery document. A token must match the audience of the host it arrived on. `/.well-known/oauth-protected-resource` is answered per request host as `https://<host>/mcp`.
- A token whose `org_id` differs from the provisioned one is refused with 403. `sub` is not used. No owner checks.
- The alias is kept in the local tunnel config; serve prints the public MCP URL at every start with the flag and says clearly when it differs from the last one printed.
- No new state, severity, halt type or status value anywhere.

## INTENT

The wrapper in front of the HTTP apps (`snodo/cli/commands/serve_tunnel_asgi.py`, `install_tunnel_mcp_paths`) is the one place that sees every request before the MCP SDK does. With two public hosts it has to record, for each request, which of the serve's known hosts the request arrived on so the verifier (earlier task) can pick that host's audience, and it has to answer `/.well-known/oauth-protected-resource` for that host (`resource` = `https://<host>/mcp`), where the SDK's route today answers with the one URL fixed at start.

## Evidence

```text
- install_tunnel_mcp_paths(mcp, verifier, *, oauth_enabled, access_path="mcp-st") wraps both streamable_http_app and sse_app; the wrapper chain is TunnelMCPPaths -> _MissingAuthorizationObserver (packages/snodo-mcp/src/snodo/mcp/transport.py) -> Starlette app.
- AuthSettings.resource_server_url is a single URL set once in serve_cmd.py; the SDK serves the metadata route from it.
- tests/mcp/test_tunnel_host_protection.py drives the real wrapper with real SDK apps; tests/mcp/test_auth.py covers the metadata route.
```

## Outcome

- The wrapper can be told the set of hosts the serve answers for. When it is, each request's host (from the Host header) is checked against that set; a request on any other host is refused the way the SDK refuses a bad host today; the host is recorded for the verifier for the duration of that request only.
- For a request on a known host, the discovery document is answered for that host and for no other. When the wrapper is not given a host set, nothing changes, including the discovery document.
- The host is read only from the request's Host header (the relay sets it, earlier task); nothing else, such as a forwarded-host header, is trusted.

## Acceptance
