# 2.1 — the 401 challenge points at the discovery document of the host the request arrived on

GitHub issue #1032 already exists for this work. Do not open another; put "Fixes #1032" in the commit message. Do not edit the CHANGELOG (task 1.2 owns the entry).

## Context (same for every task in this plan)

A ws serve with `--public-url` answers on two hosts: the private host and a public alias `<label>-pub.snodo.dev` (shipped in #1031). The wrapper `TunnelMCPPaths` in `snodo/cli/commands/serve_tunnel_asgi.py` already checks the Host header against the known hosts, tells the verifier which host the request arrived on, and answers the unsuffixed `/.well-known/oauth-protected-resource` per host. Two places still name the private host when the request came in on the alias (found in the first live check by snodo cloud, exchange file 2026-10-26 14:10Z; MCP clients such as the Claude connector fail to register because of them):

- `GET https://<alias>/.well-known/oauth-protected-resource/mcp` (the RFC 9728 path-suffixed form, the one MCP clients use) comes from the MCP SDK and returns `resource: https://<private host>/mcp`, because the SDK builds it once from the single `resource_server_url` fixed at start. It carries `authorization_servers: ["https://mcp-auth.snodo.dev/"]`.
- The `401` challenge for a missing or bad token carries `www-authenticate: Bearer error="invalid_token", ... resource_metadata="https://<private host>/.well-known/oauth-protected-resource/mcp"`, also from the SDK and also built from the one URL.

Clients compare `resource` with the URL they connected to and follow `resource_metadata` from the challenge, so both must name the host the request arrived on. The same rule holds for the private host. The relay already sets Host from the caller's host; the wrapper reads only the Host header and trusts no forwarded-host header. Cloud needs no change.

Rules for the whole plan: the Cloudflare path and a serve with no host set behave exactly as today; no new state, severity, halt type or status value anywhere; the 403 for another organization and the 421 for an unknown host keep their current behaviour and order.

## INTENT

When the SDK answers 401 (missing, malformed or rejected token), its `www-authenticate` header contains `resource_metadata="https://<private host>/.well-known/oauth-protected-resource/mcp"`. For a request on a known host the wrapper must make that URL name the request host (the same `/.well-known/oauth-protected-resource/mcp` path, the host replaced), so a client that follows it gets the document from the host it is talking to.

## Evidence

```text
- The header is produced by the SDK's RequireAuthMiddleware from the single resource_server_url, inside the app the wrapper calls.
- The wrapper already sits in front of that app, so it can wrap `send` for the request and adjust the header on the `http.response.start` message. This does not start a second response (an earlier attempt in #1031 that decided too late produced a double http.response.start; do not call send twice for the start message).
- 1.1 of this plan answers the two documents in the wrapper.
```

## Outcome

- For a request on a known host, any `www-authenticate` header on the response whose `resource_metadata` URL names a different known host is rewritten to name the request host; headers without that parameter, other headers, the status and the body are untouched. Responses that are not 401 pass through unchanged.
- Works for both the private host and the alias, and for a loopback Host mapped to the private host. Without a host set nothing changes.
- Streaming bodies and further messages are passed on untouched.

## Acceptance

- Tests with the real wrapper and real SDK app: a request without a token on the private host and on the alias each get 401 whose `resource_metadata` names that host; a request with a valid token is unaffected; the existing 403 and 421 tests pass unchanged.
- The linter is clean.

## Constraints

- Only serve_tunnel_asgi.py and tests. Never trust a forwarded-host header.
