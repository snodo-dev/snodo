# 1.1 — both well-known discovery documents name the host the request arrived on

GitHub issue #1032 already exists for this work. Do not open another; put "Fixes #1032" in the commit message. Do not edit the CHANGELOG (task 1.2 owns the entry).

## Context (same for every task in this plan)

A ws serve with `--public-url` answers on two hosts: the private host and a public alias `<label>-pub.snodo.dev` (shipped in #1031). The wrapper `TunnelMCPPaths` in `snodo/cli/commands/serve_tunnel_asgi.py` already checks the Host header against the known hosts, tells the verifier which host the request arrived on, and answers the unsuffixed `/.well-known/oauth-protected-resource` per host. Two places still name the private host when the request came in on the alias (found in the first live check by snodo cloud, exchange file 2026-10-26 14:10Z; MCP clients such as the Claude connector fail to register because of them):

- `GET https://<alias>/.well-known/oauth-protected-resource/mcp` (the RFC 9728 path-suffixed form, the one MCP clients use) comes from the MCP SDK and returns `resource: https://<private host>/mcp`, because the SDK builds it once from the single `resource_server_url` fixed at start. It carries `authorization_servers: ["https://mcp-auth.snodo.dev/"]`.
- The `401` challenge for a missing or bad token carries `www-authenticate: Bearer error="invalid_token", ... resource_metadata="https://<private host>/.well-known/oauth-protected-resource/mcp"`, also from the SDK and also built from the one URL.

Clients compare `resource` with the URL they connected to and follow `resource_metadata` from the challenge, so both must name the host the request arrived on. The same rule holds for the private host. The relay already sets Host from the caller's host; the wrapper reads only the Host header and trusts no forwarded-host header. Cloud needs no change.

Rules for the whole plan: the Cloudflare path and a serve with no host set behave exactly as today; no new state, severity, halt type or status value anywhere; the 403 for another organization and the 421 for an unknown host keep their current behaviour and order.

## INTENT

For a request on a known host, the wrapper answers `/.well-known/oauth-protected-resource` and `/.well-known/oauth-protected-resource/mcp` itself, each with `resource` = `https://<request host>/mcp`, instead of leaving the suffixed form to the SDK. The document must carry the same fields the SDK's own document carries today (read them from the installed SDK's protected-resource metadata, including `authorization_servers` from the configured issuer), so a client that read the SDK's document before reads an equivalent one now, only with the right host. The unsuffixed form today carries `resource` alone; it should carry the full set too.

## Evidence

```text
- serve_tunnel_asgi.py: __call__ answers only the unsuffixed path, through _protected_resource(send, host) which returns {"resource": ...} alone.
- serve_ws_auth.py builds AuthSettings(issuer_url=https://mcp-auth.snodo.dev, resource_server_url=<private host>/mcp, ...). The SDK builds the suffixed document from resource_server_url.
- Live result on the alias: suffixed form returns resource=https://<private host>/mcp with authorization_servers ["https://mcp-auth.snodo.dev/"].
- tests/mcp/test_tunnel_host_protection.py drives the real wrapper with real SDK apps.
```

## Outcome

- On a known host (private, alias, or a loopback Host mapped to the private host) both paths answer 200 JSON with the host's own `resource` and the issuer-derived `authorization_servers`, plus any other field the SDK document carries; `cache-control: no-store` as the unsuffixed answer has today.
- The wrapper needs the issuer to build `authorization_servers`. Prefer reading it where the wrapper is installed (the call site that already holds the AuthSettings) and passing it through `install_tunnel_mcp_paths` as an optional argument; when it is not given, the documents are answered without `authorization_servers`. Keep any call-site change to the one argument and keep serve_cmd.py under the file-length limit (it is near 1000 lines; put any new logic in serve_ws_auth.py or serve_tunnel_asgi.py).
- A request on an unknown host still gets 421. Without a host set nothing changes.
