# Pin the deferred acceptance pass to its own model's provider (Fixes #993)

GitHub issue #993 already tracks this work. Put "Fixes #993" in the commit message.

## INTENT
The acceptance validator runs in a second pass after the other post-execute validators, so it is dispatched through its own code path in the validator runner. #991 tested a pinned validator in the main pass. Add the same protection for the acceptance pass, so a later change to either path cannot quietly send the acceptance judge to the default provider.

## EVIDENCE FROM THE PREVIOUS ATTEMPT
The previous attempt wrote the new test file (tests/engine/test_deferred_acceptance_provider_binding.py, still in the workspace) and it failed. The reason is a wrong assumption in the test, not in production code: the validator of type quality is an execution validator. It runs the real verification in the workspace and makes no model call at all. In the test it came back as a blocker ("Verification failed: tracked files were dirty before tests ran") and, having made no model call, it left nothing for the "default provider" assertions to find. Its only role in this scenario is that the runner defers the acceptance validator to the second pass whenever a quality-type validator is in the run.

## THE CHAIN
1. Keep the quality-type validator in the run only to put the acceptance validator on the deferred path, and give it a stand-in so it does not execute real verification and returns a pass: use whatever seam the runner already offers for replacing validator dispatch, or the way other runner tests neutralise execution validators. Look at how existing tests do it before inventing anything.
2. Put a second, ordinary model-backed validator on the default model in the same run (a plain model-judge type, as the #991 two-provider test uses, in the same post-execute phase) so there is a default-provider call to compare against. Assert the default-provider expectations on that validator, not on the quality one.
3. Pin the acceptance validator to a model on a provider with a different base URL and key than the role default, run through the normal runner entry in the post-execute phase with a recording stand-in for the model call, and assert its calls reach its own provider's base URL, key and routing name, and none carries the default provider's.

## CONSTRAINTS
- Only the test file changes (rewrite the existing one in the workspace); no production code changes. If production changes look necessary, stop and say what is missing instead of making them.
- No network, no real keys, no new third-party dependency.
- Do not touch CHANGELOG.md.
- Do not add a status, severity, halt type or audit event.
- Do not buy the pass by loosening assertions or skipping.
- Targeted tests only: run the new test and the #991 two-provider test and report the output.

## ACCEPTANCE
- The acceptance validator's calls carry its pinned model's base URL, key and routing name; none carries the default provider's.
- The default-model validator's calls carry the default provider's.
- The acceptance validator really took the deferred pass (the test would fail if it were dispatched in the main pass with no quality-type validator present, or say so in a comment of one line).
- The test passes and lint is clean for the whole tree.
