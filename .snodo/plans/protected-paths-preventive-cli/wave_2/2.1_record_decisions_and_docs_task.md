INTENT: The written record of how protected paths work should match how the product actually behaves. Today the decisions record describes post-execution diff detection as the enforcement level and states plainly that the work deliberately does not prevent writes, and the operator documentation describes the declaration without saying what it is compared against or that coders are told about it in advance. Wave 1 of this plan changes two things that those documents must account for: CLI coders are now told, before they run, which paths are off-limits (a request, not a boundary), and the post-execution guard measures a task's changes from the branch's common ancestor with the base rather than from a base ref that a rebase can leave behind, so commits that arrived from the base branch are no longer blamed on the task.

OUTCOME: There is a decisions record that succeeds the existing detection-first record and explains where advisory prompt guidance sits relative to it: it is not a new enforcement level, it claims no boundary, and the post-execution diff remains what actually rejects a task. That record also captures the corrected comparison basis and what it means for the evidence detection produces. The existing detection-first record is left intact as dated history apart from a pointer so a reader does not conclude the new guidance contradicts it, and the decisions index makes the new record findable in the same style as its neighbours. The operator-facing protocol documentation tells an operator what a protected path declaration does, what the task's changes are compared against, and that the declarations are also surfaced to CLI coders beforehand as guidance. A reader of the operator documentation alone can state all of that without opening source.

CONSTRAINTS: Documentation only. No file under the packages directories changes in this task: the behaviour being described is already committed by wave 1, and if the code and the existing records disagree, the records win and the disagreement is reported rather than quietly fixed here. The new record takes the next free number in the repository's existing decisions sequence and does not renumber history. The earlier record is amended only by a status pointer; its context, decision, and alternatives stay as written. Shipped protocol templates keep the protected paths declarations they already have, including the empty ones. Nothing in the wording may suggest the coder is sandboxed or that writes are blocked, because the reason is documented in the existing record.

ACCEPTANCE: The new decisions record exists, is listed in the decisions index, and is cross-referenced by the record it succeeds. Reading the operator documentation answers what a protected path is, when it is checked, what it is checked against, and that coders see it in advance. The golden template tests still pass, showing no shipped template gained or lost a declaration. The change set for this task touches only documentation.
