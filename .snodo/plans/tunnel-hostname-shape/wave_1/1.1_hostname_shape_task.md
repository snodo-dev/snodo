Title: Recognise the cloud's real tunnel hostname shape

Start by opening a GitHub issue in snodo-dev/snodo describing this change (pass the body with --body-file), or reuse an open one that already covers it. The commit message must include "Fixes #<issue number>". Add an entry to CHANGELOG.md under [Unreleased].

INTENT
The cloud issues managed tunnel hostnames as a single label directly under snodo.dev, shaped "<slug>-<mode>-<short>-tunnel.snodo.dev" (for example "nfc-card-v2-build-iy4ssd-tunnel.snodo.dev"). This is its canonical form: a third-level name is covered by the zone's certificate, while a fourth-level "x.tunnel.snodo.dev" would not be. The CLI still assumes the older ".tunnel.snodo.dev" suffix, so it misreads every real hostname.

THE CHAIN
- When provisioning returns a conflict (one tunnel per project and mode already exists), the CLI pulls the blocking hostname out of the reply with a pattern that only matches ".tunnel.snodo.dev". A real hostname never matches, so the operator is not told which tunnel to delete.
- The warning for hostnames that can never serve TLS (a name with an extra dot before the tunnel domain) keys on the same old suffix, so it never runs against real names. With the new shape the rule is: the hostname must be exactly one DNS label in front of snodo.dev, and that label ends in "-tunnel".
- The tunnel spec in the docs still describes the old shape.

CONSTRAINTS
- Recognise the new shape. Names in the old ".tunnel.snodo.dev" shape may still appear in older local records; treat them as recognisable for delete and conflict messages, and as unservable for the warning, since no certificate covers them.
- Keep the matching strict: a single lowercase DNS label, no embedded dots, ending in "-tunnel" before snodo.dev.
- Update tests and fixtures that use the old shape, and the tunnel spec doc.
- The serve command module is over the file-length ratchet; do not make it longer.
- Run `uv run --extra dev ruff check` on changed files and only the serve and tunnel tests plus any you add. Tests must not touch the real home folder. Do not run the snodo CLI, make gate or make release, and do not touch .snodo/.

ACCEPTANCE
- A conflict reply naming "nfc-card-v2-build-iy4ssd-tunnel.snodo.dev" yields that hostname in the operator message.
- A hostname with a dot before "-tunnel.snodo.dev", or in the old ".tunnel.snodo.dev" shape, triggers the unservable warning; a normal new-shape hostname does not.
- No test or doc still presents ".tunnel.snodo.dev" as the shape the cloud issues.
- ruff reports no errors on the changed files.
