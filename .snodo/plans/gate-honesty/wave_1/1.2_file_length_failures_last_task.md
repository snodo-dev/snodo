# File-length ratchet failures are cut off from the gate's output tail

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
When `scripts/enforce_file_length.py` fails, the lines naming the offending files are at the end of its output. The tail that snodo's quality validator and the orchestrator see then always says which file broke the ratchet.

## THE CHAIN
- Evidence: during the overnight plans of 2026-10-10, several tasks were blocked by the file-length ratchet. The gate failure's output tail, which is what the validator verdict carries, showed the summary table but not the offending file, so each coder had to rerun the script to find it.
- In `main()` of `scripts/enforce_file_length.py`, the `FAIL:` lines are printed first, then `render_summary(report)`, then the count. A long summary pushes the FAIL lines out of a bounded tail.

## CONSTRAINTS
- Keep the same information. Reorder so the failures (each naming its file, current length and allowed length) come last, after the summary, ending with the count line. Repeating them after the summary is fine too.
- Do not change the ratchet's rules, the baseline format or exit codes.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run ruff check` on touched files. Run only the targeted tests for this script.

## ACCEPTANCE
- A test with a failing file and a non-empty summary shows that the last lines of output name the failing file, and the final line is the violation count.
- There is a CHANGELOG entry under ## [Unreleased].
