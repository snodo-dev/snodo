# Blocked-task guidance doesn't say how to reset the retry counter

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
When a plan task is blocked (including at max retries), the guidance snodo prints and returns names the concrete action that gives the task a fresh attempt budget, both for MCP and for the CLI. An orchestrator following it then never stalls on an exhausted counter.

## THE CHAIN
- Evidence: an orchestrator edited a blocked task's spec file by hand, as "replace its spec, then run that wave" seemed to invite. The rerun stopped at max_retries again, because only regenerating the spec through MCP `generate_spec` with `replace=true` resets the counter.
- The wording "replace its spec, then run that wave" appears in `snodo/cli/commands/plan_delivery.py` (around line 87) and `packages/snodo-mcp/src/snodo/mcp/plan_handlers.py` (around line 151). A similar line is in `packages/snodo-foundation/src/snodo/infrastructure/next_actions.py` (around line 43).
- Find what actually resets the counter (spec hash change through the spec-generation path, or whatever it is). Name that action explicitly: the MCP call `generate_spec(..., replace=true)` and the CLI equivalent. Also say that hand-editing the spec file does not reset it, if that is still true.
