# Concurrent OAuth refreshes can burn the refresh token

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
When the OAuth access token expires while several snodo processes are running (serve, background jobs, parallel task processes), exactly one of them refreshes it. The others wait and use the token that one saved, so a rotated refresh token is never sent twice. When a refresh does fail, the reason is logged (never the token itself), so the next person debugging it sees why.

## THE CHAIN
- Observed: a machine logged in with OAuth, running a plan with 3 parallel tasks, stopped syncing right at access-token expiry. Eight hours later `snodo cloud status` still said "expired; next sync will refresh it", with a refresh token present.
- Recon rec_267c88 traced it. `resolve_cloud_credential` (`packages/snodo-foundation/src/snodo/infrastructure/cloud_credentials.py`, around lines 14–37) works in three separate steps:
  - it loads the state under the file lock (`load_oauth_state`, `cloud_oauth_store.py`);
  - it releases the lock and calls `client.refresh(...)` over HTTP;
  - it saves under the lock again (`save_oauth_state`).
- Nothing stops two processes from refreshing with the same refresh token at once. With refresh-token rotation, the second request presents a token that is already spent.
- A refresh exception is swallowed with no logging (`except Exception: return None, True`, around line 27).

## CONSTRAINTS
- Serialise the whole check, refresh and save sequence across processes. After taking the lock, re-read the stored state: if another process has already refreshed and the token is no longer near expiry, use it without refreshing.
- `load_oauth_state` and `save_oauth_state` take the same flock. Avoid nesting in a way that deadlocks within one process. Threads inside `snodo serve` must also be safe.
- Keep the lock bounded: the refresh HTTP call already has a timeout. Never hold the lock indefinitely.
- On failure, log one warning naming the failure type: network error, HTTP status, or OAuth error code such as `invalid_grant`. Never log token values.
- Keep the public signatures of `resolve_cloud_credential` and `safe_cloud_sync_credential` unchanged.
- No new status, severity, halt type or audit event.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo. Tests use a temporary snodo home.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the cloud credential and OAuth store tests.

## ACCEPTANCE
- Tests show:
  - two concurrent resolvers (threads or processes) with an expired token cause exactly one refresh call, and both return the new token;
  - a resolver that finds a fresh token on disk after taking the lock does not refresh;
  - a failed refresh logs a warning with the failure reason and no token text.
