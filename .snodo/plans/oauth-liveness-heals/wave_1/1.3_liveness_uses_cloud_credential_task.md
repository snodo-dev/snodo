# Liveness ignores the OAuth login

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
Liveness authenticates the same way audit sync does: the OAuth login when there is one (refreshed when needed), otherwise the configured API key. Someone who only ran `snodo cloud login` gets liveness, and an OAuth 401 during liveness gets the same one-refresh retry audit sync gets.

## THE CHAIN
- Recon rec_267c88, confirmed in the code: `_post_snapshot` in `packages/snodo-foundation/src/snodo/infrastructure/cloud_liveness.py` (around lines 586–627) reads only `cloud.api_key` and returns early when it is empty. It then calls `get_admission_lease(api_key, ...)` without `oauth=True`, so the lease's 401 refresh retry (`cloud_lease.py`, around line 214) never runs for liveness.
- Audit sync already resolves its credential with `safe_cloud_sync_credential` (`cloud_sync.py`, around line 1293), which prefers OAuth and falls back to the API key.

## CONSTRAINTS
- Reuse `safe_cloud_sync_credential` and pass `oauth` to `get_admission_lease` to match what it returns. Don't copy the resolution logic.
- Keep liveness cheap and non-blocking; it must never raise into the caller. With no usable credential it does nothing, as today.
- Don't change the snapshot payload or the endpoint.
- No new status, severity, halt type or audit event.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the liveness tests.

## ACCEPTANCE
- Tests show:
  - an OAuth-only configuration pushes liveness with the access token and `oauth=True`;
  - an API-key-only configuration behaves as before;
  - with both present, OAuth is used, matching audit sync;
  - no credential means no push and no exception.
