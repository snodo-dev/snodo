## Intent
A plan run should hand each task a tree that matches what the operator sees on main, including work the orchestrator hand-merged mid-plan, so a task is never judged against code that already exists or built on a base that lacks it.

## Evidence
- Recent plan, waves 1 to 5: two tasks were hand-merged to main after review. The plan's integration branch was cut at plan start and never picked those commits up. A later task's worktree lacked a module that main had, so acceptance reported a half missing for work that was fine; two docs tasks were escalated at pre-execute because their base lacked a decision record and a command group that were already on main, and their specs had to be rewritten.
- The integration branch is checked out in a worktree on the host, so an orchestrator cannot safely move its ref by hand.
- In snodo/cli/commands/plan_run.py, `_run_plan` creates the integration branch and worktree when the plan starts, and child task jobs are based on that branch; delivery helpers are in plan_delivery.py.

## Outcome
- Before each wave starts, if main contains commits the integration branch lacks, the integration branch is brought up to date (a fast-forward when main contains it as an ancestor; otherwise a merge of main into it), and the wave's tasks start from the updated head. A conflict stops the wave with a clear message naming the conflicting files; it never discards work.
- A hand-merge recorded with `record_task_status` is reflected in what the next wave sees.
- An existing integration branch is updated in place, never replaced.
- Tests: a plan where main gains a commit between waves and a later task needs it; a conflicting main commit stops the wave clearly; the up-to-date case changes nothing.
- `make gate` passes.
