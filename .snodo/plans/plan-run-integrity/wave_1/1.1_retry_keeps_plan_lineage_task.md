## Intent
Retrying a job that belongs to a plan run should keep it part of that plan, so the retry's outcome reaches the plan's status. If that cannot be done safely in some case, the retry should say so plainly instead of running detached.

## Evidence
- Plan dispatch gives each child task job its plan, wave, parent job and the integration base when it submits the job; read how it does that and reuse the same fields.
- `handle_retry_job` in packages/snodo-mcp/src/snodo/mcp/server.py rebuilds the task arguments from the description, working directory, task id, continuation and mode only, so the plan fields are dropped; it refuses queue-run and plan-run jobs but not plan child tasks. The job wrapper (packages/snodo-mcp/src/snodo/jobs/wrapper.py) then clears the plan environment, and plan child selection requires the parent job to match the latest plan run, so no poller adopts the retry. The command-line `snodo job retry` (snodo/cli/commands/job_cmd.py) builds its run arguments without a plan too.
- As a result the plan's status.json and the plan view stay old after a retry.

## Outcome
- A retried plan child job keeps its plan, wave, parent job and integration base, through both the MCP retry and the command-line retry, so the plan's status reflects the retry.
- When the original lineage cannot be reused safely (for example its parent run has been superseded), the retry says so in plain words and either refuses or runs clearly marked as detached.
- Tests: retrying a plan child through each path carries the plan fields onto the new job; retrying a plain job is unchanged; the unsafe case is reported.
- `make gate` passes.
