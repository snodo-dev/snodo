# A project protocol doesn't record which template it came from

Before any change, open a GitHub issue in snodo-dev/snodo describing the gap. Write the issue body to a file under /tmp and pass it with `--body-file`; never pass text containing backticks or `$(` in an inline shell string. Put "Fixes #<issue number>" in the commit message, and add a CHANGELOG entry under ## [Unreleased].

## INTENT
Every protocol that `snodo init` writes says which shipped template it came from and which snodo version wrote it. A later comparison can then find the right template even if the user renamed `protocol_id`, and can tell the user how old their copy is.

## THE CHAIN
Facts from recons rec_c33098 and rec_1c9eb8:
- `init` writes the selected template's raw YAML to `.snodo/protocol.yml` (snodo/cli/commands/init_cmd.py:606-607, with test-command injection at 150-203). No template id or version is recorded.
- `Protocol` (packages/snodo-foundation/src/snodo/compiler/models.py:417-475) has no provenance field. It does have a free-form `metadata: Dict[str, Any]` (models.py:459), which nothing populates.
- Today the template link is inferred from `protocol_id` (packages/snodo-foundation/src/snodo/protocols/__init__.py:147-174). The team template's `protocol_id` is `default`, which doesn't match its file name.

## CONSTRAINTS
- Use the existing `metadata` mapping. No new Protocol field and no schema change.
- Record the template name (the file stem passed to `--template`) and the snodo version.
- Write it so the generated YAML stays readable, with comments preserved where init already preserves them.
- Protocols without this metadata keep working everywhere. Add a single helper that resolves a protocol's template from metadata first, then from `protocol_id`, and returns nothing for bespoke protocols. Don't change missing_template_validators() callers in this task.
- Do not run the `snodo` CLI or `python -m snodo` in the worktree; exercise init in tests against tmp_path. Do not create, change or delete anything under `.snodo/`.
- Run only the init and protocols tests, not `make gate`.

## ACCEPTANCE
- Tests cover:
  - init with each shipped template records the template name and version in metadata, and the protocol still loads and validates;
  - the helper resolves through metadata, falls back to `protocol_id`, and returns nothing for a bespoke protocol.
- There is a CHANGELOG entry under ## [Unreleased].
