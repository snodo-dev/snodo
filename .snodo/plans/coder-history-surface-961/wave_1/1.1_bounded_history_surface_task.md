# Give the coder a bounded, read-only git history surface

## Goal

`https://github.com/snodo-dev/snodo/issues/961`: a coder cannot consult git history,
so a task that asks it to restore or compare what a file previously said is
unsatisfiable. Observed on task `3.1_restore_removed_explanation`, which halted
`environment_error` after 11 turns. The coder's decision to stop rather than invent
content was correct — the capability simply does not exist for it.

The validators already have it: `git_show`, `git_log` and `read_diff_between_refs`
are listed in `packages/snodo-engine/src/snodo/validators/tool_registry.py:25-34`
(`BUILTIN_VALIDATOR_TOOL_NAMES`) and handled in
`packages/snodo-engine/src/snodo/validators/plugin_tool_support.py:61`. The coder's
tool surface has no equivalent. Close the asymmetry, with bounds.

## What to build

Expose the existing read-only git operations to the coder, backed by the same
`GitMCP` methods the validator path already uses
(`packages/snodo-tools/src/snodo/tools/git.py`: `show(ref, path)` at `:571`,
`log(n)` at `:601`, `diff_between_refs(ref1, ref2)` at `:512`,
`changed_paths_between_refs` at `:527`):

- **history for a path** — commits touching one file, capped (a bounded number of
  entries), so "when was this line removed" is answerable.
- **a file at a revision** — `show` for one path, size-capped like the other
  coder-facing reads.
- **a diff between two refs for one path** — bounded, and never the whole-repo diff.

Requirements that are not negotiable:

1. **Read-only.** No mutation verbs reach the coder: no stage, commit, checkout,
   merge, branch create or delete. The history surface must be a distinct, named
   capability, not the general git MCP, so a coder cannot reach the mutating methods
   by accident.
2. **Declared, not implicit.** The capability goes through the protocol's mode and
   capability surface (ADR 035): the mode that grants it is stated in the protocol,
   and a validator's mode that does not grant it must not gain it. The protocol rule
   is explicit — "a task that exposes a tool to a mode that does not grant its
   capability … is a blocker" — so the grant has to be made properly, in the same
   place the other coder tools are granted, and the surface-parity tests must cover
   the new tools.
3. **Bounded output.** Every result is capped and the cap is enforced in the tool, not
   left to the caller. `read_diff_between_refs` already has a size-measurement helper
   (`_change_size_capped` / `change_size` in `git.py:160-219`, `:541`) — reuse that
   approach. #956 is open on unbounded tool results flooding a task (one broad
   `run_tests` injected 93 MB); this new surface must not become a second way to do
   that, and its bounds should be no looser than the existing read bounds. Truncation
   must be visible in the result: say what was cut and how to ask for less.
4. **Scoped to the dispatched workspace.** History queries resolve against the task's
   own worktree/repository, and refs are validated rather than interpolated into a
   shell command. Do not open access to refs outside the repository the task is running in.

## Also worth doing, if it falls out of the above

When a task spec plainly requires history and the coder's granted surface does not
include it, the run should say so up front instead of spending 11 turns discovering it.
A pre-flight check that names the missing capability is acceptable; a heuristic that
guesses intent from the spec text is not, so skip this rather than build something
unreliable.

## Constraints

- Do not give the coder arbitrary shell to implement this. `ShellMCP`'s whitelist is
  the declared boundary (ADR 014) and stays as it is.
- The in-process coder and the host-CLI coders have different tool plumbing. If the
  bounded history surface can only be granted to one of them, deliver it there and
  record in the issue comment which coders still lack it — do not silently ship a
  capability that only half the coder backends have while claiming parity.
- Validators keep their existing tools and phases; `read_diff_between_refs` staying
  post-execute-only for validators (`llm_validator.py:105`) must not change.

## Acceptance criteria

- A coder granted the new capability can answer, in one call each: which commits
  touched this file; what this file said at a given ref; how this file differs between
  two refs. Tests assert each, against a real repository with a few commits.
- The caps are tested: an oversized history, an oversized file at a ref, and an
  oversized diff each return a bounded result that states it was truncated.
- A mutation attempt through the new surface is refused, and the surface-parity /
  mode-grant tests show the capability is declared for the coder mode and not granted
  elsewhere.
- Refs and paths are validated: a test shows a hostile ref or path cannot escape the
  repository or reach a shell.
- CHANGELOG entry under **Unreleased** naming #961, and a note on the issue stating
  which coder backends have the surface.
- `make gate` and `lint-imports` green.
