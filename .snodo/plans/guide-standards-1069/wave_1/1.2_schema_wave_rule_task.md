## Intent
The tool schema text a consumer reads when listing tools states the rules that make `generate_spec` and `propose_plan` calls succeed on the first attempt.

## Symptom and evidence
In packages/snodo-mcp/src/snodo/mcp/tools.py the `generate_spec` description of `task_id` says the format is `<wave>.<sequence>_<name>` with a required name, which is good. It does not say that the leading number must equal the wave that lists the task, nor where the spec file ends up. When the wave number is wrong the consumer sees only `Missing spec: <id>`, which names the symptom and not the rule. The refusals `task_exists` (resolved with `replace=true`), `parent_not_found`, `max_subtask_depth_exceeded` and `cycle_detected` are also not mentioned next to the parameters they concern. Recon rec_32a560 has the detail.

## What done looks like
- The `task_id` description states that the leading number must be the id of the wave that lists the task.
- The schema text for `generate_spec` and `propose_plan` mentions that spec files live at `.snodo/plans/<plan>/wave_<N>/<task_id>_task.md`, and that an existing task id is replaced only with `replace=true`.
- Wording stays short; the guide's `standards` topic carries the full explanation and the schema can point to it.

## Constraints
- Text changes in the schema descriptions only; behaviour of the tools does not change.
- If a test pins the exact schema text, update it deliberately.
- Do not add states, statuses, severities or halt types.
