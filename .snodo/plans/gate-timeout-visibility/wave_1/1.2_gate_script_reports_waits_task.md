Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased]. If CHANGELOG.md conflicts with a sibling task's entry, keep both entries. Don't run the full `make gate` inside your session; run only targeted tests. The post-execute gate runs the full suite, and a full run in-session hits the 600s silence limit.

INTENT
`make gate` pushes HEAD to the gate host and runs scripts/gate_remote.sh there over `ssh -tt`. Before running, `gate_acquire_slot` waits without limit, and without printing anything, for one of GATE_SLOTS flock slots. The slots are shared by every gate on that host under GATE_ROOT. The `gate` pytest invocation also has no per-test timeout, while `gate-ci` uses `--timeout=60`. On 2026-10-08 three snodo quality gates timed out at 600s. By hand, the same main passed `make gate` in 76s. Possible causes include a silent wait for a slot held by other gates, a hung test, and slow dependency sync, and nothing the script printed could tell them apart.

When this is done, the gate script narrates the phases that can take time. A sibling task makes snodo keep that output on timeout, so it will become the record of where time went.
- While waiting for a slot, it prints once that it is waiting and roughly every 30s after that. Where cheap, it includes what holds the slots, such as the PIDs or gate directories of the current holders.
- It prints a short line with elapsed seconds when the slot is acquired, when dependency sync starts and ends, and when pytest starts.
- The `gate` pytest invocation gets a per-test timeout, so a hung test fails fast with a traceback naming it. pytest-timeout is already a pinned dev dependency. Choose the value from measured durations with comfortable headroom; gate-ci's 60s may already be right.
Keep `gate` and `gate-ci` otherwise as they are; the script documents why they differ.
