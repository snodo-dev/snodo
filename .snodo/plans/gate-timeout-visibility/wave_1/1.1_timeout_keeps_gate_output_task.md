The post-execute gate runs the full suite, and a full run in-session hits the 600s silence limit.

INTENT
On 2026-10-08 three tasks were blocked by the quality validator. Each failed with "Test command timed out after 600.0s: 'make gate'". The `verification_executed` audit event's output_tail held only "Timeout after 600.0s". The operator then ran `make gate` by hand on the same main, from the Mini, and it finished in 1m16s. Nobody could tell what the gate was doing for those 600 seconds: waiting for a gate slot, syncing dependencies, running a slow or hung test, or something else. Whatever the timed-out command had already printed was thrown away.

When this is done, a quality-gate timeout keeps the command's partial stdout and stderr. The existing output_tail, in the audit event and in the validator's justification text, holds the last part of what the gate printed before it was killed, followed by the timeout note. The next timeout should show where the time went. The whole process tree must still be killed on timeout, as it is today.

THE CHAIN
1. In packages/snodo-engine/src/snodo/validators/quality.py, `_run_command` runs the test command with a timeout. Make the timeout path keep the output captured so far. Note that subprocess.run's TimeoutExpired carries partial output only in some modes. If the current approach can't keep it, stream to a buffer or temp file so it can. Keep the size bounded the same way output_tail is today.
2. Keep the operational-fault classification: a timeout is still an error=True blocker, not a test failure.
3. Tests:
   - a command that prints lines and then sleeps past a tiny timeout yields output_tail containing those lines plus the timeout note;
   - no child process outlives the timeout.
