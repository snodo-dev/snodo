INTENT
Running a single wave of a plan from the CLI must land completed task work on the plan's integration branch and deliver it per the protocol — the producer's root checkout is never a staging area. Issue #910: `snodo plan run <plan> --wave N` from the producer root reported success and marked tasks completed, but the work appeared as uncommitted changes on the root's `main` working tree with the task branch deleted; the integration branch head never moved, and delivery had to be rebuilt by hand. Evidence in the current code: `snodo/cli/commands/plan_run.py` exports `SNODO_PLAN_INTEGRATION_BRANCH` only when an integration branch was resolved, and only defines the wave-completion delivery hook for a full plan run (`integration_branch and not queue_integration_branch`); `snodo/cli/commands/run_merge.py` computes the merge target as `os.environ.get("SNODO_PLAN_INTEGRATION_BRANCH") if plan_name else None`, and with no target merges into the *checked-out* branch; for `delivery in {"push_branch", "change_request"}` it returns after pushing the task branch, so the integration merge is skipped; `snodo/cli/commands/plan_delivery.py` treats a plan as delivered purely because the local integration sha equals the remote one. Where this spec and the ADRs in `docs/decisions/` disagree, the records win.

THE CHAIN
1. `snodo/cli/commands/plan_run.py` — any plan run that dispatches tasks (full plan or `--wave N`) resolves and persists the integration identity before dispatch, so the merge target is always known for a plan task; when the integration branch cannot be established, the run refuses with an actionable error instead of dispatching.
2. `snodo/cli/commands/run_merge.py` — with plan context, a successful task's work ends up on the plan integration branch; the merge never silently targets the currently checked-out branch when a plan integration branch was expected.
3. `snodo/cli/commands/plan_run.py` — a healthy wave run performs the same delivery step a full plan run does (per `execution.delivery` in `.snodo/protocol.yml`), so `--wave N` no longer completes with no delivery at all.
4. `snodo/cli/commands/plan_delivery.py` — the already-delivered short-circuit only skips change-request creation when a change request actually exists for the delivered state; a matching sha with nothing pending review must not silently mark the plan delivered.
5. Tests under `tests/cli/` prove: (a) a `--wave` run merges the task branch into the plan integration branch and not into the checked-out branch; (b) a wave run with an unestablishable integration branch refuses before dispatch; (c) the already-delivered guard no longer skips creation when no change request exists.
6. `CHANGELOG.md` — an Unreleased entry describing the fix, closing issue #910.

CONSTRAINTS:
- Full-plan and queue runs keep their current healthy-path behavior (integration merge, push, change-request creation); this is about wave runs and the wrong-target failure mode, not a redesign of delivery.
- The `push_branch`/`change_request` early return for task-branch delivery keeps its meaning; the fix ensures integration still receives the task work in the situations #910 documents.
- Merge discipline (`merge_lock`, moved-branch refusal) is preserved.
- Out of scope: coder execution root (`snodo/cli/commands/run_cmd.py`, `packages/snodo-engine/src/snodo/engine/loop.py` — handled by an earlier wave that has already landed) and retry/spec-replacement state (`snodo/cli/commands/task_cmd.py`).
- The previous attempt passed the full local test gate except for two regressions it introduced itself: it edited `tests/cli/test_merge_gate_paths.py::test_task_branch_merge_requires_exact_commit_verification` by inserting a verification-audit append BEFORE the first merge, which destroyed the test's meaning (the first merge must be BLOCKED because no verification event exists yet; only the post-verification merge may succeed). Do NOT modify that test's semantics: no verification event may be appended before the first blocked merge. You may add NEW tests, but every pre-existing test in that file must keep its original meaning and pass.
- `plan_run.py` must stay within the 1000-line file-size contract; the previous attempt's approach of extracting benchmark-fixture execution from it into a new cohesive helper module under `snodo/cli/commands/` was correct — keep that pattern rather than breaching the size gate.
- The full local gate must pass with zero failures, including the complete `tests/cli/test_merge_gate_paths.py` suite. If a pre-existing test outside that file genuinely encodes the OLD broken contract (e.g. the legacy `TestRunPlan::test_run_plan_success` expectation that wave runs leave work uncommitted), update it minimally to the new contract and say so in the summary; never weaken an unverified-merge-blocks or merge-discipline guard.
