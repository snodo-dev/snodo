INTENT
Replacing a blocked task's spec must change what the validators judge on the next attempt, and an exhausted retry budget must have a supported way to reset — otherwise a task blocks forever on stale input. Issue #909: a task blocked by the pre-execute meta-spec validator could not be rescued by `generate_spec replace=true` or by editing `wave_N/<task>_task.md`, because the retry path rebuilds the prompt from the spec recorded at first failure; `snodo task abandon` printed success but left the `task_failure` entry; `snodo plan add-task --replace` updated the spec hash but left status `blocked` and the attempt counter at 3; `snodo plan run --wave 1` then refused with "max_retries reached". The issue reporter confirmed the diagnosis by clearing exactly two session decision records by hand (`decisions["task_failure"][<task_id>]` and `decisions["halt"][<task_id>]`), after which the validators judged the new spec and the task completed. Relevant code: `_resolve_failure_context` in `snodo/cli/commands/plan_run.py`, `_failure_from_halt_record` in `snodo/cli/commands/run_cmd.py`, the retry branch in `plan_run.py` that sets `task_args["retry"]`, and `task_abandon` in `snodo/cli/commands/task_cmd.py`. Where this spec and the ADRs in `docs/decisions/` disagree, the records win.

THE CHAIN
1. `snodo/cli/commands/plan_run.py` — when a task's spec content changes (hash differs from the recorded failure context), the next attempt judges the new spec: the retry prompt is rebuilt from the current spec file, not the spec recorded at first failure.
2. A spec replacement on a blocked task resets that task's attempt counter (or the CLI offers a supported command that does), so `snodo plan run --wave N` no longer refuses a fresh spec with "max_retries reached" from the previous input's failures.
3. `snodo/cli/commands/task_cmd.py` — `snodo task abandon <plan>/<task>` actually removes the task's `task_failure` and `halt` decision records; it reports what it cleared, and a subsequent run treats the task as fresh rather than replaying stale context.
4. The on-disk task record (`state.json` description and status) no longer disagrees with the replaced spec file after a spec replacement.
5. Tests under `tests/cli/` prove: (a) after replacing a blocked task's spec, the next dispatch's validators receive the new spec text; (b) replacing the spec (or abandoning) clears both decision carriers so a maxed-out task can run again; (c) abandon on a task with no records is a no-op that doesn't error.
6. `CHANGELOG.md` — an Unreleased entry describing the fix, closing issue #909.

CONSTRAINTS
- The validator quorum is never bypassed: a reset only changes what the *next* attempt judges; a pass token still gates dispatch, and no recorded status stands in for an engine verdict.
- Retry budgets for genuine repeated failures on an *unchanged* spec still apply unchanged — the reset is tied to the spec actually changing (or an explicit abandon), not unconditional.
- Halt records for other tasks are untouched; clearing is scoped to the named task.
- Out of scope: coder execution root and integration/delivery targeting (earlier waves); the protocol's validator definitions in `.snodo/protocol.yml` themselves.

ACCEPTANCE
- New tests exist and pass for the three behaviors above.
- The existing CLI retry/plan test suite passes (`uv run pytest tests/cli -q -k "retry or plan_run or abandon"`).
- `CHANGELOG.md` mentions #909 in the Unreleased section.
