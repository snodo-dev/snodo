INTENT
A dispatched task's coder must execute inside that task's worktree, never in the producer's root checkout. Issue #911: running `snodo queue run` from the producer root left every task worktree at the base commit with a clean tree while the coder subprocesses edited and committed in the producer's `main` working tree. The post-run diff then judged the tasks as "Coder produced no file operations" (false halts) and the operator's branch silently accumulated three tasks' edits. The single-task path already threads a worktree into the engine: `snodo/cli/commands/run_cmd.py` creates the worktree (`setup_for_task`) and passes `worktree_path=` into the graph builder; `packages/snodo-engine/src/snodo/engine/loop.py` roots its MCPs at `worktree_path or project_root`; `packages/snodo-engine/src/snodo/coders/subprocess_adapter.py` launches the coder with `cwd` set from the adapter's workspace, and ADR 024/025 prohibit inferring that boundary from `Path.cwd()`. What is missing is the guarantee for the queue/plan wave path and a loud failure when the identity is lost. Where this spec and the ADRs in `docs/decisions/` disagree, the records win.

THE CHAIN
1. `snodo/cli/commands/plan_run.py` — a task executed through the wave path reaches the same worktree-isolated dispatch that `snodo run` uses; the queue/plan run no longer loses the task workspace identity between the plan record and the running process.
2. `packages/snodo-engine/src/snodo/engine/loop.py` — when isolation is expected (a task worktree exists for the dispatch), the coder and its MCPs root at that worktree; `project_root` is used only in the documented degraded/no-isolation cases.
3. A pre-dispatch guard compares the expected task workspace with the root the coder will actually run in and fails loudly with a message naming both paths (e.g. "task workspace mismatch: expected <worktree>, got <root>") instead of silently running in the wrong tree. The guard lives where dispatch resolves the workspace so every coder backend benefits.
4. `packages/snodo-engine/src/snodo/coders/subprocess_adapter.py` and `packages/snodo-engine/src/snodo/coders/opencode_adapter.py` — the adapters keep honoring the explicit workspace; no adapter falls back to the process cwd when a workspace was expected.
5. Tests under `tests/coders/` and `tests/cli/` prove: (a) a dispatched task's coder working root equals its task worktree when isolation is on; (b) the mismatch guard raises with both paths in the message when the expected workspace is not the dispatch root; (c) degraded/no-isolation runs still proceed without the guard firing.
6. `CHANGELOG.md` — an Unreleased entry describing the fix, closing issue #911.

CONSTRAINTS
- Do not weaken existing post-run guards: the in-place coder snapshot in `packages/snodo-engine/src/snodo/coders/base.py` and the protected-path diff in `packages/snodo-engine/src/snodo/engine/nodes/validation.py` stay as enforcement backstops.
- ADR 024/025 remain in force: no containment boundary inferred from `Path.cwd()`.
- `--no-isolation` and the worktree-degraded path must keep working exactly as today (coder runs in the given root, warning printed); the guard fires only when a task worktree was expected but is not the dispatch root.
- Out of scope: merge/delivery target selection (`snodo/cli/commands/run_merge.py`, `snodo/cli/commands/plan_delivery.py`) and retry/spec-replacement state (`snodo/cli/commands/task_cmd.py`) — later waves handle those.

ACCEPTANCE
- New tests exist and pass: coder-cwd-equals-worktree on the wave path; workspace-mismatch guard raises naming expected and actual; degraded mode unaffected.
- The full existing coder and CLI test suites pass (`uv run pytest tests/coders tests/cli -q`).
- `CHANGELOG.md` mentions #911 in the Unreleased section.
