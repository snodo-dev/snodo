INTENT
The Delivery route should report flow efficiency: how much of a landed task's time from start to landed was clean first-pass work, and how much went into rework after the work was sent back.

Evidence: the Flow Framework defines efficiency as active time over total flow time, but a local project has no record of waiting intervals (a plan job runs many tasks in sequence, so job times do not map to one task). What does exist: start and landed times per task (.snodo/tasks/<task>/state.json, started_at and completed_at), the gate send-back marker already used by first-try rate in snodo/web/flow.py (a blocked halt in the task's state or archived attempts), and recovery rounds, which are tasks named <task>_fix_<n> listed with their parent in .snodo/wave.json task_ids and in plan status, and recorded in audit events such as recovery_resolved. Of 776 task folders only one is a _fix_ folder, so recovery timing may live in job records or audit timestamps rather than the tasks folder.

What it should do: for each landed task in the window with both a start and a landed time, find the first send-back moment (the earliest time the task was sent back by a gate or a recovery round began, from whichever records carry a timestamp). Rework time is the landed time minus that moment, or zero when there was no send-back. Efficiency is one minus total rework time divided by total flow time over the tasks whose send-back history is known, a number from 0 to 1. Tasks whose history is unknown are left out of the calculation, exactly as the first-try rate treats unknown attempts; no task is assumed clean. flow_metrics gains efficiency (0 to 1 or null) and efficiency_tasks (how many tasks it was computed over); the Delivery totals gain the same two keys, pooled across projects from summed rework and flow seconds, not an average of ratios. All existing keys, including by_type and by_week from the previous ticket, stay as they are. A first-try task counts as full efficiency; a window with no usable task gives null.
