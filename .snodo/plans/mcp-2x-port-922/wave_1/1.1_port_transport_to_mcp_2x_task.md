# Port the producer MCP transport to mcp 2.x

## Why this task exists

`snodo serve` is the producer interface the orchestrator uses. When the `mcp`
package resolves to 2.x the server dies at import time with
`ModuleNotFoundError: No module named 'mcp.server.fastmcp'` — 2.x renamed
FastMCP to `MCPServer` under `mcp.server.mcpserver` — and every producer tool
becomes unavailable, leaving only the CLI. Issue #922.

The project has been holding that resolution back with a `<2` upper bound on the
dependency in the MCP package's own manifest, and Dependabot has been told to
stop re-proposing the major bump. Neither of those is a fix: this task removes
the need for both by making the server work on 2.x.

## What "done" means

The MCP server builds and runs against mcp 2.x with the behaviour it has today:

- the same tool set is registered for a given protocol configuration, with the
  same mode filtering,
- a client completes the `initialize` handshake and `the tool listing` returns the
  same names and schemas,
- the `snodo` CLI's serve command still starts the server,
- the existing MCP test suite passes against 2.x.

Progress notifications, resources, the traffic-logging hook and the bearer-token
auth path are the *next* task in this plan; leave working shims for them rather
than deleting functionality, and do not claim those surfaces in this task.

## Acceptance criteria

1. The transport module imports and constructs the server under mcp 2.x with no
   reference to the removed v1 module path.
2. A test asserts the registered tool names match the protocol server's surface
   for a representative protocol configuration, so a silently dropped tool fails
   the gate rather than the user.
3. A test completes the `initialize` handshake and a tool-listing round trip
   against the built server.
4. `uv lock` resolves mcp to a 2.x version and the manifest's upper bound is
   raised accordingly.
5. The existing MCP tests pass.

## Constraints

- Do not fork or vendor the dependency.
- Keep the bridge delegating to the protocol server; the protocol layer stays
  the source of truth for tool resolution and mode filtering.
- `transport.py` is 843 lines against a 1000-line file-length gate — split the
  module rather than grow it past the gate.
- Do not change the tool contracts or their outputs.
- No new halt types or severities; nothing in the engine or CLI except the serve
  entry point if the import path there needs updating.
- Either the gate passes and you submit, or it does not and you fix it. Do not
  leave notes about validation anywhere in the tree.
