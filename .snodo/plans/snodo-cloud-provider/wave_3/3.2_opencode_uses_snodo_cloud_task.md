# The opencode-cli coder can't use snodo cloud models

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
A coder model of `opencode-cli/snodo-cloud/<id>`, for example "opencode-cli/snodo-cloud/gpt-6-luna", works. When snodo starts opencode for such a model, it gives that opencode run a provider named `snodo-cloud`:
- an OpenAI-compatible provider whose base URL is the snodo cloud gateway;
- whose API key is the current cloud credential (the OAuth token, refreshed as needed, or the API key);
- which declares the requested model.
The user doesn't edit any opencode config by hand. Other opencode models are untouched.

## THE CHAIN
- `OpenCodeCLIAdapter` (`packages/snodo-engine/src/snodo/coders/opencode_cli_adapter.py`) builds `opencode run ... -m <provider/model>`, passing everything after `opencode-cli/` as the model. It supports opencode 1.x and 2.x (#858).
- opencode reads providers only from its own config. snodo passes nothing else today (recon rec_d1fad8; `subprocess_adapter.py`, `_bare_model`, around lines 337–364). The repo's own `opencode.jsonc` shows the shape of an OpenAI-compatible provider block (`ollama-cloud` with `npm: @ai-sdk/openai-compatible`, `options.baseURL`, `options.apiKey`, `models`).
- An earlier wave added the built-in snodo-cloud provider, the gateway URL (`cloud.models_url`) and credential resolution (`packages/snodo-core/src/snodo/config.py`).
- The subprocess environment for coders comes from `subprocess_env_for_coder()`, called from `subprocess_adapter.py`.

## CONSTRAINTS
- Inject the provider per run, without writing the user's global opencode config or any file in the repo or worktree. First check which per-run mechanism the installed opencode supports, for both 1.x and 2.x, e.g. an inline-config environment variable or a config-file flag. Choose one that works on both, or branch by version as #858 does.
- The credential reaches opencode only through the process environment or a temp file with 0600 permissions that is removed after the run. Never put it in argv, logs or audit events.
- Only runs whose model starts with `snodo-cloud/` get the injected provider.
- Use the earlier-wave helpers as they are; don't edit `packages/snodo-core/src/snodo/config.py` (a sibling task in this wave may).
- No new status, severity, halt type or audit event.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the opencode adapter tests.

## ACCEPTANCE
- Tests show:
  - "opencode-cli/snodo-cloud/gpt-6-luna" starts opencode with `-m snodo-cloud/gpt-6-luna` and a per-run snodo-cloud provider definition, with the gateway URL and the model declared;
  - the credential appears in neither argv nor logs;
  - another opencode model gets no injection;
  - with no cloud login the run fails early with a message pointing to `snodo cloud login`.
