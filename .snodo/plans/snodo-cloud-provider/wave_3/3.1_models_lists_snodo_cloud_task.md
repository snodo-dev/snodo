# `snodo models --provider snodo-cloud` says the provider is not configured

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
When the user is logged in to snodo cloud, `snodo models` counts snodo-cloud as a configured provider. `snodo models --provider snodo-cloud` lists the models the organisation enabled, read from the gateway's `GET /v1/models` with the cloud credential, and shows them as `snodo-cloud/<id>`. The provider check and probe (models check) work against it too. Without a cloud login, it's listed as unavailable, with a hint to run `snodo cloud login`.

## THE CHAIN
- Observed on a logged-in machine: `snodo models --provider=snodo-cloud` printed "Provider not configured: snodo-cloud", with the configured list "anthropic, cloudflare, deepseek, google, ocgo, ollama-cloud, openai, openrouter, zen".
- An earlier wave added the built-in snodo-cloud provider and its credential resolution (cloud OAuth token or API key). Find it in `packages/snodo-core/src/snodo/config.py`.
- Recon rec_d1fad8:
  - `_configured_provider_names` and `_list_providers` (`snodo/cli/commands/models_cmd.py`, around lines 234–284) count a provider only when `api_key` or `api_key_env` resolves;
  - discovery falls back to `_discover_openai_compatible` (`packages/snodo-foundation/src/snodo/infrastructure/model_discovery.py`, around lines 265–319), which GETs `<base_url>/models` with Bearer auth;
  - the gateway serves `GET /v1/models` (confirmed: it answers 401 without a credential).
