# snodo cloud's model gateway is not a provider snodo knows

This work is tracked by GitHub issue #869, which is already open; reference it as "Fixes #869" and add a CHANGELOG entry under ## [Unreleased] if one for #869 isn't there yet.

## INTENT
"snodo-cloud" is a built-in model provider. A model named "snodo-cloud/<id>" routes to the snodo cloud gateway's OpenAI-compatible API, at https://models.snodo.dev/v1 by default, configurable as `cloud.models_url`. It authenticates with the user's snodo cloud login: the OAuth access token, refreshed when needed, or else the configured `cloud.api_key`. With no cloud login, it behaves like any other unconfigured provider. The full gate stays green, including the import-layer contracts.

## THE CHAIN
- An earlier attempt (task 2.1_snodo_cloud_provider in this plan) built a working implementation on its task branch: routing, `cloud.models_url`, and catalog tests that name providers instead of counting them. Its 178 focused tests passed. The coder may build on it.
- The gate rejected that attempt for one reason. The import-linter contract "snodo-core depends on nothing above it" (`.importlinter`) forbids `snodo.config` from importing `snodo.infrastructure`, including imports inside functions. The attempt imported `snodo.infrastructure.cloud_credentials` from `snodo.config`.
- The credential resolver (OAuth refresh with API-key fallback) belongs to snodo-foundation, which sits above snodo-core. Core therefore needs a way to receive that capability without importing it: dependency inversion, for example a small registration point in core that foundation fills. Whatever the mechanism, the snodo-cloud key must resolve wherever completions are built (validators, recon, the litellm coder, the models command), so check that the registering module is always loaded on those paths.
- Model names under snodo-cloud include ids starting with "gpt-" and "@cf/", which other providers' prefixes would otherwise claim (`PROVIDER_MODEL_PREFIXES` in `packages/snodo-core/src/snodo/config.py`).

## CONSTRAINTS
- `lint-imports` (the import-linter contracts in `.importlinter`) must pass. Do not weaken or edit the contracts.
- Never log or print the credential.
- An explicit `providers: snodo-cloud:` block in config.yml still overrides the defaults.
- No new status, severity, halt type or audit event.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages go through files under /tmp.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run ruff check` and `uv run lint-imports` on the change. Run the config, provider-routing, cloud-credential and model-discovery tests.

## ACCEPTANCE
- `lint-imports` passes.
- Tests show:
  - snodo-cloud model names resolve to the snodo-cloud provider and the gateway URL;
  - the key comes from the cloud login (OAuth token preferred, API key fallback) on the completion paths, or is None without a login;
  - `cloud.models_url` overrides the default;
  - plain OpenAI model names still route to openai.
- The model-discovery tests expect snodo-cloud among the default providers.
- There is one CHANGELOG entry for #869.
