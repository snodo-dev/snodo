## Intent
Give the engine one small, well-named place that answers "does this task reference belong to this task's own recovery lineage?", so the merge gate can use it in the next wave instead of comparing ids for equality.

## Evidence
- Recovery builds the id of a sub-task as the root task id, then `_fix_`, then a number (packages/snodo-engine/src/snodo/engine/loop.py, around lines 897-912, `id=f"{root_id}_fix_{fix_number}"`). Recovery can nest, but the id always starts from the root id and keeps that shape.
- The quality validator records its `verification_executed` event under the id of the task it ran for, so after recovery the passing event carries the sub-task's id, while the merge gate (snodo/cli/commands/run_merge.py, `_matching_task_verifications`) compares it to the root id for equality. The next wave changes the gate; this task only adds the helper and its tests.

## Outcome
- A new small module under packages/snodo-engine/src/snodo/engine/ exposes one public function that takes a task reference and a root task id and says whether the reference is the root itself or one of its recovery sub-tasks.
- It returns true for the root id itself and for the root id followed by `_fix_` and a positive number (one level). It returns false for any other reference: a different task, a task whose id merely starts with the root id as a prefix (for example a root id `1.1_a` against `1.1_ab_fix_1`), an empty or non-string reference, a malformed suffix such as `_fix_`, `_fix_x`, `_fix_0` or `_fix_1_extra`.
- Matching is exact and case-sensitive; it must not use substring or prefix tests alone.
- Add unit tests for the function in a new test file under tests/engine/ covering the cases above.
- No file crosses the file-length ratchet. Run the tests you touched and scripts/enforce_file_length.py yourself and report the results in your summary.

No new states, statuses, severities or halt types.
