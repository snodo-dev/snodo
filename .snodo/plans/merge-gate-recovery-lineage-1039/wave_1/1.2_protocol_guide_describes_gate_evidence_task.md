## Intent
The protocol guide should tell readers which verification evidence the merge gate accepts, including what happens after recovery, so an `unmerged` task is understandable. The decision record that states the rule should carry the same wording as a clarification, not a reversal.

## Evidence
- docs/protocol.md around line 423 describes that a merge without verification evidence is refused and that an ungated notice is printed when no quality validator is declared. Read that section and the text around it first.
- ADR 031 (docs/decisions/031-first-class-verification-audit-events.md) states the rule as "no passing verification_executed event is present for the task". After this plan the gate reads that sentence as: a passing quality verification of the exact commit being delivered, recorded for the task or for one of its own recovery sub-tasks (their ids are the task id followed by `_fix_` and a number, recognised by the helper added in this plan's first task, in packages/snodo-engine/src/snodo/engine/). The guarantee that an unverified merge is impossible does not change; the wording only says which task ids count as "the task".
- The gate change itself and the guide wording are delivered together by this plan: the plan's integration branch is only delivered once every wave is done, so the guide never describes behaviour that is not in the code on the base branch.

## Outcome
- docs/protocol.md gets one short paragraph or a short bullet pair in the section above explaining, in plain words, that the gate looks for a passing quality verification of the commit being delivered, recorded for the task or for its own recovery sub-tasks, and that a verification for a different commit or a different task does not count.
- docs/decisions/031-first-class-verification-audit-events.md gets a short clarification note at its end (follow the way other records in docs/decisions mark later clarifications; if none does, a dated "Clarification" line is enough) saying that "the task" includes its own recovery sub-tasks as above, and that the rest of the record stands. Do not change the existing decision text.
- If the guide already states the evidence rule in another place under docs/, keep the two consistent.
- The docs check the repository provides (strict link and anchor validation) still passes; run it and report the result in your summary.
- Only files under docs/ change. Text reads soft and natural, written for the reader.

No new states, statuses, severities or halt types.
