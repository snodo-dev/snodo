## Intent
A task whose recovery sub-task passes the quality gate should be delivered, not left `unmerged`. The merge gate should accept a passing quality verification recorded for the task itself or for one of its own recovery sub-tasks, for the exact commit being delivered, and stay exactly as strict as today about the commit and about unrelated tasks.

## Evidence
- Seen on a second machine: a task passed after recovery and still finished `unmerged`, with the refusal text "No passing verification_executed event recorded".
- snodo/cli/commands/run_merge.py: `_matching_task_verifications(history, task_id, target_commit, quality_validator_ids)` keeps events whose `task_ref` equals `task_id`. Recovery sub-tasks record their verification under `<task id>_fix_<n>`, so the passing event is filtered out. The same function is called by `_merge_on_success` (around lines 248-276), by the unmerged fast path `_try_merge_unmerged_task` (around lines 487-505), and by `verify_queue_merge_head` in snodo/cli/commands/plan_delivery.py. A second inline filter in `_merge_on_success` (the branch for explicit `verification_task_ids`, around lines 246-256) is for plan integration with an explicit id set and stays as it is.
- Wave 1 of this plan added the helper in packages/snodo-engine/src/snodo/engine/ (a module with one public function that says whether a task reference is the root id or one of its recovery sub-task ids) and a documentation paragraph. Read the helper before using it; use it, do not re-implement the matching.
- tests/cli/test_merge_gate_paths.py has real-Git coverage of the merge boundaries; follow its helpers and style.

## Outcome
- `_matching_task_verifications` treats an event as belonging to the task when its `task_ref` is the task id or one of its recovery sub-task ids according to the helper. Every other condition stays exactly as it is: validator id, `returncode == 0`, a non-empty target commit, and the verified commit matching the merge target.
- The refusal message and audit event keep naming the original task.
- Add tests in tests/cli/test_merge_gate_paths.py: a passing event under a recovery sub-task id for the delivered commit lets the merge through; the same event for a different commit is still refused; a passing event under an unrelated task id, or under an id that only shares a prefix, is still refused; the unmerged fast path accepts the recovery sub-task evidence in the same way as the main path.
- Do not change the inline filter used for explicit `verification_task_ids`, and do not touch other tests. If a pre-existing test fails for a reason unrelated to this change (a timing test under load), rerun it and leave it alone.
- No file crosses the file-length ratchet. Run the tests you touched and scripts/enforce_file_length.py yourself and report the results in your summary.

No new states, statuses, severities or halt types.
