## Intent
The readiness check treats a provider that signs in with a ChatGPT subscription (setting `auth: chatgpt-oauth`, no API key by design) as a normal, set-up provider instead of warning about a missing credential.

## Evidence
- In the readiness checker (packages/snodo-engine/src/snodo/readiness/checker.py), `_check_model_readiness` resolves the provider key and, when none is found, adds a `credential_missing` warning that says no credential is configured and tells the operator to run `snodo config add` or export an API key. An OAuth provider has no key field by validation, so the warning is always wrong for it, and the advice contradicts the config rules.
- The same function names the expected environment variable through `_resolve_model_provider_env`, which maps a model name prefix to a key variable; for a ChatGPT subscription model that is misleading.
- The config manager has `provider_uses_oauth(provider)` for telling these providers apart, and the token module's `chatgpt_sign_in_state()` reports sign-in from the token file only with no network call (returns a small mapping when signed in, None otherwise).

## Outcome
- For a model whose provider uses OAuth, readiness does not emit the missing-credential warning or the key advice; when the provider is not signed in it says so, naming the command `snodo models --provider <name> --authenticate`, at the same severity the missing-credential warning had; when signed in it adds no finding.
- Providers without the `auth` setting behave exactly as before, including provider objects that have no `auth` attribute (read it tolerantly).
- Tests cover a signed-in OAuth provider, a not-signed-in one (fake sign-in state, no network) and an API-key provider unchanged.
- `make gate` passes, including ruff, import-linter and the file-length and docs-coverage checks.
