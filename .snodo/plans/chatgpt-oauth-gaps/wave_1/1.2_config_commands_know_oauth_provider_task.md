## Intent
`snodo config show`, `snodo config test` and the key test treat a provider that signs in with a ChatGPT subscription (setting `auth: chatgpt-oauth`, no API key by design) as set up, instead of reporting that no keys are configured.

## Evidence
- In snodo/cli/commands/config_cmd.py, `_config_test` returns early with "No API keys configured" and exit code 1 when no provider has a key, so an operator with only an OAuth provider is told there is nothing to test; `_config_show` lists key and reference credentials and prints "No API keys configured" when neither exists, leaving an OAuth provider out of the listing.
- In the core config module, `ConfigManager.test_keys` skips every provider whose key lookup is empty, so an OAuth provider is omitted from the results.
- The config manager has `provider_uses_oauth(provider)`, and the token module's `chatgpt_sign_in_state()` reports sign-in from the token file only with no network call (small mapping when signed in, None otherwise). A real credential test of the subscription would need a network call and the operator's sign-in, which these commands should not start.

## Outcome
- `snodo config show` lists an OAuth provider with its sign-in state (signed in, or not signed in with the `snodo models --provider <name> --authenticate` command), and does not print "No API keys configured" when an OAuth provider exists.
- `snodo config test` does not exit early because only OAuth providers exist; it reports an OAuth provider's sign-in state without a network call or an interactive sign-in, and key providers are tested as before.
- Providers without the `auth` setting, and provider objects without an `auth` attribute, behave exactly as before.
- Tests cover an OAuth-only setup, a mixed setup, and an API-key-only setup unchanged (fake sign-in state, no network).
- `make gate` passes, including ruff, import-linter and the file-length and docs-coverage checks.
