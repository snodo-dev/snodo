# Orchestrators can't get a plan run's outcome summary over MCP

Before any change, open a GitHub issue in snodo-dev/snodo describing the gap. Write the issue body to a file under /tmp and pass it with `--body-file`; never pass text containing backticks or `$(` in an inline shell string. Put "Fixes #<issue number>" in the commit message, and add a CHANGELOG entry under ## [Unreleased].

## INTENT
An agent orchestrating plans over MCP gets the same run summary as `plan status`'s summary flag (per task: outcome, halt type, attempts, duration, cost, delivered; plus run totals) without reading job directories or log files.

## THE CHAIN
- MCP `get_plan` (packages/snodo-mcp/src/snodo/mcp/plan_handlers.py:221-248) returns name, intent, waves, per-task status, task_modules, task_runs, validation and instruction.
- MCP `get_job_status` (packages/snodo-mcp/src/snodo/mcp/job_handlers.py:22-73) returns no halt payload, usage or cost.
- Orchestrators currently read .snodo/jobs/*/stdout.log and state.json by hand to learn why a task blocked and what a run cost.
- This repo already has a pure function that summarises one plan run. Find it and use it.

## CONSTRAINTS
- Add the summary to `get_plan`'s response under one new key, without changing existing keys. Keep it bounded: no justifications or logs, just outcome fields and numbers. Point to the CLI for detail.
- No new MCP tool, status, halt type or audit event.
- Update the MCP tool docs where `get_plan` is described.
- Don't touch plan_cmd.py, task_cmd.py or docs/command-reference.md.
- Do not run the `snodo` CLI or `python -m snodo` in the worktree, and do not create, change or delete anything under `.snodo/`.
- Run only the MCP plan handler tests and the docs build, not `make gate`.

## ACCEPTANCE
- Handler tests over a fixture plan run cover the summary key's shape and bounds.
- Existing `get_plan` tests are unchanged and pass.
- There is a CHANGELOG entry under ## [Unreleased].
