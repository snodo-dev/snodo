Before starting, open a GitHub issue on snodo-dev/snodo titled "Discover third-party coder adapters through package entry points". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
`docs/extending.md` says coder adapters are an in-process mapping, not an installed-package entry-point mechanism. Installing a package does not add a coder, and the built-in CLI does not load third-party coder packages. So anyone wanting a new coding agent, such as another CLI agent, has to fork or embed snodo.

Code-host providers already solve this. They use the `snodo.providers` setuptools entry-point group, discovered at startup by the provider registry in snodo-tools, which reports which plugins loaded and which failed.

When this is done, a package that declares an entry point in a `snodo.coders` group registers its coder adapter, so `llm.coder.model` (or `--coder`) can name it. A plugin that fails to load is recorded with its error and does not crash snodo.

THE CHAIN
1. The coder adapter mapping discovers the `snodo.coders` entry-point group, following the provider registry's discovery and error handling. Built-in coder prefixes such as `opencode-cli/` keep priority.
2. Load failures are kept in a form a later readiness report can read, mirroring how provider load failures are kept.
3. Tests:
   - a fake entry point adds a coder that can be selected by name;
   - a broken entry point is reported and does not crash snodo;
   - built-in coders are unaffected.

CONSTRAINTS
- Snodo's state machine is closed: add no status, severity, halt type or audit event.
- Do not touch the validator or predicate registries, `snodo ready`, or `docs/extending.md`. Other tasks own those.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
