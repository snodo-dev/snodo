Before starting, open a GitHub issue on snodo-dev/snodo titled "Discover third-party predicates through package entry points". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
`docs/extending.md` says there is no third-party predicate entry-point discovery and no public plugin loader. So a predicate that a protocol references must be imported by hand before dispatch.

Code-host providers already solve this. They use the `snodo.providers` setuptools entry-point group, discovered at startup by the provider registry in snodo-tools, which reports which plugins loaded and which failed.

When this is done, a package that declares an entry point in a `snodo.predicates` group has its predicate registered automatically, so protocols can reference it by name. A plugin that fails to load is recorded with its error and does not crash snodo.

THE CHAIN
1. The predicate registry discovers the `snodo.predicates` entry-point group, following the provider registry's discovery and error handling.
2. Load failures are kept in a form a later readiness report can read, mirroring how provider load failures are kept.
3. Tests:
   - a fake entry point registers a predicate that a protocol can reference;
   - a broken entry point is reported and does not crash snodo;
   - built-in predicates are unaffected.

CONSTRAINTS
- Snodo's state machine is closed: add no status, severity, halt type or audit event.
- Do not touch the validator or coder registries, `snodo ready`, or `docs/extending.md`. Other tasks own those.

ACCEPTANCE
- The tests in link 3 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes.
