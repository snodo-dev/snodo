# 1.1 — a task's own record remembers which job ran it

GitHub issue #1018 already exists for this work. Do not open another; put "Fixes #1018" in the commit message. Do not edit the CHANGELOG (the last task in this plan owns the entry).

## INTENT

An operator holding a task name cannot get to the job that ran it. A task's durable record lives in `.snodo/tasks/<task_id>/state.json`, written when a run starts and when it completes (`snodo/cli/commands/task_record.py`), and every earlier start is archived under `.snodo/tasks/<task_id>/attempts/`. None of these files say which job the run belonged to, although the job id is available to the process while it runs (the job wrapper exports `SNODO_JOB_ID`). A task that ran as part of a plan wave runs inside that plan's job, so the plan job's id is the one that leads to its log.

Make the task record carry that link, so everything that reads the record later can show it.

## Outcome

- When a run starts inside a job, the task's state records the job id under the field name `job_id`. When there is no job (a task run by hand from a terminal), the field is simply absent; nothing is invented.
- The archived attempt files keep the `job_id` of the run they describe, so the full history of a task can be listed run by run.
- Completion and the engine's own writes into the same state file keep the field: a run that finishes, halts or fails still has its `job_id` afterwards.
- Recovery fix tasks (ids ending `_fix_1`, `_fix_2`) that run inside the same job as their root get the same job id in their own records, if they have records of their own.
- State files written before this change load and display exactly as before.

## Acceptance

- Tests that the field is written when the job id is present in the environment, absent when it is not, preserved across completion, and copied into the archived attempt when a second run starts. New cases or a new test module; do not rewrite existing tests.
- The existing task-record and run tests stay green; the linter is clean; run the targeted tests and the linter, and do not run the whole suite yourself: the engine runs it right after you finish, and a multi-minute silent command has been dropping the coder connection.

## Constraints

- Do not add a status, severity, halt type or audit event; this is one more recorded field only.
- Do not change the shape of any existing field or the meaning of existing files. No new dependency; do not raise any length baseline.
