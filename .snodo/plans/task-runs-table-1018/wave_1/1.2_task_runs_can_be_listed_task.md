# 1.2 — one place that answers "which jobs ran this task?"

GitHub issue #1018 already exists for this work. Do not open another; put "Fixes #1018" in the commit message. Do not edit the CHANGELOG (the last task in this plan owns the entry).

## INTENT

`snodo task show` and `snodo meta` should each show the runs of a task as a small table. Both need the same answer, and today no helper provides it. `snodo meta` has an inline scan of `.snodo/jobs/*/task.json` (matching the task id, or a description prefix as a heuristic); `snodo task show` has none. A reusable, tested function in its own module is wanted, so both commands call it and the logic is not duplicated again.

What exists to build on, found by reading the code:

- The job directory holds `task.json` (the submitted arguments: `task_id`, `retry_task_id`, `plan_name`, `task_plan`, `task_wave`, `parent_job`) and `state.json` (`status`, `created_at`, `started_at`, `completed_at`, `exit_code`, and the engine's `halt` payload, whose `task_id` can be a recovery fix id). The job manager already lists job summaries.
- A task's own record (`.snodo/tasks/<task_id>/state.json` and its `attempts/` archive) is about to carry a `job_id` field (a sibling task in this plan adds it). Records written earlier will not have it.
- A plan task usually runs inside the plan's job, not in a job of its own, so the plan job's id is what leads to its log. A recovery fix task `<root>_fix_N` runs in the same job as its root; the only persisted link between them is the `_fix_N` naming.
- Existing table styles in the CLI are Rich tables (the task list display, the plan list) and a hand-aligned text table (the job list).

## Outcome

- A function that, given a task id, returns the runs of that task, oldest first, one row per run, with: job id, plan name and wave when known, task id as run (so a fix task shows its own id), start time, end time or running, and how the run ended for this task.
- The primary source is the `job_id` recorded in the task's record and attempts. Where a record has no `job_id` (older history), fall back to scanning job directories and matching on the task's id in `task.json` (`task_id`, `retry_task_id`) and in the job state's halt payload. Rows found both ways appear once.
- Recovery fix tasks of the task (ids that are the task id followed by `_fix_` and a number) are included, labelled with their own id.
- A table renderer in the same style as the CLI's existing Rich tables, printing columns for job, plan/wave, task, started, ended and outcome, plus a plain data form for `--json` output. The renderer prints nothing and costs nothing when there are no runs.
- Reading is side-effect free; in particular it must not trigger the job manager's state reconciliation writes more than the existing listing already does.

## Acceptance

- Tests with fixture job directories and task records: runs from recorded `job_id` only; runs from the fallback scan only; both together without duplicates; fix tasks included under their root; a task with no runs; ordering oldest first; the plain data form has stable key names.
- The new module is imported by nothing yet except its tests; the existing CLI tests stay green; the linter is clean; run the targeted tests and the linter, and do not run the whole suite yourself: the engine runs it right after you finish, and a multi-minute silent command has been dropping the coder connection.
