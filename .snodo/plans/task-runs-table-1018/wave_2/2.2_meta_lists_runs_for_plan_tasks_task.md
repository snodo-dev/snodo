# 2.2 — `snodo meta <task>` works for plan task names and prints the runs table

GitHub issue #1018 already exists for this work. Do not open another; put "Fixes #1018" in the commit message. Do not edit the CHANGELOG (the last task in this plan owns the entry).

## INTENT

`snodo meta <id>` chooses what to describe from the shape of the id: ids starting `j_` are jobs, and ids starting `task_` are tasks, whose handler already scans the job directories for matching jobs. A plan task name such as `1.1_ws_hostnames_are_recognised` has neither prefix, so the command prints no jobs for it, and an operator following up on plan work learns nothing. The previous wave added a reusable function and table renderer for "which jobs ran this task" (look for the new task-runs module in `snodo/cli`) and made task records carry a `job_id`.

## Outcome

- An id that is not a job id but names a known task (it has a task record, or runs are found for it) is described as a task, whatever its shape. Job ids and `task_` ids behave as today.
- The task view prints the runs table from the new module instead of its own inline scan, and the description-prefix heuristic is gone from that scan in favour of the module's matching.
- With `--json`, the existing `jobs` key keeps its meaning for current consumers; a `runs` list in the plain data form is added next to it.
- An id that matches nothing keeps today's not-found behaviour and message.

## Acceptance

- Tests: a plan-style task name with a record and runs prints the table; a `task_` id still works; a job id still works; an unknown id keeps its message; `--json` carries both `jobs` and `runs`. New cases or a new test module.
- The existing meta tests stay green; the linter is clean; run the targeted tests and the linter, and do not run the whole suite yourself: the engine runs it right after you finish, and a multi-minute silent command has been dropping the coder connection.
