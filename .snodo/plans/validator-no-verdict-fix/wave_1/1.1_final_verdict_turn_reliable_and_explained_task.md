# 1.1_final_verdict_turn_reliable_and_explained

## INTENT
A tool-reading validator judge (here the ADR judge) reads files for most of its budget and then, on the turn where only `submit_verdict` is offered, returns no tool call at all. The task then halts with `validator_error` ("Validator did not return a verdict after N turn(s): the judge did not call submit_verdict. Fail-closed.") and the whole pre-execute validation has to be rerun, costing 7 to 15 minutes each time. The fail-closed behaviour is right (a judge that did not decide must never become a finding); what is wrong is that the loop gives that final turn exactly one attempt and then reports a failure that does not say why the provider returned nothing.

Evidence (all from real runs of the plan retry-reuses-validator-verdicts):
- The ADR judge failed this way on task 1.1 (after 16 turns), and twice on task 2.1 (after 22 and after 18 turns). The security judge in the same runs finished normally with `submit_verdict` at turn 27.
- In the last run (job j_f822bf11d2e2) the ADR judge read about 25 files, then turn 17 was "(no tools called)" after about 70 seconds, and turn 18 (the verdict-only turn, `tool_choice` forced to `submit_verdict`) was again "(no tools called)" after about 50 seconds. Turns that long with no tool call and no text are consistent with a judge that spent its completion budget before producing the call, but nothing recorded today lets anyone tell that apart from a provider that ignores the forced tool choice, so it is a hypothesis, not a finding.
- Code: `packages/snodo-engine/src/snodo/validators/llm_validator.py`, the loop in `_evaluate_with_tools` (around lines 440 to 590): the verdict-only turn is built at the `if is_final_turn or retried_free_text:` block, the request goes through `call_with_unforced_tool_fallback` (`packages/snodo-engine/src/snodo/validators/llm_provider_errors.py`), and when the response holds no valid `submit_verdict` the function returns the error blocker immediately. The completion budget of the request is `completion_tokens` (the default `_DEFAULT_MAX_TOKENS` is 1500) and `finish_reason` is not read anywhere in `packages/snodo-engine/src/snodo/validators/`.

What should become true: (1) when the verdict-only turn returns no valid verdict, the failure result records what the provider actually returned on that turn (at least the finish reason, the completion token count against the request limit, and whether there was any text), so the next occurrence explains itself in the justification or the `examined` log instead of staying a mystery; (2) the verdict-only turn is given one more bounded chance before failing closed, in the way that is most likely to help given what that record shows (for example a retry with a larger completion allowance when the turn ended because it hit the limit, or one repeat of the forced request otherwise); two misses still fail closed exactly as today; (3) nothing else about the loop changes: read tools stay withdrawn on that turn, `tool_choice` stays forced to `submit_verdict`, repeat-read turns stay free but bounded, prose is never turned into a verdict, and a wrong or missing task id in a verdict is still terminal.
