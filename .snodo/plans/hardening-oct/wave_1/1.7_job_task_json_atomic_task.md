# Job task.json is written in place and can be left half-written

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
A job's `task.json` is always either the old or the new complete document. A crash mid-write never leaves a job unreadable.

## THE CHAIN
- Recon rec_f3ade8 found that `packages/snodo-mcp/src/snodo/jobs/__init__.py` writes `task.json` with `json.dump` into an open file (around lines 307–309, and again around 346–347 after worktree creation).
- `snodo/cli/commands/run_cmd.py` rewrites it with `write_text` to persist `task_id` (around lines 864–865).
- `_load_task` (around lines 188–197) turns a truncated file into a `JobError`, which makes the job unreadable.
- `state.json` already uses `atomic_write_json`.

## CONSTRAINTS
- Use the existing atomic JSON helpers for every `task.json` write. Where a write is a read-modify-write, as in `run_cmd.py`, use the locked update.
- No new status, severity, halt type or audit event.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo. Tests use temporary job directories.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the targeted job and run-command tests.

## ACCEPTANCE
- Tests show every `task.json` writer goes through the atomic helpers; patching proves the calls.
- `task_id` persistence still works for retry lookup.
- There is a CHANGELOG entry under ## [Unreleased].
