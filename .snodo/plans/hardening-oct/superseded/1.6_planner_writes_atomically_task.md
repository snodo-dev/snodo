# Plan status.json and plan.yml are written non-atomically by spec generation

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
All writers of a plan's `status.json` and `plan.yml` use locked, atomic writes, so a plan run updating task status and an orchestrator replacing a spec at the same moment never truncate or clobber each other.

## THE CHAIN
- Recon rec_30f4e0: in `packages/snodo-mcp/src/snodo/mcp/planner.py`, `_write_spec_and_update` (around lines 565–576), `decompose` (around lines 326–332) and `recompute_depths` (around lines 1028–1029) write `status.json` and `plan.yml` with plain `open(..., "w")`. `update_status` (around line 863) uses the locked `atomic_update_json`.
- Related symptom seen on 2026-10-11: after two `generate_spec(replace=true)` calls on plan tidy-lifecycles, its `plan.yml` listed both wave-1 tasks twice. Check whether the replace path appends a task id that's already present, and fix that too.

## CONSTRAINTS
- Use the existing locked atomic helpers for JSON. For `plan.yml`, use an equivalent write-temp-then-rename under the same lock.
- `generate_spec` with replace must never duplicate a task id in its wave.
- No new status, severity, halt type or audit event.
- Never pass text containing backticks or `$(` through an inline shell string. Commit messages and issue bodies go through files under /tmp.
- Do not run the `snodo` CLI, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo. Tests use temporary plan directories.
- Run `uv run ruff check` and `uv run python scripts/enforce_file_length.py` on touched files. Run only the targeted planner tests.

## ACCEPTANCE
- Tests show:
  - the listed writers go through the locked atomic helpers;
  - replacing a spec twice leaves exactly one entry for that task in plan.yml;
  - a concurrent status update and spec replacement both survive.
- There is a CHANGELOG entry under ## [Unreleased].
