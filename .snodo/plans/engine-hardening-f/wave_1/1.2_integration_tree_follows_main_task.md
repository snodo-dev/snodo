Order of work: write the regression tests first, then the change, and commit both together before running `make gate` (the gate refuses to run on an uncommitted tree). A change without its tests is not complete.

## Intent
A plan run hands each task a tree that matches what the operator sees on main, including work the orchestrator hand-merged to main during the plan, so a task is never judged against, or fails for lack of, code that already exists.

## Evidence
- In a recent plan, tasks 1.2 and 2.3 were hand-merged to main after review. The plan integration branch was cut at plan start (snodo/cli/commands/plan_run.py, where the integration branch and worktree are created and its `base_sha` recorded) and never picked those commits up. A later task's worktree lacked a file that existed on main and acceptance reported the work missing; two other tasks escalated at pre-execute because their base lacked an ADR and a command group that were on main.
- The integration branch is checked out in a worktree on the host, so an operator cannot safely move its ref by hand.
- A first attempt changed snodo/cli/commands/plan_run.py but added no tests and was blocked; a clean re-implementation is welcome and nothing from it needs to be reused.

## Outcome
- Before each wave starts, the integration branch is brought up to date with main: a fast-forward when main contains the integration branch, otherwise main is merged into it, with a conflict stopping the run with a clear message instead of a half-updated tree. A hand-merge recorded with `record_task_status` is therefore reflected in what the next wave sees.
- The recorded integration base in the plan status stays truthful after the update.
- Tests: a plan where main gains a commit between waves, and a later task's worktree contains it; a main that has not moved leaves the integration branch untouched.
- `make gate` passes.
