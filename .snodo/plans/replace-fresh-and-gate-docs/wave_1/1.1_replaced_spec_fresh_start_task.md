## Intent
When a plan task's spec has been deliberately replaced and its wave is run again, the next attempt starts from the plan's current base branch, as a fresh start does, instead of resuming the stale task branch and its leftover changes.

## Evidence
- Replacing a blocked task's spec through the supported authoring path moves the task to pending and records the new spec hash. The wave run then takes the ordinary dispatch path (the blocked-task retry path is skipped), and that path does not ask for a fresh start. The attempt continues the existing task worktree: the run reports inherited work and starts at the old branch head, so work merged to the base since the branch was cut is not visible to it.
- In plan guide-standards-1069, tasks 2.2 and 2.3 had their specs replaced and failed again on a defect the base had already fixed, because the resumed branches were cut from the old base.
- The pieces already exist. The failure record keeps the spec recorded at failure. The comparison of that spec against the hash in status.json already defines "deliberately replaced", and a hand-edit of the spec file deliberately does not count (#832). The plan run option for a fresh start already creates a new workspace from the task base and keeps the earlier branch, worktree and records.

## Outcome
- A task whose recorded failure spec differs from its replaced spec, by that existing comparison, starts its next attempt as a fresh start, whichever dispatch path it takes. The earlier branch, worktree and records are preserved.
- A task with no failure record, a task whose spec file was only hand-edited, and a plain retry without replacement behave exactly as today.
