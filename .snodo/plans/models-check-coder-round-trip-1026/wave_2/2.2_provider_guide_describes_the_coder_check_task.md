## Intent
The provider guide for OpenAI tells readers that a coder configured as `opencode-cli/openai/...` shows up as NOT CHECKABLE in `snodo models --check`. Once the check sends a prompt through the OpenCode CLI, the guide should describe what readers will now see.

## Evidence
- docs/providers/openai.md mentions it at about lines 68, 79 and 87: the sentence about coder IDs beginning `opencode-cli/openai/...`, the sentence saying a passing check reports OK for direct OpenAI models, and the troubleshooting row "A coder is NOT CHECKABLE".
- Other pages under docs/ may repeat the same statement (search docs/ for "NOT CHECKABLE" and for "opencode models"); keep them consistent.
- The behaviour change itself lands in the previous task of this plan: an opencode-cli coder line becomes OK or FAILED with the CLI's error after one real prompt through the CLI; a missing CLI binary is reported as before; other subprocess coders are unchanged.

## Outcome
- The guide says, in plain words, that an opencode-cli coder is now checked with one short prompt through the OpenCode CLI on the reader's subscription (so it counts as a small call there), what OK and FAILED mean for that line, and that FAILED shows the CLI's message so a renamed flag or an unknown model is seen before a task runs.
- The troubleshooting table gets a row for a FAILED coder line that says what to look at (the CLI message, `opencode models`, the CLI version); the NOT CHECKABLE row is kept only for coders that still behave that way.
- `make docs` style checks used in this repository (strict link and anchor validation) still pass; run the docs check the repository provides and report the result in your summary.
- Text reads soft and natural, written for the reader of the guide.

No new states, statuses, severities or halt types.
