## Intent
The coder line of `snodo models --check` for an opencode-cli coder model should be a real round trip: one trivial prompt (for example "Reply with OK.") sent through the OpenCode CLI with the configured model, judged OK or FAILED with the CLI's error, the way the provider canary does for LiteLLM models.

## Evidence
- In snodo/cli/commands/models_check.py the opencode-cli branch of `check_configured_models` (about lines 182-184) only calls `_check_opencode_cli_model`, a catalog lookup, and reports healthy None, so the coder line prints NOT CHECKABLE followed by the model and "(coder)", with the hint "Verify in OpenCode with `opencode models`".
- Wave 1 of this plan added the pieces: `OpenCodeCLIAdapter.run_prompt` in packages/snodo-engine/src/snodo/coders/opencode_cli_adapter.py, which runs one prompt in a caller-supplied directory and returns the finished run unparsed (exit code, raw stdout, raw stderr), and `_judge_opencode_cli_run(exit_code, stdout, stderr)` in models_check.py, which turns that into the (healthy, reason) pair. Read both before wiring. The adapter needs an explicit workspace directory, so construct it with the temporary directory.
- The binary-on-PATH check (`check_coder_available`, lines 174-180) already runs first and keeps reporting a missing binary as it does today. Other subprocess coders (agy, codex-cli, claude-cli) stay as they are; this issue is about opencode-cli only.
- Security review of the plan: the CLI only has its edit tool denied, not its shell tool, so the check must never run in the operator's project; and for a snodo-cloud model the child environment carries a resolved credential, so the raw run must not be logged or printed. The reason line that is printed must be passed through `sanitize_verbose_output` (packages/snodo-mcp/src/snodo/mcp/transport.py) and have ANSI escape sequences and other control characters removed, because it can contain CLI text.
- An earlier attempt of this task met the quality gate with one failure, `tests/cli/test_plan_execution.py::test_plan_cli_main_integration`, a timeout under load that is unrelated to this work: leave that test and its file alone and simply rerun the gate if it times out. The same attempt also removed two tests that have nothing to do with this issue, `test_canary_shapes_recon_and_classifier_like_real_calls` and `test_validator_canary_generic_tool_choice_rejection_falls_back` in tests/cli/test_models_cmd.py. They cover the request shape of `run_canary_call` and must stay exactly as they are. Only tests that encode the old opencode-cli behaviour may be rewritten; no other test in that file may disappear.

## Outcome
- For an opencode-cli coder with the CLI available, `check_configured_models` runs `run_prompt` in a fresh temporary directory (never the operator's project, removed afterwards even on failure), with a short bounded wait, and reports the helper's verdict. A CLI that cannot start (unsupported major version, binary vanished), a timeout, or a missing cloud credential is reported as FAILED or NOT CHECKABLE with the adapter's own message, in the same vocabulary the module already uses, with nothing new added.
- Only the helper's bounded one-line reason is printed, after sanitising it as described above. The raw stdout and stderr of the run are neither logged nor written to the audit log.
- Keep the catalog lookup as an extra hint on a FAILED line (for example "model not in snodo's list"), so the two existing tests `test_opencode_cli_model_absent_from_snodo_list_is_best_effort` and `test_opencode_cli_unconfigured_provider_is_not_failed` keep their meaning: update them to the new flow rather than deleting them.
- Update `test_models_check_does_not_send_subprocess_coder_to_litellm` for the new behaviour and add tests for: success prints OK; non-zero exit prints FAILED with the CLI's error; the temporary directory is not the project root and is cleaned up; the raw output is not printed and control characters in the reason do not reach the output; a LiteLLM model is still checked by the canary and never by the CLI; the process exit code is non-zero when the coder check fails.
- No file crosses the file-length ratchet. Run the tests you touched and scripts/enforce_file_length.py yourself and report the results in your summary.

No new states, statuses, severities or halt types: the output vocabulary stays OK, FAILED and NOT CHECKABLE.
