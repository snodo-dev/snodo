# Halt with `environment_error` when a coder reports work that isn't there

## Goal

When a dispatched coder returns saying the files its task describes do not exist,
the engine currently treats "no changes" as a normal halt and then validates the
previous attempt's committed work. That converts a dispatch fault into a test
failure the operator has to debug from scratch. `https://github.com/snodo-dev/snodo/issues/975`
shows it costing two attempts on one task.

Make the engine notice the mismatch and name it.

## The behaviour to change

In the post-execution path, when the coder produced no diff, the engine checks the
task branch for commits from an earlier attempt and, finding them, prints:

> Work already present on the task branch: an earlier attempt committed N file(s)
> before the run failed. Validating the existing work instead of reporting
> no_file_operations.

and runs the validators against that existing work. That fallback is right when the
coder genuinely looked at the branch and chose not to change it. It is wrong, and
misleading, when the coder's report says the subject files are **absent** — the two
cannot both be true, because the work is on the branch the coder was dispatched to.

## What to implement

1. Detect the contradiction: the coder's report claims the task's subject files or
   named tests are missing, while the dispatched workspace's HEAD contains them.
   Compare against the workspace, not against the project root — that confusion is
   the bug being detected.
2. When detected, halt with `halt_type: environment_error` (ADR 015: a non-verdict
   operational fault), naming in the halt payload: the workspace path, the branch and
   HEAD, the files the coder said were absent, and the fact that they are present at
   that HEAD. Do not run the validators against stale work in that case, and do not
   count it as one of the coder's three attempts — an operational fault should not
   consume a coder's retry budget.
3. Keep the existing fallback for the honest case: if the coder's report does not
   contradict the workspace, validating the prior attempt's work stays as it is.

The detection should be cheap and conservative: it fires on a specific, verifiable
contradiction (named paths absent per the coder, present per the workspace), not on
any phrasing that sounds like a refusal. A false positive that halts a legitimate
attempt is worse than no detection, so prefer matching on file paths the coder
explicitly names over sentiment analysis.

## Constraints

- `environment_error` is already a halt type used for dispatch faults; follow how
  `CoderUnavailableError` and the existing environment faults are reported so the
  operator's next action is consistent (retry after fixing the environment, not
  after rewriting the spec).
- Do not change the retry-budget semantics for genuine coder failures — the three
  attempts and the `--replace` reset stay as they are (that rule is what #909 delivered).
- The halt payload must remain adjudicable: it needs the artifacts and the reason, the
  way other halts do.

## Acceptance criteria

- A test where the coder reports a named subject file as absent while the workspace
  HEAD contains it: the run halts `environment_error`, the payload names the path and
  the HEAD, and no validators run against the stale work.
- A test for the honest case (coder says nothing to change, no contradiction): the
  existing "validate the prior attempt's work" path still runs, unchanged.
- A test asserting the attempt counter is not consumed by the environment halt.
- CHANGELOG entry under **Unreleased** naming #975.
- `make gate` green.
