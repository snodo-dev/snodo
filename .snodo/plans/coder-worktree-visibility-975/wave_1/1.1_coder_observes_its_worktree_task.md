# Prove a dispatched CLI coder observes its task worktree, and pin it there

## Goal

`https://github.com/snodo-dev/snodo/issues/975` reports that a host-CLI coder
(opencode-cli) dispatched into a task worktree reads and writes the **producer's
root checkout** instead. Issue #911 was closed with the engine launching the CLI
with `cwd` set to the worktree; the defect reproduces anyway, so `cwd` alone is not
the containment boundary the CLI uses.

Reproduce it before fixing it. Do not start by changing dispatch code.

## What is known

- `packages/snodo-engine/src/snodo/coders/subprocess_adapter.py:621` sets
  `project_root = str(self._workspace)` and `:405` launches `Popen(argv, cwd=project_root, …)`,
  so the engine does start the child in the worktree.
- `packages/snodo-engine/src/snodo/coders/opencode_cli_adapter.py:51-59`: for host
  CLI major version >= 2 the argv deliberately drops `--dir`, on the reasoning that
  "the run already starts in project_root (cwd)". The installed CLI is v2.x.
- Observed in a live retry: the coder reported `run_cmd.py` at 1,535 lines (main's
  count) and "only pre-existing `.snodo/plans` files are modified" — which is the
  root checkout's `git status`, while its worktree was on a commit where the file is
  1,545 lines and the task's module and test exist. So its file tools resolved to
  the root checkout.
- The engine records a containment-boundary log line at INFO
  (`subprocess_adapter.py:626-635`); it is not visible in a normal run's output, so
  there is currently no record of which tree a dispatched coder actually used.

## Reproduce

Add a test that a linked worktree's coder observes the worktree, not the main
checkout. It has to distinguish the two trees by content, not by path:

1. Create a real repository and a linked worktree on a branch that differs from the
   base in one observable way — e.g. a file that exists only on the branch, and a
   line-count or content difference in a file present in both.
2. Dispatch the CLI adapter with the worktree as its workspace, using a stub or
   recorded CLI where necessary so the test does not need a live model, and assert
   what the child was told: the directory it was launched in, and every
   directory-identifying argument the argv carries.
3. Where a stub cannot prove the behaviour (the CLI resolves the root itself), add a
   narrow integration test guarded the way the existing real-git tests are guarded,
   and make the assertion about the tool surface the coder actually uses: reading a
   subject file by relative path must return the branch's content.

If the reproduction shows the CLI honours `cwd` and something else is at fault — the
`git` tool's root, the shell tool's root, or the session/workspace the CLI attaches
to — fix that instead, and record in the issue which it was.

## The read side is the broken side

Writes already work: the same task's earlier attempt committed 16 files to the task
branch through the workspace MCP, which is rooted at the worktree. What resolves to
`main` is the CLI's own read/grep/glob/shell surface. The two roots only disagree when
the task branch diverges from the base — a first attempt gets a worktree identical in
content to `main` and looks fine, while a retry gets a worktree carrying the previous
attempt's commits, so the coder reads a tree that no longer matches where it writes.
That is why #911's `cwd` fix seemed to work: it was verified by where commits landed.

So the reproduction must assert the read side. A test that only checks which branch a
commit reaches will pass on `main` today and prove nothing.

## Fix

Make the boundary explicit rather than implied:

- Pass the directory to the host CLI in whatever form its supported version accepts,
  and keep passing `cwd`, so the two cannot disagree. For opencode 2.x, find the
  supported mechanism (flag, config, or environment) that pins the project root; if
  none exists, say so in the adapter's comment and enforce containment another way
  rather than relying on `cwd`.
- The version branch in `_build_argv` must not silently lose containment when the
  host CLI changes its flags. Add a test that covers both major-version shapes and
  asserts the dispatched argv pins the workspace.
- Refuse, not advise, out-of-workspace edits: if the coder writes outside the
  dispatched workspace, the run must halt with the offending path named. #946
  already tracks the shell-escape case; keep that issue's scope, and cover the
  direct-edit case here.
- Record the boundary in the run's visible output (not only at INFO): the dispatch
  banner should name the tree the coder's tools will read, so a producer can see a
  mismatch without reading the adapter source.

## Constraints

- Do not change the worktree lifecycle or the retry-inheritance behaviour; this task
  is about which tree the coder sees, not which branch it is on.
- Host CLI versions differ; do not assume one argv shape. Detect the version as the
  adapter already does and cover both paths.
- Keep the coder's tool surface as declared by the protocol's mode — no new
  capabilities.

## Acceptance criteria

- A failing-then-passing test exists that distinguishes the main checkout from the
  task worktree by content, and it fails on `main` before the fix (state which
  assertion fails in the PR description).
- The dispatched CLI coder's observed tree matches the worktree in that test, and
  out-of-workspace edits are refused with the path named.
- The run output names the tree the coder will read.
- CHANGELOG entry under **Unreleased** naming #975, and a comment on #911 linking
  the regression so the closed issue's fix is not assumed sufficient.
- `make gate` green.
