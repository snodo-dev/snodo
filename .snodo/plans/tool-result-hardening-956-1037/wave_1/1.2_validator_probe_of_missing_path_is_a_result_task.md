## Intent
When an LLM validator uses its git_show tool on a path that does not exist at the requested ref, it should learn "not found at that ref" and carry on, the same way a missing file in its file-read tools already is an ordinary inspection result. Today the resulting GitError is treated as broken inspection infrastructure and the whole task halts as a validator error before the coder starts, although the spec is fine and re-running the identical spec often passes.

## Evidence
- Issue #1037. Plan suite-env-isolation-1036-v2, task 1.4: "Validator declared tool 'git_show' failed on turn 4 (GitError): … fatal: path 'src/snodo/engine/loop.py' does not exist in 'HEAD'". The real file lives under packages/snodo-engine/; the validator guessed a path, probed it, and the miss ended the task with no retry budget used. The same family halted plan job-identity-tolerance-1033 task 2.1 twice.
- packages/snodo-engine/src/snodo/validators/llm_validator.py (around lines 650-680) fails closed for any tool exception that `is_tool_argument_error` in packages/snodo-engine/src/snodo/validators/plugin_tool_support.py does not classify as a bad argument. GitMCP.show in packages/snodo-tools/src/snodo/tools/git.py raises GitError for a path that is absent at the ref.
- Earlier attempts at this task made GitMCP.show return "not found at <ref>" for an absent path while an unresolvable ref still raises, with tests in tests/mcp/test_git.py and tests/validators/test_llm_validator.py, including a validator-loop test that an unknown ref given to git_show still fails closed. The full gate passed. The last attempt ended only because the acceptance validator's model hit a provider rate limit.

## Outcome
- git_show on a path that is absent at the given ref returns a plain "not found at <ref>" tool result to the judge model, which can then probe a different path.
- Genuine git failures (unknown ref, unreadable repository, git itself failing) still fail closed as today. A missing path must not be confused with those.
- The behaviour holds for built-in validator tools and for plugin-provided calls through the same support code.
- Tests under tests/validators prove both halves through the validator loop: a missing path yields a tool result and the validator completes with its verdict; an unknown ref given to git_show still produces the existing fail-closed error result.

No new states, statuses, severities or halt types.
