# A stuck cloud sync is only visible in `snodo cloud status`

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
When cloud sync is on and a session is refused, or has a meaningful backlog of unsent events, the user sees it where they already look: `snodo ready` and the `snodo serve` startup lines. The message says what is stuck and the one command that fixes it, so the user doesn't have to know to check `cloud status`.

## THE CHAIN
- Recon rec_45af18 found that only `snodo cloud status` (`snodo/cli/commands/cloud_cmd.py`, around lines 313–399) and an exit-time stderr line (`flush_pending_syncs` in `packages/snodo-foundation/src/snodo/infrastructure/cloud_sync.py`, around lines 1228–1248) mention a refused session or pending events.
- `snodo ready` (`snodo/cli/commands/ready_cmd.py`), `snodo status` and serve startup (`snodo/cli/commands/serve_cmd.py`) say nothing.
- The user found about 1456 unsent events in an old session only by chance.
- Unsent counts are computed in `local_unsent_counts` in `snodo/cli/commands/cloud_status.py`.

- Keep it cheap: no network calls for this check; read local state only.
- Copy reads plain and soft. Avoid "not X but Y" contrast phrasing.
