# One unstorable event blocks all automatic sync and liveness for its session

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
When the server refuses one single event for size, that gap stays recorded and visible in `snodo cloud status`. Automatic syncs keep delivering the session's later events, and liveness keeps pushing, with no `--force` needed. Refusals that really are terminal (for example auth, or a malformed request) keep blocking as today.

## THE CHAIN
Recon rec_45af18, two agents agreeing:
- In `packages/snodo-foundation/src/snodo/infrastructure/cloud_sync.py`, a single-event 413 is recorded with `record_refusal(..., status_code=413)` and a "single event sequence N" reason (around lines 915–931), and the run continues to later events.
- But `is_refused` treats exactly that case as terminal (around lines 730–748). Every later automatic sync then returns early (`if not force and state.is_refused(...)`, around line 848).
- Liveness also stops for the session: `packages/snodo-foundation/src/snodo/infrastructure/cloud_liveness.py` checks `is_refused` in `request_liveness_push` (around line 381) and `_post_snapshot` (around line 611).
- So one oversize event stopped all cloud delivery for a session until someone ran `snodo cloud sync --force`. The user saw stale live status and about 1456 unsent events.
