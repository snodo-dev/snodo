Before starting, open a GitHub issue on snodo-dev/snodo titled "Task merges into plan integration no longer print or record task_merged". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased].

INTENT
The single-delivery-log-line fix (plan single-delivery-log-line, 2026-10-07) added a no-op check in `_merge_on_success` (snodo/cli/commands/run_merge.py). It reads HEAD before and after the merge, and if they match it returns early, with no "✓ Merged …" line and no `task_merged` audit event. This stopped the duplicate plan-delivery line, but it also suppresses real task merges.

Evidence: plan recon-failed-agents-keep-work, job j_95faae0e24df, on 2026-10-08:
- Task 1.1_failed_agent_trace_kept completed and its work did reach the integration branch: the following "✓ Merged plan/recon-failed-agents-keep-work/integration into the base branch" delivered real content.
- But the log has no "✓ Merged task/recon-failed-agents-keep-work/1.1_…/… into plan/recon-failed-agents-keep-work/integration" line.
- `.snodo/audit.log` has no `task_merged` event for that task. Earlier plans, such as single-delivery-log-line at 20:27Z, still recorded theirs.

The likely cause: the before/after HEAD is read from the project root's checked-out branch (main). The task-to-integration merge moves a different ref, so main's HEAD does not change and the merge is judged a no-op. Verify this before changing anything.

When this is done, the no-op check compares the merge target's own tip before and after (the integration branch for task merges, the base branch for plan delivery). Task merges into integration print their line and record `task_merged` again. A plan delivery that adds nothing to the base branch still does not print a second success line.

THE CHAIN
1. Make the before/after comparison use the target ref of the merge, not the project root's HEAD.
2. Tests, with a real temporary git repo:
   - a task branch merged into a plan integration branch, while the project root sits on main, prints the merge line and records `task_merged`;
   - delivering an integration branch that main already contains prints no second success line and records no event;
   - a real plan delivery to main prints once.

CONSTRAINTS
- Snodo's state machine is closed: add no status, outcome, halt type or audit event.
- The audit trail is the record. A real merge must always record `task_merged`.
- No file may exceed its file-length limit or baseline.

ACCEPTANCE
- The tests in link 2 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes, including lint and the file-length check.
