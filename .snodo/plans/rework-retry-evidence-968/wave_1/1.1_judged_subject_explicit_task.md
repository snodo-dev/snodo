# Make the judged subject explicit: retry and recovery are different inputs

## Why this task exists

Issue #968 is the fix-forward review of the work that landed #931. The change put
the engine's composed coder input outside the pre-execute judgement: the
validator context keeps the operator's intent as the authoritative subject and
hands the composed input to the judges as evidence instead.

That is the right shape for the CLI retry, where the composed input is a wrapper
around the operator's spec. It is also what happens for an in-loop recovery
attempt, but for a different reason and with a different input: there the
composed spec is the engine's own fix instruction, built from the original intent
per ADR 021. Today the code cannot tell the two apart — it fires whenever
`task.spec` differs from `task.root_spec` at pre-execute — so the block the
judges see describes a recovery spec as if it were an operator retry, and nothing
in the suite pins either behaviour. A reviewer read that as the recovery spec
being demoted; the ambiguity is the defect.

## What "done" means

The distinction is explicit in the code and in what the judges are told, and both
paths are pinned by tests. The authoritative subject stays the operator's intent
in both cases — this task does not change which text is judged, it changes whether
the engine knows *why*, and whether the next reader can tell.

## Acceptance criteria

1. The evidence block names its own provenance: an operator retry and an
   engine-composed recovery are described differently, so a judge is not told an
   engine fix instruction is operator guidance.
2. The validator context distinguishes the two cases rather than inferring them
   from a spec inequality, and the inference it replaces is gone.
3. A test pins the retry shape: the authoritative subject the judges see is the
   operator's spec, and the composed wrapper arrives as evidence.
4. A test pins the recovery shape: a recovery subtask at depth 1 is judged against
   the original intent, with its composed fix instruction supplied as evidence, and
   the fix instruction is not treated as the proposal for authoring criteria.
5. Existing tests in tests/engine/test_retry_judge_input.py keep passing and the
   full gate passes.

## Constraints

- Do not change which text is authoritative for either path; this task makes the
  existing semantics explicit and tested, it does not move the line.
- No new halt types, severities, validator kinds, or statuses.
- Do not re-open the decision recorded in ADR 021; the original intent is carried
  once, unchanged, and a recovery spec is built from it.
- Add one bullet under the `## [Unreleased]` section of CHANGELOG.md describing
  the change. Touch only that section — other in-flight branches edit the same
  block, so do not reflow or reorder anything else in the file.
- Keep every file under the project's file-length gate; split rather than grow.
- Either the gate passes and you submit, or it does not and you fix it. Do not
  leave notes about validation anywhere in the tree.
