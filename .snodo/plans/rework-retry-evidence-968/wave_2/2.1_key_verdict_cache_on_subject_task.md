# Key the verdict cache on what is actually judged

## Why this task exists

Issue #968, against the work that landed #931.

When the pre-execute subject is the operator's intent and the composed coder input
is supplied separately as evidence, the existing cache keys no longer describe the
input a judge saw. The delivery handled that by switching the verdict cache off
for every such attempt. That is correct but crude: it throws away reuse for
attempts whose evidence is identical to a run already judged, and it does so
silently — a retry chain now re-judges everything, every time, at full validator
cost.

The same mechanism has a second, untested property. The evidence is attached to
each backend call by wrapping the completion function, and the wrapper copies the
message list so a bounded tool loop cannot accumulate the section. Only a
single-completion path is asserted today, so the copy that prevents duplication is
load-bearing and unproven.

## What "done" means

A cached verdict is reused exactly when the judge would have seen the same input —
subject *and* evidence — and is fresh whenever either differs. The blanket disable
is gone. And the tool-loop property is pinned by a test rather than by a comment.

## Acceptance criteria

1. The verdict-cache subject for a pre-execute pass that carries retry or recovery
   evidence includes that evidence, so a verdict recorded without it cannot be
   reused for an attempt with it, and vice versa.
2. Two attempts with the same subject and the same evidence still reuse a cached
   verdict — the cache is narrowed, not disabled.
3. The unconditional cache disable in the validator context is removed.
4. A test drives a bounded tool loop with at least two completion calls and asserts
   the evidence section appears once per request and never accumulates across
   turns, and that the caller's message list is not mutated.
5. Existing cache tests and the pre-execute input tests keep passing; the full gate
   passes.

## Constraints

- Reusing a verdict is never a governance change: a miss or a cache failure stays a
  fresh judgement, not a halt. Preserve that.
- Do not weaken the rule from #912 that a pass on the baseline does not clear a
  failure; this task is about cache keys, not about verdict policy.
- No new halt types, severities, validator kinds, or statuses.
- The cloud-liveness test that the review flagged as unrelated is a legitimate
