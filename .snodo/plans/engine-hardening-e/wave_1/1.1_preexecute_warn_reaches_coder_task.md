## Intent
When a pre-execute validator raises a non-blocking warn and the task proceeds, the coder should be told about the warn and expected to address it, so a warn improves the work instead of disappearing into the audit log.

## Evidence
- The project now runs `disagreement_policy: "majority"`. A single pre-execute warn from security, architecture, adr or meta-spec lets the task proceed with `PROCEED_WITH_LOG`: the result is stored in the task's `pre_validation` metadata (packages/snodo-engine/src/snodo/engine/nodes/validation.py) and the audit trail, and no path found hands the warn text to the coder.
- The engine already passes pre-execute findings to the coder as evidence in one case, recovery attempts (`is_recovery` in `PolicyEvaluator.evaluate`, packages/snodo-engine/src/snodo/engine/policy.py), and the coder's briefing of prior verdicts is assembled in packages/snodo-engine/src/snodo/engine/loop.py ("PRIOR ATTEMPT ... outstanding verdicts, in each judge's own words").

## Outcome
- A pre-execute warn on a task that proceeds appears in the coder's input with the validator id and its own justification, phrased as something to address in the work. Passes and blockers are not added to it; a blocker still halts and operational errors still fail closed.
- The policy decision itself does not change. The existing recovery-evidence behaviour keeps working and its text is not duplicated when both apply.
- Tests: a task that proceeds with one warn shows the warn in the coder input; a task with no warns shows no such section; a recovery attempt behaves as before. Put them with the existing validation and loop tests (tests/engine/test_loop_validation.py, tests/engine/test_policy.py).
- `make gate` passes.
