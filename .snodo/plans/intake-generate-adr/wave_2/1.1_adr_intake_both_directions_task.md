New files this task will create: docs/decisions/064-intake-proposes-decision-records-from-code.md.

INTENT
A decision record explains why `snodo intake` may now also read code and propose decision records, so ADR 044 and the new behaviour agree.

Background: ADR 044 says intake reads existing decision records and proposes validator criteria, says intake is a sibling of survey and not a flag on it, and rejects "an agent reads the records and writes the criteria directly" because the normative decision is the operator's. The planned `snodo intake --generate-adr` goes the other way: a model reads code, finds patterns that no record states, and proposes records. The operator chose to put it under intake, not a new top-level command, because intake already is the place where the operator accepts or rejects proposals one at a time, and to avoid a new command.

What it should say (Nygard format, one page, like the other records): the decision that intake has two directions, selected by the flag, with the default direction unchanged; the gate is kept: the model only proposes, each proposal cites the files that show the pattern, the operator accepts or rejects each one, an accepted proposal is written with Status "Proposed" so a human still decides whether it becomes Accepted, and nothing is written for a rejected one; a pattern counts as clear only when it holds in at least three places with no counterexample found; the model is the first entry of llm.recon.models (the configured default when the list is empty); the MCP intake tool stays read-only and does not gain the flag; and a repository without a decision records folder gets a plain explanation of how to start one, with nothing created. Under alternatives, record the separate command (rejected to avoid another top-level command) and letting the model write records directly (rejected for the reason in ADR 044). State that this amends how ADR 044's "sibling of survey" reasoning applies and does not change survey. Add the row to the table in docs/decisions/README.md. Say that "Proposed" is a status of a decision record file, not a state in snodo's state machine.
