New files this task will create: one new module for the code analysis step, beside the proposal module from ticket 1.2, and one new test file for it.

INTENT
One function that asks the recon model to read the repository and returns its answer as proposals, using the checks from ticket 1.2.

Background: `snodo intake --generate-adr` needs a model to read code and find clear patterns that no decision record states. The operator chose the model that recon uses first: the first entry of llm.recon.models, or the configured default model when that list is empty. Recon already has what is needed: read-only repository tools, model resolution (resolve_recon_agents, resolve_agent_model, call_agent_chain in packages/snodo-mcp/src/snodo/recon/__init__.py) and the failover behaviour. Reuse those instead of building a second tool loop.

What it should do: build a prompt that asks for decision records that describe patterns the code follows consistently (not wishes, not one-off choices), tells the model the titles of the existing decision records so it does not repeat them, asks for at most a handful of proposals as JSON in the shape the proposal module defines, and for each proposal at least three evidence files with paths it has actually read. Run it on a single recon agent with the first model and the same deadline and tool turn limits as recon, then pass the answer through the proposal checks and return the kept proposals and the dropped reasons. If the model call fails or times out, return a clear error result; never an exception, and never a partial write (this module writes nothing).

CONSTRAINTS
Files that may change: the new module, its test file and CHANGELOG.md (one entry under [Unreleased] ending "(Fixes #<n>)"). Do not change recon's behaviour or config keys, and do not touch intake_cmd.py. Tests must not make real model calls; inject a fake call. Do not add any state, status, severity or halt type.

ACCEPTANCE
Tests show: the first recon model is the one used (and the default model when the list is empty); the prompt includes the existing record titles; a good fake answer yields proposals; a failing or timing-out call yields an error result with no proposals; bad proposals in an otherwise good answer are dropped with reasons. `make gate-task` is green.

PROCESS
Open a GitHub issue for this task first and put "Fixes #<n>" in the commit message.
