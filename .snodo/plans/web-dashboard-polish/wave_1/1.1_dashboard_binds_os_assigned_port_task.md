INTENT
`snodo dashboard --web` looks for a free port by scanning a fixed list, 55441-55460, and takes the first free one. Two faults follow. A fixed list is the wrong way to find a free port, because the operating system can hand one out. And that range is the one `snodo serve` uses for its tunnel and MCP ports, so the dashboard can take a port `snodo serve` expects to have, or the two can collide. Evidence: snodo/web/app.py scans range(55441, 55461) and raises "No free dashboard port found in range 55441-55460" when none is free; the same numbers appear in tests/web/test_app.py.

What the person should see instead: running `snodo dashboard --web` always starts, on a port the operating system chose, and prints the address that is really being served. That port is never inside 55441-55460, so the dashboard cannot take a port `snodo serve` wants. `--port N` still pins a port; asking for one that is already taken fails with a clear message saying it is in use. The server stays loopback only and the existing request guard is unchanged.

Indications, not instructions: binding to port 0 and reading back the assigned port, retrying a few times when the assigned port lands in the reserved range, and handing the already-bound socket to the server so no other process can slip in between choosing and listening, is one way to get there. Follow your own path if it meets the acceptance below.

CONSTRAINTS

Leave everything else alone, in particular tests/cli/test_serve_tunnel_slug.py and everything under snodo/web/static. Keep the import-linter layering and add no dependency. Tests must not bind any fixed port.

ACCEPTANCE
Tests that exist and pass: with no port given the dashboard obtains a bound loopback port that is non-zero and outside 55441-55460; with an explicit port that something else already holds, it fails with a message containing "in use"; when the operating system keeps returning reserved ports it gives up with an error that names the reserved range; the address printed at start-up uses the port that is really bound; the `--port` help text mentions the OS-chosen default; the other tests in tests/web still pass.
