INTENT
Write docs/providers/cloudflare.md, a step-by-step guide that takes a user from nothing to a passing `snodo models --check` with Cloudflare Workers AI. Cloudflare has several traps that each produce a confusing error; the guide exists mainly so nobody has to rediscover them.

PAGE SHAPE (shared by every provider guide)
1. What you need: the account and credential, with exact permissions.
2. Store the key: the environment variable snodo reads by default, the alternatives (`snodo config add`, an `api_key_ref`), and the precedence rule.
3. Configure: a minimal working `providers:` block, each key with a one-line reason.
4. Choose model ids: the form to write, one real example per role (coder, validator, classifier, recon), and how to list ids with `snodo models --provider cloudflare`.
5. Verify: `snodo models --check` and what a passing line looks like.
6. Troubleshooting: a short table of what you see, why, what to change.

THE CHAIN (evidence from a real setup session; confirm each point in code before writing it)
- Token permissions: Account › Workers AI › Read and Account › Workers AI › Edit, scoped to the one account you will call. Cloudflare's dashboard has a "Create a Workers AI API Token" template that fills these in (https://developers.cloudflare.com/workers-ai/get-started/rest-api/).
- The account must match everywhere. Model listing builds its URL from the account id (`account_id`, or the variable named by `account_id_env`, default CLOUDFLARE_ACCOUNT_ID), while model calls go to `base_url`, which holds the account id literally. A `base_url` pointing at a different account than the token's lets listing succeed and every call fail with Cloudflare error 10000 "Authentication error".
- Key precedence: a literal `api_key`, or an encrypted "@keys/cloudflare.key", is used before `api_key_ref` and before `api_key_env` (default CLOUDFLARE_API_KEY). A stale stored key silently overrides a correct environment variable.
- `litellm_provider: openai` together with `base_url` `https://api.cloudflare.com/client/v4/accounts/<account id>/ai/v1` sends calls to Cloudflare's OpenAI-compatible endpoint. Without it, ids written as "cloudflare/…" go to LiteLLM's native Cloudflare route instead, and an id like "cloudflare/openai/@cf/…" fails with error 5007 "No such model openai/@cf/…".
- Id forms that reach the cloudflare provider: "cloudflare/@cf/<vendor>/<model>" (recommend this one), "openai/@cf/…" and "@cf/…". The leading "openai/" in the second form is a routing detail, not OpenAI; say so. `snodo models --provider cloudflare` currently lists ids in the "openai/@cf/…" form; mention that both work.
- A working block from that session (account and key redacted): account_id, account_id_env CLOUDFLARE_ACCOUNT_ID, api_key_env, base_url as above, litellm_provider openai, models_endpoint `https://api.cloudflare.com/client/v4/accounts/{account_id}/ai/models/search`. Check which of these the built-in catalog already supplies and show only what a user must add.
- Passing check lines look like: `OK cloudflare/@cf/openai/gpt-oss-120b (validator) — LiteLLM model: openai/@cf/openai/gpt-oss-120b`.
