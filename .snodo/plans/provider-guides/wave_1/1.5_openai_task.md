Title: Provider guide: OpenAI

Start by opening a GitHub issue in snodo-dev/snodo describing this change (pass the body with --body-file), or reuse an open one that already covers it. The commit message must include "Fixes #<issue number>". Do not edit CHANGELOG.md: the guides are written in parallel, and a later task records them all in one entry that cites your issue.

INTENT
Write docs/providers/openai.md, a step-by-step guide for the built-in OpenAI provider, ending at a passing `snodo models --check`. Its trap is that several unrelated id forms start with "openai/", so users can end up paying OpenAI directly, or not reaching OpenAI at all, without meaning to.

PAGE SHAPE (shared by every provider guide)
1. What you need. 2. Store the key (default variable, `snodo config add`, `api_key_ref`, and that a literal or encrypted `api_key` wins over the environment variable). 3. Configure: the smallest `providers:` block, noting what the built-in catalog supplies. 4. Choose model ids: the form snodo maps to this provider, one example per role (coder, validator, classifier, recon), listing with `snodo models --provider openai`. 5. Verify with `snodo models --check`. 6. Troubleshooting table.

THE CHAIN (confirm each point in code)
- OpenAI is in the built-in catalog with a default key variable; ids are recognised by prefix rules. Read them from the code.
- Ids beginning "openai/@cf/" are routed to the cloudflare provider, not OpenAI.
- Coder ids beginning "opencode-cli/openai/…" run through the OpenCode CLI on the user's OpenCode subscription; `snodo models --check` reports them as NOT CHECKABLE. They do not use this provider's key.
- A bare "openai/<model>" id makes direct, billed OpenAI API calls with this provider's key.
- Custom OpenAI-compatible blocks (`litellm_provider: openai`) also send ids prefixed "openai/" to LiteLLM, but to their own `base_url`; the "LiteLLM model: openai/…" text in check output describes the request format, not the vendor.
