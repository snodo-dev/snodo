INTENT
Write docs/providers/anthropic.md, a step-by-step guide for the built-in Anthropic provider, ending at a passing `snodo models --check`.

PAGE SHAPE (shared by every provider guide)
1. What you need. 2. Store the key (default variable, `snodo config add`, `api_key_ref`, and that a literal or encrypted `api_key` wins over the environment variable). 3. Configure: the smallest `providers:` block, noting what the built-in catalog already supplies (often nothing needs adding). 4. Choose model ids: the id form snodo maps to this provider, one example per role (coder, validator, classifier, recon), listing with `snodo models --provider anthropic`. 5. Verify with `snodo models --check`. 6. Troubleshooting table.

THE CHAIN (confirm each point in code)
- Anthropic is in the built-in provider catalog with a default key variable and a probe model; ids are recognised by a prefix rule. Read both from the code rather than assuming.
- Claude models reached through a gateway (such as OpenCode Go) belong to that gateway's block, not this one; mention in one line that the id's leading provider name decides which credentials are used.

CONSTRAINTS
- Confirm every key name, default, id rule and precedence rule in the code (core config module's provider catalog and resolution) before writing it. Leave out anything you cannot confirm.
- Provider-side steps stay to a sentence or two; no external links.
- Every `snodo …` command and flag must exist; the docs-coverage check rejects dangling ones.
- Create only docs/providers/anthropic.md. Do not edit mkdocs.yml, other pages or code, and do not link to pages that don't exist yet.
- Plain, soft second-person copy, short sentences.
- Do not run the snodo CLI, make gate or make release, and do not touch .snodo/.

ACCEPTANCE
- The page follows the six-part shape.
- Troubleshooting covers a missing key, a stored key overriding the environment variable, and a model id that resolves to a different provider than intended.
