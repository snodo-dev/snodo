## Intent
A validator that sends one bad tool call should be told what was wrong and be allowed to correct it. A task whose work is fine should not halt because of one malformed argument.

## Evidence
- Adr, security and acceptance validators have sent placeholder or malformed arguments (a task id of "x" or "placeholder", a stray quote, a garbled git log argument, a `git_show` on a ref that does not exist), and the run ended "Validator error: ... operational errors — fail-closed". At least five occurrences; the usual recovery is a full unchanged rerun.
- The tool loop in packages/snodo-engine/src/snodo/validators/llm_validator.py decodes malformed argument JSON to an empty mapping and runs the built-in read; `is_tool_argument_error` in plugin_tool_support.py classifies only some errors as argument errors, so other invalid shapes become operational errors. A malformed `submit_verdict` currently yields nothing instead of feedback.

## Outcome
- A tool call whose arguments are invalid (not valid JSON, not an object, missing or wrongly typed fields, a ref or path that does not exist) returns a short, specific message to the validator as the tool result and counts as one of its turns.
- Only a fault that persists after the validator has had its chance to correct it, or a real read or transport failure, becomes a `validator_error`; fail-closed behaviour for those stays.
- Tests: a validator sends a bad argument and then a good one and completes; a validator that keeps sending bad arguments still ends in the existing error; a malformed submit_verdict is answered with feedback.
- `make gate` passes.
