## Intent
The MCP `list_jobs` tool should return something an orchestrator can read in one call.

## Evidence
- One call returned about 191,000 characters, mostly task specs repeated per job, so orchestrators avoid the tool and poll `get_job_status` by id.
- `JobToolHandler.handle_list_jobs` in packages/snodo-mcp/src/snodo/mcp/job_handlers.py returns everything `JobManager.list_jobs` provides; the tool schema is in packages/snodo-mcp/src/snodo/mcp/tools.py. The command-line job listing should keep its present behaviour unless a change is clearly intended.

## Outcome
- The MCP `list_jobs` returns a compact entry per job (id, type, status, plan, wave and parent where present, created, started and completed times, a short title or task id, and a brief error when there is one), never the task spec or logs, which stay in `get_job_status` and the logs tools.
- It accepts a `limit` (with a sensible default and maximum) and a `status` filter that rejects unknown values with a clear message, and the response says when it was truncated.
- A test pins the compact shape and bounded size; existing list_jobs tests are updated only where they relied on the large shape.
- The tool description and the docs that mention `list_jobs` describe the new shape, limit and filter.
- `make gate` passes, including the docs checks.
