## Intent
An operator who signs in to a ChatGPT subscription provider (setting `auth: chatgpt-oauth`, no models endpoint) can run `snodo models --provider <name>` and see which models they could select, instead of an empty result.

## Evidence
- `snodo models --provider chatgpt` prints "No models discovered for chatgpt". The generic OpenAI-compatible discovery function in the foundation package's model discovery module returns an empty list when there is no endpoint and no base url, and the function that discovers models across providers skips OAuth providers that have no models endpoint.
- LiteLLM already ships entries for this provider in its model price and context map (the `litellm.model_cost` mapping): each key is the word chatgpt, a slash, then the model name, each entry has `litellm_provider` equal to chatgpt and a `max_input_tokens` value. The installed version includes models named gpt-6.1-sol, gpt-6-luna and gpt-5.4 under that prefix.
- Which of those a given account can call depends on the subscription plan, which Snodo cannot know offline.

## Outcome
- For a provider with `auth: chatgpt-oauth` and no models endpoint, discovery returns the LiteLLM-known models of the chatgpt provider, shown under the operator's provider name with their context window; both `snodo models --provider <name>` and the all-provider discovery path list them.
- Providers without the `auth` setting, and providers that do declare a models endpoint, behave exactly as before. Provider objects without an `auth` attribute still work (read it tolerantly).
- The listing makes no network call and does not need a sign-in.
- Tests cover the listing for an OAuth provider (using a small fake model map, no real LiteLLM data), and an API-key provider unchanged.
- `make gate` passes, including ruff, import-linter and the file-length and docs-coverage checks.
