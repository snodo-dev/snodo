## Intent
Retrying a job that belongs to a plan run keeps its plan, wave and parent-job identity, so the retried attempt's outcome reaches the plan's status the way a retry inside a plan run does. If a case cannot be retried safely, the retry says so plainly instead of running detached.

## Evidence
- Plan dispatch (snodo/cli/commands/plan_run.py, where each child task job is set up) gives each child task job `task_plan`, `task_wave`, `parent_job` and the integration base.
- `handle_retry_job` in packages/snodo-mcp/src/snodo/mcp/server.py rebuilds the task arguments from `description`, `cwd`, `retry_task_id`, `task_id`, `retry_continuation` and `mode` only, so the plan fields are dropped. It refuses queue-run and plan-run jobs but not plan child tasks.
- The job wrapper (packages/snodo-mcp/src/snodo/jobs/wrapper.py) then clears the plan environment, and plan child selection requires `parent_job` to match the latest plan run (packages/snodo-mcp/src/snodo/jobs/__init__.py), so no poller adopts the retry. The CLI `snodo job retry` (snodo/cli/commands/job_cmd.py) builds its run arguments without a plan too.
- `snodo plan status --run-summary` overlays the task's own state file, so a retry under the same task id can change the displayed outcome while `status.json` and the selected child-job lineage stay old.

## Outcome
- Retrying a plan child job through both the MCP tool and the CLI starts a job carrying the original plan, wave, parent job and integration base, so the plan's status picks up its outcome.
- Where that cannot be done safely (for example the plan run it belonged to is no longer the latest, or the integration base is gone), the retry refuses with a clear message naming the reason.
- Tests: retrying a plan child job keeps the four fields on the new job record; retrying a plain job is unchanged; the refusal case reports its reason.
- `make gate` passes.
