## Intent
A validator's adjudicated verdict for one task must never be applied to a different task. A retry or recovery sub-task of the same task keeps the verdict.

## Evidence
- Audit events `decision_record_task_mismatch` fired in every wave of a recent plan: a stored record for a task from another plan was found while other tasks were being dispatched, and one task was escalated by a warn whose text described a different task's design.
- `DecisionRecordIssuer.find_adjudicated` in packages/snodo-foundation/src/snodo/infrastructure/decisions.py has a first pass that checks the expected task reference and a second "carry-forward" pass that verifies records without it, so a record for any other task that matches on validator and severity is returned. `PolicyEvaluator.evaluate` in packages/snodo-engine/src/snodo/engine/policy.py consumes it when it reclassifies a warn, and is called with only `loop_state.task.id` (packages/snodo-engine/src/snodo/engine/nodes/validation.py, two call sites).
- Recovery sub-tasks are named `<root>_fix_<n>`. `belongs_to_recovery_lineage` in packages/snodo-engine/src/snodo/engine/recovery_lineage.py already says whether a task reference is the root or one of its recovery sub-tasks. The import-linter contract forbids snodo-foundation from importing snodo-engine, so foundation code cannot call it directly; the matching rule has to reach foundation by being passed in or by living where both packages can reach it.

## Outcome
- A record is used only when it belongs to the same task: its task reference equals the current task reference, or the two are the same root task and one of its recovery sub-tasks (a record issued for `X` still applies to `X_fix_1`, and the other way round). A record for any other task is ignored and the validators run fresh.
- The root task reference reaches the policy evaluation from the places that already know it; the matching rule is written once. `make lint-imports` keeps passing.
- The `adjudication_carry_forward` audit event still fires when a record is carried across a recovery sub-task of the same root, and does not fire for a different task.
- Tests: a stored record for another task with the same validator and severity has no effect on the current task's policy decision; a record for the same task still applies, and so does one that crosses between a task and its `_fix_` sub-task.
- Tests that already exist keep their names, because the coverage check treats a vanished test name as lost coverage. Two existing tests encode the cross-task carry-forward and must flip their expectation with the body rewritten and the name kept: `test_attack_replay_valid_jwt_for_different_task_CARRIES_FORWARD` in tests/infrastructure/test_decisions_e2e.py and `test_carry_forward_on_retry_task` in tests/infrastructure/test_decisions.py (keep the second one meaningful by using a genuine recovery sub-task of the same root). New tests are added alongside.
- `make gate` passes.
