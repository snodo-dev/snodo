# 1.1_llm_validator_faults_log_their_traceback

## INTENT
When an LLM validator hits an operational fault, the log says only the exception type and message, so a fault that is a code defect cannot be traced to a line. Evidence: two benchmark runs halted as `validator_error` with the single stderr line `Validator architecture tool-loop hit an operational fault on turn 1 (model=ocgo/deepseek-v4.1-flash): TypeError: 'function' object is not subscriptable` (and the same for the adr validator in another job); other validators of the same runs made dozens of successful calls, and nothing in the log names the failing line. The two handlers are in `packages/snodo-engine/src/snodo/validators/llm_validator.py`: the single-shot path ("hit an operational fault", the `except Exception` after the structured-output fallback) and the tool-loop path ("tool-loop hit an operational fault on turn"). After this task the traceback of the exception is written to the log by both, so the next occurrence names the line.

## STARTING STATE
Nothing of this task exists. The surfaced justification of both handlers (`LLM validation failed due to operational error (<Type>): <message>` and `LLM tool-loop operational error on turn <n> (<Type>): <message>`) is a contract with the operator and with existing tests.

## THE CHAIN
1. Open a GitHub issue first ("Validator operational faults log no traceback") and put "Fixes #<n>" in the commit message.
2. Read both handlers and the way `_logger` is used in that file. Make each of them log the traceback together with the existing message (the standard logging way of attaching the current exception), without changing the log message wording that exists today.
3. The `ValidatorResult` that the handlers build, its justification, severity and `error=True` flag stay exactly as they are; the traceback goes to the log only, never into the justification, the halt payload or any event.
4. Add tests in a new file `tests/validators/test_validator_fault_traceback.py` with exactly these names: `test_single_shot_fault_logs_the_traceback`, `test_tool_loop_fault_logs_the_traceback`, `test_fault_justification_is_unchanged_by_the_traceback`. Use a fake completion function that raises a `TypeError` from a known helper function, capture the log with the standard logging test fixture, and assert that the captured record carries exception information whose traceback names that helper function, and that the returned result's justification contains no traceback text. No network calls. Look at `tests/validators/test_llm_validator.py` for the fakes the neighbouring tests use.
5. `CHANGELOG.md` gets one new line under `[Unreleased]` in the same commit, in the style of the neighbouring entries, ending with "(Fixes #<n>)".
6. The project supports Python 3.12. Do not run `ruff format` over whole files. Run `python -m pytest tests/validators/test_validator_fault_traceback.py tests/validators/test_llm_validator.py` and `ruff check packages tests snodo`.

## CONSTRAINTS
- Files that may change: `packages/snodo-engine/src/snodo/validators/llm_validator.py`, the new test file, `CHANGELOG.md`. Nothing else, in particular not `runner.py` (a sibling task owns it) and not any test that exists today.
- No new states, statuses, severities, halt types or event names. No change to what the operator sees as the halt.

## ACCEPTANCE

- `tests/validators/test_validator_fault_traceback.py` exists and contains the three named tests.
