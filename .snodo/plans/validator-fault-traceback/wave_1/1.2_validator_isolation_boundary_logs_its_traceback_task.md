# 1.2_validator_isolation_boundary_logs_its_traceback

## INTENT
The validator isolation boundary turns any exception raised by a validator into a `validator_error` result and keeps only the exception type and message in the log. A code defect inside a validator therefore leaves no line number anywhere. Evidence: `packages/snodo-engine/src/snodo/validators/runner.py`, in `run_validators`' per-validator helper, the `except Exception` marked as the validator isolation boundary logs `Validator %s (%s) raised: %s: %s` with the type and the message only; the branch right below it, which runs an `LLMValidator` and logs `LLM validation for %s failed: %s: %s`, does the same. Two benchmark runs halted at this kind of boundary with `TypeError: 'function' object is not subscriptable` and nothing could say where. After this task every handler of this kind in `runner.py`, `quality.py` and `protocol_adherence.py` writes the traceback to the log as well. The sibling task 1.1 of this plan did the same in `llm_validator.py` and is already merged.

## STARTING STATE
An earlier attempt of this task already attached the traceback to the isolation boundary in `runner.py` and to the operational-fault handler in `protocol_adherence.py`, and added `tests/validators/test_validator_isolation_traceback.py` with its two tests; that work is inherited by this attempt's branch. What it left undone, and what the acceptance check reported: the `LLM validation for %s failed` branch in `runner.py` and any remaining handler in `runner.py`, `quality.py` and `protocol_adherence.py` that builds a `ValidatorResult` with `error=True` from a caught exception but still logs only the type and message. (The final run also hit an unrelated provider usage limit on the acceptance judge's model; that is not about the code.)
