## Intent
Given the data a finished or halted task already leaves on disk, the notification code can say which of five situations the operator is in: success, warn with a recovery task spawned, waiting for a human decision, blocked and needing a new dispatch, or an engine fault.

## Evidence
- The job monitor in notifications.py decides from `status` and `exit_code` alone, so every non-zero exit shows the same red cross and a repaired warn looks like success.
- The facts needed are already persisted: the `halt` payload in the job/task state.json (canonical halt type, reason, validator results with severity and justification, adjudicable, retryable), and the audit events `subtask_spawned` (recovery task id, triggering validator ids), `disagreement_escalated`, `recovery_exhausted` and `recovery_stalled`.
- Halt types validator_error, internal_error and environment_error are faults of the engine rather than of the work; they should not read as "blocked".

## Outcome
- One small pure function (plus a tiny result type) takes the already-parsed state/halt data and the task's audit events and returns the situation, the recovery task id when one was spawned, and the raw halt reason. It does no network access and writes nothing.
- A task that finished after a recovery task was spawned for it is the warn situation; a pending escalation is the human-decision situation; a halt with no recovery and no pending decision is blocked; the three fault halt types are the engine-fault situation; a clean completion with none of the above is success. Missing or malformed fields fall back to success only for a clean exit, otherwise to blocked, and never raise.
- The situations are plain strings or an enum local to the new module; they are not engine states and are not written to any state file.
- Tests cover each situation, a recovery that was exhausted or stalled, and malformed input. Existing tests under tests/jobs show the style.
