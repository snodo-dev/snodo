## Intent
A pure function that classifies a finished task into one of five operator situations is part of this plan and is missing from the branch, so the following task cannot use it. An earlier commit on this branch had such a module and a later recovery commit deleted it by mistake; the branch history may be used as a reference, but this spec is the contract.

## Evidence
- The jobs package has the halt summary module and no classifier.
- The job_finished message needs one answer per finished task: success, warn with recovery, waiting for a human, blocked, or engine fault.

## Outcome
- A frozen result type carries three values: the situation name, the id of a recovery task when one was spawned (otherwise nothing), and the halt reason exactly as found (otherwise nothing).
- One function takes a task state and a list of audit events and returns that result. The state is a mapping that may carry a status, an exit code and a halt mapping; the halt mapping may carry a type (also read under the older key halt_type), a reason and an adjudicable flag. Each audit event is a mapping whose kind is read from event_type, falling back to op.
- Situations are plain lowercase strings local to the module: success, warn_recovered, human_decision, blocked, engine_fault. Nothing is persisted and no engine vocabulary is added.
- Precedence, first match wins: a halt type of validator_error, internal_error or environment_error is engine_fault; an escalation event (disagreement_escalated) together with an adjudicable flag that is exactly true is human_decision; a recovery_exhausted or recovery_stalled event is blocked; a spawned-recovery event (subtask_spawned, whose task_ref or recovery_task_id names the recovery task, the last one wins) on a task whose status is completed or finished is warn_recovered; any other halt is blocked; a status of completed or finished with exit code 0 is success; an exit code of 0 whose status is not failed or halted is success; everything else is blocked.
- Input handling is defensive. Every field is type-checked before use and anything of an unexpected type is treated as absent; a state that is not a mapping is an empty state; audit events that are not a list or tuple are no events; entries that are not mappings are skipped; unhashable or list-valued fields never raise. The function never raises, and malformed input fails closed to blocked with no recovery task id and no halt reason. Only an explicit clean exit is ever success.
- The function only reads its inputs. It does not print, log, audit, persist or send anything, and it returns the halt reason untouched, because callers sanitise it for display through the halt summary module.
- The new test module covers: success, and the clean-exit fallback; warn with the recovery id and reason returned; an adjudicable escalation is human_decision; a halt with no recovery or decision is blocked; each of the three engine fault halt types is engine_fault and not blocked; recovery exhausted or stalled after a spawned recovery is blocked; malformed inputs (no state, wrong types, junk events) fail closed without raising; list-valued fields never raise.
