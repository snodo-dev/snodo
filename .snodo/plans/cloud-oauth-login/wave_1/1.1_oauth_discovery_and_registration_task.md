INTENT
snodo can learn where the cloud's OAuth server lives and register itself as a public client there, once, so that later tickets can run a browser sign-in. This ticket is the protocol plumbing for that, as a small self-contained module.

What the cloud side has agreed (from the exchange with the snodo-cloud agent): an OAuth server at https://mcp-auth.snodo.dev with metadata at the standard authorization-server metadata path on that host listing the authorize, token, register and jwks endpoints. It supports authorization code with PKCE (S256) for a public client (token endpoint auth method none), and dynamic client registration (POST to the register endpoint; redirect URIs of the form http://localhost:<port>/... with the hostname exactly "localhost", not 127.0.0.1). A `cli` scope is being added. Clients identify themselves with User-Agent `snodo/<version>` and a header `X-Snodo-Device: <hostname>`. Do not hard-code endpoint URLs other than the discovery URL, which should be configurable through the existing cloud config the way other cloud URLs are (see get_cloud_ingest_url in the core package's config module).

Indications: a new module in the infrastructure package of snodo-foundation, named cloud_oauth_client with: fetching and validating the metadata document (https only, required endpoints present); registering a client with redirect_uris ["http://localhost:*"] style registration as the metadata allows, returning the client_id; PKCE helpers (random verifier, S256 challenge, random state); building the authorize URL (response_type code, client_id, redirect_uri, scope `cli`, state, code_challenge, code_challenge_method S256); exchanging an authorization code at the token endpoint; and refreshing with a refresh token. Network failures and non-2xx answers become clear errors without leaking tokens. Keep this module free of any CLI or filesystem concerns; persistence belongs to another ticket (the token store) and the loopback listener to a third, both written in parallel, so do not edit their files.

Acceptance: tests with a stubbed transport cover metadata validation (missing endpoint, non-https), registration, the PKCE challenge against a known vector, the authorize URL contents, code exchange and refresh success, and error handling that never includes a token in the message.
