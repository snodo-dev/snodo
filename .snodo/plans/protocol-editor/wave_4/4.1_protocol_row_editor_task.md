New files this task will create: tests/web/test_static_protocol_editor.py.

INTENT
An open validator row shows the editor from the mockup and changes the working copy as the user types, so the page, the tiles, the pipeline and the save bar all reflect unsaved edits.

Evidence: in the mockup (docs/design/protocol-editor.html) an open row reveals an edit area with: a fields grid of four fields (Type: a select of the validator types; Phase: a two-button segmented control pre_execute and post_execute with the active one marked; Severity cap: a select; Tools (read-only): a text input with the placeholder "none" taking a comma-separated list), then a "Criteria" label, then one textarea per criterion each with a small × remove button (a criterion that differs from its original gets the modified look), then a "+ Add criterion" button, which appends an empty criterion and focuses it, and a "Remove from <mode> mode" or "Add to <mode> mode" button. Typing in a criterion updates the modified look and the save bar without losing focus. The previous ticket in this plan created the rows with an empty edit container, and protocol.js holds the original and the working copy.

What it should do: fill the edit container with exactly that structure, classes and copy (edit, fields, label, seg with on, crit with mod, textarea, x, btn). The type options are the validator types the protocol schema allows, plus the validator's current type if it is not among them. Severity cap options are none plus the values the schema allows, none meaning no cap. The tools input shows the validator's tools joined by comma and space and writes back a list (an empty input means no tools). Changes go to the working copy through the shared state so every other section re-renders, but typing into a textarea or the tools input must not rebuild the field being typed in. Removing the last criterion is allowed; an empty criterion is flagged to the save bar as a problem. The mode button toggles whether the initial mode runs the validator.
