INTENT
The tunnel first-run test passes on its own and in any test order, instead of depending on an earlier test having imported snodo.version.

Symptom and evidence: running only tests/mcp/test_server.py::TestTunnelRunErrors::test_first_run_provisions_and_starts_services fails with ValueError: not enough values to unpack (expected 2, got 0). The traceback goes from _run_tunnel in snodo/cli/commands/serve_cmd.py, which imports snodo.version lazily on the first-run provisioning path, into snodo/version.py, which runs git rev-list --count HEAD with subprocess.run when the module is first imported. The test patches snodo.cli.commands.serve_cmd.subprocess.Popen with a MagicMock, and because that is the real subprocess module, the patch is global. So the version module runs its git call through the mock, and communicate() returns a MagicMock that cannot be unpacked. When some earlier test has already imported snodo.version the test passes, which is why it passes in a full run and fails alone or when a per-task gate runs a small subset in a different order. A docs-only ticket in another plan was blocked three times by this.

What it should do: make the tunnel tests that patch subprocess.Popen in tests/mcp/test_server.py independent of whether snodo.version was imported before. The product code should stay as it is unless the coder finds a reason to change it. Check the other tunnel tests in that file that use the same Popen patch and make them robust in the same way.

CONSTRAINTS
Files that may change: tests/mcp/test_server.py and CHANGELOG.md (one entry under [Unreleased] ending with the issue reference Fixes #<n>). Do not change serve_cmd.py or version.py. No new state, status, severity or halt type.
