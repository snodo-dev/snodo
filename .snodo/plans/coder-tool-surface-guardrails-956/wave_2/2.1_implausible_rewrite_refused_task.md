# 2.1 — a whole-file rewrite of an existing file must be plausible

## Why this task exists

The in-process coder reads files with a tool that truncates large files, and then persists
whatever it passes as a whole-file replacement. Nothing checks that the submitted body is a
plausible replacement for the file that exists on disk, so a model that reconstructs a file
from a partial read silently deletes the unread tail. The result is a commit that destroys
thousands of lines of unrelated code.

Observed on a real dispatch on 2026-10-15: several reads of large engine files, then a
submission of eight files, producing a commit of +355 / −7705. The changelog went from five
thousand lines to twenty-one; an engine node module went from nine hundred lines to
forty-five; other files were reduced to stubs, and some submitted paths do not exist on the
base branch at all.

Nothing in the coder layer flagged it. The run stopped only because the post-execute quality
validator ran the suite (56 failures) and a repository vocabulary script caught a missing
symbol. That safety net is incidental: a truncation that leaves the suite green would be
committed, pushed and eligible for merge.

## Outcome

- A whole-file write to a path that already exists is refused at the tool surface when the
  submitted body is materially smaller than the file on disk, unless the coder says in the
  same call that the file is intentionally being replaced. The rejection names the path,
  the size delta and what the coder should do instead — re-read the file, or edit the
  region it actually needs — so the coder can recover in its own turn rather than have the
  deletion reach the merge gate.
- The check is about implausibility, not about a particular fraction: a submission that
  keeps most of the file, or that shrinks a file the task was told to shorten, is not
  blocked. The threshold and its wording must be legible to the coder that hits it.
- New files are unaffected: a path that does not exist is a creation, not a rewrite.
- The same surface that enforces protected paths today is the one that enforces this, so the
  two cannot drift apart (the in-process coder's tool layer, per ADR 026).
- The coder is told about the risk before it writes, not only after: a read that returned a
  truncated file says so in its result, and that notice must survive into whatever the coder
  is later reminded of when its write is refused.

## Acceptance

- A test that submitting a body materially shorter than the existing file is refused, that
  the refusal names the path and the delta, and that the file on disk is unchanged.
- A test that the same submission with the explicit acknowledgement writes through.
- A test that creating a new file is unaffected, and that a normal edit that keeps the file's
  substance passes without needing the acknowledgement.
- A test that a task whose specification asks a file to be shortened is not obstructed by
  the check.
- The existing protected-path tests in `tests/mcp` and the coder tests in `tests/coders` stay
  green.
- The coder and engine test suites pass, and the linter is clean.

## Constraints

- Refuse and explain, do not silently repair: the engine must not reconstruct or restore the
  file's tail on the coder's behalf.
- Do not block legitimate deletions of whole files when the task asks for them.
- The guard belongs at the write surface the coder calls, not in a post-hoc validator, so the
  coder gets the chance to correct itself within the same attempt.
- No new dependency.

## Diff discipline

Confine the change to what this task asks for. Do not reformat, reword, rename or delete code,
comments, docstrings or tests that this task does not change — the rationale notes in this
repository name the issue or incident that produced each branch and are part of the behaviour.
Messages an existing test quotes are a contract with the operator: add new text where this task
needs it, never replace pinned text. New coverage goes in new cases or new files rather than by
rewriting existing ones. Before submitting, look at the diff and remove any hunk that this task's
outcome does not require, then run the whole gate command from the contributing guide and leave
it clean.
