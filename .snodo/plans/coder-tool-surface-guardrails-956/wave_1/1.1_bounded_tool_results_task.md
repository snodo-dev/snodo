# 1.1 — every tool result that reaches the model must be bounded

## Why this task exists

The in-process coder sends a tool's result back into the conversation with no size bound,
so one broad test run can make the next request impossible to serve. The task, the spec and
the protocol are fine; the run halts as an operational fault and burns an attempt.

Observed on a real dispatch, 2026-10-16: turn five called a directory-wide test run, and
turn six halted with

```text
litellm.BadRequestError: OpenAIException - Invalid 'input[21].output[0].text': string too
long. Expected a string with maximum length 10485760, but got a string with length
93550113 instead.
```

93.5 MB of text entered the conversation from a single tool result.

The mechanism is in `packages/snodo-engine/src/snodo/coders/litellm.py`: file reads are
bounded (a byte cap, with the result telling the model what was omitted and how to
continue), while the test-run tool returns the captured stdout and stderr verbatim from
`run_tests_raw` in `packages/snodo-tools/src/snodo/tools/shell.py`. A helper that looks like
a guardrail bounds only the audit log, not what the model sees.

The halt text makes the situation worse than it is: the engine reports that nothing about
the spec, the code or the protocol needs fixing, when a missing bound is precisely an engine
defect that recurs for any task whose test output is large.

## Outcome

- Every tool result that enters the model conversation is bounded the way reads already
  are: the model gets the head of the output, is told plainly that it was truncated, how
  much was dropped, and what to do next — a narrower test target, or the log path it can
  read selectively.
- The bound applies to test runs and to any other tool that falls through the coder's tool
  dispatch, not only to file reads. One place owns the rule so the tools cannot drift apart.
- The bound is stated in characters that fit inside a provider's per-string limit with room
  to spare, and the truncation notice itself survives it.
- The audit record still keeps the fuller output where it does today; the bound is about
  what the model is sent, not about what the engine stores.
- A halt caused by an over-long request is named for what it is: an engine-side bound that
  was missing, not a coder or spec fault.

## Acceptance

- A test that a tool result larger than the bound is truncated before it is sent back to
  the model, and that the text the model receives says it was truncated and names the
  omitted size.
- A test that a large test-run result keeps the failure summary the model needs — the tail
  of the output where the failures are — rather than only the head, so the bound does not
  hide the reason the run failed.
- A test that a result within the bound is passed through unchanged.
- The existing coder tests in `tests/coders` stay green, including the truncation and
  execution-failure tests already there.
- The coder and engine test suites pass, and the linter is clean.

## Constraints

- Do not bound the audit log any tighter than it is today.
- Do not change what the test runner itself runs or reports to the operator; this is about
  the conversation.
- No new dependency, and no per-tool special cases that leave the fall-through path unbounded.

## Diff discipline

Confine the change to what this task asks for. Do not reformat, reword, rename or delete code,
comments, docstrings or tests that this task does not change — the rationale notes in this
repository name the issue or incident that produced each branch and are part of the behaviour.
Messages an existing test quotes are a contract with the operator: add new text where this task
needs it, never replace pinned text. New coverage goes in new cases or new files rather than by
rewriting existing ones. Before submitting, look at the diff and remove any hunk that this task's
outcome does not require, then run the whole gate command from the contributing guide and leave
it clean.
