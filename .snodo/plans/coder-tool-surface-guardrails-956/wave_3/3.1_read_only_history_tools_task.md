# 3.1 — a coder must be able to consult the repository's history

GitHub issue #961 already exists for this work. Do not open another; put "Fixes #961" in the commit message. Add one CHANGELOG entry under [Unreleased] (soft wording, "(Fixes #961)").

Length note: the LiteLLM adapter module has a file-length baseline that may only fall, and it was just tightened. Put the new history-tool logic in a small sibling module under the coders package with only thin wiring in the adapter, and keep the adapter at or below its baseline. Never raise a baseline.

## Why this task exists

A coder dispatched through the protocol engine has no way to see the repository's history.
Its tool surface is listing, reading, running tests and submitting files — all of which see
only the current working tree of the task workspace. There is no git tool and no shell, and
reading the git directory is refused as a protected path.

That makes a whole class of legitimate task impossible: anything that asks the coder to
recover, compare or reconcile against a previous revision. The engine already relies on
history elsewhere — the rebase attribution work compares a task branch against its merge
base — but the coder cannot do the same thing.

Observed on the task that restored the explanation deleted in plan
`verdict-subject-accountability-951`: the spec asked for comments and docstrings that an
earlier task in the same plan had removed. The attempt halted after eleven turns saying it
could not faithfully restore them because it had no history access and its reads were
blocked, and asked the operator for the diff instead. That refusal was the right behaviour —
inventing plausible-looking explanation and submitting it as restored would have been worse.
The task was simply unsatisfiable as written. The operator's workaround is to paste the
removed text into the spec, which turns a recovery job into a transcription job and puts the
burden of correctness on whoever extracts the diff.

## Outcome

- The coder's tool surface gains read-only history capability: which commits touched a path,
  what a path looked like at a given revision, and the difference between two revisions.
  Whatever the validators already have for git is the model — the same names and the same
  meanings, so a coder reading a decision record finds the tool it expects.
- Every one of those results is bounded the way reads are bounded, and says what was omitted
  and how to narrow the request.
- The capability is read-only and confined to the task's own repository. It does not open a
  shell, does not allow writes, and does not weaken the protection that keeps the engine's
  own state unreadable to coders.
- A coder that asks for a revision that does not exist gets an answer it can act on, not a
  crash: the record names the ref it could not resolve.
- The tool surface a coder is given is recorded, so a halt can be read as "this attempt had
  no history access" rather than rediscovered by inference.

## Acceptance

- A test that a coder can list the commits touching a path and read that path at a previous
  revision, and that the content it receives is the historical content.
- A test that a history result larger than the bound is truncated with a notice, reusing the
  bound the earlier wave introduced rather than a second one.
- A test that the history tools cannot write and cannot reach the protected engine state.
- A test that an unresolvable revision produces a legible refusal rather than an
  operational fault.
- The existing coder tool tests in `tests/coders` stay green, including the ones pinning the
  shape of the tool surface.
- The coder and engine test suites pass, and the linter is clean.

## Constraints

- Read-only. Do not give the coder a general shell to solve this.
- Do not change what validators may read; their grants stay as they are.
- Reuse the existing git tooling rather than adding a new dependency or a second
  implementation of the same queries.

## Diff discipline

Confine the change to what this task asks for. Do not reformat, reword, rename or delete code,
comments, docstrings or tests that this task does not change — the rationale notes in this
repository name the issue or incident that produced each branch and are part of the behaviour.
Messages an existing test quotes are a contract with the operator: add new text where this task
needs it, never replace pinned text. New coverage goes in new cases or new files rather than by
rewriting existing ones. Before submitting, look at the diff and remove any hunk that this task's
outcome does not require, then run the whole gate command from the contributing guide and leave
it clean.
