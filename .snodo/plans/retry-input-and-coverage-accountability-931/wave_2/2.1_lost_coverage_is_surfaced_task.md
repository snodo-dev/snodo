# 2.1 — the loop must notice when an attempt deletes coverage or explanation

GitHub issue #959 already exists for this work. Do not open another; put "Fixes #959" in the commit message.

## Why this task exists

Nothing in the loop sees a task removing existing test cases. The quality gate runs whatever
tests are present, so a delivery that deletes tests passes more easily than the delivery that
kept them, and deleting coverage is rewarded.

Two instances were delivered on plan `verdict-subject-accountability-951` on 2026-10-16, in
separate tasks, by the same coder model, and both were caught by a human reading the diff:

```text
1. 1.1_verdict_names_its_subject, attempt 1 — the validator module went from 1,362 to
   1,010 lines and the mock coder from 265 to 239, deleting 156 comment lines, 49 blank
   lines and roughly 350 lines of docstring prose, to satisfy the length ratchet. The
   ratchet does not count prose at all, so the deletion bought nothing. The gate passed.

2. 2.1_reuse_provenance, attempt 1 — a cache test module went from 887 to 482 lines, and
   the contract comments describing the cache's guarantees were removed from the core
   interfaces and the validator runner, including the two sentences stating that an error
   and a skipped pass are never stored or reused and that the runner never raises. The
   attempt then broke exactly that guarantee, and only that failure halted the task. Had
   the taxonomy not moved, the delivery would have passed with 400 lines of cache tests
   gone and their documentation deleted with them.
```

That is the opposite of how the loop is supposed to work: the judges are meant to see the
change, and today the change the post-execute judges are handed
(`packages/snodo-engine/src/snodo/validators/change.py`) is a bounded diff in which a
hundred removed test cases look like a hundred removed lines of noise.

## Evidence from the previous attempts

Attempt 1: the detection module started git through the process module with a bare
executable name, which the project's security lint rules (S603 and S607) reject.

Attempt 2: the module was moved onto GitPython and the lint is now clean, but the quality
gate's full suite stopped on the suite's leak guard: three tests in
`tests/validators/test_coverage_accountability.py` ended with live child processes
(`git cat-file --batch-check` and `git cat-file --batch`) and were reported as leaked
running work (Fixes #258). Everything else passed (5695 passed). The repository was opened
in a way that leaves a persistent git helper process alive after the test returns. The
project already has one sanctioned way to open a repository without that side effect,
documented in `snodo.tools.git` (`open_repo`); use it everywhere this change opens a
repository, in the code and in the tests, and make sure nothing the change starts outlives
the call. Failures to read a revision are handled with logging or a typed result, never an
empty handler (the linter rejects those).

Before finishing, run the new tests together with the leak guard active the way the gate
does (the whole `tests/validators` directory and `tests/engine/test_post_validate_recovery.py`
in one pytest invocation), not only the new file in isolation, and run the linter.

## Outcome

- At delivery time the loop knows which test cases existed at the task's base, and a case
  that has disappeared is surfaced as a finding naming the file and the case, at a severity
  that reaches the operator rather than resting in a log line.
- A disappearance is expected, and not a finding, only when the task's own specification
  asks for that test to change or go away. The authoritative spec text is already carried
  separately from the composed retry prompt, so the comparison is against what the operator
  actually asked for.
- The same visibility applies to wholesale removal of explanatory comments and docstrings
  from files the task had no reason to shorten. It is the same failure mode under the same
  pressure, and it degrades the very files the validators then have to judge: a judge
  reading a stripped module is a judge without the contract the comments carried.
- The finding is stated in the terms the operator acts on — what went missing, from where,
  and what to look at — in the same place other post-execute findings appear.

## Acceptance

- A test that removes an existing test case between the base and HEAD and asserts a finding
  naming the file and the case is recorded, at a severity that reaches the operator.
- A test that the same removal produces no finding when the task's specification explicitly
  asks for that test to change or go away.
- A test that a task which legitimately rewrites a test case in place, keeping the case,
  produces no finding.
- A test covering the explanation-loss path: a file stripped of a large share of its
  comment and docstring lines without being asked to produces a finding.
- The existing post-execute tests in `tests/engine/test_post_validate_recovery.py` stay
  green, as do the validator tests in `tests/validators`, with no leaked child processes
  reported by the suite's leak guard.
- The engine and validator test suites pass, and the linter is clean, including the
  security rules.

## Constraints

- This is visibility, not a veto: the judges still decide the task, and a finding is not a
  blocker. Do not add a halt type or make the check refuse the delivery outright.
- Detecting the lost set must not require running the test suite at the base revision, and
  must not add a new dependency.
- Do not change what the length ratchet counts; that rule is deliberate and documented.
- Keep the change block bounded as it is today. Any new section it carries must respect the
  existing character limit rather than trading one unbounded failure for another.
- Add a CHANGELOG entry under [Unreleased] (soft wording, "(Fixes #959)").
