Before starting, open a GitHub issue on snodo-dev/snodo titled "Judge a pull request's changes with the project's own protocol validators from the CLI". Put "Fixes #<n>" in the commit message, and add a CHANGELOG.md entry under ## [Unreleased]. If an earlier attempt already opened this issue, reuse it.

INTENT
Snodo's value is that a project's protocol judges work. The only CI integration today is the advisory PR-review workflow (`.github/workflows/pr-review.yml` and `scripts/pr_review.py`). It runs a recon review and posts a comment; it does not run the project's own protocol validators. Teams that want "this PR must pass our snodo protocol" have to build that themselves. That is evidence from adoption recon rec_d6ff28.

When this is done, the CLI can run the project's validators against the changes on a branch or pull request and report the verdicts. It uses the existing machine-interface exit codes and the structured halt payload, so a CI job can gate on it.

- **A git ref range** (base ref and head ref) is the core input and stays vendor-neutral.
- **A pull or merge request number** is resolved to that ref range through the code-host provider plugins, not core code.

A previous attempt implemented this but `make gate` failed its file-length check: the change pushed an existing CLI module past its line-count ratchet. The gate's file-length check (and its frozen debt list) is the rule. New logic belongs in its own focused module that the existing entry point calls, not appended to an already-large file.

THE CHAIN
1. Extend an existing CLI entry point that runs validators. Read how `validate_task` and the CLI validation path work, and reuse them. Do not add a new top-level command; the owner avoids adding top-level CLI commands.
2. Ref-range input is resolved with git only. The PR or MR number is resolved through the provider plugin interface; the GitHub provider is the first implementation.
3. Output follows `docs/machine-interface.md`: `--json`, the documented exit codes, and the structured halt payload on a block.
4. Tests:
   - a ref range with passing validators exits 0;
   - a blocking verdict exits with the documented code and payload;
   - a PR number is resolved through a fake provider.

CONSTRAINTS
- Core stays git-only. Code-host API calls live only in provider plugins.
- Snodo's state machine is closed: use the existing outcomes and severities.
- No file may exceed its file-length limit or baseline. Do not raise a baseline or add a file to the frozen debt list.
- Do not edit the container image files, GitHub Action files or CI docs page. Other tasks own those.

ACCEPTANCE
- The tests in link 4 exist and pass.
- The CHANGELOG entry is present.
- `make gate` passes, including the file-length check.
