# 2.1 — the tunnel path wrapper in front of a real mcp 2.x app keeps host protection

GitHub issue #1027 already exists for this work. Do not open another; put "Fixes #1027" in the commit message. Do not edit the CHANGELOG; the entry is already there.

## INTENT

For a service-token tunnel the MCP server's `streamable_http_app` and `sse_app` factories are wrapped so the tunnel path router (`TunnelMCPPaths`) sits in front of the real app. On mcp 2.x the factories take `host` and `transport_security`; if the wrapper dropped or mis-forwarded either, the router would serve an app without the tunnel hostname allowed (or without protection) and nothing would say so. The previous task of this plan moved the wiring into one named function (`install_tunnel_mcp_paths` in `snodo/cli/commands/serve_tunnel_asgi.py`) that `_run_server` calls.

The deliverable is ONE new test module, `tests/mcp/test_tunnel_factory_host_protection.py`, that builds a real mcp 2.x server through the project's server builder, calls that same function the way `_run_server` does (do not re-implement the wrapper in the test), calls each wrapped factory the way `run` does, with `host` and the value of `build_transport_security_settings` for a tunnel hostname, and drives the resulting ASGI app in process (no sockets, no `TestClient`):

- a request whose `Host` is the tunnel hostname is not refused with 421; the SDK default protection would refuse that name, so a wrapper that dropped `transport_security` fails here;
- a request whose `Host` is a foreign name is refused with 421;
- both factories are exercised on their own routes, read from the app rather than assumed (`sse_app` serves its own paths, not `/mcp`);
- the streamable-http app needs its session manager's task group: `tests/mcp/test_auth.py` shows how this repo's tests install it (`mcp.session_manager._task_group` inside an anyio task group); do the same.

The Access verifier may be stubbed; everything else is real.

## What is already on this task's branch, and what went wrong

This task has been attempted several times and its branch carries leftovers. Two test modules exist on the branch and neither is on main:

- `tests/mcp/test_tunnel_factory_security.py`: an earlier attempt using `TestClient` and a fixed wrapper depth. It hangs (it sends a request to the SSE route through `TestClient`, which never returns because an SSE response never ends), and it is the reason the engine's whole-suite gate has twice timed out after ten minutes and failed this task. Delete this file. It is this task's own leftover, not an existing module, so removing it does not break the "do not edit existing modules" rule.
- `tests/mcp/test_tunnel_factory_host_protection.py`: the current attempt, not passing. Rewrite it in place as described below.

Known facts to use:

1. A stub protocol that exposes no tools cannot build a server (the real builder refuses when its generated instructions name tools the server does not expose). Build the server from a real protocol: write a minimal protocol file to `tmp_path` (`tests/mcp/test_serve_http_real_process.py` has one that the real server builds from without complaint), read it with the same `load_protocol` that `snodo.cli.commands.serve_cmd` uses, and construct `ProtocolMCPServer` and `build_fastmcp_server` the way `_run_server` does. Do not stub the protocol, `ProtocolMCPServer`, or `get_tools`.
2. A wrapped factory returns a `TunnelMCPPaths` instance, and it does not own the routes: the server builder wraps the factories too (`_MissingAuthorizationObserver` in the snodo-mcp package's `transport.py`, possibly more), so the Starlette app sits several `.app` hops down. Find the routes by following `.app` from the wrapper until an object has `.routes`. Send the requests to the `TunnelMCPPaths` instance itself so the wrapper stays in the path under test. Do not add attributes to production classes to make the test easier.
3. Drive the ASGI app by hand: a `receive` that delivers the request and then `http.disconnect`, and a `send` that records the messages. A refused request completes by itself; read its status from the first `http.response.start`.
4. For a refused SSE request the SDK (the `connect_sse` method of the SDK's SSE transport) sends the 421 and then raises `ValueError("Request validation failed")`. That is expected: catch that `ValueError` around the call and assert on the recorded 421.
5. An SSE response for an allowed host never ends on its own. Record the first `http.response.start`, assert it is not 421, and let the `http.disconnect` end the call. Every in-process call must be bounded by a short timeout (for example `anyio.fail_after(5)`), so the worst case is a failing test, never a hang. If one case cannot be made to finish on its own, drop that case and say so in the commit message rather than leaving it hanging.
