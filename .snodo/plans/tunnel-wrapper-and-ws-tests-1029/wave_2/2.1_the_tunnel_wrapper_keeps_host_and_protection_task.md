# 2.1 — the tunnel path wrapper in front of a real mcp 2.x app keeps host protection

GitHub issue #1027 already exists for this work. Do not open another; put "Fixes #1027" in the commit message. Do not edit the CHANGELOG; the entry is already there.

## INTENT

For a service-token tunnel the MCP server's `streamable_http_app` and `sse_app` factories are wrapped so the tunnel path router (`TunnelMCPPaths`) sits in front of the real app. On mcp 2.x the factories take `host` and `transport_security`; if the wrapper dropped or mis-forwarded either, the router would serve an app without the tunnel hostname allowed (or without protection) and nothing would say so. The previous task of this plan moved the wiring into one named function that `_run_server` calls.

In a new test module under `tests/mcp` (do not edit existing modules), build a real mcp 2.x server through the project's server builder and call that same function the way `_run_server` does (do not re-implement the wrapper in the test), then call each wrapped factory the way `run` does, with `host` and the value of `build_transport_security_settings` for a tunnel hostname, and drive the resulting ASGI app in process (no sockets):

- a request whose `Host` is the tunnel hostname is not refused with 421; the SDK default protection would refuse that name, so a wrapper that dropped `transport_security` fails here;
- a request whose `Host` is a foreign name is refused with 421;
- both factories are exercised on their own routes, read from the app rather than assumed (`sse_app` serves its own paths, not `/mcp`);
- the streamable-http app needs its session manager's task group: `tests/mcp/test_auth.py` shows how this repo's tests install it (`mcp.session_manager._task_group` inside an anyio task group); do the same.

The Access verifier may be stubbed; everything else is real.

## Acceptance

- The new tests pass and cover both factories.
- A wrapper that dropped `transport_security` or `host` would fail them.
- Existing tests stay green; the linter is clean.
