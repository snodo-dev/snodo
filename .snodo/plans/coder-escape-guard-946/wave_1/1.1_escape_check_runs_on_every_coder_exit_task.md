## Intent
The engine's workspace-escape check should run on every way a coder run can end, so a coder that escapes its workspace is reported whether or not it also produced artifacts, timed out, ran out of turns or failed. Reporting an escape must never launder, replace or reclassify a failure the run already had.

## Evidence
- packages/snodo-engine/src/snodo/engine/nodes/executor.py: `_repo_ref_snapshot` is taken once before `coder.implement(...)` and `_escaped_repo_commit` compares it afterwards. In `_default_executor` the comparison runs only on the empty-artifact path, in the `TurnBudgetExhausted` handler and in the `CoderTimeoutError` handler. The path that commits non-empty artifacts, the findings-only path and the `SnodoMutationError`, `AdapterError` and generic exception handlers never run it.
- Subprocess coders can return non-empty artifacts after a timeout or a nonzero exit instead of raising (packages/snodo-engine/src/snodo/coders/subprocess_adapter.py), so those runs also take the unchecked path.
- Live case recorded in issue #946: an `opencode-cli` coder ran `git checkout`, `git commit` and `git clean` in the operator's checkout while its task worktree stayed empty of commits.
- An escape is reported today by raising the existing `ExecutionError`, which the loop routes to `internal_error` with a generic `execution_failed` audit event.
- Failures that already carry their own classification must keep it. ADR 027: a `SnodoMutationError` is caught by `_execute_node` and becomes the terminal blocker halt with a `snodo_mutation_blocked` audit event naming the paths; replacing it with `ExecutionError` would hide that governance event. ADR 015: an `AdapterError` (including `CoderUnavailableError`) is an operator-fixable `execution_error` family halt, canonically `environment_error`; turning it into `ExecutionError` would report a coder fault as an engine defect.

## Outcome
- The escape comparison happens once on each way `_default_executor` can finish after the coder was started, before artifacts are committed or accepted.
- Where the run would otherwise succeed (non-empty artifacts, findings-only), or already ends in `ExecutionError` or the generic-exception wrapper, an escape ends the run with the existing `ExecutionError` carrying the escape description; when the run was already failing for another reason in that group, the original reason stays visible in the message.
- Where the run ends with `SnodoMutationError` or `AdapterError` (and its subclasses), the original exception, halt classification and audit events are unchanged. The escape description is made visible without changing that outcome (for example appended to the message or recorded through the logging or audit mechanism the executor already uses); the executor decides which, and says so in its summary.
- A run with no escape behaves exactly as today on every path, including the messages of the existing errors.
- Tests cover: escape plus non-empty artifacts, escape plus findings-only result, escape during a timeout and a turn-budget exhaustion, escape plus `SnodoMutationError` (halt type and `snodo_mutation_blocked` event preserved), escape plus `AdapterError` (halt classification preserved), and a clean run on each of those paths that is not reported. Follow the existing executor test style in tests/engine/.
- Only the executor and its tests change. No new states, statuses, severities or halt types.
