## Intent
An operator who explicitly configures `sandboxed: true` for a host CLI coder (the subprocess coder family, such as `opencode-cli`) should be told no, not given an INFO line. The host CLI cannot be contained, so the run halts as `environment_error`, the same existing halt a contained coder gets when containment cannot be provided, and the message says what to do instead.

This is an amendment to how ADR 051 treats a coder that cannot honour `sandboxed`, and the task must say so: ADR 051's Decision says such an adapter reports through the path that already reports settings a coder does not read, while its Consequences say a protocol that declares containment "gets a refusal when the environment cannot provide it, instead of an uncontained run that looks identical in the log". An explicit `sandboxed: true` on a host CLI is exactly that second case. The task carries out the Consequences sentence and records the clarification in the ADR, so the record and the code agree.

## Evidence
- packages/snodo-engine/src/snodo/coders/subprocess_adapter.py: `honoured_settings` is `model`, `timeout_seconds`, `workspace`; `sandboxed` is absorbed by `**kwargs` and dropped. The container `OpenCodeAdapter` honours it and raises `CoderUnavailableError` when containment cannot be provided (packages/snodo-engine/src/snodo/coders/opencode_adapter.py).
- packages/snodo-engine/src/snodo/coders/inert_settings.py: `report_inert_coder_settings` logs an INFO line for an explicit setting the coder cannot honour and by contract never raises. That contract stays as it is, for every setting. It is called where a coder is selected: graph build in packages/snodo-engine/src/snodo/engine/loop.py (around lines 1340-1359) and the governance respawn in packages/snodo-engine/src/snodo/engine/nodes/writeback.py.
- `CoderUnavailableError` (packages/snodo-engine/src/snodo/coders/base.py) is the existing way to say the environment cannot provide the coder, and the loop canonicalises it to `environment_error`.
- docs/decisions/051-coder-containment-is-declared-not-deployed.md carries both statements quoted above.

## Outcome
- When `sandboxed` is explicitly true (explicit in the llm.coder config or the mode's coder_config; not the default) and the selected coder is a host CLI coder, the run halts as `environment_error` through `CoderUnavailableError`. The message names the setting, the coder, that a host CLI cannot be contained, and the two ways out: remove the setting, or use the container coder that honours it (ADR 051). The refusal is a separate check; `report_inert_coder_settings` keeps reporting and never raising.
- Everything else keeps today's behaviour: an unset or false `sandboxed`, the container coder, and any other setting a coder cannot honour still get only the informational line.
- Find the point where raising actually reaches the `environment_error` halt (graph build may be too early to reach it); a test must observe the halt type `environment_error`, not just the exception. Cover graph build and the governance respawn path.
- Append a short dated clarification note to the end of docs/decisions/051-coder-containment-is-declared-not-deployed.md (existing decision text untouched) stating that an explicit `sandboxed: true` on a host CLI coder is refused as `environment_error` instead of only reported, following the Consequences sentence, and that unset `sandboxed` and other unhonoured settings are still only reported. Run the docs strict check yourself and report the result.
- No new states, statuses, severities or halt types. Do not touch packages/snodo-engine/src/snodo/engine/nodes/executor.py (another task in this wave edits it).
