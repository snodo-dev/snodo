## Intent
An operator who configures `sandboxed: true` for a host CLI coder (the subprocess coder family, such as `opencode-cli`) should be told no, not given an INFO line. The host CLI cannot be contained, so the run halts as `environment_error`, the same existing halt a contained coder gets when containment cannot be provided, and the message says what to do instead.

This amends how ADR 051 treats a coder that cannot honour `sandboxed`, and the task says so: ADR 051's Decision says such an adapter reports through the path that already reports settings a coder does not read, while its Consequences say a protocol that declares containment "gets a refusal when the environment cannot provide it, instead of an uncontained run that looks identical in the log". A configured `sandboxed: true` on a host CLI is exactly that second case. The task carries out the Consequences sentence and records the clarification in the ADR, so the record and the code agree.

## Evidence
- packages/snodo-engine/src/snodo/coders/subprocess_adapter.py: `honoured_settings` is `model`, `timeout_seconds`, `workspace`; `sandboxed` arrives as a constructor keyword (the engine always passes it, false unless configured) and is absorbed by `**kwargs` and dropped. The container `OpenCodeAdapter` honours it and raises `CoderUnavailableError` from inside its run path when containment cannot be provided (packages/snodo-engine/src/snodo/coders/opencode_adapter.py).
- `CoderUnavailableError` (packages/snodo-engine/src/snodo/coders/base.py) is the existing way to say the environment cannot provide the coder. Raised from a coder's run path it reaches the existing halt `environment_error` (packages/snodo-engine/src/snodo/engine/nodes/validation.py handles it ahead of the general adapter error).
- packages/snodo-engine/src/snodo/coders/inert_settings.py: `report_inert_coder_settings` logs an INFO line for a setting the coder cannot honour and by contract never raises. That contract stays as it is, for every setting. Graph build (packages/snodo-engine/src/snodo/engine/loop.py, around lines 1340-1359) and the governance respawn (packages/snodo-engine/src/snodo/engine/nodes/writeback.py) construct the coder; raising at construction is too early to reach the halt, so the refusal belongs where the coder runs.
- A previous attempt at this task stopped without changes because it could not find where to place the refusal; the adapter's run path, not graph build or the executor, is the place.
- docs/decisions/051-coder-containment-is-declared-not-deployed.md carries both statements quoted above.

## Outcome
- A host CLI coder constructed with `sandboxed` true refuses when it is asked to run, by raising `CoderUnavailableError` before it starts any subprocess. The message names the setting, the coder, that a host CLI cannot be contained, and the two ways out: remove the setting, or use the container coder that honours it (ADR 051). With `sandboxed` unset or false the adapter behaves exactly as today. The refusal is a separate check; `report_inert_coder_settings` keeps reporting and never raising, and other unhonoured settings still get only the informational line.
- Tests cover: the refusal message and exception from the adapter's run path for the subprocess coder family; no refusal when `sandboxed` is false or absent; and one test through the engine that observes the halt type `environment_error`, not just the exception. Follow the existing coder and executor test styles; do not edit packages/snodo-engine/src/snodo/engine/nodes/executor.py (another task in this wave edits it).
- Append a short dated clarification note to the end of docs/decisions/051-coder-containment-is-declared-not-deployed.md (existing decision text untouched) stating that a configured `sandboxed: true` on a host CLI coder is refused as `environment_error` instead of only reported, following the Consequences sentence, and that unset `sandboxed` and other unhonoured settings are still only reported. Run the docs strict check yourself and report the result.
