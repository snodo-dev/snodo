## Intent
A host CLI coder that edits the operator's checkout through its shell should be stopped at acceptance, whether or not any branch tip moved. The executor takes a content baseline of the operator's checkout before dispatch and compares it when the run ends, reporting any change through the same existing escape error. If the baseline cannot be established, the run does not proceed on a guess.

## Evidence
- Wave 2 of this plan added a checkout-state helper in packages/snodo-engine/src/snodo/engine/ (the checkout snapshot module; read it first; use it, do not re-implement it). It returns the changed paths between a baseline and now, or an explicit "could not establish or compare" result. Its `.snodo/` handling already keeps only operator-authored files (protocol.yml, plan.yml, wave spec files) and ignores engine runtime state.
- Wave 1 (already on main) made the executor's escape comparison in packages/snodo-engine/src/snodo/engine/nodes/executor.py run on every way a coder run can end after the coder started. Read the current `_default_executor` and name those exits for yourself; they are: the empty-artifact path, the non-empty-artifact path (checked before the commit), the findings-only / no-workspace / recovered-work end of the function, `SnodoMutationError`, `AdapterError` (and subclasses such as the coder-unavailable error), `TurnBudgetExhausted`, `CoderTimeoutError`, `ExecutionError`, and the generic exception wrapper. An `escape_checked` guard prevents a double check. The new comparison runs at exactly these points, next to the branch-tip comparison, not in a new place.
- On `SnodoMutationError` and `AdapterError` Wave 1 deliberately keeps the original exception, halt classification and audit events (ADR 027, ADR 015) and only makes the escape visible by logging it. A found checkout change on those two exits is made visible the same way and does not replace the original exception or halt; on every other exit it is reported through the same `ExecutionError` the branch-tip escape uses.
- Which coders the guard applies to is decided by the declared kind of coder, not inferred from how it behaves: it applies to host CLI coders, meaning the subprocess adapter family (the coders that run a host shell). In-process tool-loop coders do not need it. The one fact consulted besides the coder kind is whether the dispatched workspace is a different directory from the primary checkout; when they are the same directory (a run without isolation, or an in-place project) the coder legitimately edits the checkout and the guard does not apply. A host CLI coder configured `sandboxed: true` is already refused before it runs (Wave 1), so it never reaches this guard.
- A real operator can edit their own checkout while a run is in flight; the guard cannot tell that from a coder. The halt is the existing execution error, so the operator reads the listed paths, settles the checkout, and re-runs the task the usual way; nothing else is blocked.

## Outcome
- Before the coder starts, the executor takes the baseline at the same point as the branch-tip snapshot. When the guard applies, an unavailable baseline stops the run before dispatch with the existing `ExecutionError` (it reaches the existing `environment_error` halt), saying the checkout could not be examined.
- On every exit listed in Evidence where the executor already runs the escape comparison, it also compares against the baseline. A changed path produces the escape error naming up to a small number of changed paths and the total count. An unavailable comparison after the run is also reported, with a message that clearly says the checkout could not be compared, distinct from the message for changed paths; it is never silently ignored.
- On the `SnodoMutationError` and `AdapterError` exits the original exception and halt are unchanged and the finding is logged, matching Wave 1.
- Runs where the guard does not apply (in-place work, in-process coders, no distinct primary checkout) behave exactly as today, with no extra git calls beyond what is needed to decide that.
- Tests with real Git repositories: a shell-style edit of a clean file, of an already-dirty file, and a deleted untracked plan record, each stop the run; an unchanged checkout passes; in-place work is not blocked; an in-process coder is not checked; an unavailable baseline halts before dispatch with the could-not-examine message; an unavailable comparison after the run reports the could-not-compare message; a changed checkout on the `SnodoMutationError` and `AdapterError` exits leaves the original exception and halt classification untouched; engine runtime state written during the run is not reported.
- `make gate` passes. If an unrelated test in the gate times out or leaks a process, say so in the commit message rather than editing unrelated tests.
- No new states, statuses, severities or halt types. No new configuration setting.
