## Intent
A host CLI coder that edits the operator's checkout through its shell should be stopped at acceptance, whether or not any branch tip moved. The executor takes a content baseline of the operator's checkout before dispatch and compares it when the run ends, reporting any change through the same existing escape error. If the baseline cannot be established, the run does not proceed on a guess.

## Evidence
- Wave 2 of this plan added a checkout-state helper in packages/snodo-engine/src/snodo/engine/ (read it first; use it, do not re-implement it). It returns the changed paths between a baseline and now, or an explicit "could not establish or compare" result.
- Wave 1 made the executor's escape comparison run on every way a coder run can end (packages/snodo-engine/src/snodo/engine/nodes/executor.py). The new comparison belongs beside it so both fire on the same exit paths and report through the same `ExecutionError`.
- A coder that works in place in the operator's checkout (a run without isolation, or a project where the dispatched workspace is the primary checkout) legitimately changes it; the guard must not apply there. In-process tool-loop coders write only through workspace tools and do not need it; it is for coders that run a host shell.
- A real operator can edit their own checkout while a run is in flight; the guard cannot tell that from a coder, so the message must list the changed paths so the operator can judge.

## Outcome
- Before the coder starts, the executor takes the baseline at the same point as the branch-tip snapshot. When the coder is a host CLI coder and the dispatched workspace is a task worktree separate from the primary checkout, an unavailable baseline stops the run before dispatch with the existing `ExecutionError` (it reaches the existing `environment_error` halt), saying the checkout could not be examined.
- On every exit that already runs the escape comparison, the executor also compares against the baseline. A changed path produces the existing escape `ExecutionError` naming up to a small number of changed paths and the total count. An unavailable comparison after the run is treated the same way as a found change: it is reported, not ignored.
- Runs where the guard does not apply (in-place work, in-process coders, no distinct primary checkout) behave exactly as today, with no extra git calls beyond what is needed to decide that.
- Tests with real Git repositories: a shell-style edit of a clean file, of an already-dirty file, a deleted untracked plan record, all stop the run; an unchanged checkout passes; in-place work is not blocked; an unavailable baseline halts before dispatch; engine runtime state written during the run is not reported.
- No new states, statuses, severities or halt types. No new configuration setting.
