## Intent
Give the engine a way to say whether the content of the operator's checkout changed between two moments, so a later task can use it to catch a coder that edits the main checkout through its shell without moving any branch tip. This task adds only the capability and its tests; nothing calls it yet. A good attempt already exists on this task's branch (the snapshot module under the engine package and its test file, built on GitPython); correct and extend that work rather than starting over.

## Evidence
- packages/snodo-engine/src/snodo/engine/nodes/executor.py `_repo_ref_snapshot` and `_escaped_repo_commit` compare branch-tip SHAs only. A `git apply`, heredoc, `cp` or `python` write to the main checkout, or a `git clean`, changes no branch tip and is invisible. Issue #946 records a live case where untracked plan definition files (plan.yml and the wave spec files) in the operator's checkout were deleted this way.
- Comparing git status paths alone misses an edit to a file that was already dirty, so the comparison must be against a baseline of content, not a clean-tree assumption.
- The operator's checkout is the repository's primary working tree; the dispatched GitMCP root may be a task worktree or the same checkout, so the helper discovers the primary checkout explicitly rather than assuming the root it is handed.
- ADR 010 (docs/decisions/010-gitpython-over-subprocess.md): git operations go through GitPython, not subprocess. The branch's current code already does this via `open_repo` in packages/snodo-tools/src/snodo/tools/git.py; keep it that way with no lint suppressions.
- The engine writes many runtime files under `.snodo/` while a run is in flight, and the set grows over time. Today they include: `.snodo/audit.log` (plus weekly archives such as `audit.log.2026-w42`, `audit.log.lock`), `.snodo/queues.json`, `.snodo/.merge.lock`, `.snodo/.queues.lock`, `.snodo/queue-locks/`, `.snodo/wave.json` and its lock, `.snodo/state.json`, `.snodo/verdict_cache.json`, `.snodo/telemetry_drops.json`, `.snodo/jobs/`, `.snodo/tasks/`, `.snodo/recons/`, `.snodo/notifications/`, `.snodo/queue-integration/`, and each plan's `.snodo/plans/<plan>/status.json`. The previous attempt tried to exclude these by listing names and listed names the engine does not use (`audit.jsonl`), so real engine writes were not excluded. A fixed deny-list is the wrong shape because new runtime files appear over time.

## Outcome
- Under `.snodo/`, only an allow-list of operator-authored definition files is watched: `.snodo/protocol.yml`, `.snodo/plans/<plan>/plan.yml`, and the wave spec files under `.snodo/plans/<plan>/wave_*/`. Every other path under `.snodo/` (all runtime state, present and future, including each plan's status.json) is ignored. Changes to or deletions of the watched files are reported, tracked or untracked. Everything outside `.snodo/` that git reports is watched as before.
- A small engine module (with its own tests) takes a baseline of the primary checkout (HEAD, tracked and untracked non-ignored paths with a content fingerprint for every path git reports as modified, added, deleted or untracked) and later compares it with the current state, returning the sorted list of paths whose content differs, including edits to files that were already dirty at baseline, deletions and newly created or removed untracked files.
- It reports "could not establish or compare" as an explicit result the caller can see, never as an empty list or a swallowed exception. A checkout that is not a git repository, or git failing, is that result.
- Bounded cost: it must not read the content of every tracked file on each call; reading only paths git reports as changed is enough. A large number of changed paths is capped in what is reported while still reporting that the cap was hit; the cap parameter is honoured.
- GitPython only (ADR 010), no subprocess, no new lint suppressions.
- Tests use real temporary Git repositories and the real filenames above, and cover: clean tree unchanged; edit of a clean tracked file; further edit of a file that was ALREADY dirty when the baseline was taken (baseline taken while the file is dirty, then it is edited again); deleted tracked file; untracked file created and removed; ignored file ignored; writes to real engine runtime files ignored (at least `.snodo/audit.log`, an archive like `.snodo/audit.log.2026-w42`, `.snodo/queues.json`, `.snodo/.merge.lock`, and a plan's `.snodo/plans/<plan>/status.json`); an untracked plan.yml and an untracked wave spec file under `.snodo/plans/` edited or deleted is reported; a change to `.snodo/protocol.yml` is reported; cap reached is reported; a directory that is not a git repository gives the explicit unavailable result; a git failure gives the explicit unavailable result.
- `make gate` passes for this change. If an unrelated test in the gate times out or leaks a process, say so in the commit message rather than editing unrelated tests.
- Only the snapshot module and its test file change. No new states, statuses, severities or halt types.
