## Intent
Give the engine a way to say whether the content of the operator's checkout changed between two moments, so a later task can use it to catch a coder that edits the main checkout through its shell without moving any branch tip. This task adds only the capability and its tests; nothing calls it yet.

## Evidence
- packages/snodo-engine/src/snodo/engine/nodes/executor.py `_repo_ref_snapshot` and `_escaped_repo_commit` compare branch-tip SHAs only. A `git apply`, heredoc, `cp` or `python` write to the main checkout, or a `git clean`, changes no branch tip and is invisible. Issue #946 records a live case where untracked plan records in the operator's checkout were deleted this way.
- Comparing git status paths alone misses an edit to a file that was already dirty, so the comparison must be against a baseline of content, not a clean-tree assumption.
- The operator's checkout is the repository's primary working tree; the dispatched GitMCP root may be a task worktree or the same checkout, so the helper discovers the primary checkout explicitly rather than assuming the root it is handed.
- The engine itself writes runtime state under `.snodo/` (audit log, job and task records, plan status and lock files) while a run is in flight; those writes must not count as changes.

## Outcome
- A small engine module (new file, with its own tests) that can take a baseline of the primary checkout (HEAD, tracked and untracked non-ignored paths with a content fingerprint for every path git reports as modified, added, deleted or untracked) and later compare it with the current state, returning the sorted list of paths whose content differs, including edits to files that were already dirty at baseline, deletions and newly created or removed untracked files.
- It reports "could not establish or compare" as an explicit result the caller can see, never as an empty list or a swallowed exception. A checkout that is not a git repository, or git failing, is that result.
- Engine runtime state under `.snodo/` that the engine itself writes during a run is excluded; plan spec files and everything else under the checkout are not.
- Bounded cost: it must not read the content of every tracked file on each call; reading only paths git reports as changed is enough. A large number of changed paths is capped in what is reported while still reporting that the cap was hit.
- Tests use real temporary Git repositories: clean tree unchanged; edit of a clean tracked file; further edit of an already-dirty file; deleted tracked file; untracked file created and removed; ignored file ignored; engine runtime state ignored; git unavailable gives the explicit unavailable result.
- Only the new module and its test file change. No new states, statuses, severities or halt types.
