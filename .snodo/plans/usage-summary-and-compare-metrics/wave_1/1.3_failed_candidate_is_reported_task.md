## Intent
When a benchmark candidate does not complete, `snodo models --benchmark-run` and `snodo models --compare` still produce a report, saying how the candidate ended and showing what it did produce, instead of refusing with an error and discarding everything the run recorded.

## Evidence
- A benchmark run of a local model reached its turn limit, halted with a blocker after the first attempt, and `--benchmark-run` printed only "Job ... is not a completed benchmark candidate" (snodo/cli/commands/plan_compare.py, `_benchmark_candidate`, and `compare_models_command`). The run had recorded its status, halt type, validator findings, files created and tokens; none of it was shown.
- The comparison already computes content overlap, validator outcome and changed-file signals from a candidate patch, and it reads a benchmark candidate's changes from the benchmark branch (`_candidate_patch`).
- A failed candidate is the case where a comparison is most informative: it shows how far a model got.
- A first attempt already exists on this task's branch: plan_compare.py no longer rejects a finished non-completed candidate and reports status, halt type and a truncated, redacted blocker reason. Keep it. It was not accepted only because the tests for the new behaviour were never written (it passed quality and the five existing tests).

## Outcome
- A candidate job that ended failed, blocked or otherwise not completed is reported. The report states the job status and halt type (and blocker reason when present, truncated and with credential-like strings redacted), then the signals computed from whatever the candidate produced. A candidate that produced no patch scores as having produced nothing; it is not an error.
- The JSON output carries the same facts (status, halt type, reason) next to the existing benchmark block, additively under the existing schema name.
- A job that is still running, or an id that does not exist or does not belong to the plan and task, is still refused with a clear message.
- The exit status says whether the report was produced, not whether the candidate was good.
- Tests are written and committed for each of: a completed candidate (unchanged output), a failed candidate with a partial patch, a failed candidate with no patch, a blocked candidate, a running job, and a blocker reason containing a credential-like string (redacted in both human and JSON output).
- Keep the change inside plan_compare.py and its tests; if the file crosses the file-length ratchet, put the new logic in a small helper module beside it. Run make gate-task, the tests you touched and scripts/enforce_file_length.py, and report the results in your summary. Everything is committed on the task branch.
