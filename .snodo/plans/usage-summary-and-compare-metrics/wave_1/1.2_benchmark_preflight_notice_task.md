## Intent
Before `snodo models --benchmark-run` starts a candidate, tell the operator what the baseline was produced with and what the candidate will run with, and flag a difference in coder harness, so nobody reads a comparison of two different harnesses as a comparison of two models.

## Evidence
- A baseline records the coder and model that produced it (`coder` and `model` in `.snodo/baselines/<plan>/<task>/baseline.json`, written by snodo/cli/commands/models_baseline.py). A baseline captured from an opencode-cli run carries `coder: opencode-cli`.
- `--benchmark-run` (snodo/cli/commands/models_benchmark.py) submits the candidate as an ordinary task job with `--model`; a model such as a gpu2 LiteLLM model runs in snodo's own LiteLLM coder loop, which has a turn cap and a different tool set. The result then compares two harnesses and two models at once, and nothing says so.
- The command already prints a note about untracked files that the task worktree cannot see; the new notice sits beside it.
- A first attempt already exists on this task's branch: a notice module named models_benchmark_notice in the cli commands package, and a test file named test_models_benchmark_notice in the tests directory. Keep and build on them; do not start over. That attempt was blocked for two reasons: the test file assigns a lambda (`resolver = lambda ...`, ruff E731, which fails make gate-task), and models_benchmark.py never calls the notice, so the user sees nothing.

## Outcome
- Before the job is submitted, the command prints two short lines: the baseline's coder and model, and the candidate's coder and model as the task will actually resolve them from the configuration and `--model`.
- When the coders differ, a third line says so plainly and names both, for example that the baseline ran in opencode-cli and the candidate runs in the LiteLLM loop. When the baseline file does not record a coder, the notice says it is unknown instead of guessing.
- The notice is informational: the run still starts, and the exit code is unchanged.
- The notice module is actually called from models_benchmark.py (only the few call-site lines are added there; the logic stays in the notice module), and a test proves the benchmark-run path prints the notice before the job is submitted.
- The lint error is fixed (a def instead of an assigned lambda), make gate-task passes, and everything is committed on the task branch.
- Tests cover the same coder, different coders, a baseline without a coder, and a candidate model given with and without a provider prefix.
- No file crosses the file-length ratchet; run the tests you touched and scripts/enforce_file_length.py and report the results in your summary.
