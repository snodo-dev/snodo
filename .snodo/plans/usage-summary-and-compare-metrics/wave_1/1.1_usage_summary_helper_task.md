## Intent
Give snodo one small, well-named place that turns the usage records of a run into a usage summary, so the end of a task, the end of a recon and the comparison of two runs all report the same numbers the same way.

## Evidence
- A job or task `state.json` holds a `usage` list with one record per model call: `role` (for example `coder`, `validator:adr`), `model`, `input_tokens`, `output_tokens`, `duration_ms`, `cost`, and `prompt_tokens`/`completion_tokens`/`total_tokens` (packages/snodo-foundation/src/snodo/infrastructure/usage_tracker.py).
- In-place coders such as opencode-cli write records with `input_tokens` and `output_tokens` set but `prompt_tokens`, `completion_tokens` and `total_tokens` deliberately null (the same file, `record_inplace_coder_run`). The task-level roll-up in snodo/cli/commands/task_record.py requires all three of those fields, so it reports no tokens for such a run even though the numbers exist.
- A recon result keeps per-agent usage entries with `input_tokens`, `output_tokens` and `duration_ms` (packages/snodo-mcp/src/snodo/recon/__init__.py), and prints none of it.
- No record carries a provider-reported generation rate today.
- In a measured run the validators dominated: one coder call took 35 seconds while the whole task took 1318 seconds, so a single total hides the coder.

## Outcome
- A new small module exposes a function that takes a list of usage records, an optional total elapsed time in seconds, and returns a summary: one row per role plus a total row. Each row has the number of calls, input tokens, output tokens, the time spent inside model calls, an output tokens per second figure, and the source of that figure.
- Input and output tokens are read from `input_tokens`/`output_tokens` first and fall back to `prompt_tokens`/`completion_tokens`. When no record in a row carries a token count, the row says the count is unknown; it is never reported as zero.
- The rate is output tokens divided by the time spent in model calls for that row, and its source is "calculated" (shown as C). If a record carries a provider-reported output rate under a field name that the module documents, the row uses it and its source is "reported" (shown as R). No existing record carries one and the module does not invent values; a row with no usable time shows the rate as unknown.
- Records for a recon agent (an `agent` instead of a `role`) are accepted and each agent becomes its own row.
- A second function renders the summary as plain text lines suitable for the end of a command: a header, one line per row, and a total line, each showing input tokens, output tokens, time, and the rate with its C or R mark. Unknown values print as "n/a".
- Tests cover: litellm-style records, in-place coder records with null prompt/completion fields, unknown tokens, a reported rate, a missing or zero duration, several roles, a recon-agent record, and the rendered lines.
- Put the code in a new module and a new test file; do not change any existing source file. No file crosses the file-length ratchet; run the tests you touched and scripts/enforce_file_length.py and report the results in your summary.
