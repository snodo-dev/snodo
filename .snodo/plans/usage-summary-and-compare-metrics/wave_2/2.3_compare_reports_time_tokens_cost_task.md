## Intent
`snodo models --compare` (and the report that ends `--benchmark-run`) shows, for the baseline and the candidate side by side, how long each took, how many coder turns, how many tokens and what it cost, split by coder and validators, plus how many post-validation findings of each severity; so two runs can be judged on speed and cost as well as on the patch. These figures are shown and are not added to the score.

## Evidence
- Today the comparison scores patch content, validator outcome and changed files, shows line totals as "not scored", and ignores wall time, coder turns, tokens and cost (snodo/cli/commands/plan_compare.py, `compare_evidence` and `compare_models_command`).
- A benchmark run writes no task record, so a candidate's figures are in its job state: the `usage` list (per call, with `role`, `input_tokens`, `output_tokens`, `duration_ms`, `cost`), `halt.coder_report` (`turns_used`, `wall_time_ms`, `tokens_used`) and `halt.validator_results`.
- A baseline's figures are in the job state of the run that produced it (its task state names the job); a baseline file written by task 2.4 of this plan may also hold a copy of them.
- In a measured baseline the coder took 35 seconds of a 1318-second task; validators were most of the rest.
- The helper from task 1.1 turns usage records into per-role rows with output rate and its source; the comparison reuses it.

## Outcome
- The text report gains a block with a baseline column and a candidate column for: time spent by the coder and total elapsed time, coder turns, input and output tokens for the coder and for all validators together, cost, and the number of findings per severity from post-validation. Output tokens per second for the coder is shown with its C or R mark.
- A figure that was not recorded shows as n/a on that side; it is never shown as zero and never causes an error. A baseline whose job state is gone is handled the same way.
- Where the number of coder turns is not recorded and has to be taken from the count of model calls, the block says so.
- The JSON output carries the same figures under a clearly named block, next to the existing signals, without changing the existing keys.
- Tokens are shown as recorded, with a short line explaining that an in-place coder and a LiteLLM coder count prompt tokens differently, so input tokens are not directly comparable between them.
- Put the gathering of the figures in a small new module with its own tests, using the helper from task 1.1; plan_compare.py gains only the lines needed to call it and print the block. Tests cover a baseline and a candidate with full data, a candidate with a failed run, missing data on either side, and the JSON block.
