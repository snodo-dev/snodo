## Intent
When a baseline is captured with `snodo models --set-baseline`, it keeps the usage summary of the run it came from, so the baseline's time, tokens and cost remain available after the job records are cleaned up.

## Evidence
- A baseline today stores the model, coder, validator results, change size and the diff (snodo/cli/commands/models_baseline.py, `baseline.json` with schema `snodo.task-baseline.v1`). It stores nothing about time, tokens or cost, so a later comparison has to find the original job state.
- The job state of the original run holds a per-call `usage` list with `role`, `input_tokens`, `output_tokens`, `duration_ms` and `cost`, and the coder report with turns used. The helper from task 1.1 of this plan turns the records into per-role rows.
- Existing baselines must keep working: the comparison treats the new data as optional.

## Outcome
- `--set-baseline` adds a `usage` block to `baseline.json` holding the per-role summary of the recorded run (as the helper returns it) and the coder turns used when recorded. The schema name stays the same; the block is additive, and a baseline without it is read exactly as before.
- When the original job state cannot supply usage records, the block is omitted or marked as not recorded, and the command still succeeds.
- The command prints one extra line saying a usage summary was stored, or that none was available.
- Tests cover a baseline captured with full usage, one without usage records, and that an existing baseline file without the block still loads.
- Keep the change to snodo/cli/commands/models_baseline.py and its tests; put new logic in a small helper module if the file would cross the file-length ratchet. Run the tests you touched and scripts/enforce_file_length.py and report the results in your summary.
