## Intent
Every finished task ends with the usage summary the earlier helper produces: input tokens, output tokens, total elapsed time and output tokens per second, with the rate marked reported or calculated, shown per role (the coder, each validator) and as a total.

## Evidence
- The end of a successful task prints "Task completed successfully!" (snodo/cli/commands/run_cmd.py); a halted task prints its own halt block. Neither printed a usage summary, although the task's state holds a per-call `usage` list with `role` on each record.
- A task run as part of a plan, and a benchmark run, are ordinary task jobs, so their final lines come from the same task command.
- In a measured run the validators accounted for most of the elapsed time, so a single total would hide how long and how many tokens the coder used.
- run_cmd.py is above the file-length limit; an earlier task that put its logic into that file kept failing review for that reason.
- Earlier work exists on this task's branch: a small new module that reads the task's recorded usage and prints the summary, with tests, and a few call-site lines in run_cmd.py. The previous attempt stopped only because the orchestrator wrote into the operator checkout during the run (a workspace-escape halt); nothing was wrong with the work. Keep it and finish the job: check it against the outcome below, fix gaps, and do not start over.
- One gap a reviewer noted: a non-dict element inside the usage list is not filtered before it is read, so a hand-corrupted state file would raise after the task closed. The summary must never raise; on unreadable or malformed records it prints nothing for those records.

## Outcome
- When a task finishes, whatever the outcome (completed, blocked, failed), the command prints the usage summary after its existing final lines: a row for the coder, a row per validator role, a total row, and the total elapsed time of the task.
- Records are read from the task's own usage as recorded for that run; a retry or recovery attempt reports its own run, not the earlier attempts'. In-place coder records (opencode-cli) show their input and output tokens even though their prompt/completion fields are empty.
- The summary printing and the reading of the records live in a small module that uses the usage helper; run_cmd.py gains only the few call-site lines needed to invoke it. Do not delete or reformat unrelated lines to make room.
- Tests cover a completed task, a blocked task, a task whose coder record has no token counts, a malformed usage list, and that nothing is printed when the task recorded no usage at all.
