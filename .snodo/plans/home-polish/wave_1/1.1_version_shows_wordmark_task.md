# `snodo --version` shows the same header as bare `snodo`

First open a GitHub issue for this work. Write the body to a file under /tmp and pass it with `gh issue create --body-file`, never as an inline string. The commit message must say "Fixes #<that issue number>". Add a CHANGELOG entry under ## [Unreleased].

## INTENT
On a terminal, bare `snodo` prints the snodo.dev wordmark with the version beside it. `snodo --version` prints only the plain line "snodo 0.24.0+…". Both are the user asking "what is this and which version", so on a terminal they should look the same: the wordmark with its version. When the output is not a terminal (piped, captured with `$(...)`, NO_COLOR, CI), `snodo --version` must stay the exact plain line it prints today, because scripts read it. `docs/install.sh` captures it, for example.

## THE CHAIN
- `snodo/cli/main.py`, the root callback: the `--version` branch prints the plain line, then on a TTY may print an update notice to stderr. The bare-`snodo` branch prints `colored_wordmark()` when `should_show_wordmark()`.
- `snodo/cli/banner.py` holds the wordmark and the TTY or colour decision.
- `snodo/cli/update_check.py`: the update notice should still appear after the wordmark.

## CONSTRAINTS
- Non-TTY output of `snodo --version` stays byte-identical to today.
- Reuse the existing wordmark and TTY decision; do not add a second rendering path.
- No new status, severity, halt type or audit event.
- Do not run the `snodo` CLI against this repo, `make release` or `make gate` in the worktree, and do not create, change or delete anything under `.snodo/` in the repo.
- Run `uv run --extra dev ruff check` on touched files, and run the banner and main CLI tests.

## ACCEPTANCE
- Tests show:
  - on a TTY stub, `--version` prints the wordmark with the version, just as bare `snodo` does;
  - without a TTY, and with NO_COLOR, it prints exactly "snodo <version>";
  - the update notice still goes to stderr on a TTY.
- There is a CHANGELOG entry under ## [Unreleased].
