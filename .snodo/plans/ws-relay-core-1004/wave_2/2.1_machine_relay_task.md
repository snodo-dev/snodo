INTENT
One relay process per machine holds a single outbound WebSocket to the cloud and forwards each incoming request to the matching local `snodo serve` port, streaming the reply back. Nothing here is wired into the CLI yet; this ticket delivers the relay as a library with tests against a fake cloud socket and a fake local server. It builds on the serve registry (issue #1002) and the frame codec (issue #1003) from the previous wave: read what they actually look like on the branch before using them.

CONTRACT (agreed with snodo-cloud, 2026-10-22)
- Connect: GET wss://app.snodo.dev/runner/connect?machine_id=<id>, with the runner lease as Authorization: Bearer on the upgrade. The cloud address comes from the same configuration the other cloud calls already use, not a new hard-coded host.
- The runner lease is minted by POST {lease_url}/m with body {"audience":"runner","machine_id":"<id>"}; the response carries the token and an expiry (about 300 seconds), in the same shape the ingest lease already uses. Use the existing lease code and extend it for the new audience rather than writing a second exchange. The ingest exchange must behave exactly as it did before: the same call shape, with the request body sent only for the runner audience. Fetch a fresh lease on every connect and reconnect. An open socket is never closed by the client because its lease expired.
- Connect statuses: 426 not an upgrade, 401 bad, expired or wrong-audience lease, 403 machine_id differs from the lease. On 401 fetch a fresh lease once and retry; 403 and 426 are reported plainly and not retried in a tight loop.
- machine_id is generated once (random, not derived from anything about the machine) and kept in the user config directory, next to the other user-level state, with owner-only permissions. A new connection from the same machine replaces the old one on the cloud side, so a restarted relay always wins.
- After connect the relay sends hello with the endpoints read from the serve registry (hostname and auth ["oauth"] for each entry that has a hostname), and sends hello again whenever the registry changes. The cloud ignores endpoints it does not know; the relay does not need to know which were accepted.
- For each req: forward to http://127.0.0.1:<port><path> for the endpoint whose registry hostname matches, with the given method, headers and reassembled body; stream the reply back as res followed by chunk frames. The reply may be plain JSON or text/event-stream with several events; forward the bytes in order as they arrive without waiting for the end where the framework allows it. An unknown hostname or a local connection refused or timed out becomes an err frame with a short code and message.
- While a local request is in flight the relay sends a keep frame for it every 30 seconds. On cancel, abort the local request and stop sending for that id.
- Up to 8 requests in flight at once; a ninth waits for a free slot rather than failing.
- Reconnect with jittered exponential backoff from 1 second to 60 seconds, reset after a connection that stayed up for a while. Use WebSocket protocol pings only for keepalive.
