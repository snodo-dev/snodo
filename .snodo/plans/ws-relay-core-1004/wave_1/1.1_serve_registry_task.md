INTENT
A separate process on the same machine can discover which `snodo serve` endpoints are running. Today nothing records running serve processes (only .snodo/tunnel.json exists, and only for managed tunnels). Each serve writes one entry about itself to a small user-level registry file when it starts and removes it when it exits. A reader returns only the entries whose process is still alive, so a crash that left an entry behind cleans itself up on the next read.

GitHub issue #1002 already exists for this. Do not open another; put "Fixes #1002" in the commit message. This ticket adds no CHANGELOG entry (nothing user-visible); the last ticket in this plan owns the single entry.

THE CHAIN
Serve starts and knows its project, mode and local port, and its tunnel hostname when it has one -> it records project, mode, port, hostname (empty when none), pid and started time under the user's snodo home directory, not in the project -> on a normal exit and on the usual termination signals the entry is removed -> a reader lists the entries and drops any whose pid is not a live process (a pid that was reused by an unrelated process should be recognised using the process-identity helper the project already has for jobs, rather than trusting the pid alone) -> several serve processes starting at the same moment all end up recorded.

Follow the pattern the user-level cloud state files already use for the file location, atomic writes and locking (look at how the cloud login state and the sync state are stored); do not invent a second storage style. Keep the registry code in the foundation layer next to those, and the one call that records and removes the entry in the serve startup path. The entry is keyed by project and mode, so a second serve for the same project and mode replaces the first rather than duplicating it.

CONSTRAINTS
- The registry holds no secrets: no tokens, no credentials, no URLs with credentials.
- A corrupt or unreadable registry file reads as empty and is rewritten on the next write; it never stops serve from starting.
- Failure to record or to remove an entry is logged at debug level and never stops serve.
- Do not touch the tunnel config, provision code, MCP transport or auth code.
- No new status, severity, halt type or audit event.
- No new third-party dependency.
- Respect the layer rules (foundation does not depend on engine, mcp or app). Run the import-layer check for this cross-package change.
- Targeted tests only. Do not run the snodo CLI, make gate or make release. Do not touch .snodo/.

ACCEPTANCE
- Tests (with the home directory redirected to a temporary one) cover: write then list; removal; two entries; same project and mode replaced; a dead pid dropped; a reused pid not trusted; corrupt file read as empty; concurrent writers from threads or processes all recorded.
- A test shows serve startup records its entry and the exit path removes it, without opening a real network socket where that can be avoided.
- Existing tests still pass and lint is clean.
- Run the targeted tests and report their output.
