# 2.2_machine_interface_validate_options

## INTENT
Task 1.1 of this plan gave `snodo validate` the options `--validator <id>` and `--model <provider/model>`; its JSON payload did not change. `docs/machine-interface.md` describes the `snodo validate` JSON and options; a script that runs one validator with a chosen model needs to know the options and the error for an unknown validator id. Evidence of the gap: the section was written before these options existed.

## STARTING STATE
Wave 1 is merged, so the options exist in `snodo/cli/commands/validate_cmd.py` and are tested in `tests/cli/test_validate_single_validator.py`.

## THE CHAIN
1. Open a GitHub issue first ("Machine interface does not describe snodo validate --validator and --model") and put "Fixes #<n>" in the commit message.
2. Read `snodo/cli/commands/validate_cmd.py` and that test file. Every statement you write must be checked against that code; do not invent fields or output.
3. Update the `snodo validate` section of `docs/machine-interface.md`: the two options and what each does, the error for an unknown validator id (what it lists), and the statement that the command never uses the verdict cache, so a replay is always judged afresh. State that the payload and its schema (`snodo.validate.v1`) are unchanged by these options: no field is added, and with `--validator` the `results` list simply holds that one validator.
4. `CHANGELOG.md` gets one new line under `[Unreleased]` in the same commit, in the style of the neighbouring entries, ending with "(Fixes #<n>)".
5. Run the docs checks the gate runs for `docs/`; fix what they report in your own change only.

## CONSTRAINTS
- Only `docs/machine-interface.md` and `CHANGELOG.md` may change. No code, no test file.
- The documented schema name and key sets stay exactly as `tests/cli/test_machine_interface.py` pins them.
