# 2.1_benchmark_run_accepts_validator

## INTENT
Connect the pieces: `snodo models --benchmark-run --plan <plan> --task <task> --validator <id> --model <provider/model>` replays that one validator on the recorded input and prints the comparison with the recorded verdict. Without `--validator` the command behaves exactly as today (the whole task is run again with the candidate coder). Evidence of the need: a validator cannot be benchmarked at all today; the building blocks exist (wave 1 of this plan).

## STARTING STATE
Wave 1 is merged. These exist: `models_validator_replay.py` (resolves the recorded input of one validator of a baselined task), `models_validator_run.py` (replays one validator on a recorded commit with a chosen model and reports elapsed time and tokens), `models_validator_compare.py` (compares two verdicts, with a human and a JSON rendering), `print_validator_replay_notice` in `models_benchmark_notice.py`, and `snodo validate --validator --model`. Use them; do not reimplement them.

This task has been attempted twice. Both times the wiring (`--validator` in `models_cmd.py`, the branch in `models_benchmark.py`) and the five new tests in `tests/cli/test_models_benchmark_run_validator.py` were right, and the second attempt also moved `models_validator_run.py` onto `snodo.tools.git.open_repo`, closing the repo. Both times the quality gate failed on the same remaining defect, which is the only thing left to repair: `tests/cli/test_models_validator_run.py` still leaks persistent `git cat-file --batch-check` / `git cat-file --batch` child processes. The gate output was `ERROR tests/cli/test_models_validator_run.py::test_replay_uses_no_verdict_cache - TEST LEAKED running work into later tests ... live child process(es): git cat-file --batch-check; git cat-file --batch` (earlier: the same for `test_replay_runs_only_the_named_validator`). The leak check reports the child at the test it is noticed in, which can be a later test than the one that started it, so every one of the five tests in that file is a suspect. Evidence of the cause: that test file builds its temporary repositories with GitPython's `Repo.init(...)` and reads objects through that `Repo` (the default object database, which starts a persistent `git cat-file` child on the first object read and ends it only when the `Repo` is garbage collected). The docstring of `open_repo` in `packages/snodo-tools/src/snodo/tools/git.py` explains the mechanism.
