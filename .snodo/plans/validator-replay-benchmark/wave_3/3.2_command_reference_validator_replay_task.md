# 3.2_command_reference_validator_replay

## INTENT
`docs/command-reference.md` lists the options of `snodo models` and describes `--benchmark-run`. It does not mention `--validator`. A reader must learn that `--benchmark-run` with `--validator <id>` replays one validator instead of re-running the whole task, that `--model` then names the validator's model, what it judges, and what it compares.

## STARTING STATE
Waves 1 and 2 are merged, so the option exists in `snodo/cli/commands/models_cmd.py` and the replay in `models_benchmark.py`.

## THE CHAIN
1. Open a GitHub issue first ("Command reference: --benchmark-run --validator") and put "Fixes #<n>" in the commit message.
2. Read `models_cmd.py`, `models_benchmark.py` and the replay modules named in `models_validator_*.py`; every statement must be checked against that code.
3. In `docs/command-reference.md`: add `--validator` to the `snodo models` option row, and add a short paragraph after the `--benchmark-run` description that says what `--validator` changes (one validator replayed on the baseline's recorded spec and commit, in a temporary worktree, with the chosen model; no verdict cache; no merge), what is compared (severity by the existing ordering, justification, time, tokens, cost; only the severity is scored), and the errors for a missing `--model` or an unknown validator id.
4. `CHANGELOG.md` gets one new line under `[Unreleased]` in the same commit, in the style of the neighbouring entries, ending with "(Fixes #<n>)".
5. Run the docs checks the gate runs for `docs/`; fix what they report in your own change only.

## CONSTRAINTS
- Only `docs/command-reference.md` and `CHANGELOG.md` may change. No code, no test file.
