# 1.1_validate_selects_one_validator_with_model

## INTENT
`snodo validate` runs every validator of a mode and phase, with the models the protocol and configuration give them. To benchmark one validator with another model, it must be possible to run just that validator and to say which model it uses. This task adds those two options to `snodo validate`, which is also the building block the later tasks of this plan reuse. Evidence of the gap: `snodo/cli/commands/validate_cmd.py` resolves all validators for the phase, takes the validator model from configuration only (`resolve_validator_completion`), and offers no way to narrow or override either.

## STARTING STATE
Nothing of this task exists yet; an earlier attempt was refused before any code was written, so the checkout is the plan integration branch as it stands.

## THE CHAIN
1. Open a GitHub issue first ("snodo validate cannot run a single validator or with a chosen model") and put "Fixes #<n>" in the commit message.
2. Read `snodo/cli/commands/validate_cmd.py`, and in `packages/snodo-engine/src/snodo/validators/runner.py` the functions `resolve_validators`, `resolve_validator_completion`, `build_completion_fn` and `run_validators`. Find how a validator can pin its own model in the protocol and how `default_model` interacts with that pin; the `--model` override is the "provided override" of the precedence in ADR 039 and must win over both the pin and the default.
3. Add `--validator <id>` (the validator ids of the resolved mode and phase) and `--model <provider/model>` to `snodo validate`. With `--validator`, only that validator is run; an unknown id is an error that lists the ids available for that mode and phase. With `--model`, the validator that runs uses that model instead of its pinned or configured one. The policy decision and the exit codes stay exactly as they are. The command must not use or write the verdict cache (it does not today; keep it that way and say so in a code comment, because a cached verdict would defeat a replay).
4. The JSON payload of `snodo validate` does not change at all: same schema name `snodo.validate.v1`, same top-level keys, same per-result keys (ADR 022 pins them in `tests/cli/test_machine_interface.py`, and this task does not amend that record). The judging model is therefore not added to the payload; it is observable in the model the completion function receives.
5. Add tests in a new file `tests/cli/test_validate_single_validator.py` with exactly these names: `test_validate_runs_only_the_selected_validator`, `test_validate_unknown_validator_lists_available_ids`, `test_validate_model_override_beats_pinned_model`, `test_validate_never_touches_the_verdict_cache`. Use the fakes the neighbouring validate tests use; no network calls. `test_validate_model_override_beats_pinned_model` asserts on the model the fake completion (or the completion builder) actually received for the selected validator, not on any payload field.
6. `CHANGELOG.md` gets one new line under `[Unreleased]` in the same commit, in the style of the neighbouring entries, ending with "(Fixes #<n>)". The command table in `docs/command-reference.md` lists the options of `snodo validate`; add the two new options to that row (this one-line edit is part of this task). `docs/machine-interface.md` is described by a later task of this plan (2.2) and is not touched here.
7. The project supports Python 3.12. Do not run `ruff format` over whole files. Run `python -m pytest tests/cli/test_validate_single_validator.py tests/cli/test_machine_interface.py` and `ruff check packages tests snodo`.
