# 1.2_resolve_recorded_replay_input

## INTENT
To replay one validator of a baselined task, the replay needs the same input the validator had: the task spec, the phase and mode it ran in, the tree it judged, and the verdict it gave then. All of it is recorded, in different places. This task adds one pure, tested function that gathers it, so the command wired up in wave 2 only has to call it. Evidence: `snodo models --set-baseline` stores `validator_results` and the change range (`base_sha`, `head_sha`) in `.snodo/baselines/<plan>/<task>/baseline.json`, and the spec is found by `_task_spec` in `snodo/cli/commands/models_benchmark.py`, but nothing combines them per validator.

## THE CHAIN
1. Open a GitHub issue first ("Resolve the recorded input for replaying one validator of a baselined task") and put "Fixes #<n>" in the commit message.
2. Read `snodo/cli/commands/models_baseline.py` (the baseline record), `models_benchmark.py` (`_task_spec`) and the validator result records written into a task state, to see what a recorded result contains (validator id, severity, justification, phase, any usage or timing). Find which phase a validator belongs to in the protocol (pre-execute validators judge the spec at the base commit; post-execute validators judge the tree at the head commit and the diff from base).
3. Add a new module `snodo/cli/commands/models_validator_replay.py` with a function (name your own, the tests below call it) that, given project root, plan, task and validator id, returns a small record: the spec text, the phase, the base commit, the head commit to judge, and the recorded result of that validator (severity, justification, and its time and token usage when recorded, otherwise absent). It raises a clear error when the baseline is missing, when the validator id is not in the baseline's recorded results (listing the ids it has), or when the commit range is absent. It does not run any validator and makes no model call.
4. Add tests in a new file `tests/cli/test_models_validator_replay.py` with exactly these names: `test_replay_input_for_post_execute_validator_uses_head_commit`, `test_replay_input_for_pre_execute_validator_uses_base_commit`, `test_replay_input_unknown_validator_lists_recorded_ids`, `test_replay_input_missing_baseline_is_a_clear_error`. Build baselines in a temporary directory the way the neighbouring baseline tests do.
5. `CHANGELOG.md` gets one new line under `[Unreleased]` in the same commit, in the style of the neighbouring entries, ending with "(Fixes #<n>)".
6. The project supports Python 3.12. Do not run `ruff format` over whole files. Run `python -m pytest tests/cli/test_models_validator_replay.py` and `ruff check packages tests snodo`.

## CONSTRAINTS
- Files that may change: the new module, the new test file, `CHANGELOG.md`. Nothing else; the module is not wired to any command yet.
- No new states, statuses, severities, halt types or event names.

## ACCEPTANCE
- `snodo/cli/commands/models_validator_replay.py` exists and its function makes no model call and runs no validator.
- `tests/cli/test_models_validator_replay.py` exists and contains the four named tests.
- The diff adds one line under `[Unreleased]` in CHANGELOG.md that mentions the issue.
- No file outside the list under CONSTRAINTS differs.
