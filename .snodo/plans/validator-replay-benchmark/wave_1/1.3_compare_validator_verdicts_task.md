# 1.3_compare_validator_verdicts

## INTENT
A validator replay produces a new verdict that has to be set beside the recorded one: did the severity change and in which direction, how do the justifications differ, and how do time and tokens compare. `snodo/cli/commands/plan_compare.py` already ranks severities for the task comparison. This task adds a pure comparison function and its human and JSON rendering for one validator, so the wiring task of wave 2 only has to call it. Nothing in the repository compares two verdicts of the same validator today.

## STARTING STATE
Nothing of this task exists yet; an earlier attempt was refused before any code was written, so the checkout is the plan integration branch as it stands.

## THE CHAIN
1. Open a GitHub issue first ("Compare a replayed validator verdict with the recorded one") and put "Fixes #<n>" in the commit message.
2. Read `snodo/cli/commands/plan_compare.py` (the severity ordering `_OUTCOME_RANK`, `_direction`, how missing values are printed as `n/a`, the run-metrics rows) and reuse its ordering and wording rather than defining a second severity scale. The coupling is deliberate and kept narrow: the new module imports the ordering through one public name. If the ordering is private today, give it a public alias in `plan_compare.py` (for example `OUTCOME_RANK = _OUTCOME_RANK`, the private name staying in place) so the new module never imports an underscore name; no behaviour of `plan_compare.py` changes.
3. Add a new module `snodo/cli/commands/models_validator_compare.py` with a pure function that takes a recorded result and a candidate result (each: severity, justification, optional elapsed seconds, optional input and output tokens, optional cost) and returns a comparison record: baseline and candidate severity, direction (better, worse or same, by the existing ordering), whether the justifications differ, and the metric pairs with their differences where both sides are known and `n/a` otherwise. Add a renderer for the human report (a few lines in the style of the task comparison) and one for JSON. The score uses severity only; time, tokens and cost are shown but not scored, as in the task comparison. The module only compares and renders: it runs no validator, makes no model or network call and reads no files.
4. The JSON record is a machine-interface payload, so it follows ADR 022: it carries a `schema` field built with `schema_name(...)` from `snodo/cli/json_output.py` (the form `snodo.<command>.v<N>`, version 1 for this new shape), and its exact key set is pinned by a test. Documenting the payload in `docs/machine-interface.md` belongs to task 3.3 of this plan (wave 3), which describes the replay output once it is emitted; this task does not touch that file.
5. Add tests in a new file `tests/cli/test_models_validator_compare.py` with exactly these names: `test_pass_to_warn_is_worse`, `test_warn_to_pass_is_better`, `test_same_severity_with_different_justification_is_same_direction`, `test_missing_metrics_render_as_not_available`, `test_json_record_contains_both_sides`. The last one also asserts the `schema` value and the exact set of top-level keys.
6. `CHANGELOG.md` gets one new line under `[Unreleased]` in the same commit, in the style of the neighbouring entries, ending with "(Fixes #<n>)".
7. The project supports Python 3.12. Do not run `ruff format` over whole files. Run `python -m pytest tests/cli/test_models_validator_compare.py` and `ruff check packages tests snodo`.

## CONSTRAINTS
- Files that may change: the new module, the new test file, `CHANGELOG.md`, and `plan_compare.py` only to add the public alias for the severity ordering without changing its behaviour.
- No new states, statuses, severities, halt types or event names; the severities are the existing ones (pass, warn, blocker); better, worse and same are a comparison direction, the vocabulary `plan_compare` already uses, not states.

## ACCEPTANCE
- `snodo/cli/commands/models_validator_compare.py` exists, has no model or network call, and uses the existing severity ordering through a public name.
- The JSON record carries a versioned `schema` made with `schema_name`.
- `tests/cli/test_models_validator_compare.py` exists and contains the five named tests.
- The diff adds one line under `[Unreleased]` in CHANGELOG.md that mentions the issue.
- No file outside the list under CONSTRAINTS differs.
