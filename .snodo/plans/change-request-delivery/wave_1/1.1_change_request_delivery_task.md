INTENT
A protocol can set `execution.delivery: change_request` (or a mode-level `delivery: change_request`). When a task resolves cleanly and its work is verified, snodo pushes the task branch to the delivery remote and opens a change request for it through the project's code-host provider (GitHub pull request, GitLab merge request, ...). The local base branch is not touched. Core stays vendor-neutral: it only calls the provider contract.

What is already true: `push_branch` delivery works (Fixes #563). `snodo/cli/commands/run_merge.py` `_merge_on_success` pushes with `repo.git.push(remote, branch)` when `delivery == "push_branch"`; `_deliver_on_success` records `delivered_branch` in task state through `snodo/cli/commands/task_record.py` `_record_task_completion`; a push failure emits the existing `task_unmerged` audit event and the task ends `unmerged`. `packages/snodo-foundation/src/snodo/compiler/models.py` `validate_delivery_configuration` still rejects `change_request` ("not yet supported"). The provider contract in `packages/snodo-tools/src/snodo/providers/base.py` has `create_change_request(branch, title, body, target_branch=None) -> str`; providers are resolved with `snodo.providers.registry.detect_provider(project_root, protocol_metadata)`.

Evidence of a gap to close at the same time: in `_merge_on_success` the `push_branch` branch returns before the `verification_executed` check that guards local merges, so unverified work can be pushed. ADR 031 (docs/decisions/031-first-class-verification-audit-events.md) makes unverified delivery impossible; a change request must never be opened for unverified work.

Authoritative records: docs/decisions/031-first-class-verification-audit-events.md, docs/decisions/015-mcp-validation-four-outcome-contract.md (closed outcome vocabulary), docs/decisions/054-cloud-sees-recons-queues-and-delivered-commits.md (new audit event types or event fields are a cloud interface bump). Where this spec and a record disagree, the record wins.

THE CHAIN
1. `packages/snodo-foundation/src/snodo/compiler/models.py` — `change_request` is accepted at protocol and mode level; `delivery_for` resolves it.
2. `snodo/cli/commands/run_merge.py` — push delivery and change-request delivery both pass the same verification gate as a local merge (a passing or `no_tests` `verification_executed` event for the task's commit) before anything leaves the machine; refusal behaves like today's `unverified_merge_blocked`.
3. `snodo/cli/commands/run_merge.py` — with `change_request`, the branch is pushed to the delivery remote, then the provider opens a change request from that branch into the base branch, titled from the task and with a body that summarises the task and names its task id. The returned change-request URL/id is recorded with the task outcome.
4. `snodo/cli/commands/task_record.py` — the task state records the change-request URL/id alongside `delivered_branch`.
5. A push failure, a missing/unconfigured provider (e.g. only `local`, or no token), or a provider error leaves the task `unmerged` through the existing `task_unmerged` event with a reason that says what to fix. The pushed branch is kept.
6. `docs/protocol.md` — `change_request` documented as supported in the execution and mode delivery rows (what it does, that it needs a code-host plugin and its credentials, what happens on failure). Only those rows; the rest of the page is out of scope.
7. `CHANGELOG.md` — entry for this change.
8. `tests/cli/test_run_cmd.py` and `tests/compiler/test_models.py` — the tests listed under ACCEPTANCE.

CONSTRAINTS
- No new job status, task status, halt type or severity; reuse `completed` / `unmerged` (ADR 015).
- No new audit event types and no new fields on existing audit events: the cloud ingest contract check (`make gate`) refuses them, and they need a cloud interface bump the cloud has not advertised (ADR 054). Record the change-request reference in task/job state only.
- Core must not import any vendor library or name a vendor; go through the provider contract.
- `snodo/cli/commands/run_cmd.py` is at its file-length ratchet baseline; do not grow it. Put the logic in run_merge.py.
- Out of scope: `packages/snodo-provider-*`, docs other than the delivery rows of docs/protocol.md, `.snodo/protocol.yml`.

ACCEPTANCE
- `tests/compiler/test_models.py`: protocol and mode accept `delivery: change_request`.
- `tests/cli/test_run_cmd.py`: with a fake provider and a bare test remote, a verified resolved task pushes its branch, calls `create_change_request` once with that branch, records the returned reference in task state, and leaves the base branch unchanged.
- `tests/cli/test_run_cmd.py`: provider failure → task `unmerged`, `task_unmerged` event with the reason, branch still pushed.
- `tests/cli/test_run_cmd.py`: no passing verification for the commit → nothing is pushed and no change request is opened, for both `push_branch` and `change_request`.
- `uv run pytest tests/cli tests/compiler tests/golden -q` passes (regenerate goldens with `SNODO_UPDATE_GOLDENS=1` only if the compiled templates change).

PROCESS
- First open a GitHub issue in snodo-dev/snodo for this change and put "Fixes #<that number>" in the commit message; commit yourself.
- Do not run `make gate` (it needs a clean committed tree and a remote host); the full suite exceeds your shell timeout, so run the targeted tests above.
