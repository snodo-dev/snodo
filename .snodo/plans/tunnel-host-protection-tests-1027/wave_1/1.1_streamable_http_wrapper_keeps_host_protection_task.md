# 1.1 — a test pins that the tunnel wrapper keeps host protection on the streamable-http app

GitHub issue #1027 already exists for this work. Do not open another; put "Fixes #1027" in the commit message. Do not edit the CHANGELOG; the entry is already there.

## INTENT

For a service-token tunnel the MCP server's `streamable_http_app` factory is wrapped so the tunnel path router (`TunnelMCPPaths`) sits in front of the real app. On mcp 2.x that factory takes `host` and `transport_security`. If the wrapper dropped or mis-forwarded either, the router would serve an app that refuses the tunnel hostname (or has no protection) and nothing would say so. `install_tunnel_mcp_paths` in `snodo/cli/commands/serve_tunnel_asgi.py` is the named function `_run_server` calls to do the wrapping.

Pin this with one new test module, `tests/mcp/test_tunnel_streamable_http_host_protection.py`, that exercises the real code: the real server builder, the real installer, the real `build_transport_security_settings` for a tunnel hostname, and the wrapped `streamable_http_app` factory called the way `run` calls it (with `host` and `transport_security`), driven in process with no sockets. The Access verifier may be stubbed; nothing else may be.

## Acceptance

- A request carrying the tunnel hostname as `Host` is not refused with 421, and a request carrying a foreign hostname is refused with 421. The SDK default protection would refuse the tunnel hostname, so a wrapper that dropped `transport_security` or `host` fails the test.
- The route is discovered from the app, not assumed.
- The test finishes by itself in a few seconds and cannot hang; a hanging test stalls the engine's whole-suite gate, which has already failed an earlier attempt at its ten-minute limit.
- Existing tests stay green and the linter is clean.

## Findings from earlier attempts

These are observations, not instructions; solve them as you see fit.

- A server cannot be built from a protocol that exposes no tools: the builder refuses when its generated instructions name tools the server does not expose. `tests/mcp/test_serve_http_real_process.py` writes a minimal protocol that does build.
- What a wrapped factory returns is not the object that owns the routes: the builder wraps the factories as well, so the routes sit some `.app` hops below the `TunnelMCPPaths` instance. Requests must still go through the wrapper, since the wrapper is what is under test.
- The streamable-http app needs its session manager's task group; `tests/mcp/test_auth.py` shows how this repo's tests provide it.
- `TestClient` is a poor fit here; in-process ASGI calls with a bounded timeout are enough.
